# i18n (`next-intl`, single-locale pt-BR, no routing)

> For the why behind these rules, see [`../decisions/i18n.md`](../decisions/i18n.md).
> For universal, cross-cutting rules, see the root [`CLAUDE.md`](../../CLAUDE.md).

- One locale, no `[locale]` segment or middleware: `app/layout.tsx` calls `getMessages()` and wraps the tree in `NextIntlClientProvider` with the single catalog `messages/pt-BR.json`, keyed **per component namespace** (`Footer`, `Topbar`, `ChatPanel`, `TechSheetTab`, `Login`, …). Every component reads its own namespace via `useTranslations("ComponentName")` — all static UI chrome comes from the catalog, never hardcoded pt-BR JSX. This is deliberately **not** a translation system — it's the seam that lets one land later without another sweep through every component.
- `lib/` stays framework-free (no `next-intl` import), so functions that produce display text take an injected resolver: `Translate` (`lib/i18n/translate.ts`, `(key, values?) => string`) — next-intl's `t` is structurally assignable to it and passed through `draftGarment`/`draftPiecesCm`/`buildExportModel`/`planCutLayout`/`applyGarmentSpec`/`refitSleeve`. Drafter strings (`piece.detailRows`/`name`) and `detectConflict`'s title/description/suggestion live in the `PatternData` namespace. Drafters emit the **resolved string**, not the key, so the persisted blob shape is unchanged — no reset migration was needed.
- A persisted `Pattern` holds a draft-time-locale snapshot: its piece labels/conflict text reflect the locale in effect when it was drafted, not retranslated except by the next generation, "Corrigir manga", or graduation.
- The verification email's copy lives in the `VerificationEmail` namespace and reaches `lib/mail/templates.ts`'s `verificationEmail(t, link, name)` through the same injected `Translate` seam.
- The AI's `assistantMessage`/chat text is model-produced, outside the catalogs entirely: `lib/ai/prompt.ts`'s system prompt (written in English) instructs the model to mirror the language of the user's own message in `assistantMessage` and clarifying-question labels/options — so an AI chat reply may not be pt-BR even though the rest of the UI is.
- **The wire and the database carry codes, never pt-BR prose.** Every `app/api/*` error payload is `{status, error: <code>}` where the code is machine-readable and the client resolves it through the catalog (`t("errors." + code)`), the `SignupErrorCode` precedent (see [`api-routes.md`](api-routes.md) for the route-level shape of this). Shared route-level codes and the `apiError` helper live in `lib/api/errors.ts`; domain codes stay beside their own pure logic. Its internal `STATUS_WORD` map reproduces each response's pre-existing wire `status` discriminator, **warts included**: `/api/account/*` answers its 404 with `status: "error"`, not `"not_found"`.
