# Seam-conflict detection and assembly/sewing order

> For the why behind these rules — the dress waist-join gap, why an earlier pass at it was itself wrong, the per-pair risk analysis, and the phase table's reasoning — see [`../decisions/seams-and-assembly.md`](../decisions/seams-and-assembly.md).
> For universal, cross-cutting rules, see the root [`CLAUDE.md`](../../CLAUDE.md).

## Seam-conflict detection (live, apply-with-warning) — the seam graph

- **`draftAll` builds a real seam graph, not a single hardcoded comparison.** Each drafter declares its own edge-index ranges on `DraftedPiece.seamEdges`, and `draftAll` — the one place that knows the whole garment's topology — pairs matching edges across pieces into `SeamPairDecl` entries (`lib/draft/seams.ts`). `walkSeamPairs` is the pure function that measures every declared pair's **real arc length off the already-drafted pieces** (`curveArcLengthCm`, never a bespoke per-drafter number) and returns the full graph — every pair, divergent or not.
- **`seamCheck` is a consumer of that graph, not the comparison itself** — it narrows to the pairs whose actual gap misses their own intended ease by more than `SEAM_TOLERANCE_CM` (1 cm), **on either `diffCm` (the two sides' summed totals) or `subSegmentDiffCm` (#253, below)**. `applyGarmentSpec` calls it on the `seamGraph` and `detectConflict` attaches a real `ConflictInfo`. **The generation still applies, bumps the version, and debits**; the chat message gets `tone: "conflict"` and the route responds `status: "conflict"`.
- **Most pairs are equal by construction and are declared anyway, as regression guards** — shoulder, side seam, the sleeve's own underarm, the skirt panel's own `skirt-side` (#330, below), the three sub-piece pairs (`collar-neckline`, `cuff-hem`, `waistband-waist`) and the five trousers pairs. **The armhole/cap pair is the one pair reachable today that can genuinely diverge, in two independent ways**: `style.armholeDeepenCm` deepens only the body's armhole while the cap is sized from the base one, unless refit (a **total** mismatch, `diffCm`); and a real `backWidth` divergence between the front and back panels (`docs/architecture/drafting.md`) can make the TOTAL still agree while the front/back **split** projects onto the wrong point of the cap's own arc (`subSegmentDiffCm`, #253) — "a sleeve cap whose total matches but whose front/back split is wrong measures as a perfect seam" otherwise.
- **`walkSeamPairs` returns per-edge fractions, not only each side's summed total (#253).** `SeamMeasurement.aEdges`/`bEdges` (`SeamEdgeMeasurement[]`) carry each declared edge's own measured `lenCm` and its cumulative `endFracOfSide` — the same per-edge fraction GarmentCode's `Interface.projecting_fractions()` derives before projecting a multi-edge side's own internal boundary onto whichever edge(s) it's mated to. `SeamPairDecl.expectEqualSplit` is **opt-in, not a blanket default** — declared `true` only for `armhole-cap` (front and back are drafted to be an equal split of the cap unless `backWidth` widens one side); a pair like `collar-neckline` (whose front+back neckline arcs are NOT meant to split evenly — a V-neck front is a genuinely different length than the shallow-scoop back) never opts in, so `subSegmentDiffCm` stays `0` for it regardless of how asymmetric its edges are.
- **Any pair whose `subSegmentDiffCm` exceeds tolerance has its `fixable` downgraded to `false`, even when the pair itself declares `fixable: true` and even when `diffCm` ALSO exceeds tolerance** — `refitSleeve` only changes which TOTAL the cap solves against (base vs. deepened armhole); it cannot correct a front/back split imbalance, so a pair diverging on both axes at once would still be broken after refit if `fixable` stayed `true`. `seamCheck` (not the UI) is what keeps a fix button from being offered for a divergence it can't actually close. `lib/draft/assembly.ts`'s own `AssemblySeamStep.fixable`/`subSegmentDiffCm` read this same corrected value and the raw sub-segment number, not just the graph's total-only fields.
- **`sideSplitDevCm` (`lib/draft/seams.ts`) is checked on BOTH sides of an `expectEqualSplit` pair, not only whichever side happens to declare more than one edge** — a many-to-many pair (not reachable today; `armhole-cap`'s cap side is always one edge) would otherwise have one side's own split imbalance silently ignored. `subSegmentDiffCm` reports the worse of the two.
- **The armhole/cap pitch notch is derived from the same projected total, not two independently-clamped fractions (#253).** `lib/draft/seams.ts`'s `pitchNotchDistanceCm(totalLenCm)` is the ONE place that clamps the 8cm pitch rise to a fraction (0.35) of the pair's own **combined** total; `draftBody` (`lib/draft/body.ts`) drafts front and back **twice** — once to learn each panel's own armhole length, then again with the shared distance both calls receive verbatim — so `sleeve.ts` no longer re-clamps against its own cap arc (0.35 there used to be a SEPARATE, only-coincidentally-consistent fraction). This is what makes all three edges (front's own armhole curve, back's own, the cap's own two ends) "generated as pairs from the same computation" (see `drafting.md`'s mated-notch rule) even when `backWidth` makes front and back genuinely unequal.
- **`SeamPairDecl.gatherRatio` (#255) represents a deliberate length ratio between the two sides of a stitch, in either direction** — GarmentCode's `Interface(..., ruffle=1.)`. `diffCm` is computed against `aLen * gatherRatio + easeCm`, not the pre-#255 `aLen + easeCm`, so a pair whose two sides are meant to differ still reports zero divergence instead of a false conflict. **A ratio above 1 is added fullness** (a gathered skirt waist or a puff sleeve, side b genuinely longer than side a — #255's original framing); **a ratio below 1 is take-up** (side a's own flat cut edge is longer than what it presents once its own darts/pleats are folded away, #319/#320's `presentedEdgeLenCm`) — same field, same formula, read in whichever direction the pair needs. **Optional, defaulting to 1** for a pair with nothing to declare. Four production sites declare a ratio below 1 today: `garment.ts`'s `trouser-waistband-waist` (the trousers' waist dart), `waistband-waist` on a pleated skirt (`skirt.ts`'s pleat take-up), and `waist-join-front`/`waist-join-back` on a fitted dress (#335: the bodice's own two hem darts) — every other declared pair still leaves it unset. `SeamMeasurement.gatherRatio`/`AssemblySeamStep.gatherRatio` carry it through unchanged; `lib/ai/prompt.ts`'s assembly-order instructions phrase a ratio below 1 as "fold/sew the take-up first, then the two match," never as a mismatch, and a ratio above 1 as fullness to distribute.
- **A fitted bodice ends at the natural waist, so its hem is sized off the waist, never the hip** — `dressWaistHalfCm(waistCm)` takes **no silhouette parameter at all**, because the bodice describes the body and which skirt happens to be attached cannot change its own hem width. **The topology must also match the seam's physical shape:** `skirtPiece.qty === 1` signals one undivided panel whose single waist arc is the _full_ waist, so each bodice half pairs against its own half of that arc. **#335: `dressWaistHalfCm` is what the hem PRESENTS, not what it's CUT to** — the bodice's own two hem darts widen the cut edge above that value (`body.ts`'s `dressHemDartIntakeCm`), and the pair above closes on the declared take-up rather than on both sides measuring the same raw number.
- **Multiple simultaneous divergences render as a list, not multiple panels.** `ConflictInfo.entries?: ConflictEntry[]` (additive — absent on a conflict persisted earlier) holds one entry per divergence with a pre-resolved `label`, `diffCm`, `fixable`, and its own canvas `markers`. The canvas's single top-right slot still holds exactly one card, now rendering one group per entry (see [`design-system.md`](design-system.md) on canvas-overlay exclusivity).
- **The two divergent lengths behind each entry are NOT persisted** — `ConflictEntry` carries only `diffCm`. `measureSeamGraph(spec, baseMeasurements, t)` is called once in `CanvasArea` and matched back to each entry by `key`, the same derive-at-render-time rule as `fitPieceLabel`/`measureSeams`. **`ConflictEntry.diffCm` (and `ConflictInfo`'s own top-level `diffCm`) is `max(m.diffCm, m.subSegmentDiffCm)`, not the raw total-only `diffCm` (#253)** — a pair `seamCheck` flagged purely on its sub-segment split can have a near-zero `diffCm` (the total closes fine); citing that number as "the divergence" would show a real, unfixable conflict as barely there. The legacy `armhole-cap`-specific "cap is N cm larger/smaller" copy (`lib/editor/state.ts`'s `isLegacySingle`) is gated on `diffCm` itself exceeding tolerance, since that sentence's "larger/smaller" framing only describes a total mismatch — a split-only divergence falls through to the generic, magnitude-only copy instead.
- **`conflict/resolve` is free, no debit.** "fix" calls `refitSleeve` — setting the internal `style.sleeveRefit` and re-drafting so the cap uses the adjusted armhole — closing **only** the armhole/cap divergence; any other entry is untouched and the conflict stays open with whatever remains. "ignore" clears the whole warning regardless of how many entries it holds. **`sleeveRefit` is deliberately not accepted by `validateSpec`, so the AI can never fake a refit.** `ConflictActions`'s "Corrigir manga" button renders **only while at least one entry is `fixable`**.
- **#330: the skirt panel's own two side edges (`seamEdges.sideRight`/`sideLeft`, `lib/draft/skirt.ts`) are declared as a self-pair, `skirt-side`, unconditionally — every silhouette, dress or standalone, waistband or none.** Same shape `sleeve.ts`'s own `underarmRight`/`underarmLeft` self-pair already uses: two edges on the _same_ `DraftedPiece` id, equal by construction (the panel is symmetric about its own foldEdge/apex), so `walkSeamPairs` measuring one against the other is a real regression guard, not a trivial self-comparison. This is what closes the one reachable gap #330's own sampled-space audit found: a standalone skirt with `waistband: "none"` used to declare **zero** seam pairs at all (an orphaned piece with no sewing instruction whatsoever), and every skirt/dress — waistband or not — had no side-seam step in its own assembly order. **`placket` (`lib/draft/subpieces.ts`'s `draftPlacket`) stays the one piece with no declared pair, on purpose**: it binds into the sleeve's own vertical opening above the cuff, and the sleeve's outline has no distinct edge there to mate against — declaring a real pair would mean `sleeve.ts` drafting that slit as boundary geometry, which does not exist today. A drafting change, not a declaration; tracked as its own follow-up rather than folded into #330's test-quality scope.
- **#341: an edge may be named by more than one declared pair when the real garment genuinely sews it more than once.** The hoodie's `body-front`/`body-back`/`sleeve` neckline edges appear in BOTH `hoodie-hood-neckline` (attaching the hood) and `hoodie-neck-binding` (applying the finishing strip over that same seam) — a deliberate exception to "one edge, one pair" made only when a specific piece of construction reasoning justifies it (here: a binding is applied over an already-closed seam, not instead of it), never as a shortcut to avoid drafting a second edge. Nothing in the machinery assumes uniqueness (`walkSeamPairs` has none, the orphan-piece gate above is per-piece not per-edge, `hemEdgeIsConsumed` only ever inspects a piece's own `seamEdges.hem` key) — the constraint is a convention to state explicitly next to any pair that relies on it, not a mechanical one the code enforces. See [`../decisions/seams-and-assembly.md`](../decisions/seams-and-assembly.md)'s #341 entry.

## Assembly / sewing order

- **The sewing order is derived data, walked from the seam graph — not a hand-written sequence per garment archetype.** `lib/draft/assembly.ts`'s `buildAssemblyOrder(pattern, t)` is pure and DB-free, redrafting from the pattern's own frozen `sizeTable`/`engine` (so it works on a pattern drafted before it existed) and **never persisted**. It produces one ordered `steps` list: a `"dart"` step per piece that has any, a `"pleat"` step per piece that has any (`#244`, same "shapes the piece before any seam" priority as darts, its own separate step so a piece with both gets one of each rather than a conflated count), one `"seam"` step per `SeamMeasurement` the graph actually walked — **never more, never fewer** — and a `"hem"` step for any piece whose own `seamEdges.hem` isn't already claimed by another declared pair.
- **Ordering among seam steps is a lookup by the pair's own stable `key`, not a branch on `spec.type` or `pattern.engine`.** `PHASE_BY_KEY` maps every key — from **every registered engine** (`#323`) — to one of six phases — `primary`, `sleeve`, `side`, `attach`, `waistJoin`, `band` — and **darts and pleats are unconditionally sewn before every seam/hem step**. A future key with no entry falls to `"other"` (sewn last, never dropped) rather than crashing; `assembly.test.ts`'s own exhaustiveness guard walks `ENGINE_IDS` (not one hand-picked default), so a new pair key on any engine fails the build instead of silently landing in `"other"`. A key is a property of the _pair's own identity_, not of which engine's wrapper declared it — freesewing's raglan/yoke-backed designs (hoodie/coat/shirt) needed real construction-order judgment, not a mechanical copy of moldai's own six phases: a raglan seam is `primary` (it replaces the shoulder seam entirely, on a design that has none), not `sleeve`; a center-back or yoke-attach seam is `primary` (the garment's first structural closure), not folded into `side`. See [`../decisions/seams-and-assembly.md`](../decisions/seams-and-assembly.md) for the per-key reasoning.
- **Which piece a free `"hem"` step names is derived from the seam graph's own per-edge data, not a second hand-maintained table.** A piece's `seamEdges.hem`, when declared, needs a step only when nothing else in the graph already sews that exact edge to another piece — checked directly against `SeamMeasurement.aEdges`/`bEdges` (`lib/draft/seams.ts`'s per-edge `{pieceId, from, to}` breakdown, #253), which every pair declaration references verbatim off the piece's own `seamEdges.hem` object. A hand-written `pieceId → consuming key` table (pre-`#323`) had to be extended by hand per engine and was silently wrong for freesewing's hoodie/coat: both reuse moldai's own `"body-front"`/`"body-back"` piece ids, and the old table mapped those to moldai's `waist-join-front`/`waist-join-back` pair keys — pairs that never appear in a hoodie/coat graph, so it minted two spurious "free hem" steps per garment even though the waistband pair already sews those edges.
- **Each seam step cites the two real drafted lengths and the pair's own intended `easeCm`** — `SeamMeasurement` carries `easeCm` precisely so "how much ease to distribute" is a real number a step can cite rather than a guess. `diverges` comes from `seamCheck`, **not a second threshold**; `AssemblyOrder.hasConflict` is true when any step does. The order is still returned — knowing the sequence is still useful — but **a consumer must say so rather than presenting a plausible-looking, fully-closing seam.**
- **Piece names come from the pattern's own already-persisted, already-locale-resolved `pieces` list** (`pieceDisplayName`, matched by id), never a fresh redraft. A seam step's `key` is deliberately **not** resolved through a catalog label: it's handed to the model as a stable English identifier for it to phrase itself.
- **A piece set with nothing to derive gets an honestly empty order (`steps: []`), not a fabricated one.**
- **Reachable from chat, not a new screen.** A sewing-order question answers through the existing `decision: "explain"` path (same debit, same credit chip — see [`generation-flow.md`](generation-flow.md)). `RawToolInput`/`AiDecision` carry an `assemblyOrder?: boolean` the model sets **only** alongside `explain`. The route tags the persisted `ChatMessage` with `assembly: true`, and `ChatBubble` renders the **catalog-sourced** disclaimer — the chrome and disclaimer come from the catalog, the step prose does not.
- **The model may never invent a step for a seam absent from the structure** — enforced by instruction, not by re-validating the model's prose against the JSON. `buildSystem` embeds the JSON and its own prompt section instructs: walk the steps in order, name pieces by `aPieceName`/`bPieceName`, cite lengths and (only when meaningfully above 0) the ease, and state when a step `diverges` that the seam needs the conflict resolved first.
