# Size charts (`/size-charts`)

> For the why behind these rules — the `validateSizeChartPatch` bug in detail, the ABNT provenance removal, and the seed reconstruction — see [`../decisions/size-charts.md`](../decisions/size-charts.md).
> For universal, cross-cutting rules, see the root [`CLAUDE.md`](../../CLAUDE.md).

Real, per-account, and they drive generation/grading.

- **`SizeChart` (Prisma, JSON-blob-per-row like `Pattern`/`Wallet`)** holds `SizeChartData`: `name`, `gender`, `bodyType`, `isSystem`, ordered `sizes`, `baseSizeIndex`, `baseMeasurements`, a `progressionRule` (cm delta per size step), and per-cell `overrides` that win over the rule. Resolution lives in `lib/sizeCharts/compute.ts`. **`bodyType` is descriptive metadata only — it never affects drafted geometry**, an honest limitation the screen states via a caption tied to the control by `aria-describedby`.
- **Every account lazily gets two seeded `isSystem` charts on first access**, derived losslessly from the legacy tables. **System charts can be duplicated but not edited or deleted, enforced in the repository layer.** Both names resolve from the catalog rather than a hardcoded literal, threaded through as a required `t: Translate`. **A rename affects nothing already seeded** — existing rows keep the name they were created with, the `PatternData.newPatternName` precedent.
- **`User.activeSizeChartId` is not a promise the chart will be used, and the app says so.** `pickSizeChartForGeneration` returns a `SizeChartChoice` (`{chart, rejectedActive}`) rather than a bare record. **Surfaced in three places, per the three places the question comes up:** a `tone: "notice"` chat bubble at generation time, a "Grade usada" chip in `TechSheetTab`, and the active badge now reading its _scope_ ("usada só em peças femininas"). The frozen `Pattern.sizeChartName` backs the chip — additive, frozen for the same reason `sizeTable` is, **absent on older patterns and therefore omitted rather than guessed.**
- **A `PATCH` body is validated before it can reach the drafter** — `validateSizeChartPatch` (`lib/sizeCharts/validate.ts`) is the size-chart half of the `validateSpec` trust boundary (see [`generation-flow.md`](generation-flow.md)), and `updateSizeChart`'s `patch` parameter is deliberately `unknown`. **It drops or clamps, never throws**, so an unusable field is ignored while the rest of the patch applies. So `baseMeasurements` **merges** onto the current row — a patch can change a value but can never drop a key — and **`isSystem` appears in no branch**, so a request can never claim it. `MEASUREMENT_KEYS` and `BODY_TYPES` are exported for it, and `SizeChartTable` reads those instead of its own copies.
- **A generation request may name the chart it drafts from, and that choice is per molde, not per account.** `sizeChartId` on `POST /api/patterns/[id]/generate` is resolved through `getSizeChartGenderForUser` **before** the transaction, so an id the account does not own answers 400 `invalid_size_chart` with no debit, no Anthropic call and no state mutation. The chart's own `gender` becomes the drafted spec's gender, which is why the new-pattern form has no gender control. **Choosing a chart for one molde never changes `User.activeSizeChartId`.**
- **A pattern snapshots its size chart once, at its first-ever generation.** The route calls `getSizeChartForGeneration(tx, userId, gender, t, requestedId?)`, which prefers a `sizeChartId` the request named outright, and otherwise falls back to the pre-existing pick (the active chart if its gender matches the spec, else the system default for that gender), then `seedPatternSizeSnapshot` freezes `sizes`/`baseSize`/a fully resolved `sizeTable`. **Every later regeneration reuses the frozen snapshot** — editing or reassigning the active chart never retroactively changes an in-progress pattern. A blank pattern bootstraps from the system female chart via the **name-free** `buildSystemSizeChart`, so `sizeTable`/`sizes` are always populated, never optional.
- **Screen:** `SizeChartsShell` + `SizeChartLibrary` + `SizeChartTable`, with their own `useSizeChartsStore` (see [`client-state.md`](client-state.md)). Browse; edit a custom chart's base row/progression rule/per-cell overrides/size list; duplicate any chart; mark one active.
- **Spreadsheet import is real, not the inert dashed placeholder it shipped as.** `ImportSizeChartDialog` parses a file entirely client-side via `lib/sizeCharts/import.ts`'s `parseSizeChartFile`, previews exactly what will be created **including every rejected cell and its reason**, and only then persists through `createSizeChartFromImport`. **The preview is a review step, not the trust boundary** — the server re-runs everything through `validateSizeChartPatch` exactly as a hand-typed `PATCH` would. Deliberately **`.csv`/`.tsv` only, no `.xlsx`**: a binary format needs a real parsing dependency an MVP import doesn't justify, and the limitation is stated on screen before a file is even picked, with an `.xlsx` upload answering `unsupported_file_type`.
