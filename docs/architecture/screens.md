# Screens

> For the why behind these rules — the `/planos` "em breve" audit, the settings-section split, and the pattern-card badge decision — see [`../decisions/screens.md`](../decisions/screens.md).
> For universal, cross-cutting rules, see the root [`CLAUDE.md`](../../CLAUDE.md).

- **The editor (`/pattern/[id]`) opens on a blank pattern.** No pieces, empty chat, name "Novo molde", `version: 0` — the user always generates from scratch, and the first generation creates the garment's (variable) piece set. `CanvasArea` shows an empty state and hides the floating toolbar while `pieces` is empty; `sendMessage` auto-selects the first piece once a generation produces one.
- **The editor's Ficha técnica tab owns the spec, the chip row owns everything else.** `TechSheetTab`'s "Parâmetros" panel (`SpecParamsCard`) lists every style field the pattern's spec carries **that the pattern's frozen engine actually reads for its garment type** — the order and the filter both come from `styleFieldsByType` via `lib/draft/specParams.ts`'s `buildSpecParams`, never a second table in the component. **A field the type does not read is omitted, not badged**: a value that shaped nothing must not be presented as if it had, and a row that says "não se aplica" is noise on a read-only sheet. **Two more filters, both #353's corrections to #332:** a field whose value shaped nothing because a _sibling_ field contradicts it is dropped — `cuff` on a short sleeve, gated by `hasPlacketOpening`, the one cross-field coupling the app declares (it lives in the leaf `capability.ts`, not in `sleeve.ts`, precisely so a client component can ask; #333 owns generalizing it) — and so is a field the **piece cards further down the same sheet already state**. `seamAllowanceCm` is the only member of that second set: every drafter emits its own `rows.seamAllowance` row per piece, labelled "Folga de costura (na linha de corte)", which says more than a bare number and stays honest when the field is unset (the drafters, the export screen and the PDF all apply the effective `?? 1`). **`fit`/`stretch` moved out of the summary chip row into the panel**, so the chips carry only what is not style (tipo, modelagem, peças, cópias, grade, motor); that migration also retired the hand-written `knit`/`hasBodice` branch, since the capability map already lists `fit` for blouse/dress and `stretch` for tshirt alone. The frozen size chart and engine stay chips and are **not** repeated inside the panel.
- **Canvas overlays are mutually exclusive:** `PieceDetailsPanel` and `ConflictInfoCard` share the top-right slot in `CanvasArea`, and **a conflict always takes the slot**. Fold new overlays into that same exclusivity check rather than adding a third independent floating panel.
- **`/` is the dashboard for a signed-in, onboarded account — but it has four branches, not one.** `app/page.tsx` renders `<LandingPage />` for a signed-out visitor; `redirect("/login")` when the session's account no longer exists; `redirect("/onboarding")` when `onboardedAt === null`; otherwise `DashboardShell`, reading `?missing=pattern` as plain data — the `?section=` precedent, not a client `useSearchParams`. It is **the one route whose `generateMetadata` depends on session state**, and the one that must spell out its own `— MoldAI` suffix: Next.js does not apply a layout's `title.template` to a `page.tsx` in that _same_ route segment, and root layout + `/` are the same segment.
- **Dashboard** — `DashboardShell` renders through `AppShell` passing **neither `title` nor `backHref`** (it _is_ `/`, and its sidebar already marks the section) and composes `Sidebar`, `PatternGrid` (search + garment-type filter reusing the `garmentType.*` catalog keys), and `CreditsCard`/`RecentUsageCard`. **`Sidebar` takes `active` and `onNewPattern` as props rather than reading `useDashboardStore` itself**, because `/slopers` renders the same component and a failed create there has to record its error on _that_ screen's store (see [`client-state.md`](client-state.md)). **`PatternGrid` owns no scroll region** — `DashboardShell` wraps it with the summary cards in one non-`fill` `ScrollArea`, so an empty grid takes its natural height instead of pinning the cards to the floor. Rename and delete live **only** in the card "⋯" menu; the editor has no delete affordance. **Pattern cards deliberately show no state badge** — export never touches the server, so "exportado" can't be derived honestly. **`/pattern/[id]` redirects to `/?missing=pattern`** for a pattern that is gone or not owned, deliberately one flag rather than distinguishing "deleted" from "not yours."
  - **`OnboardingChecklistCard.tsx` renders a 5-step "Comece com o pé direito · N de 5" checklist.** Its "convidar alguém da equipe" step stays **permanently unreachable** — disabled + "em breve" badged, never a checkmark — rather than built or linked externally, since multi-user accounts don't exist. Dismissal is `localStorage`-only (browser-local, not synced per account).
- **`/` doubles as the public landing for a signed-out visitor** (`components/landing/`). Its argument runs hero (offer + a proof strip) → benefits → **tagline reveal** → how it works → what a credit buys → FAQ → risk reversal and closing CTA, the `landing-page-design` skill's A2 order. `MarketingShell` owns the chrome shared with `/planos`, `/privacy` and `/terms`: the skip link, the `<main id="main">` landmark, the scroll region, and `LandingNav` — a **floating glass pill**, not a bar, collapsing on a narrow viewport behind a hamburger whose lines rotate into an X. **The marketing surface is the one genuinely responsive part of this repo**; the authenticated app stays desktop-only.
  - **The four images are cartooned SVGs drawn from real captures of the app** (`public/landing/*.svg`): the hero is the editor (conversation, drafted pieces, credit chip), and the three step thumbnails are the chat, the **seam-conflict warning** (the product's actual differentiator) and the cut plan.
  - **The illustrations still have to be TRUE.** Every panel, label and figure in them exists in the product, and the conflict card's numbers are the ones the app actually produced. A stylised drawing of the real thing is fine; an invented capability is not. **Prova 3D is deliberately not depicted**: it is a beta parametric approximation of cones and cylinders, and its own screen says so.
  - **Each `imageAlt` describes what the drawing shows** and calls it an illustration; redraw an asset and the alt has to follow. `marketingDesignSystem.test.ts` checks every referenced asset exists in `public/`.
  - **Proof is product facts, never social proof.** There are no customers, so there is no testimonial or logo strip. The hero's three proof points read from `PLAN_CREDITS`/`EXPORT_FORMATS`, and every benefit and FAQ answer interpolates `COSTS`/formats, so a price or cost change can never leave a stale promise here.
  - **The risk reversal deliberately does NOT say "cancele quando quiser".** Downgrades are refused server-side (only upgrades are self-serve — see [`billing.md`](billing.md)), so that promise would be false; it says the free plan needs no card and renews every 30 days. `LandingPage.test.tsx` pins the absence.
  - **Motion is IntersectionObserver-only** (`components/landing/reveal.tsx`) — never a scroll listener. `Reveal` writes `data-reveal` straight to the DOM rather than through React state, which keeps the server and client first paints identical; without the API both primitives fall back to the **end** state. `prefers-reduced-motion` neutralises all of it in one place in `app/globals.css`.
  - **SEO/AEO:** indexed and canonical-tagged, with `openGraph`/`twitter` metadata, a generated 1200×630 card (`app/opengraph-image.tsx`), and an `@graph` of Organization + WebSite + **FAQPage structured data emitted from the same `FAQ_KEYS` list the section renders** (`lib/landing/faq.ts`). See [`seo.md`](seo.md).
  - **`/privacy` and `/terms`** (`components/legal/LegalPage.tsx`) are honest plain-language summaries of what this codebase actually does, and both say on screen that they have had no legal review rather than implying an authority they do not have.
- **`/onboarding` is the 3-step post-signup wizard** — a centered card rendering its own `Wordmark`, local `useState`, no store. **`User.onboardedAt`/`workStyle`** back it: `app/page.tsx` gates on `onboardedAt === null` only, and existing rows were backfilled as already-onboarded. **`workStyle` is honest, unused research data**, never read by any drafting or billing path; the route still **rejects an unrecognised value rather than storing it**. Step 2 activates the system female chart; step 3 creates a pattern and generates, **staying put with a notice on anything that isn't a real draft** rather than navigating to a blank pattern. Both "Pular por agora" and a successful submit stamp `onboardedAt`, and the page redirects to `/` if it's already set. Its two "em breve" rows are disabled+badged, not hidden.
- **`/pattern/[id]/versions` is the version-history screen** — `components/versions/`, local `useState`, no store. **`PatternVersion` stores the `GarmentSpec` plus the frozen size snapshot only — never the drafted pieces**, on the `Sloper` reasoning (see [`slopers.md`](slopers.md)): `draftGarment` is deterministic, so geometry would duplicate what `spec` + `sizeTable` already determine. `userId` is denormalized so ownership is one indexed lookup. **A row is written by `recordVersion` inside the SAME transaction as every `bumpVersion`** — generate, graduate, `conflict/resolve`, restore — so a snapshot can never exist without the state that produced it. `reason` is machine-readable, never pt-BR prose. `GET .../versions` returns `null` (never an empty array) for a pattern that isn't the caller's. **Restore is free and append-only:** it uses `withPatternVersioned` (a Pattern-only transaction, never `withPatternAndWallet` — it must not be able to debit), carries the OLD version's frozen snapshot forward rather than re-resolving against today's active chart, and **restoring v3 while at v5 produces v6 carrying v3's spec** — it never rewrites or deletes v3. No retention cap, no plan gate. `VersionCompare.tsx` renders a **Comprimento (length) delta** alongside the existing Cava/Consumo deltas, via `lengthDeltaLabel`.
- **`/import` is the DXF import flow** — `ImportShell`/`FileSummaryCard`/`LayerMappingPanel`/`VerificationPanel`, a two-step parse → analyse → verify screen with no sidebar. **Analysing a file is entirely client-side and free** — no server call, no credit cost. `lib/import/` is the framework-free half — `dxf.ts` hand-parses DXF's group-code/value stream in **a single forward pass**, which is what makes "never loops forever" structurally guaranteed; `analyze.ts` detects layer roles and emits machine-readable `ImportCheckCode`s the screen resolves as `t("checks." + code)`. **An uploaded file is untrusted input, the `validateSpec` trust boundary:** `parseDxf` never throws and caps text length, entity count and vertices per entity, with `MAX_IMPORT_FILE_BYTES` rejecting an oversized upload before any parse work. **Creating a `Pattern` from the parsed geometry is real**: `VerificationPanel`'s "Importar molde" button renders the layer preview to an image and runs it through the ordinary create+generate pipeline (`lib/importStore.ts`'s `createPatternFromImport`), costing `COSTS.adjust` like any other generation — still tagged "beta" since the reconstruction quality is unproven at scale. `FileSummaryCard` resolves each of `pick()`'s three failure causes to its own message rather than a fixed banner.
- **`/settings` is one unified page, not a modal**, reached from the shared header's avatar menu, deep-linked via `?section=` (`profile` default, plus `password`/`usage`/`plan`/`danger`). **`SettingsSection`/`SETTINGS_SECTIONS` live in plain `lib/settings/sections.ts`, outside the `"use client"` component** — the Server Component page needs them as plain data. The page loads user, wallet and the last 30 ledger entries server-side, so first render needs no API round-trip. **Five sections, in this order — profile, password, usage, plan, danger (danger deliberately last)**:
  - `ProfileSection` — name editable; **email deliberately read-only** (it's the Credentials login identifier).
  - `PasswordSection` — client-side confirm-mismatch gating plus a server-verified current-password check. **Password changes do not invalidate the current JWT.**
  - `UsageSection` — balance/renewal, a top-up reusing `purchase("topup")` with an optimistic ledger update, and the full transaction history.
  - `PlanSection` — real plan switching. Every tier above the account's own renders an enabled subscribe button; **a lower tier stays disabled + badged with a note explaining that only upgrades are self-serve**. A successful switch calls `router.refresh()` so the header's credits bar picks up the new plan.
  - `DangerZoneSection` — deletion gated by both a typed-email match **and** a server-verified password.
- **`/planos` is a public route** — the pricing screen, reachable without a session. Four cards from `lib/billing/plans.ts`, and a cost-per-action footer rendered from `COSTS`/`TOPUP_*` — **never a literal number that doesn't match what the app actually charges.** **The Mensal/Anual toggle is real** — see [`billing.md`](billing.md) for the annual-billing mechanics. **Four capabilities are marked "em breve" rather than claimed as shipped** (a second AI model, per-plan seats, a priority queue/API, dedicated support — none exist), and **"Plano de corte automático" and "Histórico ilimitado de versões" are deliberately absent from every bullet list rather than shown as a paid differentiator**, because both ship free on every plan. "Falar com vendas" is always disabled — there is no destination to link to. CTAs: signed-out → `/signup`; signed-in on another plan → `/settings?section=plan`; the current plan shows "Plano atual".
- **`/pattern/[id]/export`** — see [`export.md`](export.md).
