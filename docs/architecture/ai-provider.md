# AI provider (`lib/ai/provider/`)

> For the why behind this abstraction — and for the VRAM/hosting cut it was built under — see [`../decisions/ai-provider.md`](../decisions/ai-provider.md).
> For universal, cross-cutting rules, see the root [`CLAUDE.md`](../../CLAUDE.md).
> For the drafting-engine facade this deliberately mirrors, see [`drafting.md`](drafting.md).

- **A provider facade, exactly like `lib/draft/engine/facade.ts`.** `lib/ai/provider/{types,registry}.ts` declare the contract; `anthropic.ts` and `openaiCompat.ts` implement it; `getProvider()` (registry.ts) reads `LLM_PROVIDER` at call time and defaults to `"anthropic"`. `lib/ai/index.ts`'s `proposeGarment` no longer imports the Anthropic SDK at all — it builds an `LlmCallOptions` (system sections, the forced tool, history, images, `maxTokens`) and hands it to whichever provider is active. Same justification `drafting.md` states for its own facade: in-repo scoring (the eval harness, `lib/ai/eval/`), a stated contract (`LlmProvider`), and a per-request choice.
- **One method is the provider's whole job, including its own repair retry.** `LlmProvider.propose(opts): Promise<{ toolInput: unknown; usage?; repaired? }>` — the one-repair-attempt loop (#261) lives _inside_ each provider, never in `index.ts`, because the repair protocol is provider-specific: Anthropic answers a failed tool call with a `tool_result` block addressed to its own `tool_use_id`; an OpenAI-compatible endpoint instead appends a `role: "tool"` message addressed to a `tool_call_id`. Forcing both through one neutral turn shape would either lose fidelity or leak provider detail back into `index.ts`. Mirrors `DraftingEngine.draft()` in `lib/draft/engine/types.ts` on purpose. `usage`/`repaired` (#276) are optional on `LlmCallResult` for exactly the same "existing mock keeps typechecking" reason `AiDecision.adjustments` (#250) is optional; when a repair attempt fires, `usage` sums BOTH calls' tokens (both are real, billed requests), never just the repair's own.
- **`LlmProvider.model()` is a function, not a static field, for the same reason `getProvider()` reads `LLM_PROVIDER` at call time.** `anthropicProvider.model()` returns a fixed literal (the same `MODEL` const `buildRequestParams` sends); `openaiCompatProvider.model()` resolves `LLM_MODEL` from the environment on each call, so a snapshot taken at module load could go stale. Added so `scripts/ai-eval.ts`'s report header reads `getProvider().id`/`.model()` instead of a second, hand-copied `"claude-sonnet-5"`/`"anthropic"` pair — the exact drift CLAUDE.md's "never a second copy of a fact that already has an owner" rule names; the Langfuse trace (#276) labels each call from the same pair, for the same reason.
- **Every `propose()` call is traced to Langfuse from `proposeGarment` (`lib/ai/index.ts`), never from inside a provider.** The facade is the one seam that sees both the production Anthropic path and the eval-harness/local-vLLM path, so `traceProposeGarment` (`lib/observability/langfuse.ts`) is called exactly once per `proposeGarment` call, in a `finally` block, whether `propose()`/`resolveDecision` succeeded or threw — model, provider id, token usage, latency (`startedAt`/`finishedAt`), whether the repair retry fired, and `decision.adjustments` (#250, unfiltered — field names and enum/numeric values only, never personal data) all land on one trace. **Mirrors `lib/observability/sentry.ts` exactly**: `"langfuse"` is only ever a dynamic `import()`, gated behind `LANGFUSE_SECRET_KEY`/`LANGFUSE_PUBLIC_KEY` both being set, so an environment that never configures it (every test run, and any deploy that hasn't opted in) never even loads the SDK. `traceProposeGarment` is synchronous and fire-and-forget — its real work runs inside an un-awaited internal async function — specifically so calling it adds no `await` inside `withPatternAndWallet`'s (`lib/db/pattern-wallet.ts`) 30s transaction window, which already spends most of its budget on the AI call itself. Prompt/response bodies (chat text) are LGPD personal data: `LlmCallTrace.content` is only ever constructed by `proposeGarment` when `isTraceContentEnabled()` (`LANGFUSE_TRACE_CONTENT=true`) is true, never merely omitted when read — off by default. Attached reference photos (`ProposeOptions.images`) are never included in trace content regardless of this flag — only their surrounding prompt text travels, never image binaries. `ProposeOptions.evalRun` (set only by `scripts/ai-eval.ts`) tags a trace's `source` as `"eval"` instead of `"app"`, so harness traffic is distinguishable from the generate route's real production traffic.
- **`LlmTool`'s `input_schema` field name is not cosmetic.** `lib/ai/prompt.test.ts` pins a sha256 of `staticSectionsFor("moldai") + JSON.stringify(toolFor("moldai"))`. `LlmTool` is deliberately shaped byte-identical to the Anthropic SDK's own `Tool` type (`{name, description, input_schema}`) so that hash never moves for a provider-facade change — only for an actual prompt/schema change. Never rename that field to `inputSchema` or similar without also intentionally regenerating the pinned hash.
- **`lib/ai/schema.ts` imports zero SDK types.** It used to import `Anthropic.Tool` as a type only; it now returns the local `LlmTool` (`lib/ai/provider/types.ts`). The Anthropic SDK import is confined to exactly one file, `lib/ai/provider/anthropic.ts` — the smallest true "one file per external SDK" case in the repo (contrast `lib/billing/stripe.ts`, which the original comment there was written against).
- **Every enum/bound still renders from the active drafting engine's capability, unconditionally, regardless of provider.** `lib/ai/index.ts` still calls `engineFor(state.pattern.engine)` and `toolFor(engine)`/`staticSectionsFor(engine)` before ever touching the provider — swapping providers changes _how_ the request is sent, never _what vocabulary the model is told about_. A provider must never widen or narrow that vocabulary on its own (e.g. a self-hosted model "helpfully" supporting a collar shape the schema didn't offer) — `validateSpec`/`checkEngineSupport` are the only gates that get to narrow it further, downstream.
- **The self-hosted provider is dev/eval only today, not a production path.** Production's `TX_OPTS` (`lib/db/pattern.ts:21`, a 30s Prisma transaction holding `Pattern`+`Wallet` locks) and `ANTHROPIC_OPTIONS`'s 20s/8s repair budget (`lib/ai/provider/anthropic.ts`) assume a call fast enough to fit inside that lock window. `openaiCompat.ts` uses a deliberately longer 60s/20s budget instead, sized for a local model rather than for that transaction — **it must never be wired into the generate route's live traffic without first reworking the debit-before-call/refund-on-throw flow to run the AI call outside the transaction.** Until that happens, `LLM_PROVIDER=local` is for `npm run eval:ai` and manual testing against `docker-compose.gpu.yml`, never for `docker:prod`.
- **The eval harness (`lib/ai/eval/`, `scripts/ai-eval.ts`) is the only thing allowed to say a provider/prompt change is "better".** `docs/decisions/generation-flow.md` already states the rule this exists to satisfy: a prompt/schema change used to ship on inspection alone. `npm run eval:ai` writes `docs/reference/ai-eval/report.md`; compare it against the previous commit's report, never trust a change from reading the diff.
- **A JSON-schema-shaped tool call must be structurally guaranteed, not merely requested, for a self-hosted model.** `openaiCompat.ts` forces `tool_choice` to the one function, but that alone is not enough for a smaller open model to reliably emit valid JSON — the vLLM-side flag `--guided-decoding-backend xgrammar` (`docker-compose.gpu.yml`) is load-bearing. Without it, expect the repair path to fire on nearly every call, which is expensive and, on the real generate route, would cost a refund far more often than Anthropic's forced tool-use ever does.
- **`LLM_PROVIDER`/`LLM_BASE_URL`/`LLM_MODEL`/`LLM_API_KEY` are all optional, unset by default (`lib/schemas/env.ts`).** An unset or unrecognized `LLM_PROVIDER` falls back to `"anthropic"` rather than throwing — production sets none of these today, and must keep working unchanged if this file is never touched again.
- **`ChatMessage.decision`/`.draftVersion` (`lib/types.ts`) are the training-data capture surface, never a second copy of the prompt.** Set on the primary AI bubble of each `proposeGarment` branch in `app/api/patterns/[id]/generate/route.ts`; `draftVersion` only on `apply`, read after `bumpVersion` so it matches the `PatternVersion.version` `recordVersion` just wrote in the same transaction. Both must stay named in `lib/schemas/pattern.ts`'s `ChatMessageSchema` or they are silently stripped on the next mutating turn — the exact trap `hasImage`/`assembly` already hit once.
- **The LoRA training pipeline (`scripts/lora/`, `docs/reference/lora-training/README.md`) runs on a separate rented GPU, never on the machine `docker-compose.gpu.yml` serves inference from.** `prepare_dataset.py` has zero dependency on this Node project on purpose — the training host will not have it checked out. See the decision doc for the measured (near-zero) yield of distilling training data from the pattern-catalog-benchmark corpus against today's narrow drafting capability, before spending tokens re-running it at scale.
- **The combinatorial generator (`lib/ai/training/*`, `scripts/generate-training-data.ts`, `npm run generate:training`) is a second, parallel dataset source — never edit `scripts/distill-training-data.ts` to add this behavior.** `lib/ai/training/combinations.ts` is a leaf (only `MOLDAI_CAPABILITY` plus type-only imports, no drafter) so a client or a fast test can enumerate combinations without pulling in the drafting engine; `verify.ts` is the one place "does this enumerated spec actually draft" is checked, reused by both `combinations.test.ts` (the shipped seed, as a regression pin) and the generator script (whatever seed/options a real run used, before a token is spent) — never re-implement that check a third way.
- **`verify.ts`'s `draftsCleanly` is deliberately NOT `lib/ai/eval/score.ts`'s `draftSucceeds`.** A combination naming `armholeDeepenCm` is DESIGNED to produce a real "armhole-cap" `seamCheck` conflict (`sleeveRefit`, the field that would pre-empt it, is internal-only) — `expectsArmholeCapConflict` (`combinations.ts`) is what tells the two verifiers apart from an actual drafting failure. Discovered by this generator's own test, not assumed in advance — a future style field with a similar "expected side effect" shape should extend this same allowance, not add a second one.
- **Batch API requests reuse `buildRequestParams` (`lib/ai/provider/anthropic.ts`, exported for exactly this) — never a second, hand-built request shape in `lib/ai/training/batch.ts`.** Only the transport differs (submit/poll/collect vs. a single `messages.create`); the model, the cached static system block, the tool, and the forced `tool_choice` must stay identical to what a live call sends, or the dataset would not represent the app's own real requests. `custom_id` is capped at 64 characters by the API itself — well under this generator's own descriptive task ids — so the wire id is a short hash (`shortId` in the script) while the full descriptive id lives only in the output JSONL; a batch's sidecar (`data/training/combinatorial.batch.json`) is deleted once its results are fully collected, so a later run submits fresh work instead of re-"resuming" an already-finished batch — both were real bugs this feature's own live smoke-testing caught, not hypothetical risks.
