# API routes

> For the why behind these rules — the six routes that 500'd on a `null` body, and the per-route `parseBody` adoption notes — see [`../decisions/api-routes.md`](../decisions/api-routes.md).
> For universal, cross-cutting rules, see the root [`CLAUDE.md`](../../CLAUDE.md).

**Every route that reads a body does it through `readJsonObject(request)` or `parseBody(request, schema)` (`lib/api/body.ts`) — with exactly one exception, `POST /api/billing/webhook`, which must hash the RAW bytes.** Stripe's authenticity check is an HMAC over the exact body it sent, so parsing and re-serializing would make every real event fail verification; that route reads `request.text()` and hands those bytes to the SDK's `constructEvent`, which parses only _after_ verifying. The parsed payload's own trust boundary is `parseGatewayEvent` (`lib/billing/stripe.ts`). Otherwise: both return the parsed value **or the 400 to return**, shaped like `requireUser()` so `if (x instanceof NextResponse) return x;` reads as the guard idiom already in use.

**`parseBody<T>` also proves the body against a zod schema (`lib/schemas/*`) before the route sees it, answering a bare `bad_body`** rather than a zod issue path. It does **not** replace a route's own downstream trust boundary: a field stays `z.unknown()` (or `.optional()`) wherever the route already clamps or narrows it itself. **`PATCH /api/size-charts/[id]` is a deliberate, permanent exception, still on `readJsonObject`:** it forwards its raw body to `validateSizeChartPatch`, whose drop-or-clamp-never-throw merge semantics a schema would either duplicate or regress into reject-on-invalid (see [`size-charts.md`](size-charts.md)).

All pattern-mutating routes live under `/api/patterns/[id]/*`, scoped to one pattern and 404'ing via `patternNotFound()`.

- **`requireUser()` (`lib/auth/guard.ts`) gates every route — 401 without a session — with exactly six deliberate exceptions, none of which can carry one:** `POST /api/signup`, the email-verification and password-reset routes, `GET /api/health`, `POST /api/billing/webhook` (authenticated instead by Stripe's HMAC signature over the raw body), and NextAuth's own handlers.
- `POST /api/signup` — returns `{status:"ok"}` or a machine-readable `SignupErrorCode`. Deliberately at the top level, outside both the `[...nextauth]` catch-all and the uniformly-gated `/api/account/*`. `createUser` returns `null` on the P2002 insert race so a lost race reads as `email_taken`.
- `POST /api/verify-email` (consumes the token, stamps `emailVerified`, **mints no session**) and `POST /api/verify-email/resend` (credential-gated, 60 s cooldown).
- `POST /api/password-reset/request` — **always answers 200 regardless of whether the address exists**; an "ok" body must not double as an account-existence oracle. `POST /api/password-reset/confirm` is IP-keyed only, like `verify`, since the 256-bit token is the real backstop.
- `GET /api/health` — unauthenticated, backs the Compose healthcheck (see [`observability.md`](observability.md)).
- `GET`/`POST /api/patterns` — list, and create a blank one. With a `{sloperId}` body it copies that base's frozen snapshot into an already-drafted pattern and **costs 0 credits** (see [`slopers.md`](slopers.md)).
- `GET`/`PATCH`/`DELETE /api/patterns/[id]` — the composed `EditorState`, rename, delete. **Delete + create is the only "reset"** — there is no reset endpoint.
- `POST /api/patterns/[id]/generate` — the core AI flow (see [`generation-flow.md`](generation-flow.md)). Debit-then-mutate; insufficient balance → **402, no debit, no AI call**.
- `POST /api/patterns/[id]/graduate` — same shape. **Its precondition is `pieces.length === 0` → `pattern_not_drafted`, not the size list.**
- `POST /api/patterns/[id]/conflict/resolve` — free, no debit (see [`seams-and-assembly.md`](seams-and-assembly.md)).
- `GET /api/patterns/[id]/versions` and `.../[versionId]/restore` — see [`screens.md`](screens.md).
- `GET /api/account/summary` — account-level: `{credits, recentUsage}` backing the dashboard cards. Also `/api/account/ledger`, `PATCH /api/account/profile`, `POST /api/account/password`, `DELETE /api/account`, `POST /api/account/onboarding`, `GET`/`PUT /api/account/export-preset`.
- `/api/size-charts/*` (including `[id]/activate` and `[id]/duplicate`) and `/api/slopers/*` — see their own files. `POST /api/slopers` alone can tell 404 from 400 (`invalid_name`, `pattern_not_drafted`, `pattern_has_conflict`).

**The wire and the database carry codes, never pt-BR prose** (the full rule, shared with the DB and the AI flow, lives in [`i18n.md`](i18n.md)). Every `app/api/*` error payload is `{status, error: <code>}` where the code is machine-readable and the client resolves it through the catalog (`t("errors." + code)`), the `SignupErrorCode` precedent. Shared route-level codes and the `apiError` helper live in `lib/api/errors.ts`; **domain codes stay beside their own pure logic** (`ChangePasswordResult` in `lib/account/settings.ts`, `SignupErrorCode` in `lib/account/signup.ts`) because those unions type a pure function's return — each route unions the two and maps its own HTTP statuses in a local `Record`. `apiError` takes a bare `string` for exactly that reason: a fixed union would drag every domain union into `lib/api/errors.ts` and invert the dependency. Its internal `STATUS_WORD` map reproduces each response's pre-existing wire `status` discriminator, **warts included**: `/api/account/*` answers its 404 with `status: "error"`, not `"not_found"`.
