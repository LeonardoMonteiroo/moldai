# SEO and crawlability

> For the why behind these rules — the localhost `og:image` measurement, and why blocking and de-indexing are opposite tools — see [`../decisions/seo.md`](../decisions/seo.md).
> For universal, cross-cutting rules, see the root [`CLAUDE.md`](../../CLAUDE.md).

- **`lib/seo/site.ts` is the one module that knows what origin this deployment answers on.** `metadataBase`, every sitemap entry and robots.txt's `Sitemap:` line all resolve through it, so they cannot name three different hosts. `parseSiteUrl` is total — an absent, blank, unparseable or non-HTTP(S) `APP_URL` falls back rather than taking the render down, and **empty string counts as absent** because a Docker `ARG` that was never passed produces `ENV APP_URL=`.
- **`metadataBase` is not optional on a self-hosted deploy** — Next resolves relative social-image URLs against `metadataBase || VERCEL_PROJECT_PRODUCTION_URL || http://localhost:3000`, and neither Vercel variable exists here.
- **`APP_URL` is therefore a BUILD input as well as a runtime one.** The four public routes are dynamic and read it at server boot, but `/login` and `/signup` are statically prerendered and freeze whatever the build saw — so the Dockerfile's `build` stage takes it as an `ARG` (both prod services pass the same value, or the layer cache forks into two near-identical images). It is not a secret, unlike everything else in `env_file`.
- **`app/robots.ts` and `app/sitemap.ts` are `force-dynamic` on purpose** — both are cached route handlers by default, which would bake the build-time origin into the `Sitemap:` line and every `<loc>`.
- **Blocking and de-indexing are opposite tools, and the route lists encode that.** `NOINDEX_ROUTES` (`/login`, `/signup`, `/verify`, `/password-reset`) carry a `robots` meta tag and are deliberately **absent** from `CRAWLER_DISALLOWED_PREFIXES` — a disallowed URL is never fetched, so the crawler would never read the directive and the URL stays indexable from any inbound link, just without a snippet. `lib/seo/site.test.ts` pins that invariant, and `app/seo.test.ts` derives its per-page assertions from the same lists, so adding a route to one without touching its page fails.
- **The sitemap emits `url` alone** — no `lastModified`, `changeFrequency` or `priority`. Add `lastModified` the day there is a real content timestamp to read.
- **Structured data is built by `lib/seo/jsonLd.ts` from the same constants the screens render from**, never a second transcription: Organization + WebSite + FAQPage on `/` (FAQPage still walking `FAQ_KEYS`), Organization + SoftwareApplication with per-plan `Offer`s on `/planos` (priced from `PLAN_PRICE_CENTS`). **`Organization` carries no `logo` and no `sameAs`** — there is no square brand asset (`Wordmark` is live text) and no social profile, and inventing either is the same line the landing page's "proof is product facts, never social proof" rule draws. `jsonLdGraph` escapes every `<`, since the block is injected with `dangerouslySetInnerHTML`.
