# Billing (real; only the gateway is mocked)

> For the why behind these rules — the #179 → #193 → #196 → #198 defect chain in detail, each reversal's exact semantics, and the migration backfill reasoning — see [`../decisions/billing.md`](../decisions/billing.md).
> For universal, cross-cutting rules, see the root [`CLAUDE.md`](../../CLAUDE.md).

- **`Wallet` (1:1 with `User` — credits are account-level, shared across all its patterns) + an append-only `Transaction` ledger**, same pure-logic + thin-repo split: `lib/billing/wallet.ts` + `lib/db/wallet.ts`. Wallets are lazily seeded on first access (`INSERT … ON CONFLICT DO NOTHING` inside `lockWallet`) at the **Free tier** — open sign-up must not grant a paid balance.
- **`lib/billing/plans.ts` is the one exported source for every paid tier's terms**: `PLAN_CREDITS`/`PLAN_PRICE_CENTS`, `TOPUP_CREDITS`/`TOPUP_PRICE_CENTS`, `CURRENCY`, `formatBRL`, **`priceDecimalString`** (the machine-readable counterpart to `formatBRL` — major units, `.` separator, no symbol, for schema.org's `Offer.price`), `PaidPlanId`, the trust-boundary narrower `isPaidPlanId`, **`SELF_SERVE_PLAN_IDS`** (the tiers actually buyable without talking to a human — Confeccao is absent, since its CTA is permanently disabled; `PlanCta` and `/planos`' structured data both read it), `isPlanOrIntervalUpgrade(from, to)` (ranks `{plan, interval}` pairs by `effectiveCredits`, **no second rank table**), and `PLAN_FEATURES`. Never hardcode a price, credit count or rank anywhere else.
- **Prices are stored in centavos and formatted in exactly one place.** Stripe's `unit_amount` is always the currency's minor unit, so `PLAN_PRICE_CENTS.atelier` is `5900`. **`formatBRL(cents)` is the only place a currency symbol or decimal separator appears** — the catalog carries **no price literal at all** any more. Note `Intl` emits a **non-breaking space** between symbol and amount, which is why `components/test-utils.tsx` exports `priceText` for `getByText` matchers.
- **Settlement is BRL-only, but the app no longer says so on screen.** A Brazil-based Stripe account is in a foreign-exchange-control country, so Adaptive Pricing converts the amount for _presentation_ at checkout while the charge still settles in reais; that account also accepts **only Visa and Mastercard** (no Elo/Amex/Hipercard/Diners), and Pix is invite-only. `PlanSection.paymentNote` and `Pricing.paymentNote` both match the design handoff's generic "Pagamentos processados pela Stripe." — a deliberate exception to the "surface feature limitations on-screen, never silently" rule elsewhere in this repo.
- **`applyPurchase(wallet, purchase, now)` is the one function every mutation path routes through — mock and gateway alike — so guards belong in it, not in a route.** It takes a discriminated union (`{type:"topup"}` or `{type:"subscribe", plan}`) and can move a wallet to any paid tier. An upgrade's balance becomes `PLAN_CREDITS[plan] + wallet.purchased`, never destroying a prior top-up.
- **Four invariants govern every wallet mutation, each mapping to a shipped defect of the same shape — a reversal or reapplication that did not mirror what it undid or repeated:**
  1. **A renewal never touches `purchased`** — it is a carry-over pool, separate from the plan allowance (`total`). `total` stays the plan allowance only, or it misreports the plan. Because `balance` can legitimately exceed `total`, **every credits-meter bar clamps its fill at 100%**.
  2. **A confirmation never walks the plan down.** `applyPurchase`'s subscribe branch carries a monotonicity guard reusing `isPlanOrIntervalUpgrade` (so a same-tier, same-interval reapply — or an annual-to-monthly interval downgrade — is refused by the identical check). **A refused plan change never swallows the payment:** the money has settled, so the tier's full credit value folds into `purchased` and the ledger entry keeps `type: "subscribe"`.
  3. **A refund reverses exactly what its entry contributed, decided against the _locked_ wallet.** `reverseRefundedEntry(wallet, entry, refundedExternalId)` is the one pure dispatch for every shape a gateway refund can name: `"topup"` and a _folded_ subscribe share one reversal (`reversePurchasedCredits`); a subscribe resolves `"reset"` only when it **is** `wallet.planSourceExternalId`, `"folded"` when `entry.planChanged` was false, and `"superseded"` when a later upgrade has since overwritten it. Two additive columns make those cases distinguishable: **`Wallet.planSourceExternalId`**, written once and centrally by `withWalletIdempotent`, and **`Transaction.planChanged`**.
  4. **`lib/billing/invariants.test.ts` is the standing guard**, not one case per issue. It drives the real pure functions through 200 seeded 60-step walks of credits/debits/refunds/plan changes/renewals in arbitrary order, checking after **every** step: the ledger reproduces the balance; `total === PLAN_CREDITS[plan]`; `purchased` equals the sum of unreversed grants and is never negative; `planSourceExternalId` names an entry that really moved the plan; a confirmation never walks the plan down.
- **`withPatternAndWallet(patternId, userId, fn)` (`lib/db/pattern-wallet.ts`) is the only function ever allowed to hold both locks, and it always takes `Pattern` first, then `Wallet`** — which makes cross-lock deadlock structurally impossible. It returns `null` without ever locking the wallet when the pattern isn't found/owned. `generate` and `graduate` debit atomically through it.
- `lib/api/compose.ts` exports `buildCredits(wallet, now)` and `composeEditorState(patternState, wallet, now)` — the wire `EditorState`. `Credits.renewsInDays` derives from the real `Wallet.renewsAt`.
- **Auto-renewal** is `scripts/cron-renew.ts`, scheduled by the `cron` Compose service (hourly, no external scheduler): resets `balance` to `total + purchased` and rolls `renewsAt` forward 30 days from the _scheduled_ time. "Use it or lose it" governs only the plan allowance. **Its past-due query excludes any wallet with a non-null `stripeSubscriptionId`** — a subscribed wallet is renewed by its own `invoice.paid` webhook instead. That column is written inside the same transaction as the first payment's credit (`withWalletIdempotent`'s optional 4th argument), never best-effort afterwards.
- **A subscription renewal calls `renewWallet`, never `applyPurchase`. This is invariant 1, not a style choice.** A recurring payment leaves the plan unchanged, so routing it through `applyPurchase` would fold the whole plan allowance into `purchased` — the carry-over pool a renewal must never touch. `invoice.paid` + `billing_reason: "subscription_create"` → `applyPurchase` (a real plan change); `subscription_cycle` → `renewWallet`.
- **`POST /api/billing/purchase` has two providers.** Mock (the default) simulates instant success and returns the pattern's composed `EditorState` when given a `patternId`, else `{status:"ok", credits}`. Under `PAYMENT_PROVIDER=stripe` it answers `{status:"redirect", url}` (a hosted Checkout Session) and **never touches the wallet** — the webhook does, once payment confirms. Both branches run the same `resolvePurchase` trust check before any provider call, and both **refuse a downgrade inside the wallet lock** (`plan_not_upgradable`) via `withStripeCustomerId`'s `guard`. **Which plan a subscribe checkout was for round-trips through Stripe `metadata`**, stamped on **both** the session and the subscription, and `parsePurchaseMetadata` **re-validates the embedded plan with `isPaidPlanId`**. The line item is priced with **inline `price_data` from `lib/billing/plans.ts`, never a Dashboard `Price` object**.
- **Every credit is keyed on the Stripe payment-intent id**, because that is the only id a refund and its original credit can both name in this API version. An invoice that yields no payment intent is reported unprocessable rather than credited under a guessed key. **A PARTIAL refund is never applied**: `reverseRefundedEntry` reverses an entry's whole contribution, so it is logged for reconciliation instead of clawing back more than was given back.
- **The webhook's status codes were re-decided for Stripe, not copied from Asaas.** Stripe retries with backoff for ~3 days, so: **400** for a missing/invalid signature (nothing to retry), **200** for a genuine but permanently unprocessable event, and **500** for a transient failure on our side, so Stripe retries.
- **`type` is validated, and `applyPurchase` is exhaustive.** `isPurchaseType` narrows it (unknown/absent → 400, wallet untouched) and `applyPurchase` `switch`es with a `never` binding. **The pattern is also resolved before the wallet is touched** — charging first meant a bad `patternId` credited the account and then answered 404.
- **`Wallet` has no `planLabel`.** `PageHeader` resolves ``tPlan(`plans.${credits.plan}.name`)`` from the existing catalog instead of a stored label that could drift from the plan it names.
