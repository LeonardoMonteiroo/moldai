## The engine is a swappable choice, not the only code path (#266 → #267)

**This is a documented, deliberate exception to the "don't add abstractions beyond what's needed" rule** (see [`conventions.md`](conventions.md)). A second engine, `"freesewing"` (`lib/draft/engine/freesewing/`, backed by pinned `@freesewing/*@4.10.1` design packages), IS registered — `docs/reference/garmentcode-spike/` remains evidence from a spike that was declined, not shipped, but the freesewing spike graduated into `lib/draft/engine/registry.ts`. It drafts `tshirt` (Teagan), `blouse` (Diana), `skirt` (Sandy), `trousers` (Titan), `hoodie` (Hugo), `coat` (Jett) and `shirt` (Simon) today; `dress` was evaluated (Sophie, Sasha) and declined — neither maps to moldai's own bodice+skirt dress concept (see `docs/decisions/drafting.md`). The exception is justified by three concrete capabilities the decision log argues for, not by "we might swap engines someday": in-repo scoring of a candidate against `tshirtBenchmark.test.ts`, a stated contract for what each engine actually supports (making a gap reportable instead of implicitly defaulted), and a per-pattern frozen engine choice that a second engine can build on without redrawing existing patterns.

- **`lib/draft/engine/facade.ts` is the one and only public surface** — `draftPiecesCm`, `measureSeams`, `measureSeamGraph`, `draftGradedOverlays`, `draftGarment`, each taking an `EngineId` as a **required** first parameter (not an optional trailing one defaulting to `"moldai"`), so every call site was forced to a compile error until updated. No consumer may import `garment.ts`'s functions directly any more — enforced by `lib/draft/engine/conformance.test.ts`'s own source scan.
- **`EngineCapability` (`lib/draft/engine/capability.ts`) is a stated contract for what one engine actually supports** — required/optional measurements, supported `GarmentType`s, style enums/limits, and which style fields each supported type reads — so a gap is **reportable** (`checkEngineSupport`) instead of silently defaulted. `checkEngineSupport` narrows an already-**valid** spec (`validateSpec` has already run) to what the engine can honestly honor, and **may only report, never substitute** — a legitimate stated intent must never be silently swapped for something else, the opposite half of `validateSpec`'s own "may substitute a default for garbage" contract. **`validateSpec` may still substitute — but never silently (#250):** `lib/draft/specAdjustments.ts`'s `describeSpecAdjustments` diffs the model's raw payload against `validateSpec`'s own return value, and the generate route turns that into the identical `tone: "notice"` bubble shape `checkEngineSupport`'s own gaps already use. See [`generation-flow.md`](generation-flow.md).
- **`lib/ai/prompt.ts`/`schema.ts` render every enum and numeric bound from the _active_ engine's capability**, not a hardcoded constant — the same "never hardcode a bound in the prompt or schema" rule in [`generation-flow.md`](generation-flow.md), now scoped per-engine.
- **A pattern freezes its engine at first generation, the same snapshot-once rule size charts and sloper specs already follow.** `Pattern.engine?: string` (additive, absent ⇒ `DEFAULT_ENGINE_ID`, `"moldai"`) is written once; switching the app's default engine must not silently redraw an existing pattern with different geometry. `engineFor(value)` is the trust boundary that narrows an untrusted persisted/wire string back to a real `EngineId`, reporting (never throwing) on a recognized-but-retired id. `SloperData.engine?`/`PatternVersion.engine` carry the identical additive field for the same reason `sizeChartName` does on both: a base and a historical version must each determine their own geometry (spec + sizeTable + engine), not borrow whatever the app's current default happens to be. `/pattern/[id]/versions` never loads the `Pattern` blob at all, so without the column on `PatternVersion` those screens would have no way to know which engine drafted a historical version.
- **The seam graph and assembly order stay engine-agnostic.** `walkSeamPairs` (`lib/draft/seams.ts`) and `buildAssemblyOrder` (`lib/draft/assembly.ts`, see [`seams-and-assembly.md`](seams-and-assembly.md)) are shared post-processing over whatever pieces an engine declares — neither may grow an engine-specific branch. Structural, not just conventional: an engine's `draft()` method can only return `SeamPairDecl[]` (declarations), never a measured `SeamMeasurement[]` — it is not physically possible for an engine implementation to hand back a measurement.
- **`lib/draft/vocabulary.ts` and `lib/draft/engine/capability.ts` are leaf modules; `lib/draft/engine/{moldai,registry,facade}.ts` are not.** The leaf/heavy split exists because a client component (`NewPatternForm`, which reads BOTH `MOLDAI_CAPABILITY` and `FREESEWING_CAPABILITY` to render its own engine `Select` and gate the garment-type `Select` by whichever one is chosen) needs those constants without pulling the whole drafter tree (`body.ts`/`sleeve.ts`/`skirt.ts`/`trousers.ts`/`subpieces.ts`, plus every freesewing design wrapper) into its bundle. A client component reads the capability constants directly, never `lib/draft/engine/registry.ts`.
- **The engine is a real, user-facing choice, not just an internal registration.** `NewPatternForm`'s own engine `Select` sends `engine` on the pattern's first `generate` call (`POST /api/patterns/[id]/generate`'s body); the route narrows it via `isEngineId` (rejecting a present-but-unrecognized value with `invalid_engine` before any lock/debit, the same discipline `formSpec`/`sizeChartId` already follow) and sets `state.pattern.engine` as soon as it knows this is the pattern's first-ever draft — BEFORE the AI call, not only at the size-chart snapshot, since `proposeGarment`'s own `engineFor(state.pattern.engine)` read picks which engine's tool schema/prompt section the model sees. `Pattern.engine`, once set, still never changes again (`state.test.ts`'s own "never changes an already-frozen pattern.engine" contract) — it can just freeze a turn or two earlier than the size snapshot now, e.g. on an `ask` turn, since only `createFromForm` ever sends `engine` and it does so on exactly this pattern's first `generate` call regardless of what the model decides that turn.
- **`docs/reference/tshirt-benchmark/comparison-report.md`'s deltas are circular and not an independent quality signal** — it's auto-generated, and no delta in it is a pass/fail gate, so it can confirm regressions but cannot prove fit accuracy. Treat any number in it as "did this change" not "is this right." `tshirtBenchmark.test.ts` scores every registered engine (`"moldai"` and `"freesewing"`), and an engine whose required measurements the benchmark's own `SIZE_TABLE_MALE` can't satisfy is reported with a stated reason and skipped, never scored against a silent zero row. **Since #282, this is true for panel height only, not width:** `TSHIRT_BASE_EASE_CM` (`lib/draft/ease.ts`) no longer derives from this benchmark's panel width, so `widthCm` and (freed of that calibration) `areaCm2` are now genuine, non-circular comparisons — `TSHIRT_HEM_DROP_CM` (`garment.ts`) still derives panel height from this same benchmark, so `heightCm` (and anything built from it) stays circular.

## Pieces are drafted from measurements, not deltas

- `lib/measurements.ts` defines `Measurements` (`shoulder` is the half-width from the centre line to the shoulder tip, not the full seam) plus the legacy `SIZE_TABLE`/`SIZE_TABLE_MALE`, now only seed data for the two system size charts and the pre-generation bootstrap.
- **`Measurements` has two tiers.** `CORE_MEASUREMENT_KEYS` — the 9 proportional keys (`bust`, `waist`, `hip`, `hipHeight`, `backLength`, `shoulder`, `skirtLength`, `shortSleeveLength`, `longSleeveLength`) — stay **required**, enforced by `assertResolvedMeasurements` on every base row. `EXTENDED_MEASUREMENT_KEYS` are 8 **optional** overrides, each read by exactly one drafter and each falling back to the proportion it replaces:

  ```
  neckGirth       → body.ts   neckHalf = neckGirth/6 + offset      ← bust/14 + offset
  highBust        → body.ts   armholeDepthBase = highBust/8 + off  ← bust/8 + offset
  shoulderSlope   → body.ts   shoulderSlope                        ← 4.0 female / 4.5 male
  backWidth       → body.ts   BACK PANEL ONLY: armCtrlX at midArmY ← (shoulderHalf + halfChest)/2 - 1
  bicep           → sleeve.ts bicep = bicep + wearingEase          ← bust*BICEP_PROPORTION_OF_BUST + ease
  rise            → trousers.ts riseCm (crotch depth)              ← hip/4 + 4
  bustPointHeight → body.ts   shoulder seam → bust apex, vertical  ← 26.5 (seeded default)
  bustSpan        → body.ts   apex-to-apex, horizontal             ← 18.5 (seeded default)
  ```

  **`halfChest` (the underarm-level width where front, back and sleeve all meet) stays bust-derived for both panels, always — never wire `backWidth` into it.** `backWidth` is an upper-chest/shoulder-blade measurement feeding the armhole curve's control point; routing it through `halfChest` makes a user who measures honestly get a back too narrow per side. Seeding is a deliberate no-op for four keys (`neckGirth`/`highBust`/`shoulderSlope`/`bicep` seed to the exact value reproducing the fallback formula) but **intentionally not** for `backWidth` (`bust*0.4`, a real proportion) or `rise` (per-size graded) — both genuinely change what a new chart drafts. **No migration:** a pattern snapshots its chart once, so an existing pattern keeps taking every fallback forever.

- `resolveMeasurements(base, overrides)` applies chat-driven `measurementOverrides` onto an already-resolved base row, clamped to `MEASUREMENT_RANGES`. No size/gender table lookup happens here — the base row comes from the pattern's frozen `sizeTable`.
- `GarmentType` = `"blouse" | "dress" | "skirt" | "tshirt" | "trousers" | "hoodie" | "coat" | "shirt"`. A `GarmentSpec` (`type` + `gender` + `measurementOverrides` + `style`) plus a resolved `Measurements` flow into `draftGarment(spec, baseMeasurements, t)` (`garment.ts`), which calls the per-block drafters (`body.ts`, `sleeve.ts`, `skirt.ts`, `trousers.ts`, shared helpers in `core.ts`) and lays the pieces into one computed `viewBox` (`autoLayout`). The engine doesn't know `SizeLabel` — it's a per-chart `string`. **`hoodie`, `coat` and `shirt` are drafted by the `freesewing` engine ONLY** — `MOLDAI_CAPABILITY.types` (`lib/draft/engine/capability.ts`) deliberately excludes all three (no moldai drafter exists for a raglan hood, a placket-front lined jacket, or a yoked button-front shirt — none of these have an equivalent in `body.ts`/`sleeve.ts`), and `garment.ts`'s own `draftAll` throws rather than silently returning an empty pattern if ever asked to draft any of them — the same defensive backstop `lib/draft/engine/freesewing/index.ts`'s own dispatch already has for a type it doesn't wire.
- `tshirt` is a knit archetype (round neck, no darts, short sleeves) through the same drafters, with `knit: true` in `BlockOpts`.
- **Curvature is per-edge-range and opt-in.** `outlinePath` (`core.ts`) takes cm points plus `curvedSpans: [number, number][]`; only marked ranges (neckline, armhole, sleeve cap) get Catmull-Rom-derived Béziers with tangents locked at span edges. Every other edge is a straight `L`. No global smoothing pass.
- Each drafter attaches its own `piece.detailRows` (label/value pairs).
- **A decoration is placed from the piece's own boundary, never from its bounding box.** It starts at `neckDrop + 3` now. Placement that depends on _rendered text width_ can't live in the drafter: `lib/canvas/pieceLabel.ts`'s `fitPieceLabel` recomputes the canvas label at render time from `piece.vertices`, which also repairs already-drafted patterns. **The invariant is guarded generically:** `garment.test.ts`'s containment suite asserts every grainline and dart point lies inside its own outline across the whole `DECORATION_CASES` matrix.
- **Notches are typed, drafter-derived, and never persisted or user-movable.** `DraftedPiece.notches` (`core.ts`'s `NotchCm`: `type` + `outerCm` + `innerCm`) follows the derive-don't-store precedent. `single`/`double`/`triple` are told apart purely by depth (`NOTCH_DEPTH_CM` 0.3/0.6/0.9 cm), which is simultaneously the printable size. `notchAt(point, tangent, insideRef, type)` orients the inward normal by biasing toward a caller-known interior point, so it works regardless of which winding direction that outline walks.
- **Mated notches share one computed distance, not two independent guesses.** `draftBody` (`lib/draft/body.ts`) drafts front and back **twice**: once to learn each panel's own armhole length, then again with `lib/draft/seams.ts`'s `pitchNotchDistanceCm(totalLenCm)` — clamped off the pair's own **combined** total, not either panel's own single-side length — handed to both `bodice()` calls verbatim, so `f.pitchNotchCm === c.pitchNotchCm` by construction rather than merely "equal because the formulas happen to agree" (#253: a real `backWidth` divergence used to desync the two, since body.ts clamped to 0.7 of one panel's own length while sleeve.ts separately clamped to 0.35 of the cap's own arc — consistent only when front and back were equal). `draftAll` picks whichever of `pitchNotchCm`/`basePitchNotchCm` matches the armhole the cap was **actually** drafted against and passes that single number into `draftSleeve`, which now uses it verbatim with no clamp of its own. Single marks the front, double the back; the cap's apex notch is excluded from the cross-check.
- **Every other notch is placed by direct convention, not by cross-piece coordination** — a hem-fold notch at every piece's own `foldEdge` hem-end vertex, dress-hem double/single notches at waist-join corners and dart-leg intersections.
- **`Piece`/`DraftedPiece` carry a typed `internals` channel** — `InternalCm` (`dart`/`foldLine`/`drillHole` ship; `pleat`/`styleLine`/`placementMark` reserved). A dart's **fold line** is its own press line, a different concept from the piece's cut-on-fold axis (`foldEdge`). `dartInternals` derives all three marks together; each free apex gets a drill hole `DRILL_HOLE_SETBACK_CM` (1.25 cm) short of the point. **Migration:** the legacy `Piece.darts` field is never written again but stays readable via `lib/types.ts`'s `resolvePieceInternals` at render time.
- **Three sub-piece drafters live in `lib/draft/subpieces.ts`, each sized from a MEASURED edge on an already-drafted piece, never a proportion of the bust/waist.** `GarmentStyle` gained `collar?: "none" | "convertible"`, `cuff?: "none" | "straight"`, `waistband?: "none" | "straight"`, clamped by `validateSpec` and rendered into the prompt/schema from the exported vocabulary constants. **There is deliberately no third enum value for an unsupported shape**, so the AI's only path for one is `decline`/`ask` — never a silent substitution. Collar: sized to the summed real neckline arc. Cuff: the measured sleeve hem plus `WRIST_EASE_CM`, long sleeves only. Waistband: the skirt/trouser waist summed across the panel's own `qty` plus `WAISTBAND_OVERLAP_CM`, and **defaults ON** (unlike collar/cuff).
- **A fifth archetype, `trousers` — a straight-leg block only.** Front and back are each a genuinely asymmetric single-leg shape, so **neither declares a `foldEdge`**; both are `qty: 2` (mirrored by flipping fabric, not folding). They share rise depth, total length and hip quarter-width; only the crotch extension differs. `style.trouserLengthCm` defaults to a flat per-gender constant — there is no per-size leg-length measurement to grade against yet. **Prova 3D does not cover trousers:** `Proof3DTab` renders a named `notSupportedForTrousers` gap rather than a silently empty preview.
- **The drafted-ease report (`lib/draft/easeReport.ts`'s `buildEaseReport`) states how much ease the FINISHED garment has**, deliberately distinct from `wearingEaseCm` (the ease the drafter was _asked_ for). Pure and DB-free, redrafting from the pattern's own frozen `sizeTable`. Per girth it scans the piece's real width at a height derived from **public data only** (a `seamEdges` vertex or a raw `Measurements` field — never an internal per-drafter formula), then subtracts what any dart removes at that same height. **A girth it cannot measure honestly is reported `unavailable` with a reason, never a wrong number** — a circle/gore/half-circle panel is drafted from polar coordinates where a horizontal scanline is meaningless (`unsupportedSilhouette`), and a bust-less garment has `noPanel`. Fit class comes from `classifyGirthFit`, whose band boundaries are the **midpoints between consecutive `FIT_EASE_CM` figures** — never a second, competing scale.
- **The knit branch's base ease is a percentage of bust, never a flat cm figure, and never calibrated against `comparison-report.md`.** `TSHIRT_BASE_EASE_CM` (a flat 55.9 cm, ~56% of bust) was solved backwards from that report's own contested `widthCm`; `TSHIRT_BASE_EASE_PCT = 18` (`lib/draft/ease.ts`) replaced it, sourced from FreeSewing's Teagan at published defaults, which holds ease flat at 18.0% of bust across every graded size — the property a flat cm constant cannot reproduce. See `docs/decisions/drafting.md`'s #282 note before touching this constant again.
