### Drafting engine (`lib/draft/*`)

- **Pieces are drafted from measurements, not deltas.** `lib/measurements.ts` defines `Measurements` (bust, waist, shoulder, … — `shoulder` is the half-width from the body's center line to the shoulder tip, not the full shoulder seam) plus the legacy `SIZE_TABLE` (female)/`SIZE_TABLE_MALE` (male) tables, now used only as seed data for the two system size charts and the pre-generation bootstrap default.
- **#132: `Measurements` widened past the original nine proportional keys.** Those nine (`bust`, `waist`, `hip`, `hipHeight`, `backLength`, `shoulder`, `skirtLength`, `shortSleeveLength`, `longSleeveLength`) are `CORE_MEASUREMENT_KEYS` and stay required — `assertResolvedMeasurements` (below `resolveMeasurements`) still demands every one, on every base row. Six more are `EXTENDED_MEASUREMENT_KEYS`, and every one of them is **optional** — a chart, or a pattern's already-frozen `sizeTable` snapshot, can simply not have it. Each is read by exactly the drafter it lets a user override, and falls back to the exact proportion it replaces when a chart doesn't set it:

  ```
  neckGirth     → body.ts neckHalf = neckGirth/6 + offset            → falls back to bust/14 + offset
  highBust      → body.ts armholeDepthBase = (highBust ?? bust)/8 + offset → falls back to bust/8 + offset
  shoulderSlope → body.ts shoulderSlope                              → falls back to 4.0 female / 4.5 male (a flat constant either way)
  backWidth     → body.ts BACK PANEL ONLY: armCtrlX = backWidth/2 + wearingEase, at midArmY → falls back to (shoulderHalf + halfChest)/2 - 1
  bicep         → sleeve.ts bicep = (bicep ?? bust*BICEP_PROPORTION_OF_BUST) + wearingEase  → falls back to bust*BICEP_PROPORTION_OF_BUST + wearingEase
  rise          → trousers.ts riseCm = rise (crotch depth, waist to seat)   → falls back to hip/4 + 4
  ```

  `backWidth` earned a real design correction mid-review, worth recording so it isn't repeated: `armCtrlX` is the armhole curve's own control point, at a height strictly between the shoulder tip and the underarm — roughly shoulder-blade/upper-chest height, which is exactly where `SizeChartTable.measurementGuide.backWidth` sends the user's tape ("axila a axila pelas costas, na altura das omoplatas"). `halfChest` — the underarm-level width, where front, back and sleeve all meet — stays bust-derived for **both** panels, always; a first version of this wired `backWidth` into `halfChest` instead (seeded as `bust/2` purely so the fallback formula stayed a no-op), which meant the seeded "across-back" value was ~46cm at a 92cm bust while a real tape measures ~36-38cm there. A user who actually measured and entered that real number got a back panel roughly 5cm narrower per side than intended — the exact fit failure this issue exists to prevent, and it was only caught because a reviewer checked the _present_ case, not just the (byte-identical, well-tested) _absent_ one. `armholeLenCm` still sums front + back (#139), so the sleeve cap resizes to a changed back automatically; no new seam-conflict path was introduced.

  **Seeding is a no-op for four of the six fields, and deliberately not for the other two.** The two seeded system charts (`lib/sizeCharts/seed.ts`'s `extendedMeasurementsFor`) populate `neckGirth`/`highBust`/`shoulderSlope`/`bicep` with the exact value that reproduces the fallback formula above — `neckGirth = bust*3/7` (so `neckGirth/6 == bust/14`), `highBust = bust` (the legacy tables never modelled a cup difference, so "no assumption" is the honest default), `shoulderSlope` = the same per-gender constant, `bicep = bust*0.3` (the existing `BICEP_PROPORTION_OF_BUST`) — so populating a brand-new account's system chart with these four changes **nothing** about what it drafts. `backWidth` is seeded as `bust*0.4` (~36.8cm at bust=92) instead: a real across-back proportion, not a value chosen to cancel out algebraically. It is a field where populating the system chart is an intentional geometry change — a pattern drafted after this shipped has a genuinely different (more anatomically honest) back than one drafted before it, at the same bust. `rise` (#128) is the other non-no-op field, for a different reason: it's graded per size (`(male ? 27 : 26) + 0.5 * sizeIndex`, the same linear-step shape `skirtLength`/`hipHeight` already use) rather than reproducing `trousers.ts`'s own hip-derived fallback — there was nothing to reproduce until #128 shipped a drafter that reads it.

  **No migration, and none is needed.** A pattern snapshots its size chart once, at first generation (see Size charts below) — an existing pattern's frozen `sizeTable` predates all six EXTENDED keys entirely, so it keeps taking every fallback path forever and keeps drafting exactly as it always has. Only a pattern generated for the first time _after_ this shipped snapshots a chart that already has `backWidth` set, and picks up the real value. This falls straight out of the existing snapshot-once rule (same as a size chart's `name`/`bodyType` never retroactively touching an in-progress pattern) — don't "fix" the difference with a backfill; there's nothing broken to fix.

- `resolveMeasurements(base, overrides)` applies chat-driven `measurementOverrides` onto an already-resolved base row (clamped to `MEASUREMENT_RANGES`); the base row comes from the pattern's frozen `sizeTable` snapshot (see Size charts). No size/gender table lookup happens here anymore.
- `GarmentType` = `"blouse" | "dress" | "skirt" | "tshirt" | "trousers"`. A `GarmentSpec` (`type` + `gender` (`"female" | "male"`) + `measurementOverrides` + `style`) plus a resolved `Measurements` row flow into `draftGarment(spec, baseMeasurements, t)` (`lib/draft/garment.ts`), which calls the per-block drafters (`body.ts`, `sleeve.ts`, `skirt.ts`, `trousers.ts`, shared helpers in `core.ts`) to build each `Piece`'s outline/guide/grainline/dart in cm and lay them into one computed `viewBox` (`autoLayout`). The engine doesn't know `SizeLabel` — it's a plain per-chart `string` now, not the old fixed `"PP"|"P"|"M"|"G"|"GG"` union.
- `tshirt` is a knit archetype (round neck, no darts, short sleeves by default) drafted through the same `body`/`sleeve` drafters, with `knit: true` in `BlockOpts` and those style defaults pre-filled in `draftGarment`.
- Outlines: `outlinePath` (`core.ts`) takes a flat cm point list plus drafter-supplied `curvedSpans: [number, number][]` — only marked ranges (neckline, armhole, sleeve cap) get Catmull-Rom-derived Bézier curves with tangents locked at span edges; every other edge is a straight `L`. No global smoothing pass, no `curvedIds` — curvature is per-edge-range, opt-in per drafter.
- Each drafter attaches its own `piece.detailRows` (label/value pairs) — the old fixed `PieceDetails` shape is gone.
- **A decoration is placed from the piece's own boundary, never from its bounding box.** The bbox is a superset of the piece, so a constant offset measured from it lands _outside_ the outline wherever the piece is scooped (a neckline) or tapered (a sleeve hem) — and both shipped that way. The body grainline started at `y = 3` cm from the bbox top, which put it inside the neck opening for **every** front bodice (measured: 4.6 cm outside a round neck, 6.9 cm on a male t-shirt, 17.6 cm on a max-depth V); since the grainline reaches all five export formats, that was a data defect, not a screen one. It now starts at `neckDrop + 3` — 3 cm below the piece's own neckline. The canvas label was the other half: `place()` anchors it at `bbox-left + 6` and `PatternCanvas` drew it `text-anchor: start` at a fixed 11 px, but "MANGA · 2×" is wider than a size-M sleeve's bicep (68–75 px of text against 64 px of piece), so it spilled past the outline. Placement that depends on the _rendered text's_ width can't live in the drafter, so `lib/canvas/pieceLabel.ts`'s `fitPieceLabel` recomputes it at render time from `piece.vertices` — a scanline for the piece's real horizontal span at the label's baseline, then the largest size up to `MAX_LABEL_FONT_SIZE` that fits — which also repairs patterns drafted before the fix. A piece with no `vertices` (blobs predating the measure tool's snap) keeps the stored anchor, so `piece.label` survives as the legacy fallback only; it is also why nobody noticed that it ignores `bbox.minX`/`minY` and is correct purely because every drafter happens to normalize its outline to 0,0. `estimateTextWidth`'s 0.7em advance is deliberately wider than Archivo's real uppercase average, so a mis-estimate shrinks the label instead of overflowing the piece — `getComputedTextLength()` would be exact but needs a render pass, and jsdom doesn't implement it, which would put the rule beyond a test's reach. The invariant is guarded generically, not per-case: `garment.test.ts`'s containment suite asserts every grainline and dart point of every piece lies inside its own outline across seven garment/style combinations. (Note the design prototype puts each label _below_ its piece rather than inside it; contained-inside is what the bug report asked for and what shipped.)
- **#124: notches are typed (`single`/`double`/`triple`), drafter-derived, and never persisted or user-movable** — `DraftedPiece.notches` (`core.ts`'s `NotchCm`: `type` + `outerCm` on the net outline + `innerCm` nudged inward), following the same derive-don't-store precedent as `measureSeams`/`fitPieceLabel`/`foldEdge`. The three types are told apart purely by how far the tick reaches — `NOTCH_DEPTH_CM` (0.3/0.6/0.9 cm) — which is simultaneously the AC's own "printable size" (3 mm/6 mm), not a second number to keep in sync. `core.ts` exports the geometry primitives every drafter calls: `notchAt(point, tangent, insideRef, type)` orients the tick's inward normal by biasing toward `insideRef` — a point the caller knows lies inside the piece — so it points into the fabric regardless of which winding direction that outline happens to walk (drafters mix clockwise/counter-clockwise, the same problem `lib/export/offset.ts` self-calibrates for on a whole outline); `notchAtVertex` derives the tangent from a vertex's own neighbours (exact at a straight-edge midpoint like a `foldEdge` endpoint, a good approximation at a smooth symmetric peak like the sleeve cap apex); `pointAndTangentAtCm`/`notchAtArcLengthCm` walk `distCm` from one vertex toward another along the same Catmull-Rom/Bézier geometry `curveArcLengthCm` measures, clamped to the segment's own length. `place()` (`core.ts`) translates `outerCm`/`innerCm` into a `Piece.notches` entry (`PieceNotch`, px, the same two-point-line shape as `grainline`).
- **Mated notches share one computed distance, not two independent guesses.** `body.ts`'s `bodice()` computes `pitchNotchCm`/`basePitchNotchCm` (`min(8, armholeEdgeLenCm * 0.7)`, off the actual and the un-deepened armhole respectively) and returns both from `draftBody`; `garment.ts`'s `draftAll` picks whichever matches the armhole the sleeve's cap was ACTUALLY drafted against (refit or not — the same actual/base choice it already makes for `sleeveArmhole`) and hands that single number into `draftSleeve`'s new `pitchNotchCm` parameter. Both pieces then place their pitch notch by walking that identical value from their own underarm vertex, so a front's single notch and the sleeve's own single-side notch land at truly matching positions "generated as pairs from the same computation" by construction, not by coincidence — verified in `garment.test.ts` across the full `DECORATION_CASES` matrix (chord-distance-from-underarm matches within 0.2 cm) plus the seam-conflict case (deliberately diverges when unrefit, exactly mirroring the seam's own divergence). Single marks the front, double the back — standard pattern-making convention — and the sleeve's single/double pair sits on opposite cap sides (bilaterally symmetric, so either physical arm can be cut from the same flat piece by flipping fabric); the cap's third notch (the apex, marking where the shoulder seam meets the cap) is deliberately excluded from that cross-check, since it has no single body-side counterpart to pair with (the shoulder point is a plain corner vertex on both the front AND back panels, not itself notched).
- **Every other notch is placed by direct convention, not by cross-piece coordination.** A hem-fold notch (single) sits at every piece's own `foldEdge` hem-end vertex (body panels and every skirt silhouette). A dress bodice's hem/waist-join edge additionally gets: double notches at its two outer corners (`hemL`/`hemR`) mirrored by the skirt panel's own waist-edge corners when `draftSkirt`'s new `isDressWaist` parameter is true (`garment.ts` passes `spec.type === "dress"`) — both sewn edges are the identical length by construction (`dressWaistHalfCm`, #79/#177 — straight/a-line always was; a circle/gore/half-circle skirt only became true once #177 moved the bodice hem off the hip and, for half-circle specifically, split the panel's one waist arc between the two bodice halves — see Seam-conflict detection above), so the corners are a real join, not an approximation; and single notches at each dart's leg-seam intersections, only for the dress-hem (single-ended) dart, since the fisheye (double-ended) dart on a non-dress piece is fully internal and touches no edge to notch.
- **#127: `Piece`/`DraftedPiece` carry a typed `internals` channel — darts (now zero or more per piece, not "at most one"; that premise was already false before this issue, since #122 had made `darts` an array), each dart's own fold line, and its drill hole(s).** `lib/draft/core.ts`'s `InternalCm` union (`dart`/`foldLine`/`drillHole` ship geometry; `pleat`/`styleLine`/`placementMark` are reserved — no drafter emits any of the three yet) is the cm-space shape a drafter attaches to `DraftedPiece.internalsCm`; `place()` translates it into `Piece.internals` (`PieceInternal`, px, path strings for path-shaped kinds like `notches`/`grainline` already do). `core.ts`'s `dartInternals(ptsCm, fold, apexesCm)` is the one place a dart's own three marks are derived together: the fold line is the dart's own press line (apex-to-apex for a double-ended/fisheye dart, apex-to-seam-midpoint for a single-ended one) — a different concept from the piece's own cut-on-fold axis (`foldEdge`/`fold`, unchanged by this issue) — and each free apex (not a seam end) gets a drill hole `DRILL_HOLE_SETBACK_CM` (1.25 cm, within the 1.0–1.5 cm convention) short of the point, clamped to 90% of the fold segment's own length. `body.ts`'s `bodice()` is the one drafter that builds darts; it now returns `internalsCm` instead of the old `dartsCm`. **Migration:** the legacy `Piece.darts?: { d: string }[]` field (#122's array, not a single dart) is superseded but kept readable — no new draft ever writes it, and `lib/types.ts`'s `resolvePieceInternals(piece)` maps an old blob's `darts` into the same `PieceInternal[]` shape at render time, the `savedAgo` precedent (no reset migration). `PatternCanvas` renders every internal kind distinctly (dart: solid path; foldLine: dashed line; drillHole: small open circle) via that same resolver. Export's `ExportPiece` keeps its own existing `darts` field (always freshly rebuilt by `buildExportModel`, never persisted, so it has no legacy shape to reconcile) and adds two siblings, `internalFoldLines`/`drillHoles`, built from the same `internalsCm`. `toDxf` writes a dart's fold line as a `LINE` and a drill hole as both a `POINT` and a `CIRCLE`, all on the existing `INTERNO` layer; `toDxfAama` writes the fold line as a `LINE` on layer 8 (joining the dart it belongs to) and the drill hole as a `CIRCLE` on layer 13 — D6673's own reserved drill-hole layer, closing that half of issue #2 (see `toDxfAama` below). `toSvg`/`toPdf` draw the fold line as a fine dotted line in the dart's own color and the drill hole as a small open ink circle; `toPlt` shares the dart's own pen for the fold line and adds a dedicated `PLT_PENS.drillHole` pen, emitting the hole via HPGL/2's native `CI` (circle) command.
- **#129/#130/#131 (Wave 2/W4): three small sub-piece drafters — collar, cuff+placket, waistband — live in `lib/draft/subpieces.ts`, each sized from a MEASURED edge on an already-drafted piece, never a proportion of the bust/waist.** `GarmentStyle` gained three closed enums (`lib/types.ts`): `collar?: "none" | "convertible"`, `cuff?: "none" | "straight"`, `waistband?: "none" | "straight"` — `validateSpec` clamps each the same way `neckline`/`sleeve`/`skirt` already do, and `lib/ai/schema.ts`/`prompt.ts` render the same exported `COLLARS`/`CUFFS`/`WAISTBANDS` constants (`lib/draft/garment.ts`) rather than a hardcoded duplicate. Because there is no third value for an unsupported shape (mandarin collar, shaped cuff, contoured waistband) to fall into, the AI's only path for one is `decline`/`ask` — never a silent substitution — and `prompt.ts`'s own catalog lines spell that out; on-screen, the drafted piece's own detail row says the rest are "em breve" (there is no dedicated style-picker UI these fields could otherwise disable+badge in, since `GarmentStyle` is chat-driven, not form-driven).
  - **Collar** (`draftCollar`): `body.ts`'s `bodice()` exposes two more `seamEdges` per panel, `necklineLeft`/`necklineRight` (the same `[cf, hpsL]`/`[hpsR, wrap-to-cf]` index pair its own neckline `curvedSpans` already use). `draftAll` sums all four (front+back, both halves) via `curveArcLengthCm` into the real drafted neckline circumference and drafts the collar's own straight neckline-seam edge to exactly that length — applies to any body-having garment (blouse/dress/tshirt) with `style.collar === "convertible"`, qty 1 (cut on fold at center back).
  - **Cuff + placket** (`draftCuff`/`draftPlacket`): `sleeve.ts` exposes `seamEdges.hem` (the straight edge between its two hem vertices); `draftAll` measures it and adds `WRIST_EASE_CM` (a flat knit/woven table, `sleeve.ts` — the issue's own "not a proportion" instruction, since the hem is bicep-derived and far wider than an actual wrist) to size the cuff's own seam. Only reachable with `style.sleeve === "long"` — a short/sleeveless spec simply never drafts the cuff branch, the same "type-mismatched style field is unused" precedent skirt-only fields already follow on a bodice. The placket is fixed-dimension (not measured — only the cuff's own AC requires that), qty 2 each (one per sleeve).
  - **Waistband** (`draftWaistband`): reuses `skirt.ts`'s existing `seamEdges.waist`, summed across the panel's own `qty` (the closed waist loop is `qty` copies of one drafted panel's waist arc, not one panel's share of it) plus a fixed `WAISTBAND_OVERLAP_CM` closure allowance. Applies to the standalone skirt archetype (`spec.type === "skirt"`) and, since #128, to trousers too (summed across both the front AND back panel's own measured waist edges — see the trousers bullet below) — a dress's skirt panel joins the bodice directly at the natural waist instead (the pre-existing `waist-join-front`/`-back` pairs, and #177's own tracked gap there); waistband and waist-join never both apply to the same garment. **Defaults ON** (`style.waistband ?? "straight"`), unlike collar/cuff's default-off: a skirt or trousers with no waistband is the exact defect #131 exists to fix, so both draft one unless a request explicitly sets `"none"`. The button/zip closure position is a placement mark the issue's own decision deferred ("needs the internal-geometry channel... emit the band without the mark and say so") — #127 later added exactly that channel (`InternalCm`'s reserved `placementMark` kind), but that decision was settled and is deliberately not reopened here; the waistband's own detail row still says the mark is missing.
  - **Seam graph:** each new piece declares its own `seamEdges` and is paired into `lib/draft/garment.ts`'s `seamPairs` the same way every other mated pair is (`collar-neckline`, `cuff-hem`, `waistband-waist`) — a collar/cuff/waistband that stopped matching its own seam would be exactly as detectable as an armhole/cap mismatch. All three are `fixable: false` (there is no automatic resolution for any of them, the same "equal by construction" regression-guard shape as `shoulder`/`side`/`sleeve-underarm`) and measure at (or within floating-point noise of) zero `diffCm` by construction, verified within the AC's own 0.3 cm bound in `garment.test.ts`'s "seam graph (#134)" suite — tighter than `seamCheck`'s general 1 cm `SEAM_TOLERANCE_CM`.
  - **Export:** no export-format code changed — every format already draws whatever `ExportModel`/`Piece` it's handed, so the four new pieces flow into every DXF/PDF/SVG/PLT format and `CutPlanTab`'s nesting automatically, the same way #8/#135/#136 already made that true for any new piece. `model.test.ts`'s "cut-line area growth is within 5% of perimeter x allowance" invariant (#123) needed a small fixed floor added to its tolerance (`6 * allowance²`) once these small, mostly-rectangular band pieces existed: a mitred uniform offset legitimately grows a shape's area by `perimeter × allowance` **plus** a real per-corner correction (exactly `allowance²` per 90° corner for a plain rectangle) that a flat 5% relative bound has no room for once a piece's perimeter is short enough for that correction to matter — a large, curve-heavy body panel never noticed it; a ~5 cm-tall band does. This is the offset math behaving correctly, not a defect the fix is papering over.
- **#128 (Wave 2/W5): a fifth archetype, `trousers` — a straight-leg block only (the issue's own scope decision; tapered/wide/flared/cargo are follow-ups), front + back panels plus a waistband, all in `lib/draft/trousers.ts`.** Unlike a bodice/skirt panel, a trouser leg's front and back are each a genuinely asymmetric single-leg shape (the inseam and outseam are different edges, not mirror halves of one centre line) — so neither declares a `foldEdge`; both are cut `qty: 2` (one leg mirrors the other by flipping the fabric, not by folding it). Front and back deliberately share the same rise depth, total length and hip quarter-width (an equal front/back split, the same simplification `skirt.ts`'s own `hip/4` panel already makes) — only the crotch curve's own extension differs (the back's own seat curve reaches further out than the front's), which is what keeps the inseam and outseam an _identical_ length front vs back by construction (both are plumb verticals sharing the same dy, independent of the crotch extension that tells them apart). Each panel gets one waist dart, the same single-ended (apex-to-seam-midpoint) shape `body.ts`'s own dress-hem dart already uses. **Total length has no per-size measurement to fall back to** — #132 added only `rise` (crotch depth), not a leg-length field — so `style.trouserLengthCm` (AI/user-settable, `STYLE_LIMITS`-clamped like `skirtLengthCm`) defaults to a flat per-gender constant (`TROUSER_DEFAULT_LENGTH_CM`, same at every graded size until a future measurement-vocabulary issue adds a real one), the same "not graded across sizes" shape `shoulderSlope`'s own flat per-gender constant already uses for a different field. **`rise` is read when the chart has it, falling back to `hip/4 + 4`** (a documented crotch-depth proportion) when it doesn't — both seeded system charts already carry a real, per-size-graded `rise` (see the measurement-vocabulary section above), so the fallback is a robustness path, not the common case.
  - **Seam graph:** five pairs, all `fixable: false`. `trouser-front-rise`/`trouser-back-rise` are **self-pairs** — each panel's own centre-front/back edge (the fly seam, the back rise seam) sewn to the mirrored copy of itself, the same self-pair shape `sleeve.ts`'s own two underarm edges already use for its own left/right mirror seam — trivially exact (comparing a curve to itself). `trouser-inseam`/`trouser-outseam` pair front vs back, exact by construction (see above). `trouser-waistband-waist` reuses `draftWaistband` **verbatim, not forked** (`lib/draft/subpieces.ts`, #131's own "reused by the trousers block" acceptance criterion) — summed across both panels' own measured waist edges (each times its own `qty`), the same "closed circumference, not one panel's share of it" rule the skirt's own waistband pairing already follows; verified within 0.3 cm in `garment.test.ts`'s "seam graph (#134)" suite, the same bound #129/#130/#131's own pairs are held to.
  - **Prova 3D (`/pattern/[id]`'s 3D fitting preview) does not cover trousers.** `lib/proof3d/mesh.ts`'s `buildProofMesh` only recognizes the body/sleeve/skirt piece ids — a trousers pattern's pieces (`trouser-front`/`trouser-back`) match none of them, so without this fix it would silently return a bare mannequin with zero garment shells instead of failing or saying so. `Proof3DTab` now treats `spec.type === "trousers"` as an explicit, named gap (`notSupportedForTrousers`, its own catalog string, distinct from the ordinary "generate a pattern first" empty state) rather than rendering an unlabeled/empty preview indistinguishable from a bug — the same "surface the limitation where the user meets it" rule this tab's own beta badge already follows. Extending the mesh builder to trousers is out of scope here.
  - **`components/dashboard/PatternGrid.tsx` had its own hardcoded `GARMENT_TYPES` array**, independent of `lib/draft/garment.ts`'s `TYPES` — the exact "duplicated fact" mistake this file's own convention section warns about (`Wallet.planLabel`, `FREE_PLAN_CREDITS`, `FORMAT_KEYS`, `PLAN_IDS`). Left alone, the dashboard's garment-type filter would have simply never offered "Calça" for a real, drafted archetype. Now imports `TYPES` directly.
- **#137: the drafted-ease report — `lib/draft/easeReport.ts`'s `buildEaseReport(pattern, t)` — is the second geometric fit answer in the app, alongside `seamCheck`'s armhole/cap comparison.** It states how much ease the FINISHED garment actually has at bust/waist/hip, deliberately distinct from `wearingEaseCm` (the ease the drafter was merely _asked_ for): a style adjustment, a dart, or a silhouette can make the two diverge. Pure, DB-free, redrafts via the same `draftPiecesCm`/`measureSeamGraph` (#134) `buildExportModel` already uses — no new blob key, so it works unchanged on a pattern drafted before this issue. Per girth: a scanline (`polygonSpanAt`, the `lib/canvas/pieceLabel.ts`'s `horizontalSpanAt` precedent — curved spans read as their chord) reads the piece's real width at a height derived from public data only (a `seamEdges` vertex, or a raw `Measurements` field like `backLength`/`hipHeight` — never an internal per-drafter formula), then subtracts whatever any `internalsCm` dart removes at that same height (its own leg polygon, scanned identically, gives exactly the fabric its fold takes up — full width at the seam end, tapering to zero at the apex). That single mechanism handles every drafter's dart shape generically (`body.ts`'s fisheye AND dress-hem darts, `trousers.ts`'s waist dart) without this module knowing any of their suppression formulas. **Bust:** front+back at the armhole's own underarm height, only for a bodice (blouse/dress/tshirt) — a skirt or trousers has none. **Waist:** front+back at `backLength` for a bodice (coincides with the hem for a dress, #79); the trousers panels' own top edge WITH dart subtraction (the true, sewn waist); a standalone skirt's real `seamEdges.waist` arc length (silhouette-agnostic, no dart to subtract, the same edge the waistband sizing already measures). **Hip:** a skirt panel (standalone or a dress's) at `hipHeight` below its own waist — but ONLY for the straight/a-line silhouette; a circle/gore/half-circle panel is drafted from polar coordinates, where a horizontal scanline reads a meaningless width, so hip is reported `unavailable` (`unsupportedSilhouette`) rather than a wrong number. A skirt-less bodice reads hip at `backLength + hipHeight`, still inside the same panel. Trousers read the panel's own top edge again, this time WITHOUT dart subtraction (`includeDarts: false`) — a waist dart shapes the waist, it doesn't remove hip fabric, and the block happens to draft both at the identical height, so subtracting there would collapse hip into waist. A girth with no matching panel is `unavailable` (`noPanel`) — trousers' missing bust is the issue's own named example, generalised to any bust-less garment. **Cap ease** ("cap arc minus full armhole arc") is read straight off the existing seam graph's own `"armhole-cap"` entry (`aLenCm`/`bLenCm`), not a bespoke number. **Fit class** comes from `lib/draft/ease.ts`'s new `classifyGirthFit(girth, easeCm)` — band boundaries are the MIDPOINTS between consecutive `FIT_CLASSES`' own `FIT_EASE_CM` figures (never a second, competing scale), so a measured ease and `wearingEaseCm`'s requested one are judged on the one table `lib/ai/prompt.ts` already renders `FIT_CLASSES` from. Negative ease (a knit) classifies as `close`, not an error. `TechSheetTab` renders the report as its own card (bust/waist/hip rows: finished cm, body cm, diff cm/%, fit class — reusing the existing `PatternData.fit.*` catalog lookup — plus cap-ease chips), replacing the old single bust-only `chipEase` chip that showed _requested_ ease under the same word "folga" a measured number now owns unambiguously; an `unavailable` girth renders as a stated reason, never a silent gap. `lib/ai/prompt.ts`'s `buildSystem` also embeds the report as JSON (a no-op identity `Translate`, since the whole prompt is deliberately English/i18n-free) so an `explain` answer about fit can cite the real numbers instead of guessing from the spec alone.

### Export (client-side transform, no server call)

- `lib/export/` turns the drafted pattern into a downloadable file with no API route, credit cost, or state mutation. `buildExportModel(pattern, t)` (`lib/export/model.ts`) re-drafts the pieces in exact cm via `draftPiecesCm(spec, baseMeasurements, t)` (exposed from `lib/draft/garment.ts`) — it never reverses the store's px back to cm, so it doesn't inherit `PX()` rounding. The `ExportModel` is format-agnostic: per-piece outlines as typed cm segments (`line`/`cubic`, Béziers preserved) plus grainline/dart/notches/name/qty and a `seamAllowanceCm` annotation. **#123: every piece now carries two outlines — `outline` (the net sewing line, unchanged) and `cutOutline` (the real cut boundary, `outline` offset outward by `seamAllowanceCm`).** Before this shipped, `seamAllowanceCm` was purely a `detailRow`/chip annotation nothing exported ever turned into geometry — the exact gap the DXF's old "net line" comment and `TechSheetTab`'s "Folga de costura" chip were already honestly flagging. **#124: `ExportPiece.notches` (`ExportNotch[]`, each an `outer`/`inner` point pair) mirrors `DraftedPiece.notches` one-for-one** through the same local (net-outline-bbox-shifted) frame as grainline/dart/fold — a plain per-format tick draw, no new offsetting math, since a notch's `innerCm` is already computed at draft time.
- **`offsetOutlineCm` (`lib/export/offset.ts`) computes `cutOutline`.** It flattens every curved span to a dense polyline first (the same Catmull-Rom tangents `outlinePath`/`outlineSegments` already derive, reused via the shared leaf module `lib/export/bezier.ts`'s `flattenCubic` — extracted out of `dxf.ts` so this module doesn't have to import `model.ts`'s `ExportModel`-typed surface), then translates every fine segment outward by its own distance and rebuilds each vertex as the intersection of its two adjacent offset lines. That single rule _is_ issue #123's two named corner treatments at once: a convex corner's offset lines diverge past the original vertex (mitre); a concave one's cross before reaching it, discarding the resulting sliver (trim) — no per-corner branching needed. Outward direction is self-calibrated, not assumed from a fixed winding (drafters walk some pieces clockwise, others counter-clockwise): it builds the real candidate offset polygon for both signs and keeps whichever encloses the larger area. A `removeSelfCrossingLoops` post-pass repairs the one real limitation of per-vertex miter offsetting — a sharp reflex feature (a deep V-neck's apex, reached at `STYLE_LIMITS.necklineDepthCm.max`) can leave a small self-crossing loop further along the boundary; it splices at the first non-adjacent crossing and keeps whichever resulting sub-path is larger, repeating until none remain. Verified against the real drafting matrix, not just hand-built shapes: `lib/draft/fixtures.ts`'s `DECORATION_CASES` (extracted out of `garment.test.ts`'s own containment suite so both share one source of truth) feeds `model.test.ts`'s "cut line (#123)" suite, asserting every case's cut line never self-intersects and its area growth over the net line matches `perimeter × allowance` within 5%.
- **`foldEdge` turned out to be a chord, not a boundary edge — #123's own "0cm across the fold" text assumed the latter.** `DraftedPiece.foldEdge` (`lib/draft/body.ts`/`lib/draft/skirt.ts`, #126) names two indices into an already-whole, mirrored outline — a top-centre and a bottom-centre vertex diametrically opposite each other — because every current drafter joins both mirrored halves into one closed outline before `foldEdge` is even attached; there is no literal boundary edge to zero out. Measured: `offsetOutlineCm`'s adjacent-edge check (`foldEdge[1] === foldEdge[0] + 1`) is inert for every piece any drafter currently produces, and it doesn't need to fire to keep the fold intact — at a true axis-of-symmetry vertex the curve's own tangent is forced perpendicular to the fold by the mirror symmetry itself, so its outward normal already points _along_ the fold, and a uniform offset keeps the point on the fold line with no special-casing (`model.test.ts`'s axis-of-symmetry case, checked against a real drafted body piece). The check stays wired for a future drafter that genuinely emits a half-piece with the fold as one real edge.
- **A mitred convex corner can grow past a plain edge offset, and the sheet-packer has to reserve for that or two pieces' cut lines touch.** `buildExportModel`'s shelf-packing pre-dates #123 and only ever reserved each piece's _net_ bbox (`widthCm`/`heightCm`) plus a fixed 8 cm gap; the solid cut line is now the thing actually printed/plotted, and its bbox can legitimately exceed the net one by more than the seam allowance on a sharp corner (mitre growth is `d / sin(θ/2)` for interior angle θ — unbounded as the corner sharpens). Measured against the real drafting matrix at the maximum allowance (`STYLE_LIMITS.seamAllowanceCm.max`, 4 cm): several real pieces grow up to ~4.9 cm on a side, so two adjacent pieces' _combined_ growth can exceed the old fixed 8 cm gap outright — a real, exploitable overlap, not a theoretical one. `buildExportModel` now computes each piece's `growLeft`/`growTop`/`growRight`/`growBottom` (how far the cut line's own bbox reaches past the net one on each side) and packs by the resulting effective footprint, offsetting `originCm` by `(growLeft, growTop)` so the cut line's own bbox — not the net one — lands on the shelf cursor; the actual gap between two neighbours' cut lines is exactly the fixed gap again, however unevenly each one grew (`model.test.ts`'s "cut lines never overlap between pieces on the sheet, even at the maximum seam allowance" case, run across the full matrix). `planCutLayout` (`lib/export/cutplan.ts`) had the same exposure with an even tighter 3 cm gap — fixed differently there, by re-zeroing each `CutInstance`'s outline to the cut line's own bbox up front (`outlineBBox`/`shiftOutline`) rather than carrying growLeft/Top through the packer, since a fresh `CutInstance` has no net outline to keep a shared frame with.
- `exportPattern(pattern, format, t, onError?, size?, opts?)` (`lib/export/index.ts`) builds the model, serializes, and triggers a browser download via `downloadFile` (`lib/export/download.ts`, the only DOM touchpoint), dispatching all seven formats (`svg`/`dxf`/`dxf-aama`/`pdf-a4`/`pdf-single`/`pdf-layered`/`plt`) via an exhaustive `switch`/`never`. The `Footer`'s "Exportar" menu is disabled when a conflict is active, the pattern is blank, or there is no `spec`. **`opts: ExportRenderOptions` (`#135`/`#136`) is the one addition beyond the pre-existing `size` param** — `{pageSize?, rollWidthCm?}`, optional and additive, so every pre-`#135`/`#136` call site is unaffected. `pdf-layered` is handled before the single-model `buildExportModel` call, since it redrafts one model per size rather than one model total (see below); its own filename is `<slug>-graduado.pdf` rather than the `<slug>-<size>` pattern every other format uses, since it isn't scoped to one size.
- **#135: `toPlt` (`lib/export/plt.ts`) emits standard HPGL/2** — one dialect, written to the spec and verified two ways, neither of them a real device. **(a) Structurally**, by `plt.test.ts`: valid HPGL syntax, coordinates round-trip to the input cm within 0.02cm, strip count matches the roll-splitting math, distinguishable pens present. **(b) Differentially**, by `plt.differential.test.ts`: the emitted file is parsed back by `plt-test-reader.ts` — an HPGL reader written from the format's own semantics that **imports nothing from `plt.ts`** — and the geometry a plotter would actually draw is compared against the `ExportModel` the serializer was handed, across the whole `DECORATION_CASES` matrix.
  - **(b) exists because (a) structurally cannot fail on a misconception the serializer and its own assertions share** — `plt.test.ts` asserts on substrings of the very output it is checking. Measured, by reverting each behaviour in turn: `plt.test.ts` passes **8/8** with the `LB` label's ETX terminator deleted (on a real plotter the first label then swallows every following command, so the rest of the plot is printed as text rather than drawn) and **8/8** with drill holes emitted at double their radius. The differential suite fails both, matrix-wide. It also catches a wrong units-per-cm constant and a dropped Y flip, which `plt.test.ts` already caught on its own. **No production defect was found when this landed:** `plt.ts` was byte-identical before and after — both blind spots were in the test suite, not the serializer.
  - **`plt-test-reader.ts` is test-only** (the `components/test-utils.tsx` precedent): nothing under `app/`/`components/` imports it, so it never reaches a bundle, and it is **not** the seed of a PLT import feature — `/import` (#11) is where a user-facing importer would live. Its entire value is that it was derived from HPGL rather than from the writer, so extending it by reading `plt.ts` would quietly restore the circularity it exists to break.
  - **It remains never plotted on a physical device**, since no plotter or vendor software was available in this environment — that gap, not the modelling, is what the "beta" badge names, and an independent parser agreeing is not a device agreeing. Physical verification is deferred to the maintainer and to users; a real plot that contradicts this is a new issue with an artifact attached, not a reopening of #135. The export menu badges the format **"beta"** (the same marker `formatDxfAama` uses for its own known gap — PLT's is the larger uncertainty of the two, since nothing has ever confirmed the file drives a real plotter) and states both the untested-hardware caveat and that piece-name (`LB`) text renders in whatever font the physical plotter has loaded, not a specific typeface. Plotter units are `1016/2.54` per cm (exactly 400, i.e. 0.025 mm/unit); coordinates are `IN`-initialized, then per-piece `SP<pen>;`/`PU x,y;`/`PD x,y;` polylines, reusing `flattenOutlineCm`/`TOL_CM` from `dxf.ts` exactly like every other flattened format. **Distinguishable pens** (`PLT_PENS`: `cut`/`net`/`grainline`/`fold`/`dart`/`notch`/`text`, plus `drillHole` (#127), emitted via HPGL/2's native `CI` circle command) mirror the DXF layer split one-for-one. Roll-width splitting reuses the shared `lib/export/strips.ts` (`planRollStrips`/`stripIntersectsBBox`) — each strip is a separate `PG;` (page/plot advance) section in the same file, with only the pieces whose absolute cut-line bbox actually reaches that strip's window emitted into it (an `outlineAbsBBoxCm` helper local to `plt.ts`, deliberately not the PDF module's `pieceBBoxesCm` — PLT has no text-label bbox-growth problem, since `LB` isn't clipped by anything).
- **#136: page sizes and the roll/layered PDF modes are documented alongside `toPdf` above**, not duplicated here.
- `toSvg` (`svg.ts`) — 1:1 SVG in mm (`MM = 10`, so a 10 cm edge is 100 units; `width`/`height` in `mm`). **#123: the cut line renders as the primary solid boundary, the net line as a secondary dashed path** (its own gray, `3 2` dash — distinct from the grainline's `6 4` and the fold's `8 2 2 2`). **#124: each notch draws as a short solid `#000` tick, outer→inner** — the same ink as the cut line (a notch is a cut mark, not an internal construction line), with single/double/triple told apart purely by the tick's length.
- `toDxf` (`dxf.ts`) — the **generic geometry-only DXF**: `$INSUNITS=4` mm, 1:1, Y flipped to DXF's up-axis; hand-written ASCII `LWPOLYLINE`/`LINE`/`TEXT` on named layers `CONTORNO`/`COSTURA`/`INTERNO`/`GRAINLINE`/`TEXTO`/`DOBRA`/`PIQUE` (**#124**); cubics flattened by adaptive De Casteljau (`flattenCubic`, 0.2 mm tolerance). **#123: `CONTORNO` is now the cut line (`cutOutline`), `COSTURA` the net stitch line** — each its own `LWPOLYLINE` per piece; **#124: one `LINE` per notch on its own `PIQUE` layer**, geometry-only like `GRAINLINE`/`DOBRA`.
- `toDxfAama` (`dxf-aama.ts`) — a **"compatível AAMA/ASTM D6673" subset**: numbered layers with fixed semantics (`1` piece boundary + piece system text, `4` notches (**#124**), `6` fold/mirror line, `7` grainline, `8` internal/dart lines, `14` sew line), each piece wrapped in a `BLOCK`/`INSERT`, header R13 (`AC1012`), classic `POLYLINE`/`VERTEX`/`SEQEND` (not R14's `LWPOLYLINE`) for wider Audaces/Gerber compatibility; reuses `flattenOutlineCm`/`TOL_CM` from `toDxf`. **#123: layer 1 now carries the cut line (`cutOutline`) — a real boundary a cutter follows, matching D6673's own semantics for that layer — and the net line moved to layer 14**, closing half of issue #2's tracked gap. **#124: layer 4 (D6673's own reserved notch layer) now carries one `LINE` per notch**, dropping the "beta" note's notch caveat. **#127: layer 13 (D6673's own reserved drill-hole layer) now carries one `CIRCLE` per dart's free apex** — 1.0–1.5 cm short of the point, see the drafting-engine note above — closing the other half of issue #2's tracked gap; a dart's own fold line joins it on layer 8, alongside the dart itself. The menu item stays tagged "beta" — not for a modelling gap any more, but because none of this has ever been opened in a real CAD importer (Audaces/Gerber), only verified by parsing the emitted file back apart in this repo.
- `toPdf` (`pdf.ts`) — a 1:1 PDF in three `PdfMode`s: `"a4"` (tiled, page numbering, a 10 cm calibration ruler on the first sheet), `"single"` (one page the exact size of the pattern sheet, for plotter/large-format), and **`"roll"`** (**#135/#136**, below). It reuses `flattenOutlineCm` and loads `pdf-lib` (the feature's only added runtime dependency) via a dynamic `import()` inside `toPdf`, code-splitting it out of the main bundle — `toPdf` is `async` and the facade's pdf cases are fire-and-forget. **#123: the cut line draws solid in `INK`** — what the a4 tiling/glue-overlap rectangle is now sized against, per the sheet-packing fix above — **and the net line dashed in its own gray (`0.4`), kept distinct from the fold's own `GRAY` (`0.6`)** so the two never collide in the same content stream. **#124: each notch draws as a solid `INK` segment**, printing at its true physical depth (3 mm single/6 mm double/9 mm triple) since the PDF is 1:1 — the AC's "printable size" and the drafted cm depth are the same number by construction, nothing to keep in sync.
- **#136: `"a4"` mode's page format is now a parameter, `PdfPageSize` (`"a4" | "a0" | "letter"`, `PDF_PAGE_SIZES`), not the hardcoded A4 constant** — `planTiles`'s optional `opts.pageSize` defaults to `"a4"`, so every pre-existing call/test is unaffected; A0 (the copyshop plotter format, 84.1 × 118.9 cm, a widened 1.5 cm margin) and Letter (US paper, A4's own margin) are the two new presets. `"single"` mode's own margin stays exactly what it always was (`SINGLE_MARGIN_CM`, unaffected by `pageSize`), since a single sheet is sized to the pattern, not to a named format.
- **#135/#136: `"roll"` mode is the copyshop/plotter split — a single row of numbered strips, each up to a chosen `rollWidthCm` wide and the sheet's full height** (no vertical tiling; roll length is unconstrained), overlapping by `STRIP_OVERLAP_CM` so neighbouring strips can be taped/aligned in register. Its splitting math lives in the shared leaf module `lib/export/strips.ts`'s `planRollStrips`/`stripIntersectsBBox`, reused by both `toPdf`'s `"roll"` mode and the PLT writer below, so the two report the same strip count for the same roll width. `exportPattern`'s `pdf-single` format dispatches into `"roll"` instead of `"single"` whenever an `ExportRenderOptions.rollWidthCm` is supplied — the format itself doesn't change, only the mode `toPdf` runs in. Strip pages reuse `#120`'s blank-tile filter and the existing calibration-ruler-on-page-1 convention, with their own `pdf.stripLabel` catalog key (row/col phrasing doesn't apply to a mode with no vertical tiling) — drawn only once a sheet genuinely needed splitting (`pages.length > 1`), so a roll-width choice that turns out not to matter leaves a plain, unmarked single-strip export exactly like `"single"` mode always has.
- **#136: `toPdfLayered` (`pdf.ts`) is a fourth, single-page PDF mode — one real Optional Content Group (OCG) per size, layered on the same sheet, plus an always-visible legend and the same calibration ruler.** Reachable as its own `ExportFormat`, `"pdf-layered"` — deliberately not folded into `"a4"`/`"single"`/`"roll"`, since a layered comparison is inherently a single "everything overlaid" artifact, the same way a real cutting room's graded-nest reference sheet works, not a variant of tiling/splitting. `exportPattern` redrafts one `ExportModel` per size in `pattern.baseSize` ∪ `pattern.sizesApplied` (the account's real graded run — `#59`'s per-size `buildExportModel`, not a guess), never fewer than one layer. Each size's cut line/grainline/notches draw in their own color from a small `LAYER_PALETTE` (cycling past 5 sizes) as the "distinct line style per size" the issue asks for — **the net sewing line and fold are deliberately not drawn at all** (overlaying N monochrome sets per size would be illegible; color-coding sizes is the tradeoff instead), and `Footer.formatPdfLayeredNote` states that gap on the export menu itself, not only here, per the "surface feature limitations on-screen, never silently" rule above. The OCGs are built with pdf-lib's low-level `context.obj`/`context.register`/`PDFOperator.of(BeginMarkedContentSequence/EndMarkedContent, …)` API (wrapping each size's geometry in `BDC …/OC …/EMC`) and registered on the document catalog's `/OCProperties` with a `/D` default configuration naming a real `/Order` and `/ON` list — verified by inflating the saved PDF's compressed object streams (pdf-lib defaults to `useObjectStreams: true`, so a plain byte search for `/OCProperties` finds nothing; the existing `inflatedContent` test helper already does this for content streams and works identically for the catalog). OCGs were not dropped for a badge, per the issue's own fallback clause — they proved practical against pdf-lib's real API, verified live in `pdf.test.ts`.
- The cm-accurate model is also reused **on-screen**: `buildPathD` (`lib/export/model.ts`) is the shared outline→SVG-`d` builder for both `toSvg` and the React previews, and `planCutLayout` (`lib/export/cutplan.ts`) reuses `buildExportModel` to compute a real cut-plan nesting — expanding each piece by its cut quantity and packing the copies into a selectable fabric-width strip (grain locked, no rotation), returning positioned copies + consumed length + efficiency. **#123: nests the cut line, not the net line** — what actually has to be cut from the fabric, so a larger seam allowance now legitimately consumes more length; each instance's outline is re-zeroed to the cut line's own bbox (see the sheet-packing fix above) before packing, so `widthCm`/`heightCm` are an honest 0-based extent. This backs the data-driven `CutPlanTab` (fabric-width presets `FABRIC_WIDTHS_CM`, consumption/efficiency metrics, an SVG nesting preview) and `TechSheetTab` (per-piece dimensions from the same model plus a garment summary header).
- **#8: `planCutLayout` exposes two `NESTING_MODES`, `"auto"` and `"manual"`, both nesting each copy's _bounding box_, not its outline** — true outline/no-fit-polygon nesting is out of scope and `CutPlanTab.layoutNoteAuto` says so. `"auto"` is `packAuto`, the best of two pure packers — `packShelf` (the original first-fit-by-height-desc shelf packer, unchanged) and `packSkyline` (a bottom-left skyline packer: each copy lands at the lowest, then leftmost, gap along a running per-x occupied-height profile, reserving a `widthCm+GAP_CM` × `heightCm+GAP_CM` footprint so `GAP_CM` spacing survives on every side) — never worse than shelf alone by construction (`min(shelf, skyline) ≤ shelf`), measured up to ~31% shorter on a real garment. `"manual"` starts from the auto placement and overwrites named instances' origins from a caller-supplied `placements` map, clamped inside the fabric width by `clampOriginCm`; `overlappingInstanceIds` flags (never auto-corrects) any resulting overlap in `CutPlan.overlaps`, per "a control must not rewrite what you typed." Grain stays locked and no rotation is offered (not even 180°, since MoldAI doesn't model directional/napped fabric). The manual placements live in `useEditorStore` (`cutFabricWidthCm`/`nestingMode`/`cutPlacements`, plus `CutPlanPreview`'s pointer-drag and arrow-key nudge), cleared on the same pattern-version-change reset that already clears `measurements` — a regeneration changes the copy set, so placements keyed on `pieceId#n` become meaningless. They do **not** survive a page reload (no `Pattern` blob key, no route); `CutPlanTab.layoutNoteManual`'s own `<em>` says so.
- **`/pattern/[id]/export` (design `5h`, issue #17) is a dedicated screen, distinct from the editor footer's `Exportar` link** — `app/pattern/[id]/export/page.tsx` (thin server component, the `/pattern/[id]` ownership/redirect precedent) renders `components/export/ExportShell.tsx` through `AppShell`. It lists every real `EXPORT_FORMATS` entry as a selectable row plus the still-unbuilt ones (today: Molde.me, ficha técnica) disabled and badged "em breve"; an options panel (`ExportOptions`) whose seam-allowance/marks/piece-naming selects are honestly disabled with a stated reason until their underlying capability ships, while tamanho-da-página/largura-do-rolo are real, format-conditional controls; and a pre-download checklist (`ExportChecklist`: seam conflicts, closed-piece count, estimated fabric consumption) that **blocks** the download button while a conflict is active. Exporting itself is still free and server-call-free — the checklist and preset round trips are the only network activity this screen adds.
- **`User.exportPreset Json?`** (migration `20260827120000_add_user_export_preset`, additive/nullable) is "Salvar preset" — one preset per account, not per pattern and not multiple named presets, matching design 5h's single "remember my choices" affordance. `GET`/`PUT /api/account/export-preset` (`requireUser`-gated) are the round trip; `lib/db/exportPreset.ts` re-validates on **every** read and write through `lib/export/preset.ts`'s `validateExportPreset` (`ExportShell`'s pre-existing localStorage-era validator, unchanged — the same drop-unknown-field/clamp-out-of-range/never-throw contract `validateSizeChartPatch` has), so a hostile or stale body can never persist verbatim: an unknown format/page size/fabric width falls back to its default, an out-of-range custom roll width drops to `null` (no split). `PUT`'s route handler deliberately stays on `readJsonObject`, not `parseBody` — the `PATCH /api/size-charts/[id]` precedent (API routes, above): the validator already owns the whole trust boundary, so a zod schema here could only prove "this is an object," which `readJsonObject` already guarantees. `ExportShell` fetches the saved preset on mount (first paint is always `DEFAULT_EXPORT_PRESET`, matching the server render, so there is no hydration mismatch to reconcile) and applies it only if the visitor hasn't already started editing; a failed fetch shows a dismissible, retryable notice without blocking the rest of the screen (the default preset stays usable), and a failed save surfaces the same way rather than silently no-op'ing. **`localStorage` was dropped, not kept as a fallback**: a per-browser cache of an account-level fact is exactly the "second copy of a fact that already has an owner" mistake `Wallet.planLabel`/`EXPORT_FORMATS` duplication already document, and `ExportShell` had no code path that needed to keep working offline.

### SEO and crawlability (2026-09-03 audit)

- **The finding that started it: `metadataBase` was never set, so production served `og:image` and `twitter:image` pointing at `http://localhost:3000`.** Confirmed at source rather than inferred — `node_modules/next/dist/lib/metadata/resolvers/resolve-url.js`'s `getSocialImageMetadataBaseFallback` resolves `metadataBase || VERCEL_PROJECT_PRODUCTION_URL || createLocalMetadataBase()`, and `createLocalMetadataBase()` is literally `http://localhost:${PORT || 3000}`. This app is self-hosted Docker: no `VERCEL_PROJECT_PRODUCTION_URL`, no `VERCEL_URL`, so every page took the localhost branch in production exactly as it did in dev. The effect is that `app/opengraph-image.tsx` — a satori card written specifically so "a link to this site shared anywhere should preview as something branded rather than a bare URL" (its own B10 comment) — was **unreachable for every real share since it shipped**. This is the worst failure shape there is: the build passes, all the tags render, `next build` prints nothing, and the only symptom is a blank preview on a machine you do not own. Re-verified after the fix by running `next start` with `APP_URL=https://moldai.example.com` and reading the served `<head>`: all four dynamic public routes emitted the real origin.
- **`APP_URL` turned out to be a build input, not only a runtime one — and the split is visible in the output.** `metadataBase` is read at module scope in `app/layout.tsx`, which is server boot for a dynamic route (so `/`, `/planos`, `/privacy`, `/terms` get the runtime value from `env_file`) but **build time** for a statically prerendered one. Measured in the same verification run: with `APP_URL` overridden at start, `/login` still served `http://localhost:3000/opengraph-image` because it is `○` and had frozen the build's value, while every `ƒ` route served the override. Hence `ARG APP_URL` in the Dockerfile's `build` stage. It is passed to both `app` and `cron` in `docker-compose.prod.yml` with the identical expression — not because the cron loop renders anything (it does not), but because two services building the same `runner` target with different build args fork the layer cache into two near-identical images. Baking it is safe in a way the other env vars are not: it is the URL users type, not a secret, and the prod stack builds locally per deploy anyway.
- **`app/robots.ts` and `app/sitemap.ts` are `force-dynamic`, which is not the default.** Next's own docs for both file conventions say they are "cached by default unless it uses a Request-time API or dynamic config option." Left cached, each would bake the build-time origin into the `Sitemap:` line and every `<loc>` — the same class of bug as the `metadataBase` one, in the two files whose entire job is to state absolute URLs. The cost is two uncached string renders at a request rate measured in crawls per day.
- **Blocking a URL and de-indexing it are opposite tools, and reaching for both achieves neither.** The four public-but-unwanted routes (`/login`, `/signup`, `/verify`, `/password-reset`) get a `robots` meta tag and are deliberately **left out** of robots.txt's disallow list. A `Disallow` stops the crawler fetching the page, which stops it ever seeing the `noindex`; the URL can then still be indexed from an inbound link, just with no snippet — strictly worse than either tool used alone. This is the one non-obvious rule in the whole change, so it is pinned by a test (`lib/seo/site.test.ts`, "never disallows a route that relies on a noindex meta tag") that cross-products the two exported lists rather than restating either. `/verify` and `/password-reset` additionally get `nofollow`, because their URLs carry a single-use token from a mailed link.
- **The route lists live in `lib/seo/site.ts` and are hand-maintained, not derived from the filesystem.** "Renders without a session" and "belongs in the index" are different questions — deriving the second from the first would have enrolled the two auth pages and the two token screens into the sitemap automatically. `app/seo.test.ts` then derives its per-page assertions **from those lists** (mapping `"/planos"` to `planos/page.tsx`), so adding a route to a list without touching its page fails, which is the only thing that keeps a hand-maintained list honest.
- **The sitemap emits `url` alone.** `lastModified` has no truthful source here: `new Date()` claims all four pages changed on every crawl forever, and a hardcoded date rots silently. Google states it ignores a `lastmod` it does not trust, and ignores `changefreq`/`priority` outright — so all three would be invented numbers that nothing reads, in a repo whose standing rule is not to ship a value it cannot substantiate. The test asserts the property's absence by matching the property, not the bare word, since the doc comment explaining the omission necessarily contains it.
- **`Organization` carries no `logo` and no `sameAs`, and that is a decision rather than an oversight.** Google wants both. This repo has neither: `components/shared/Wordmark.tsx` is live text on the page, not an image asset, and `app/opengraph-image.tsx` is a 1200x630 social card that would render as a wide type banner in a knowledge panel expecting a square mark. There is no social profile at all. Pointing the logo at the OG card, or inventing a profile URL, is the same fabricated-record line the landing page's own "proof is product facts, never social proof — there are no customers, so there is no testimonial or logo strip" rule already draws. Guarded by a test asserting both properties are absent, so a future "improvement" has to argue with the rule rather than quietly add a fake. **Adding a real square logo asset is the one follow-up this audit deliberately left open.**
- **`/planos` emits an `Offer` for three tiers, not four.** Confecção has a real published price and renders a card like the others, but its CTA is permanently disabled behind an "em breve" badge, because there is no sales channel anywhere in this repo to route "Falar com vendas" to (issue #9's own audit). A JSON-LD `Offer` with `availability: InStock` is a machine-readable claim that something is for sale — emitting one would be precisely the overclaim `PLAN_FEATURES`' own comments refuse to make in prose ("A public pricing page must not sell what another screen admits does not exist"), restated in the format a crawler actually parses. Rather than encode that judgement twice, `SELF_SERVE_PLAN_IDS` moved into `lib/billing/plans.ts` and `PlanCta` now tests membership instead of `id === "factory"`, so the rendered page and its structured data read one constant.
- **`priceDecimalString` lives in `lib/billing/plans.ts`, next to `formatBRL`, for the reason `formatBRL` does.** schema.org's `Offer.price` wants `"59.00"` — major units, `.` separator, no symbol — where `formatBRL` produces `"R$ 59,00"`. That is still a decimal separator, and this module is documented as the only place one may appear; building the conversion at the call site would be a second copy of a number Stripe charges, the exact drift the deleted `Wallet.planLabel` column stands for. The `/planos` test asserts the emitted prices equal `SELF_SERVE_PLAN_IDS.map(id => priceDecimalString(PLAN_PRICE_CENTS[id]))` rather than the literals, so a price change cannot leave the schema stale.
- **What was checked and deliberately not changed.** `<html lang="pt-BR">`, the viewport meta, a single `<h1>` per public page with no skipped levels, alt text on all four landing illustrations, the hero preloaded while below-fold thumbs lazy-load, HSTS/`nosniff`/`X-Frame-Options`, and nav+footer internal linking were all already correct. One expected finding was disproved by checking rather than assumed: the `<img>` tags carry no `width`/`height` attributes, but all four SVGs declare intrinsic `width`/`height` alongside `viewBox` (`hero-editor.svg` is `540x347`), so the browser already has an aspect ratio and there is no CLS exposure to fix.

### Billing (real; only the gateway is mocked)

- `Wallet` (1:1 with `User` — credits are an account-level resource, shared across all its patterns) + append-only `Transaction` ledger, same pure-logic + thin-repo split: `lib/billing/wallet.ts` + `lib/db/wallet.ts` (`lockWallet`/`saveWallet`, plus `saveLedger`). Wallets are lazily seeded on first access (`INSERT … ON CONFLICT DO NOTHING` inside `lockWallet`) — no backfill migration was written for the pre-Phase-C mock credits. New wallets seed at the design's **Free tier** (`free`/"Grátis", 30/30, 30-day renewal, both from `lib/billing/plans.ts`'s `PLAN_CREDITS.free`) rather than the pre-billing mock's Ateliê 320/500 — open sign-up must not grant a paid balance.
- **`lib/billing/plans.ts` is the one exported source for every paid tier's terms** (issue #9), the same leaf-module precedent as `lib/export/formats.ts`: `PLAN_CREDITS`/`PLAN_PRICES` (keyed by `PlanId`, design 5c's four tiers), `TOPUP_CREDITS`/`TOPUP_PRICE`, `PaidPlanId` (`Exclude<PlanId, "free">`), the trust-boundary narrower `isPaidPlanId`, `isPlanUpgrade(from, to)` (derived from `PLAN_CREDITS`, no second rank table), and `PLAN_FEATURES` (the public pricing page's per-plan bullets, see Screens below). `applyPurchase(wallet, purchase: Purchase, now)` takes a discriminated union — `{type:"topup"}` or `{type:"subscribe", plan: PaidPlanId}` — and can move a wallet to **any** paid tier, not just Ateliê: `PlanId`'s other two paid members are real destinations now. An upgrade's `balance` becomes `PLAN_CREDITS[plan] + wallet.purchased` (never destroys a prior top-up, the same `purchased` carry-over rule below), and the ledger entry's `reason` is the purchased `PlanId` (`UsageSection` suffixes a subscribe row with the plan name it bought, resolved from `PlanSection`'s own catalog). `POST /api/billing/purchase`'s mock path validates `plan` before touching the wallet (absent/unknown/`"free"` → 400 `invalid_plan`) and refuses a non-upgrade **inside** the wallet lock (`plan_not_upgradable`, decided against the row under its lock, not a stale read) — downgrades are refused server-side by design (issue #9 decision 2), not merely hidden; a lower tier just stays disabled + badged on screen with a note explaining why. **#179: the asaas checkout path is plan-aware now, not a flat Ateliê-only price.** `POST /api/billing/purchase`'s asaas branch runs the same `resolvePurchase` trust-boundary check the mock branch does (absent/unknown/`"free"` plan → 400 `invalid_plan`, before any provider call) and then prices/names the checkout item straight from `lib/billing/plans.ts` — `PLAN_PRICES[purchase.plan]` for a subscribe checkout (item name resolved from `PlanSection.plans.*.name`, the same catalog `PageHeader`'s own plan label already reads), `TOPUP_PRICE` for a topup. **Which plan a subscribe checkout was for now round-trips through `externalReference`:** `buildExternalReference`/`parseExternalReference` (`lib/billing/asaas.ts`) take the whole validated `Purchase`, not a bare `type` — `{userId}:subscribe:{plan}` or `{userId}:topup` — and `parseExternalReference` re-validates the embedded plan with `isPaidPlanId` before it can reach `applyPurchase`, so a forged or tampered reference still cannot name an arbitrary tier. `handleConfirmed` (`app/api/billing/webhook/route.ts`) now applies `parsed.purchase` directly instead of hardcoding `plan: "atelier"`. This is verified against the mock provider and by unit test only — there is no Asaas sandbox account reachable from this environment, so the per-plan checkout price and the widened `externalReference` have not been confirmed to round-trip through Asaas's own API. **#193: `applyPurchase`'s subscribe branch itself now carries a monotonicity guard**, closing the gap #179 left open — two distinct checkouts for different plans confirmed out of order (Asaas's own documented at-least-once, out-of-order delivery) used to be able to apply a lower plan after a higher one already landed, since the mock path's `plan_not_upgradable` check only ever ran synchronously at checkout-creation time and had no equivalent inside the webhook's async `withWalletIdempotent` callback. The guard lives in `applyPurchase` itself (`lib/billing/wallet.ts`), not in the webhook route, because that is the one function every mutation path — mock and asaas alike — routes through, so it can't be bypassed by a future caller. It reuses `isPlanUpgrade` (the exact function the mock path's own synchronous check already calls), so both paths agree on what counts as an upgrade; a same-tier reapply is refused by the identical check (`isPlanUpgrade` is false when the credits are equal), not a separate comparison. **Only a rank-based guard is achievable, not a true chronological one:** the webhook route already documents that a payment's own `value` is never trusted, and Asaas's payload carries nothing else this app treats as an honest ordering signal — building real timestamp-based ordering would mean persisting a new per-wallet high-water mark with no source of truth to validate it against, so "never move to a lower-or-equal tier" is the one honest guard available from what Asaas actually sends. **A refused plan change never swallows the payment:** by the time this runs the money has already settled, so `plan`/`total`/`renewsAt` stay exactly as they are and the paid tier's full credit value is folded into `purchased` instead — the same carry-over pool a top-up uses, never reset by a renewal — so the account keeps every credit it paid for without ever losing the higher plan it was already on; the ledger entry keeps `type: "subscribe"`/`reason: <plan>`, an accurate record of what was paid for even though it didn't change the wallet's plan. `handleConfirmed` (`app/api/billing/webhook/route.ts`) additionally reports this case via `reportError` for operator visibility, once the transaction has committed — the ledger row alone can't tell a human the payment arrived out of order.
- **#196: refunding a `subscribe` ledger entry only resets `plan`/`total` when that entry is actually the one currently backing the wallet's plan.** `reverseSubscription`'s unconditional reset-to-free predates #193; once #193 shipped, a "superseded" subscribe entry (folded into `purchased`, plan untouched) became a _normal_ outcome rather than an edge case, and such an entry is by definition never the plan-setter — refunding one used to wipe a valid higher plan back to free anyway. Two additive columns make the three real cases distinguishable: `Wallet.planSourceExternalId` (nullable `String`, migration `20260827130000_add_wallet_plan_source`) is the externalId of the `Transaction` row that currently backs the wallet's plan, written **once, centrally**, by `lib/db/wallet.ts`'s `withWalletIdempotent` whenever `fn`'s returned entry is `{type: "subscribe", planChanged: true}` — not by each webhook handler individually, so every present and future caller of `withWalletIdempotent` gets the bookkeeping for free; the mock purchase path (`withWallet`) has no externalId to point at and never sets it, which is safe because it also has no refund flow (no gateway to deliver a `PAYMENT_REFUNDED` for a mock-originated payment). `Transaction.planChanged` (`Boolean @default(false)`) records, per entry, whether `applyPurchase` actually moved `plan`/`total` when it ran (`true`) or folded into `purchased` instead (`false`, the #193 guard branch) — `LedgerEntry` carries the same flag before persistence. `reverseRefundedSubscription(wallet, entry, refundedExternalId)` (`lib/billing/wallet.ts`) is the pure decision, run against the **locked** wallet inside `handleRefunded`'s own `withWalletIdempotent` callback: **"reset"** when `refundedExternalId === wallet.planSourceExternalId` (this entry IS the current plan source — `reverseSubscription`'s pre-#196 full reset, now also clearing the now-dangling `planSourceExternalId`); **"folded"** when `entry.planChanged` was `false` (this entry never touched the plan — `reversePurchasedCredits` undoes precisely what it added, symmetrically subtracting from both `purchased` and `balance`, regardless of what plan the wallet is on now); **"superseded"** otherwise — the entry DID change the plan when it ran, but a _later_ real upgrade has since overwritten `total`/`plan` again (`applyPurchase`'s upgrade branch always assigns, never adds), so nothing about this entry's contribution survives to claw back and the wallet is left untouched (a zero-amount `debit`/`asaas_refund_superseded` ledger row records the refund's own idempotency; `handleConfirmed`'s and `handleRefunded`'s reportError calls are now symmetric — "landed as `purchased` instead of a plan change" vs. "acknowledged, nothing left to reverse"). This also covers the chain-of-upgrades case from #196's own issue text (atelier→studio, then separately →factory, then the _original_ atelier payment is refunded): atelier's entry has `planChanged: true` but is no longer `wallet.planSourceExternalId` (factory's later entry overwrote it), so it resolves "superseded", not "reset". **Migration `20260827130000` backfills both columns best-effort**, treating each paid-plan wallet's most recent gateway-originated `subscribe` row as its plan source — exact whenever a wallet's history has no fold after its last real upgrade (the only case reachable before this migration, since #193 is what made a fold possible at all); the `Wallet.purchased` migration precedent (`20260822220000`, "no way to retroactively attribute") is the accepted-approximation shape this follows, and the failure mode is milder still — a wrongly-backfilled row resolves "folded" on its next refund rather than "reset", which still never reintroduces this issue's own bug.
- **#198: refunding a `topup` entry now decrements `purchased` too, not only `balance` — and the whole refund dispatch moved out of the route into pure code.** `applyPurchase`'s topup branch adds to **both** `balance` and `purchased`, but `handleRefunded` reversed it with a plain `debitWallet`, which only undoes the balance half. Because `purchased` is the carry-over pool a renewal never resets (`renewWallet`: `newBalance = total + purchased`), the inflated value was silently re-granted at **every renewal from then on, forever**, with no ledger row explaining why the balance kept coming back higher than `total` predicts — the same not-mirroring-what-it-undid shape as #196, one entry type over. `reverseFoldedSubscription` was already exactly the right operation (subtract from both), so it was generalized and renamed **`reversePurchasedCredits`**: a topup entry and a _folded_ subscribe entry (#193's guard branch) perform the identical wallet movement, so they share one reversal rather than two that can drift. The per-entry-type branching also left `app/api/billing/webhook/route.ts` entirely: **`reverseRefundedEntry(wallet, entry, refundedExternalId)`** (`lib/billing/wallet.ts`) is now the one pure decision for every shape a gateway refund can name — `"topup"`, then `reverseRefundedSubscription`'s own `"reset"`/`"folded"`/`"superseded"`, plus `"other"` (unreachable today — only `withWalletIdempotent` writes an externalId, and only for a confirmed topup/subscribe and a refund's own `<id>:refund` row — kept so a future gateway-originated entry type degrades to undoing the balance movement instead of reversing nothing). The route just reads the outcome back and reports `"superseded"`, exactly as it already did. That extraction is what makes the invariant suite below able to exercise the real dispatch rather than a copy of it.
- **`lib/billing/invariants.test.ts` asserts the wallet/ledger properties over pseudo-random operation sequences, and is the standing answer to how #179 → #193 → #196 → #198 happened.** Four defects in one small surface, each found only by fixing the previous one, none in the original backlog, and every one the same shape: _a reversal or reapplication that did not mirror what it was undoing or repeating_. One-case-per-issue testing could never converge on that — each new case only ever pinned the scenario its own issue described, and the pre-#198 route test asserted precisely `plan`/`total` were untouched by a topup refund (both true) while `purchased` drifted right beside it. The suite instead drives the real pure functions through 200 seeded 60-step walks of credits/debits/refunds/plan changes/renewals in arbitrary order, checking after **every** step: **A** the ledger reproduces the balance (`balance == seed + Σ signed amounts`, each entry's own `balanceAfter` matching); **B** `total === PLAN_CREDITS[plan]`; **C** `purchased` equals the sum of unreversed purchased-credit grants; **D** `purchased` is never negative; **E** `planSourceExternalId`, when set, names an entry that really moved the plan; **F** a confirmation never walks the plan down and only a plan-source refund moves it at all. **C is computed from what each entry itself contributed at credit time, never from the outcome the dispatch reports for its reversal** — the difference between an independent check and a self-fulfilling one, and what makes a _misclassified_ reversal (pre-#196: every refunded subscribe treated as a full plan reset, folded ones included) fail C rather than redefine it. Verified by reverting each fix in turn and watching the suite go red on the right invariant: #37 (renewal wipes `purchased`) → the renewal assertion, #193 (no monotonicity guard) → F, #196 (unconditional reset) → C, #198 (plain debit on a topup refund) → C, 199 of 201 walks failing. A seeded LCG rather than a property-test dependency: these shapes need a biased op picker, not shrinking, and a failing seed is named in its own test title.
- `generate` and `graduate` debit atomically with the pattern mutation via `lib/db/pattern-wallet.ts`'s `withPatternAndWallet(patternId, userId, fn)`: both rows locked in one transaction, **always `Pattern` first, then `Wallet`** — it is the only function ever allowed to hold both locks, which makes cross-lock deadlock structurally impossible — and it returns `null` without ever locking the wallet when the pattern isn't found/owned.
- `lib/api/compose.ts` exports `buildCredits(wallet, now)` (account-level, pattern-independent) and `composeEditorState(patternState, wallet, now)` (built on top of it) — the wire `EditorState` the client sees. `Credits.renewsInDays` derives from the real `Wallet.renewsAt` timestamp.
- Auto-renewal: `scripts/cron-renew.ts` (run via `tsx`), scheduled by the `cron` Docker Compose service (hourly loop, no external scheduler), resets `balance` to `total + purchased` and rolls `renewsAt` forward 30 days from the _scheduled_ renewal time for every past-due wallet — "use it or lose it, no accumulation" governs only the monthly plan allowance (`total`). **#161: its past-due query excludes any wallet with a non-null `asaasSubscriptionId`.** A subscribed wallet is renewed instead by its own subscription's next `PAYMENT_CONFIRMED` webhook (`handleConfirmed` in `app/api/billing/webhook/route.ts`, which calls the identical `applyPurchase` path) — without the exclusion, a subscribed wallet whose `renewsAt` fell past-due before (or in the same hour as) that webhook would be renewed by both paths, silently doubling its credits with no ledger row flagging the double-credit as wrong.
- **`Wallet.purchased`** (migration `20260822220000_add_wallet_purchased`) is a carry-over pool a renewal never touches, separate from the plan allowance. Before it existed, a top-up purchase raised `balance` without raising `total`, and `renewWallet` reset `balance = total` — so credits bought outside the monthly allowance were silently deleted at the next hourly renewal, with a `renew` ledger row giving no hint they'd been destroyed. `total` stays the plan allowance only (never inflated by a top-up, or it would misreport the plan); a subscribe purchase also adds `purchased` on top of the new plan's allowance, so upgrading plans doesn't erase a prior top-up either. Because `balance` can now legitimately exceed `total`, every credits-meter bar (`CreditsCard`, `UsageSection`, `PageHeader`) clamps its fill percentage at 100 rather than overflowing its track. Existing wallets migrate with `purchased = 0` — there is no way to retroactively attribute an already-elevated balance to a past purchase.
- `POST /api/billing/purchase`, under the mock provider (`PAYMENT_PROVIDER` unset or anything other than `"asaas"` — the default), simulates instant success. With an optional `patternId` it returns that pattern's full composed `EditorState` (so the editor shows the just-purchased credits without a second fetch); without one, `{status: "ok", credits}` (the account-level context the dashboard has). It only adds credits — it has no 402 path. Under `PAYMENT_PROVIDER=asaas` it instead answers `{status: "redirect", url}` and never touches the wallet at all — see the client-side handling of that third shape above, and the Billing section below for the checkout/webhook flow.
- **`type` is validated, and `applyPurchase` is exhaustive.** It used to be read through an `as` cast (an assertion, not a validation) and `applyPurchase` treated anything that wasn't literally `"topup"` as `"subscribe"` via an implicit else — so `POST /api/billing/purchase {}` answered 200 and moved the wallet from free/30 to **atelier/500**, for any authenticated user, verified against the running app. Now `isPurchaseType` narrows it (unknown/absent → 400 `invalid_purchase_type`, wallet untouched) and `applyPurchase` `switch`es with a `never` binding, so a new `PurchaseType` member is a compile error rather than a silent subscribe — the same shape `exportPattern` uses for its five formats. **The pattern is also resolved before the wallet is touched:** charging first meant `{type:"topup", patternId:"does-not-exist"}` credited +100 and then answered 404, so the credits landed and the client never saw them.
- `Wallet` has **no `planLabel`** (migration `20260821120000_drop_wallet_plan_label`). It stored pt-BR (`"Grátis"`/`"Ateliê"`) fully derivable from `plan`, which let the label drift from the plan it named. `PageHeader` now resolves ``tPlan(`plans.${credits.plan}.name`)`` from the **existing** `PlanSection.plans.*.name` catalog entries, per the catalog-lookup-keyed-by-EN-enum rule — which is what makes it work for all four `PlanId` members (`free`/`atelier`/`studio`/`factory`), not just the two `applyPurchase` ever issues.

Three real product calls, not implementation details: (1) annual credits are a lump sum (`PLAN_CREDITS[plan] * 12`, granted once) rather than a monthly refill decoupled from billing — simpler to reason about, and matches "you paid for the year" more literally than a hidden monthly drip; (2) the billing interval can be switched anytime, self-serve, ranked by the same upgrade-only rule as tier switching, generalized to `effectiveCredits(plan, interval)` — this is what makes monthly-to-annual on the same tier a self-serve upgrade and annual-to-monthly a refused downgrade, with no new special-casing; (3) folded in a fix for a pre-existing gap this change would otherwise make more likely to hit — every plan/interval change creates a brand-new Stripe subscription rather than updating an existing one, and the old one was never canceled, so an account that changed plans twice would be billed for multiple live subscriptions. `handleSubscriptionStarted` now cancels the previous one, but only when the confirmation genuinely changed the plan (not a folded/superseded out-of-order delivery, where the previous subscription is still the real one). `isPlanUpgrade` was replaced outright by `isPlanOrIntervalUpgrade` (ranking `{plan, interval}` pairs by `effectiveCredits`) rather than kept alongside it — its four real call sites all moved, leaving it with no caller.

### Authentication (Google OAuth, #235)

- **`allowDangerousEmailAccountLinking: true` is the intended behavior here, not a misconfiguration left on by accident.** Auth.js's default — refuse a Google sign-in with `OAuthAccountNotLinked` whenever the email already names a `User` row with no linked `Account` — exists to protect providers that do NOT verify email ownership. Google does: its OAuth profile carries `email_verified`, and the `signIn` callback in `auth.ts` checks it explicitly (`profile.email_verified === true`) before ever reaching the adapter's auto-link path. The flag's own "dangerous" name describes the failure mode of trusting an unverified provider blindly; this repo never does that, because the callback runs first.
- **Linking also retroactively verifies an existing unverified Credentials account.** Before Google OAuth, an account that signed up but never clicked MoldAI's own mail link stayed locked out of Credentials login forever (or until it found that mail). Google's own proof of the same address is strictly stronger evidence than an unclicked link this repo sent itself, so `stampEmailVerifiedIfMissing` (`lib/db/users.ts`) fires on every Google sign-in and is a no-op for an already-verified row — a single `updateMany` with the null check in its own `WHERE` clause, not a read-then-write, so there is no race to close. This is a deliberate asymmetry: MoldAI's own verification flow (spec B, `2026-08-20-email-verification-design.md`) never retroactively grants access from a _different_ signal — Google is trusted here specifically because it is a second, independent verifier, not because the bar for "verified" was quietly lowered.
- **`Session` and `VerificationToken` exist and are permanently empty — a real, considered tradeoff, not an oversight.** `@auth/prisma-adapter` is typed against the full standard Auth.js schema; this app keeps JWT sessions (required anyway, since the Credentials provider cannot use database sessions) and already has its own `EmailVerificationToken`/`PasswordResetToken` for the flows Auth.js's own `VerificationToken` would otherwise back (its Email/magic-link provider, unused here). The alternative — a lightweight `googleId` column on `User` with no adapter at all — was considered and rejected: it would mean re-implementing account-linking logic (matching by email, creating the linking record, handling the at-least-once nature of an OAuth callback) that the adapter already gets right. Two empty tables were judged cheaper than that reimplementation.
- **No new rate-limit bucket for the Google/NextAuth routes.** Unlike Credentials, there is no password to brute-force behind `POST /api/auth/callback/google`, and neither `OAuthAccountNotLinked` nor `AccessDenied` reveals whether a given email has a MoldAI account — the enumeration concern the Credentials/password-reset buckets exist for doesn't apply here.
- **`User.passwordHash` became nullable rather than backfilled with a placeholder hash.** A Google-only account genuinely has no password; a fabricated unusable hash would be a value nothing could ever legitimately produce, indistinguishable at the type level from a real one, and every future `passwordHash` read site would need to know to treat it as fake. `null` makes "this account has no password" a fact the type system carries, which is what let `authorizeUser` (`no_password`), `changePassword`, and `verifyForDeletion` each get one explicit branch instead of a magic-string check. **One call site the initial design missed:** `POST /api/verify-email/resend` also compares against `user.passwordHash` directly (outside `lib/account/settings.ts`) — the typecheck surfaced it immediately once the type widened, since it would otherwise call `bcrypt.compare(password, null)` and throw. It needed the identical guard, spending the same dummy-hash cost as its unknown-address branch so a Google-only account (which can never legitimately reach this route — Google signups skip MoldAI's own verification mail entirely) doesn't answer measurably faster than a real credential check.
- **`LoginCard` needed a `<Suspense>` boundary it didn't have before.** Reading a failed Google redirect's `?error=` requires `useSearchParams()`, and Next.js requires that hook's Client Component subtree to sit inside a `Suspense` boundary or the whole page opts out of static prerendering (`missing-suspense-with-csr-bailout`) — caught by `next build` itself, not a review comment. `app/login/page.tsx` now wraps `<LoginCard />` in `<Suspense fallback={null}>`, keeping `/login` statically prerenderable.
- **Two more findings, both only surfaced by an actual live Google sign-in, not by any unit or component test:**
  1. **`Google(...)` needs `clientId`/`clientSecret` passed explicitly.** Auth.js v5's `setEnvDefaults` (`@auth/core`) only auto-populates a provider's credentials from env vars named `AUTH_<PROVIDER>_ID`/`_SECRET` — for the Google provider specifically, `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET`, never an arbitrary name. This repo's own `.env.example` (matching its existing `STRIPE_SECRET_KEY`-style naming, not Auth.js's magic convention) uses `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, so without an explicit `clientId: process.env.GOOGLE_CLIENT_ID` the client id silently stayed `undefined` — every unit test mocks `next-auth` entirely, so nothing caught this until a real browser click redirected to Google with `client_id=undefined` and a 401.
  2. **The button's own width.** The design mock has the Google button spanning the same width as the email/password fields and the "Entrar" submit button. Those all get that width for free by being flex children of the credentials `<form>` (`flex flex-col`, `align-items: stretch` by default). The Google button and its divider sit **outside** that form (deliberately — they are not part of the credentials submit), so as a plain sibling in a non-flex parent, the button (`inline-flex` per shadcn's own base classes) shrank to its content width instead of stretching. Fixed with an explicit `w-full` on the button itself, in both `LoginCard` and `SignupCard`. No test caught this either — RTL's jsdom environment doesn't compute real flex layout widths, so this needed a real rendered screenshot to see.

### Seam-conflict detection (live, apply-with-warning) — the seam graph (#134)

- **`draftAll` (`lib/draft/garment.ts`) builds a real seam graph, not a single hardcoded comparison.** Each drafter declares its own edge-index ranges on `DraftedPiece.seamEdges` (`lib/draft/core.ts` — `{shoulder, side, armhole, hem}` from `body.ts`'s `bodice()`, `{cap, underarmRight, underarmLeft}` from `sleeve.ts`, `{waist}` from `skirt.ts`), and `draftAll` — the one place that knows the whole garment's topology, i.e. which panel sews to which — pairs matching edges across pieces into `SeamPairDecl` entries (`lib/draft/seams.ts`): front vs back shoulder, front vs back side seam, front+back armhole vs the sleeve cap (with the cap's own `CAP_EASE_CM` as the pair's intended ease), the sleeve's own two underarm edges, and — for a dress — each of the bodice's hem edges vs the skirt panel's waist edge. `walkSeamPairs` (`lib/draft/seams.ts`) is the pure function that measures every declared pair's real arc length off the already-drafted pieces (`curveArcLengthCm`, never a bespoke per-drafter number) and returns the full graph — every pair, divergent or not. This is the data structure issue #138 (assembly/sewing-order instructions) walks.
- **`seamCheck` (`lib/draft/garment.ts`) is a consumer of that graph, not the comparison itself** — it narrows the full list down to the pairs whose actual gap misses their own intended ease by more than `SEAM_TOLERANCE_CM` (1 cm, unchanged from before this issue). `applyGarmentSpec` calls it on `draftAll`'s `seamGraph` and `detectConflict` (`lib/editor/state.ts`) attaches a real `ConflictInfo` when anything comes back. The generation still applies, bumps the version, and debits; the chat message gets `tone: "conflict"` and the route responds `status: "conflict"`.
- **Which pairs are genuinely at risk vs. equal by construction today:** the armhole/cap pair is the one divergence possible before this issue — `style.armholeDeepenCm` (0–6 cm, AI-settable, `validateSpec`-clamped) deepens only the body's armhole while the cap is sized from the base one, unless refit. Shoulder, side-seam and the sleeve's own underarm pair are equal by construction (neither side of any of those three depends on anything that currently varies independently between the two pieces involved) — declared and checked anyway, as regression guards for #138's own graph and for whatever a future drafter change might unbalance, not because they can diverge today. **The dress waist-join pair was a REAL, previously-undetected gap #134 surfaced, closed by #177 — in two passes, because the first pass's own fix (#185) was itself incomplete.** For a straight/a-line skirt it was already equal by construction (`skirtWaistHalfCm`, #79, shared by both sides), but for a circle/gore/half-circle skirt the bodice hem was still hip-derived (`skirtWaistHalfCm(hip)`) while the skirt's own waist arc was drafted straight from the actual waist measurement — two different measurements of the same body, genuinely divergent for most real proportions (measured at `SIZE_TABLE.M`: 54 cm hip-derived hem vs. 37 cm circle/gore panel arc, 74 cm half-circle panel arc — 17–20 cm off, not a rounding-scale gap). **#177's decision: fix the bodice, not the skirt** — a fitted bodice ends at the natural waist, so sizing its hem off the hip was wrong independent of silhouette; the circle skirt only made it visible. The value both sides now read is `dressWaistHalfCm(waistCm)` (`lib/draft/skirt.ts`), and it takes **no silhouette parameter at all** — the bodice describes the body, so which skirt happens to be attached cannot change its own hem width. It resolves to `waistCm / 4`, with no added design ease: not an arbitrary pick, but the one value every silhouette's own construction can meet exactly — a circle/gore panel's own arc is `waistCm/2` (two quarters, one per bodice half) and a half-circle panel's single arc is the full `waistCm` (split between the two halves, see below) — so front + back always sum to exactly `waistCm`. A standalone skirt's own waist ease (`skirtWaistHalfCm`, `SKIRT_WEARING_EASE_CM`) is deliberately not reused here: that ease is for a separately-worn waistband, not a dress's already-eased-bodice waist seam. **The topology also has to match the seam's own physical shape, which #177's first pass (measured, not merely reasoned about) got wrong for half-circle**: a first cut of this fix made both sides' _value_ equal for all five silhouettes, verified by the seam graph reporting zero divergence — but for half-circle specifically, the skirt is a single undivided panel (`qty: 1`) whose one waist arc already equals the _full_ waist measurement, and comparing both the bodice front hem and back hem _individually_ against that same whole arc (the topology `waist-join-front`/`waist-join-back` had used for every silhouette since #134) meant satisfying "zero divergence" required drafting each bodice half to the _entire_ waist circumference — a front hem of 74 cm and a back hem of 74 cm at `SIZE_TABLE.M`, a bodice roughly twice the width of the body it's supposed to fit. The seam graph reported the fix as correct because the check itself was asking the wrong question, not because the garment was right — filed as #185 and closed by folding its fix into this same PR rather than shipping the first pass. The real fix: `skirtPiece.qty === 1` (today, only ever half-circle) is the general signal that a skirt is one undivided panel rather than two identical cut copies — `draftSkirt` (`lib/draft/skirt.ts`) exposes `waistFront`/`waistBack`, the panel's one waist arc split at its own centre vertex (the same vertex `foldEdge` already anchors on), and `garment.ts`'s `draftAll` pairs each bodice half against its own half of the arc instead of the whole thing whenever `qty === 1`; for `qty > 1` (straight/a-line, circle/gore) each cut copy is already a whole panel matching one bodice half entirely, unchanged from #79's original topology. Verified live: all five silhouettes now report the _same_ 37 cm bodice-hem value (front and back), summing to the full 74 cm waist, `diffCm: 0` on both pairs. **Every dress's geometry changed as a result of #177's underlying value move, including straight/a-line dresses that already closed by construction**: they were sized off the _hip_ (`skirtWaistHalfCm`), which a fitted bodice hem never should have read regardless of whether it happened to agree with the skirt panel; a dress persisted before #177 re-drafts with the new (smaller, waist-derived, not hip-derived) hem/waist width the next time it's regenerated, since a pattern re-drafts from its frozen `sizeTable` on every regeneration and nothing about the snapshot itself changed. **A standalone skirt is untouched** — `skirtWaistHalfCm(hip)` still sizes its own straight/a-line panel, and a standalone half-circle/circle/gore skirt's own geometry (`radialSkirt`) is untouched too; only a dress's waist join (both the value and, for half-circle, the topology) moved. **#129/#130/#131 added three more pairs to the graph** (`collar-neckline`, `cuff-hem`, `waistband-waist`, see Drafting engine below) — all three equal by construction like shoulder/side/sleeve-underarm above, since each sub-piece's own seam is sized directly from the edge it mates to. **#128 added five more, for the new `trousers` archetype** (`trouser-front-rise`, `trouser-back-rise`, `trouser-inseam`, `trouser-outseam`, `trouser-waistband-waist`, see Drafting engine below) — also all equal by construction, the same shape as the sub-piece pairs above.
- **Multiple simultaneous divergences render as a list, not multiple panels.** `ConflictInfo.entries?: ConflictEntry[]` (additive; absent on a conflict persisted before this issue, which then still renders exactly as it always did through the singular `title`/`description`/`diffCm`/`pieceAId`/`pieceBId`/`markers` fields, populated from the primary entry — the armhole/cap one when present, else the first found) holds one entry per divergence: a pre-resolved `label`/`aLabel`/`bLabel` (the same draft-time locale snapshot `title`/`suggestion` already are), `diffCm`, `fixable`, and its own canvas `markers`. The canvas's single top-right overlay slot still holds exactly one card (`ConflictInfoCard`), which now renders one label+two-bar group per entry instead of always exactly one; `PatternCanvas` draws one marker pair per entry. **The two divergent lengths behind each entry are NOT persisted** — `ConflictEntry` carries only `diffCm`, matching the pre-#134 rule (`ConflictInfo` persisted only `diffCm`) that a pile of per-seam numbers in the blob would have broken. `measureSeamGraph(spec, baseMeasurements, t)` (`lib/draft/garment.ts` — `draftAll`'s `seamGraph` without the pieces or the layout, the `measureSeams` precedent generalised) is called once in `CanvasArea` and its results are matched back to each entry by `key`, the same "derive at render time" rule `fitPieceLabel`/`measureSeams` already established — and it's what gives the comparison to conflicts persisted before this issue too. The bare-`entries` fallback and the fully-legacy (no `entries` at all) fallback both still exist in `ConflictInfoCard`/`PatternCanvas` for exactly that reason.
- `POST /api/patterns/[id]/conflict/resolve`: "fix" calls `refitSleeve` for free — it sets the internal `style.sleeveRefit` and re-drafts so the cap uses the adjusted armhole, closing only the armhole/cap divergence (any other entry in the list is untouched, and the conflict stays open with whatever remains); "ignore" clears the whole warning regardless of how many entries it holds, leaving every pair divergent. `sleeveRefit` is deliberately **not** accepted by `validateSpec`, so the AI can never fake a refit. **`ConflictActions`'s "Corrigir manga" button itself is conditional now**: it renders only while at least one entry is `fixable` (today, only ever the armhole/cap pair) — a conflict made up entirely of unfixable divergences shows the two lengths with no fix button to offer, per this issue's own decision, rather than a button that would silently do nothing for what's actually wrong. (The dress-waist-join pair was the one live example of this; #177 closed it, so today it's a regression guard, not a case a user can actually hit.)

### Assembly / sewing order (#138)

- **The sewing order is derived data, walked from the seam graph — not a hand-written sequence per garment archetype.** `lib/draft/assembly.ts`'s `buildAssemblyOrder(pattern, t)` (the `buildEaseReport`/`measureSeamGraph` precedent: pure, DB-free, redrafts via `draftPiecesCm`/`measureSeamGraph` off the pattern's own frozen `sizeTable`, so it works on a pattern drafted before this issue existed and is never persisted) produces one ordered `steps: AssemblyStep[]` list: a `"dart"` step per piece that has any (from `dartsOf(piece.internalsCm)`), one `"seam"` step per `SeamMeasurement` the graph actually walked (never more, never fewer — the AC's own invariant, `assembly.test.ts`'s matrix suite), and a `"hem"` step for any piece whose own `seamEdges.hem` edge isn't already claimed by another declared pair (see `HEM_CONSUMED_BY` below).
- **Ordering among the seam steps is a lookup by the pair's own stable `key`, not a branch on `spec.type`.** `PHASE_BY_KEY` (`lib/draft/assembly.ts`, exported for `assembly.test.ts`'s own exhaustiveness guard) maps every pair key to one of six construction phases — `primary` (shoulder; a trouser leg's own rise, sewn to its own mirrored copy), `sleeve` (cap-into-armhole and the sleeve's own underarm), `side` (side seam; trouser inseam/outseam), `attach` (collar, cuff), `waistJoin` (a dress bodice sewn to its skirt panel), `band` (waistband, last of the seams) — and darts are unconditionally sewn before every seam/hem step (a piece's darts shape it before any seam joins it to another piece; putting every piece's darts ahead of every seam, rather than interleaving per-piece, is a stricter ordering, not a looser one). A future pair key with no entry falls to `"other"` (sewn last among seams, never dropped) rather than crashing — but every key the drafting matrix actually produces today is exhaustively covered, asserted directly.
- **Each seam step cites the two real, already-drafted lengths (`aLenCm`/`bLenCm`) and the pair's own intended `easeCm`** — `SeamMeasurement` (`lib/draft/seams.ts`) now carries `easeCm` (additive: `pair.easeCm`, carried through unchanged by `walkSeamPairs`, alongside the existing `diffCm`) precisely so "how much ease to distribute" (e.g. the sleeve cap's `CAP_EASE_CM`, a waistband's `WAISTBAND_OVERLAP_CM`) is a real number a sewing-order step can cite, not a guess. `diverges` (from `seamCheck`, not a second threshold) flags a seam that is a live conflict; `AssemblyOrder.hasConflict` is true when any step does — the order is still returned (still real, still useful to know the sequence), but a consumer must say so rather than presenting a plausible-looking, fully-closing seam.
- **Piece names come from the pattern's OWN already-persisted, already-locale-resolved `pieces` list (`pieceDisplayName`, matched by id), never from a fresh redraft.** The same draft-time-locale-snapshot rule every other piece of persisted display text follows (i18n, below) — it's also what keeps a step's `pieceName` byte-identical to what `TechSheetTab`/the canvas already show for the same piece. A seam step's own `key` (e.g. `"armhole-cap"`, `"waist-join-front"`) is deliberately **not** resolved through a catalog label here — it's handed to the model as a stable English identifier for it to phrase itself, the same "hand the model a semantic English label and let it translate/phrase it" precedent the prompt's own `COST_DESCRIPTIONS`/`EXPORT_FORMATS` already use, rather than adding a second Translate-threading path into a module that otherwise needs none.
- **A piece set with no declared pairs, no darts, and no free hem edge derives an honestly empty order (`steps: []`), not a fabricated one** — the shape stays, for a future piece with genuinely nothing to derive, but no spec the drafting matrix produces reaches it today: a standalone skirt/trousers with `waistband: "none"` used to be that reachable example (neither archetype declared any other mated pair, and neither declared a `hem` edge either), but #188 gave both their own `seamEdges.hem` (see below), so that same spec now derives one real `"hem"` step instead. `lib/ai/prompt.ts`'s `# Assembly / sewing order` instructions still tell the model to say plainly that no order could be derived rather than inventing one, for whenever the shape is reached again.
- **Reachable from chat, not a new screen** — the recorded product preference. A sewing-order question answers through the existing `decision: "explain"` path (same `COSTS.adjust` debit, same credit chip, consistent with `explain` never being refunded because the Anthropic call is real and the user gets what they asked for), with one addition: `RawToolInput`/`AiDecision` (`lib/ai/schema.ts`/`decision.ts`) gain an `assemblyOrder?: boolean`, set by the model **only** alongside `decision: "explain"` when its answer specifically narrates the derived order — `resolveDecision` strips it for every other decision, even if the model set it on an `apply`. The route (`app/api/patterns/[id]/generate`) tags the persisted `ChatMessage` with `assembly: true` when that flag comes back, and `ChatBubble` renders the catalog-sourced `ChatBubble.assemblyDisclaimer` note under the bubble when it's set — **"the surrounding chrome and the disclaimer come from the catalog," not the model** (the step text itself is model-produced prose, outside the catalog, exactly like `assistantMessage` always is), satisfying "labelled as AI-generated guidance, not verified construction advice" as a structural signal rather than the route sniffing the model's own prose for keywords.
- **The model may never invent a step for a seam absent from the structure** — enforced by instruction, not by the route re-validating the model's prose against the JSON (the same trust level every other `explain` answer already has for the ease report/product facts it's handed). `buildSystem` (`lib/ai/prompt.ts`) embeds `buildAssemblyOrder`'s JSON under "Assembly order" whenever one can be derived, and its own `# Assembly / sewing order` section is the one place that instructs: walk the steps in order, name pieces by `aPieceName`/`bPieceName`, cite lengths and (only when meaningfully above 0) the ease to distribute, and state when a step `diverges` that the seam doesn't currently close and needs the conflict resolved first.
- **#188: a skirt panel's own bottom hem (every silhouette) and a trouser leg's own hem now declare `seamEdges.hem` too**, alongside body.ts's/sleeve.ts's pre-existing ones — `lib/draft/skirt.ts`'s straight/a-line panel exposes the straight edge through its own fold-bottom vertex, and its circle/gore/half-circle panels expose the already-curved `hemSpan` used to build the outline; `lib/draft/trousers.ts`'s leg panel exposes the straight edge between its own named `hemInner`/`hemOuter` vertices. Neither is ever claimed by another pair — `HEM_CONSUMED_BY` (`lib/draft/assembly.ts`) still only knows about `body-front`/`body-back` (consumed by `waist-join-front`/`-back` on a dress) and `sleeve` (consumed by `cuff-hem`), because a skirt/trouser leg's own hem, unlike its waist, is never sewn to anything (not a bodice at a dress's waist join, not a waistband) — so both now always produce a real `"hem"` step once the piece is drafted, standalone or as part of a dress.

### Generation flow (`POST /api/patterns/[id]/generate`)

- Debits `COSTS.adjust` immediately, then `proposeGarment` (`lib/ai/`) asks `claude-sonnet-5`, via forced tool-use, for `{ decision: "apply" | "decline" | "ask" | "explain", spec, questions?, declineReason?, assistantMessage, assemblyOrder? }` — `assemblyOrder` is only ever meaningful alongside `decision: "explain"` (see Assembly / sewing order below).
- **`lib/ai/` is split by responsibility, all derived from one source of truth:** `prompt.ts` (sectioned system prompt), `schema.ts` (the `propose_garment` tool), `history.ts` (pure `buildHistory` — normalizes the persisted chat into Messages-API turns: serializes an ai turn's `questions` into its text, merges consecutive same-role turns, drops leading assistant turns), `decision.ts` (pure `resolveDecision` — ask/apply normalization + validation), `index.ts` (the API call; the only file importing the SDK). **The prompt's and schema's every enum and numeric bound render from `lib/draft/garment.ts`'s exported `TYPES`/`GENDERS`/`NECKLINES`/`SLEEVES`/`SKIRTS`/`STYLE_LIMITS` plus `MEASUREMENT_RANGES`** — the same constants `validateSpec` clamps with, so the model is never told a range the validator doesn't enforce. Add a style field in one place and all three follow; never hardcode a bound in the prompt or schema. The rule now covers prices and formats too: the prompt's `# Product facts` section renders its credit costs from `COSTS` and its format list from `EXPORT_FORMATS` (`lib/export/formats.ts` — a leaf module holding the array plus the `ExportFormat` type derived from it, so `prompt.ts` can name the formats without importing the export facade's serializers and `download.ts`'s DOM access; `lib/export/index.ts` re-exports both, so existing `@/lib/export` importers are unchanged).
- A `decision: "apply"` carrying no usable `spec` object (missing, null, or an array) **throws** rather than letting `validateSpec` fabricate a default blouse — the route's existing catch refunds the credit.
- **Trust boundary:** the returned `spec` is never trusted as-is — `validateSpec` (`lib/draft/garment.ts`) re-checks every enum and clamps every numeric field before use; `questions` go through `validateQuestions` the same way. The AI never emits SVG or pixel coordinates — only a `GarmentSpec`. **The same rule now covers the _user's_ size-chart patch** (`lib/sizeCharts/validate.ts`, see Size charts) — it was written for the AI's input and initially forgotten on the human's, which reaches the identical drafter.
- `apply` → `applyGarmentSpec` → `draftGarment(spec, baseMeasurements, t)` recomputes `pieces`/`viewBox`/`baseMeasurements` from scratch and bumps the version.
- `decline`, and any API/parse error, refunds the credit.
- `ask` (underspecified request) → 1–4 single-choice `questions` attached to the AI chat message (`ChatMessage.questions`), credit refunded, response `status: "clarify"` — no draft, no version bump. The client renders `ClarifyCard`; answering calls `sendMessage(phrase, { answering: true })` with the picks as natural-language text, and the `answering` flag (threaded to `proposeGarment`, enforced by a server-side guard) prevents the AI from asking again.
- **`explain` is the one non-drafting decision that is _not_ refunded.** The user asked a question — about pattern-making, or about MoldAI itself — instead of ordering a garment: the route posts the answer with the credit chip, keeps the `COSTS.adjust` debit, and responds `status: "answered"` with no draft, no version bump and no size-chart snapshot. It is charged because the Anthropic call is as real as a draft's and the user got what they asked for, where `ask`/`decline` refund precisely because they delivered nothing. `resolveDecision` throws on an `explain` carrying a blank `assistantMessage` — the message _is_ the payload there — so the route's catch refunds instead of charging for an empty bubble. This replaced the planned glossary screen (issue #20): a hand-written term list would have been a second, thinner source of knowledge the chat's model already has, and it could not answer "por que minha manga não fecha?". The prompt's `# Modeling knowledge` and `# Product facts` sections are what the decision reads from, and out-of-scope questions still `decline`.
- **#18: a chat message can carry one photo/sketch attachment, sent as an image content block in the same `propose_garment` call — and never persisted.** `components/editor/AttachmentChips.tsx`'s photo/sketch chips (the `.dxf` chip stays disabled — #11's parser now exists in `lib/import/`, but it backs the standalone `/import` screen and does not yet feed a chat attachment) open a hidden file input; `lib/editor/attachment.ts`'s `prepareImage` downscales to `MAX_ATTACHMENT_LONG_EDGE_PX` (1568 px long edge) and re-encodes as JPEG (quality 0.85) client-side, rejecting an unsupported type or a source over `MAX_ATTACHMENT_SOURCE_BYTES` (10 MB) before any decode work — the DOM-free half, exercised in the `node` test project; everything past it is genuinely DOM-only (`createImageBitmap`/canvas). The prepared attachment travels only with the request (`useEditorStore.sendMessage`'s `opts.image` → `lib/api-client.ts`'s `generate` → the route body's `image: {mediaType, data}` → `proposeGarment(state, answering, image)`), never written to the persisted `PatternState` — only `ChatMessage.hasImage` (additive/optional) records that one was used, rendered as a small "imagem enviada" chip (`ChatBubble`), never a thumbnail that would vanish on reload.
- **The browser's own preparation is a UX affordance, not the trust boundary.** `POST /api/patterns/[id]/generate` re-validates `body.image` with `lib/editor/attachment.ts`'s `validateAttachmentInput` (the `isPurchaseType`/`validateSizeChartPatch` precedent — narrows an unknown media type, rejects an empty or over-`MAX_ATTACHMENT_BASE64_CHARS` payload) before any debit or Anthropic call, answering `invalid_attachment` (400) otherwise. The route also reads its body through a route-local, larger `readJsonObject` ceiling (`lib/api/body.ts`'s `readJsonObject` now takes an optional `maxBytes`, defaulting to the shared `MAX_BODY_BYTES` every other, text-only route keeps using) — `MAX_ATTACHMENT_BASE64_CHARS` plus headroom, since an attachment's base64 payload would otherwise blow past the 64 KB ceiling sized for plain form fields.
- **Prompt injection via an attached image's own text is not a new attack surface.** `lib/ai/prompt.ts`'s `# Attached images` section tells the model to treat any text visible inside the image as content to describe, never as an instruction — but the actual defence is structural and pre-existing: `applyGarmentSpec` drafts through `resolveMeasurements`, which clamps every measurement to `MEASUREMENT_RANGES` regardless of what the model claims prompted the value (a mocked "the image said set bust to 500" spec is clamped to `MEASUREMENT_RANGES.bust.max`, asserted in the route's own test rather than in `lib/ai/index.test.ts` — `resolveDecision` itself passes `measurementOverrides` through unclamped; the range is applied downstream, at draft time).
- Costs exactly `COSTS.adjust`, identical to a text-only message — one `propose_garment` call either way.

### API routes

**Every route that reads a body does it through `readJsonObject(request)` or `parseBody(request, schema)` (`lib/api/body.ts`), and there is no bare `request.json()` left in `app/api`.** Both return the parsed value or the 400 to return, shaped like `requireUser()` so `if (x instanceof NextResponse) return x;` reads as the guard idiom already in use — and so a route that forgets the check gets a type error rather than a 500. The bug it exists for: `null` is valid JSON, so it survived `request.json()` and only threw on the first `body.field` read, which in **six** routes sat outside the try/catch. Each answered HTTP 500, measured against the running app: `PATCH /api/patterns/[id]` (`reading 'name'`), `.../graduate` (`'sizes'`), `/api/billing/purchase` (`destructure property 'type'`), `PATCH /api/account/profile`, `POST /api/account/password` (`'currentPassword'`), `POST /api/size-charts` (`'sourceId'`). Three routes had guarded it correctly — with the same explanatory comment copy-pasted into all three, which is the actual lesson: extract the guard at the second occurrence instead of duplicating the comment. `POST /api/size-charts` keeps its deliberate tolerance of an unusable body (it just means "no `sourceId`"), so there the guard result is folded into `sourceId` rather than returned.

**`parseBody<T>(request, schema, maxBytes?)` is `readJsonObject`'s schema-validated sibling** — same shape, same guard idiom, but it also proves the body against a zod schema (`lib/schemas/*`) before the route ever sees it, answering a bare `bad_body` on failure rather than a zod issue path or message (which is English prose that would leak the schema shape to the client). It does **not** replace a route's own downstream trust boundary: a schema field stays `z.unknown()` (or `.optional()`, since zod v4 treats a bare `z.unknown()` key as required-but-any-value, not required-key-optional-absence — an entirely absent key would otherwise 400 as the generic `bad_body` before reaching a route's own more specific domain code) wherever the route already clamps or narrows that field itself downstream (`validateName`, `changePassword`, `isPurchaseType`, `validateAttachmentInput`, …) — `parseBody` only proves the body is an object carrying the right keys, the same job `readJsonObject` always did. Adopted at `PATCH /api/account/profile` and `POST /api/size-charts` (#146), then at the money/AI routes — `POST /api/billing/purchase`, `POST /api/billing/webhook`, `POST /api/account/password`, `POST /api/patterns/[id]/generate` (keeping its own route-local, larger `maxBytes` ceiling for the base64 attachment payload — `parseBody`'s third argument, identical to `readJsonObject`'s), `.../graduate`, and `.../conflict/resolve` (whose `action` field is the one schema in this app validated with a real `z.enum(["fix", "ignore"])` rather than `z.unknown()`, since #54 made an unrecognised action a hard reject with no downstream fallback to defer to) (#152). `PATCH /api/size-charts/[id]` is a deliberate, permanent exception, still on `readJsonObject`: it forwards its raw body to `updateSizeChart`, whose `validateSizeChartPatch` owns the trust boundary with drop-or-clamp-never-throw merge semantics — a schema there would either duplicate that logic or regress it into reject-on-invalid, breaking the documented behaviour that an unusable field is ignored while the rest of the patch applies.

All pattern-mutating routes live under `/api/patterns/[id]/*`, scoped to one pattern and 404'ing via `patternNotFound()`:

- `POST /api/signup` — creates an account (name/email/password) and returns `{status:"ok"}` or a machine-readable `SignupErrorCode` the client resolves through the catalog. It is unauthenticated — deliberately at the top level, outside both the `[...nextauth]` catch-all and the uniformly `requireUser()`-gated `/api/account/*`. Validation lives in the pure, DI'd `lib/account/signup.ts`; `lib/db/users.ts`'s `createUser` returns `null` on the P2002 insert race so a lost race reads as `email_taken`.
- `POST /api/verify-email` (consumes the token, stamps `emailVerified`, mints no session) and `POST /api/verify-email/resend` (credential-gated reissue, 60 s cooldown).
- `POST /api/password-reset/request` (email in, always answers 200 regardless of whether the address exists — an "ok" body must not double as an account-existence oracle — issues a single-use token and mails it) and `POST /api/password-reset/confirm` (token + new password in, IP-keyed only like `verify`, since the 256-bit token is the real backstop). Both unauthenticated by necessity: the visitor has forgotten their password, not just their session. With `POST /api/signup`, `GET /api/health` (below), and NextAuth's own handlers, these are the only unauthenticated route handlers.
- `GET /api/health` — unauthenticated, backs the Docker/Compose healthcheck. Postgres (`SELECT 1`) is a hard dependency and its failure answers 503; Redis (`PING`) is reported (`redis: "ok" | "unreachable"`) but never fails the check, matching the rate limiter's own fail-open philosophy — a Redis blip degrades throttling, it doesn't mean the app can't serve requests.
- `GET /api/patterns` — the session user's pattern list; `POST /api/patterns` — create a blank one, returns its `id`. With a `{sloperId}` body it instead copies that base's frozen snapshot into an already-drafted pattern (`createPatternFromState`) and costs **0 credits** — local drafting, no Anthropic call, the same reason `conflict/resolve` is free.
- `GET /api/patterns/[id]` — the composed `EditorState`; `PATCH` renames (body `{name}`); `DELETE` deletes (the only way to "reset").
- `POST /api/patterns/[id]/generate` — the core AI flow (below). Debit-then-mutate; insufficient balance → HTTP 402 (no debit, no AI call).
- `POST /api/patterns/[id]/graduate` — same debit-then-mutate + 402 pattern. **Its precondition is `pieces.length === 0` → 400 `pattern_not_drafted`, not the size list.** The old `sizes.length === 0` guard could never fire for the case it looked like it covered, because a blank pattern is bootstrapped with a full `PP..GG` list — so grading a freshly created pattern answered 200, bumped version 0→1, left `pieces` at 0 and debited `COSTS.graduate`, the most expensive action in the app, for grading nothing (ledger row `debit / graduate / 6`, verified live). UI-unreachable today (the button lives in `PieceDetailsPanel`, which needs a selected piece), but `withPatternAndWallet` is the money path. The route tests had _encoded_ the bug by using a blank `seedPatternState` as a stand-in for a real pattern; they now draft one first.
- `POST /api/patterns/[id]/conflict/resolve` — free, no debit (see conflicts below).
- `GET /api/account/summary` — account-level, not pattern-scoped: `{credits, recentUsage}` (last 3 debit-type ledger rows via `lib/db/account.ts`'s `getRecentUsage`) backing the dashboard's summary cards.
- `GET /api/account/ledger`, `PATCH /api/account/profile`, `POST /api/account/password`, `DELETE /api/account` — back `/settings` (below).
- `/api/size-charts/*` — see Size charts.
- `/api/slopers/*` — see Atelier bases. `GET /api/slopers` lists the account's bases (thumbnails drafted server-side, the `listPatternsForUser` precedent); `POST /api/slopers {patternId, name}` composes validate-name → `loadPattern` → drafted check → conflict check → `createSloper`, so it alone can tell 404 (`patternNotFound`) from 400 (`invalid_name`, `pattern_not_drafted` when `pieces.length === 0`, `pattern_has_conflict` when the pattern has a live seam conflict — founding a future garment on divergent seams is the same mistake as cutting fabric from them); `PATCH /api/slopers/[id]` renames (`invalid_name` gated by the same `MAX_PATTERN_NAME_LENGTH`) and `DELETE` removes one, both 404ing via `sloperNotFound()`.

### Size charts (`/size-charts`)

Real, per-account, and they drive generation/grading.

- `SizeChart` (Prisma, JSON-blob-per-row like `Pattern`/`Wallet`) holds `SizeChartData`: `name`, `gender`, `bodyType` (descriptive metadata only — never affects drafted geometry, an honest documented limitation, and one `SizeChartTable`'s bodyType control now states on screen via a caption tied to it by `aria-describedby`, not just here), `isSystem`, ordered `sizes: string[]`, `baseSizeIndex`, `baseMeasurements`, a `progressionRule` (cm delta per size step from the base), and per-cell `overrides` that win over the rule. Resolution lives in `lib/sizeCharts/compute.ts` (`resolveSizeChartSize`, `buildSizeTable`), both typed to take `Omit<SizeChartData, "name">` — neither reads `name`, and the widening is what lets `lib/sizeCharts/seed.ts`'s name-free `buildSystemSizeChart` feed into them directly.
- Every account lazily gets two seeded `isSystem` charts on first access (`lib/db/sizeChart.ts`'s `ensureSystemSizeCharts`, same lazy-seed precedent as `Wallet`): "Feminino adulto" and "Masculino adulto", derived losslessly from the legacy tables by `lib/sizeCharts/seed.ts`'s `buildSystemSizeChartData` (the rule+override reconstruction reproduces the original tables exactly). System charts can be duplicated but not edited or deleted (enforced in the repository layer). **Both names now resolve from the catalog** (`SizeCharts.systemChartName.female`/`.male`, threaded through `ensureSystemSizeCharts`/`listSizeChartsForUser`/`createSizeChart`/`getSizeChartForGeneration` as a required `t: Translate` parameter) rather than a hardcoded literal — unlike the `" (cópia)"` duplicate suffix, which already was. `buildSystemSizeChart` (name-free) is the split-out core `buildSystemSizeChartData` wraps with `t("systemChartName." + gender)`; the split exists because `seedPattern`'s blank-pattern bootstrap (`lib/editor/state.ts`) discards the name entirely and only ever holds a `PatternData`-scoped translator, so handing it a name-producing function would resolve the wrong catalog namespace. A rename affects nothing already seeded: existing rows keep the name they were created with, exactly like `PatternData.newPatternName` — verified by a test that seeds a row under one translator and confirms a later call with a different one leaves it alone. The female chart's name used to read "Feminino adulto · ABNT", a standards-body provenance the app cannot substantiate (the numbers come from this repo's own legacy `SIZE_TABLE`, not an ABNT document); `SizeChartLibrary` now also says, on every system chart's own card, that it is a proportional house standard, not a certified one.
- `User.activeSizeChartId` is the account-level "chart in use." **It is not a promise the chart will be used, and the app now says so.** `pickSizeChartForGeneration` returns a `SizeChartChoice` (`{chart, rejectedActive}`) rather than a bare record, and `getSizeChartForGeneration` returns `{chart, rejectedActiveName}` — it used to discard the fact that it had fallen back, so nothing could report it. Observed: with a male chart active, "blusa feminina manga curta" drafted from the system female chart (bust 92) while `/size-charts` still showed the male chart as active and the AI said "usando as medidas padrão". Surfaced in **three** places, per the three places the question comes up: a `tone: "notice"` chat bubble at generation time (the only moment a substitution can happen, since the snapshot is taken once), a **"Grade usada"** chip in `TechSheetTab`, and the active chart's badge in `SizeChartLibrary` now reading its scope ("usada só em peças femininas") because "ativa" alone implied it applied to everything. The frozen `Pattern.sizeChartName` is what the chip reads — additive blob key, frozen for the same reason `sizeTable` is (renaming a chart must not rewrite an existing pattern's history), absent on older patterns and therefore omitted rather than guessed.
- **A `PATCH` body is validated before it can reach the drafter** — `validateSizeChartPatch` (`lib/sizeCharts/validate.ts`), the size-chart half of the `validateSpec` trust boundary, called from `updateSizeChart` (whose `patch` parameter is deliberately `unknown`: the old `Partial<SizeChartData>` was an assertion about data straight off the wire). It drops or clamps, never throws, so an unusable field is ignored while the rest of the patch applies. The bug it exists for, verified against the running app: `gender:"banana"`, `progressionRule:{bust:"NaN-ish"}` and arbitrary unknown keys all persisted verbatim, and **`baseMeasurements:{}` replaced the whole row** — `resolveSizeChartSize` then iterated the surviving keys only and generation answered `status:"ok"` while persisting `viewBox:{w:null,h:null}`, `sizeTable` `{"bust":null,"waist":55}` and detailRows reading **"NaN cm"**. `MEASUREMENT_RANGES` was no defence: `Math.min`/`max` propagate NaN. So `baseMeasurements` **merges** onto the current row — a patch can change a value but can never drop a key — and `isSystem` appears in no branch, so a request can never claim it. (Not reachable from the UI, where `type="number"` cannot emit NaN; this is hardening on the money-and-draft path.) `MEASUREMENT_KEYS` (`lib/measurements.ts`) and `BODY_TYPES` (`lib/types.ts`) are exported for it, and `SizeChartTable` now reads those instead of its own copies — the one-exported-source rule the drafting/AI enums already follow.
- **A pattern snapshots its size chart once, at its first-ever generation:** the generate route calls `getSizeChartForGeneration(userId, spec.gender)` (`lib/db/sizeChart.ts` — the active chart if its gender matches the spec being drafted, else the system default for that gender), then `seedPatternSizeSnapshot` (`lib/editor/state.ts`) freezes `sizes`/`baseSize`/a fully resolved `sizeTable: Record<string, Measurements>` onto the pattern. Every later regeneration reuses the frozen snapshot — editing or reassigning the account's active chart never retroactively changes an in-progress pattern (same precedent as the i18n locale snapshot below). A brand-new blank pattern bootstraps from the system female-adult chart via the name-free `buildSystemSizeChart`/`buildSizeTable` pair (not `buildSystemSizeChartData` — this bootstrap only ever holds a `PatternData`-scoped translator, and that function's name would resolve the wrong catalog namespace), so `Pattern.sizeTable`/`sizes` are always populated, never optional.
- Screen: `components/size-charts/SizeChartsShell.tsx` + `SizeChartLibrary.tsx` + `SizeChartTable.tsx`, with their own `useSizeChartsStore`. Browse the library; edit a custom chart's base row/progression rule/per-cell overrides/size list; duplicate any chart (system or custom); mark one active (`POST /api/size-charts/[id]/activate`). **Spreadsheet import is real (#12), not the inert dashed placeholder it shipped as.** `ImportSizeChartDialog` parses a file entirely client-side via `lib/sizeCharts/import.ts`'s `parseSizeChartFile` (framework-free like every other `lib/sizeCharts` module — the DOM half stays in the dialog), previews exactly what will be created including every rejected cell and its reason, and only then persists through `lib/db/sizeChart.ts`'s `createSizeChartFromImport`. **The preview is a review step, not the trust boundary** — the server re-runs the whole thing through `validateSizeChartPatch` exactly as a hand-typed `PATCH` body would. Deliberately **`.csv`/`.tsv` only, no `.xlsx`**: a binary format needs a real parsing dependency (SheetJS) that an MVP import doesn't justify, and the limitation is surfaced on screen before a file is even picked, with an `.xlsx` upload answering `unsupported_file_type` rather than being silently misread as text.

### Client state (Zustand)

- **Editor:** one store — `lib/store.ts`'s `useEditorStore` — scoped to a single pattern via `init(patternId)`, threading that id through every server call (`generate`/`graduate`/`resolveConflict`/`purchase`). It mirrors the server's `EditorState` after every mutating call and owns UI-only state (active tab, selected piece, details-panel open, active tool, measure-tool measurements — auto-cleared when the pattern version changes — generation status/step, and paywall open/required/retry). All server calls go through `lib/api-client.ts`; components never call `fetch` directly. `sendMessage` optimistically appends the user's chat message before the request resolves; `cancelGeneration` rolls that optimistic message back and refunds the cost client-side (there's no server-side cancel).
- **Failures are data, not silence — and `res.ok` is actually checked now.** `getJson`/`postJson` never looked at the status, so an error body came back typed as the success shape (a 401 became an "`EditorState`" with no pattern). `lib/api-client.ts` exports **`ApiError`** (status + wire code), thrown for any non-2xx a call did not opt into; `handled` lists the statuses whose body _is_ the contract — `PAYWALL` (402, the paywall's required/balance) and `DOMAIN_ERRORS` (the codes the auth/settings screens resolve through the catalog) — enumerated per call site so each endpoint's failure contract stays visible. Every bare `fetch` (rename, delete, activate, duplicate, create) goes through it too; those used to ignore the response entirely, so a failed rename looked like a success.
- **Every store has an error path.** The editor store had _no_ `try`/`catch` at all: `init` threw on `state.pattern.pieces[0]` so `ready` never became true and the screen showed "Carregando molde…" **forever**; `sendMessage` skipped `clearTimeout(stepTimer)` so the overlay spun indefinitely; and `applyState` wrote `pattern: undefined` from an error body, which is how an expired JWT dropped a mid-session user onto a permanent loading screen. Now `error` (wire code) + `clearError`, and `EditorShell` renders a load-error screen with a retry — plus a distinct `sessionExpired` message for 401, different advice for a different cause. The dashboard, size-charts and slopers stores gain **`actionError`/`clearActionError`, kept separate from their existing `error` boolean**: a failed _load_ has nothing to show and replaces the content region, while a failed _mutation_ leaves a usable screen that needs a notice. All four screens — those three plus the editor's own `error`/`clearError` pair — render `components/shared/ActionErrorNotice` (amber `notice`, not the red alert token); `PlanSection`/`UsageSection` under `/settings` render the same component off a plain local `useState`, since that screen deliberately has no Zustand store of its own (see "Don't add abstractions beyond what's needed" above). Mutations update local state only after the server confirms, and `dashboardStore.create()` resolves to `null` instead of rejecting, because its caller navigates to the returned id.
- **The paywall is action-agnostic:** any store action that can fail on insufficient credits (`sendMessage`, `graduateSizes`) stashes its own retry closure in `paywall.retry`. Under the mock provider (the default), `purchase()` applies the response's credits directly, closes the modal, and invokes whatever `retry` was stashed — "buy credits then automatically finish what I was doing" works for any future paid action that follows the same set-paywall-state-with-a-retry-thunk pattern. **#161: `purchase()`, `UsageSection`'s top-up button and `PlanSection`'s subscribe buttons all also handle `PurchaseResult`'s third shape, `{status:"redirect", url}`** — what a real gateway (`PAYMENT_PROVIDER=asaas`) answers instead of crediting instantly, since the wallet isn't touched until the async `POST /api/billing/webhook` confirms payment. None of the three applies any state on that shape (there is nothing new to apply yet) before navigating the browser to `url` via `window.location.href`. The store additionally closes the paywall **without** invoking `retry` — issue #6's own settled decision ("Drop it. The paywall.retry thunk dies with the navigation"): retrying `sendMessage`/`graduateSizes` before the webhook has actually landed would spend a second credit hoping the purchase already went through. The user re-sends once they're back, per that same decision — the composer still holds their text.
- **Dashboard:** its own separate store (`lib/dashboardStore.ts`'s `useDashboardStore`) — same fetch-through-`api-client`-into-Zustand shape, but owning a pattern _list_ (plus account credits/recent-usage and client-side search/type-filter) instead of one pattern's state.
- **Five stores in total, one per screen family, none sharing an instance:** `lib/store.ts` (`useEditorStore`, the editor), `lib/dashboardStore.ts` (`useDashboardStore`, the dashboard), `lib/sizeChartsStore.ts` (`useSizeChartsStore`, `/size-charts`) and `lib/slopersStore.ts` (`useSlopersStore`, `/slopers`) and `lib/importStore.ts` (`useImportStore`, `/import`) — each screen's own lifetime and its own load-vs-action error split (see above), matching the size-charts/slopers precedent of a screen never reaching into another screen's store even when both list similarly-shaped cards. **`useImportStore` is the one store with no load-vs-action split at all**: `/import` has no server load — every state change is a client-side parse triggered by a user action — so it carries `actionError` alone (the mutation half) and no `error`/`ready` pair, per "don't add abstractions beyond what's needed". Two screens deliberately have **no** store: `/settings` and `/pattern/[id]/versions` both read off plain local `useState`, having no state another component needs.

### Rate limiting

Redis-backed fixed window: `consume()` (`lib/rate-limit/consume.ts`) runs one atomic `MULTI` — `INCR` + `EXPIRE … NX` + `TTL` — so the window starts on the first request and expires itself; no sweep job. The whole policy is the table in `lib/rate-limit/limits.ts`, reproduced here in full so a stale copy is a visible mismatch rather than a silent one:

```
signup 5/h · signup_email 3/h · login 20/15min · login_email 10/15min
verify 20/h · resend 10/h · resend_email 5/h · resend_attempt 10/15min
create 60/h · password_reset_request 10/h · password_reset_request_email 5/h
password_reset_confirm 20/h · purchase 10/h · purchase_user 10/h
```

Every sensitive endpoint gets an IP-keyed bucket **and** an email-keyed one — `x-forwarded-for` is spoofable when the app isn't behind a trusted proxy (`lib/rate-limit/ip.ts`'s `clientIp`), so the email-keyed bucket is the non-spoofable backstop. Deployment consequence: behind a reverse proxy, that proxy must overwrite `x-forwarded-for` for the IP limits to mean anything — Next only fills the header when the client didn't send one. Four buckets are deliberate exceptions to that IP+email pairing, each for its own reason: `verify` and `password_reset_confirm` (`app/api/password-reset/confirm/route.ts`) each guard a request that carries no email, only a single-use 256-bit token, so the token itself is the backstop and a counter would add nothing; `create` (#101) and `purchase_user` (#6) are keyed on the account id rather than the IP because the caller is already a known account — `create` — it covers `POST /api/patterns`, `/api/slopers` and `/api/size-charts`, none of which had any throttle before besides whatever credit cost the request happened to carry, while `purchase_user` pairs with an IP-keyed `purchase` on `POST /api/billing/purchase`, which had no bucket at all before — under the mock provider that meant unlimited free credits in a loop, and under asaas it means creating hosted checkouts that cost against a real third party per request. `resend_attempt` (#23) caps password-reset-style _attempts_ against a known address on `/api/verify-email/resend`, the same job `login_email` does on the login path, because the IP-keyed `resend` bucket alone is spoofable without a trusted proxy. In the resend route, the `resend_email` consume sits **after** the credential check and the cooldown check, so it counts mails actually attempted per address — a victim can't have their quota burned by someone without their password, and a legitimate user's impatient retries inside the cooldown (which send no mail) don't cost them anything. `password_reset_request`/`password_reset_request_email` (`app/api/password-reset/request/route.ts`, #24) follow the ordinary IP+email shape: consumed regardless of whether the address exists, so an attacker who knows a victim's email can't flood their inbox just because the account is unregistered.

The limiter reaches the pure `authorizeUser` (`lib/auth/authorize.ts`) through `AuthorizeDeps` (`consume`/`reset`), never an import, keeping that module DB-free, Redis-free, and testable with fakes. **It fails open:** if Redis is unreachable, `consume` (`lib/rate-limit/client.ts` holds the one lazy `ioredis` singleton) logs and allows — a system that locks everyone out when its cache dies is worse than one that briefly loses throttling. This backs rate limiting in both Docker stacks (`app` there is gated on `redis`'s healthcheck) — the host flow (`npm run dev` against `npm run db:up`) is **not** automatically covered: `db:up` brings up Redis alongside Postgres for exactly this reason, but skipping it (or running an older `db:up` that only started Postgres) means every `consume()` call on the host silently takes the fail-open branch instead.

**`REDIS_OPTIONS` (exported from `lib/rate-limit/client.ts`) is a correctness setting, not a preference.** `enableOfflineQueue` was `false`, to "fail fast rather than queue commands forever" — but ioredis connects lazily, so the first commands of a fresh process were issued before the socket was writeable and rejected outright (`Stream isn't writeable and enableOfflineQueue options is false`), which `consume` dutifully turned into fail-open. **Measured, against a healthy Redis: both `consume` calls in a new process's very first signup failed open** (`signup` at `route.ts:46` and `signup_email` at `:54`), so every deploy, restart and scale-out served its first sensitive request unthrottled. It is now `true`, which closes that window; "forever" is not the alternative, because `maxRetriesPerRequest` bounds the reconnect attempts a queued command waits through and `commandTimeout` (1 s) is a hard per-command ceiling. Both directions verified live: 0 fail-opens on a cold process's first request, and with Redis stopped the request still succeeds in ~1 s with `failing open` logged. `client.test.ts` asserts the three options as a regression guard, because the symptom only ever shows in a real process's first request.

**Accepted trade-off:** `login_email` is consumed before the password check, and only a _successful_ password clears it — so anyone who knows a victim's email can spend that bucket's 10 attempts and soft-lock the account for the rest of the 15-minute window; the victim's own correct password can't clear the counter, because the throttle returns first. Self-expiring and standard for per-account throttling, but a real property of the system, recorded here rather than left implicit.

## Commands

```bash
npm run dev      # start dev server (Turbopack) at http://localhost:3000
npm run build    # production build (also runs the TypeScript check)
npm run lint     # eslint
npm test         # vitest run — two projects (see vitest.workspace.ts)
                 #   node: lib/**/*.test.{ts,tsx} + app/**/*.test.{ts,tsx}  (pure logic, no DOM)
                 #   dom:  components/**/*.test.{ts,tsx}                    (jsdom + React Testing Library)
                 # scope one: npx vitest run --project dom
npm run db:up          # bring up local Postgres + Redis (docker compose up -d db redis), host ports 5433 / 6380
npm run db:migrate     # apply Prisma migrations
npm run docker:up     # bring up app + Postgres together in Docker (dev, hot reload) at http://localhost:3000
npm run docker:prod   # bring up the production image (next start) + Postgres
npm run smoke:prod    # brings up the prod stack and does a REAL login (catches regressions like UntrustedHost)
npm run smoke         # just the HTTP login checker, against a server already running (SMOKE_URL)
```

Also in `package.json`: `test:watch`, `typecheck`, `format`/`format:check`, `cron:renew` (one wallet-renewal sweep — see Billing). There is no seed script anymore — a dev account is created the same way a production one is, through `/signup`, then confirmed via the verification link in Mailpit's inbox at `:8025` (dev stack only). `smoke`/`smoke:prod` therefore need `SMOKE_EMAIL`/`SMOKE_PASSWORD` pointed at an account created that way.

**Docker vs host:** Inside the container, the app talks to Postgres at `db:5432` (Docker Compose DNS) and Redis at `redis:6379`. On the host — dev stack only, see below — Postgres is at `localhost:5433` and Redis at `localhost:6380`. Secrets (`.env.local`) come in via `env_file` at runtime — never baked into the image — and the npm docker scripts also pass `.env.local` as `--env-file`, since Compose's own `${VAR}` interpolation in `docker-compose.yml` (below) reads a project-level env file, not each service's `env_file:`. A third compose service, `cron`, runs the hourly wallet-renewal loop (defined in `docker-compose.yml`, so it runs in both the dev and prod stacks). **`docker-compose.prod.yml` overrides `cron` to build the `runner` target** (`#73`) — the base file's `dev` target carries no application code (it's bind-mounted in at runtime), so on an image-only deploy host the loop found nothing to run; `cron` also gets `restart: unless-stopped` there, matching `app`/`db`/`redis`, and its own entrypoint (`docker-entrypoint-cron.sh`, waits for Postgres but skips `prisma migrate deploy`) so it no longer races the app container's migration on every stack start. The base `app` service also carries a `healthcheck` now (`GET /api/health` via Node's own `fetch`, `#100`) — `restart:` alone only reacts to the process exiting, not to one that's up but wedged. A fourth base-compose service, `redis`, backs rate limiting in both the dev and prod stacks. `docker-compose.override.yml` adds a dev-only **Mailpit** (SMTP **1025**, web inbox at **:8025**) and points the app's `SMTP_*` at it; Compose auto-merges an override file for a bare `docker compose up` (`npm run docker:up`) and ignores it for the explicit two-file prod stack (`npm run docker:prod`), so production never gets Mailpit. `.env.example` documents every variable.

**`db`/`redis` publish to the host only in the dev stack.** `POSTGRES_PASSWORD`/`REDIS_PASSWORD` have no default in `docker-compose.yml` (`${VAR:?...}`) — `docker compose up` fails loudly if either is unset, rather than the committed `moldai`/no-password dev defaults silently reaching a real deploy. `docker-compose.prod.yml` additionally resets both services' `ports:` to nothing: Docker's published ports bind `0.0.0.0` and its iptables `DOCKER` chain bypasses `ufw`, so a host-published db/redis on a VPS is reachable from the internet regardless of any firewall rule — an unauthenticated-before-this-fix Redis in particular is both a `FLUSHALL`-away rate-limiter kill switch (`consume()` fails open) and, via `CONFIG SET dir/dbfilename`, a known RCE primitive. Production reaches both exclusively over the compose network; the host ports (`5433`/`6380`) exist only for the dev stack's local inspection convenience.

**Two dev-stack traps, both bind-mount-related and neither an app bug.** Turbopack's watcher misses edits through the Windows bind mount and the HMR socket never handshakes, so `docker restart moldai-app` after editing (or run `npm run dev` on the host instead). Worse, one route silently isn't served: **`POST /api/patterns/[id]/conflict/resolve` answers 404 in the Docker dev stack**, so the seam-conflict buttons ("Corrigir manga" / "Ignorar") appear broken there. Measured, on a freshly rebuilt container with renewed volumes: its depth-1 siblings (`[id]/generate`, `size-charts/[id]/activate`) and a depth-2 route with no dynamic segment (`verify-email/resend`) all answer 401, so the guard is reached; only the route two static segments below a dynamic one — whose intermediate `conflict/` directory holds no `route.ts` — 404s. The same request answers 401 against `next dev` on the host, and `npm run build` lists the route, so verify anything touching it on the host, not in the container. (Cause unconfirmed: presumably Turbopack's route discovery over the mount.) Also: the container's `node_modules` and `.next` are anonymous volumes, so `--renew-anon-volumes` against a stale image resets dependencies to whatever that image baked — rebuild the image first (`docker compose up -d --build app`), then renew, or the app boots unable to resolve packages added since.

### The marketing surface's second design system (`/`, `/planos`, `/privacy`, `/terms`)

**What was asked, and by whom.** The `landing-page-design` skill was invoked against
this repo with no target. Its Part B (typography, spacing, radius, backgrounds, hero
treatment, icons, motion) contradicts `CLAUDE.md` on **every** axis — it mandates
Geist/Manrope/Poppins where this repo uses Bricolage + Archivo, Tailwind's default
type scale where this repo forbids stock Tailwind sizes in favour of its own named
`--text-*` steps, its own spacing table, and Phosphor icons where this repo uses
lucide. Per the project-stage rule at the top of `CLAUDE.md`, that conflict was put
to the user rather than resolved silently. The answer was explicit: **adopt the full
skill and update `CLAUDE.md` to match**, scoped to the two public screens.

**Why the font change is scoped, not global.** "One typeface per site" (B1) read
literally would mean swapping `app/layout.tsx`'s fonts outright — which would
restyle all ~20 authenticated screens, none of which were in scope, and would
directly fight the in-flight `fix/design-reference-alignment` work pinning those
screens to `docs/design/screenshots/*.png`. The scoped reading is also the honest
one: a marketing site and a product UI running different type systems is ordinary,
and the alternative silently redesigns the whole app off a request about two pages.
So Geist is loaded as a third font and gated behind `font-marketing`, applied once
by `MarketingShell`. The boundary is enforced by
`components/landing/marketingDesignSystem.test.ts`, which reads the **source** of
every file under `components/{landing,pricing,legal}` — a rendered-DOM check cannot
tell a class this surface wrote from one that arrived inside a shared
`components/ui` primitive, and those primitives keep the app's scale on purpose.

**This is a divergence from `docs/design/`, recorded so it is not "fixed" back.**
`Landing.dc.html` and `Planos.dc.html` describe the previous system for these two
screens. The seven spacing-pin tests that encoded their exact pixel values
(`pt-[60px]`, `gap-[34px]`, `pb-[34px]`, `pb-11` …) were **replaced, not deleted** —
their purpose (spacing must not drift silently) is still valid, but each could only
ever catch a change to the one element it named. The replacements check the rule
across every file, so a new section is covered the day it is written. Every other
screen's `.dc.html` remains authoritative.

**Three places the skill was deliberately not followed, and why.**

1. **No social proof.** A2 #4 wants a proof signal above the fold and #9 wants
   testimonials or a case study. This product has no customers. Inventing a
   testimonial, a logo strip or a "47.2% faster" figure would be a fabricated
   record presented as genuine — B8's own content-realism rule points the same way.
   The proof is instead three verifiable product facts, read from
   `PLAN_CREDITS`/`EXPORT_FORMATS` rather than typed into the catalog.
2. **No "cancel anytime".** A4 asks for a risk reversal and lists cancel-anytime
   among the options. Plan downgrades are **refused server-side** in this app — only
   upgrades are self-serve — so that sentence would have been false on the marketing
   page of a product whose settings screen refuses it. The note says what is true:
   the free plan needs no card and renews every 30 days. A test pins the absence,
   because this is the kind of copy a future edit would "improve" back in.
3. **No icon library swap.** B6 names Phosphor/Solar/Iconamoon. The marketing
   surface renders **zero** icons, so adopting it would have meant adding a
   dependency for nothing. If icons ever land here, B6 applies then.

**`prefers-reduced-motion` was added on top of the skill, not taken from it.** B7
mandates heavy 800ms blur-and-translate reveals and per-word scroll animation with
no mention of the media query. Shipping that unguarded on the one public page is an
accessibility regression, so the reduced-motion override lives beside the animation
rules in `app/globals.css` — which is also why the visual states are CSS on
`[data-reveal]`/`.marketing-word` rather than className toggles in each component:
one override neutralises all of it.

**Two bugs found by the tests, worth recording.** The nav wrapped `Wordmark` — which
renders its own `<Link href="/">` — in a second `<Link href="/">`, producing nested
anchors and a React hydration error. And the closing CTA, made word-for-word
identical to the hero's per A2 #12, rendered its `{credits}` placeholder unresolved
because the interpolation values were not passed; the accessible names then differed,
which is what surfaced it. Both were caught by `getAllByRole`, not by inspection.

**`Reveal` writes `data-reveal` to the DOM rather than through React state.** The
first version used `useState` and tripped `react-hooks/set-state-in-effect`. The
obvious fix — deriving the initial value from `typeof IntersectionObserver` — is
wrong: it renders `"shown"` on the server and `"hidden"` on the client, a hydration
mismatch. "Revealed" is a one-way visual flag that changes nothing else on the page,
so writing the attribute directly (what `LitWords` already did) is both correct and
cheaper. **Without `IntersectionObserver`, both primitives fall back to the END
state** — visible content, never a section stuck at opacity 0 with no event that can
arrive to un-stick it. The test asserts that fallback, having first been written to
assert the opposite.

**A bug only a running browser could show: sections left permanently
invisible.** The reveals looked correct in tests and in a first screenshot,
because everything above the fold reveals on load. Driving the real page
found that scrolling to the bottom left **12 of 24** `[data-reveal]` elements
still at `opacity: 0` — including sections already scrolled well past.

Two causes, stacked, and the first fix was wrong in a way that looked right:

1. **IntersectionObserver only fires when a threshold is _crossed_.** A
   jump-scroll — which the nav's own `/#how-it-works` and `/#faq` anchors
   perform — can move a section from below the viewport to above it between
   two frames. The intersection ratio goes 0 → 0, nothing is crossed, no
   entry is ever delivered, and the section stays invisible with nothing left
   that could un-stick it. The remedy is an enormous **top** `rootMargin`, so
   "already scrolled past" counts as intersecting.
2. **That remedy silently did nothing on its own.** These pages do not scroll
   the window — `app/layout.tsx`'s body is `h-screen overflow-hidden`, so
   `MarketingShell`'s Radix `ScrollArea` viewport is the real scroller. With
   the default `root: null` the browser still clips the target by that
   scrolling ancestor, and **`rootMargin` cannot expand past an intermediate
   clip**. Re-running the measurement after adding the margin returned the
   identical 12 of 24 — which is what exposed the second cause. Naming the
   scroller as the observer's `root` (`scrollRootOf`, an
   `el.closest("[data-radix-scroll-area-viewport]")`) is what makes the margin
   apply. After that: 24 of 24.

`components/landing/reveal.test.tsx` pins it by stubbing
`IntersectionObserver` and asserting the **options** — the part that was
wrong, and the part no rendered assertion can see, since jsdom implements no
observer at all and every component therefore takes the fallback branch.
Verified by reverting `root` to `null` and watching exactly the two root
assertions go red.

The general lesson is the one the repo keeps paying for: a written spec, a
green test suite and a single above-the-fold screenshot all agreed the page
was fine. Only driving it did not.
