# API routes

### API routes

**Every route that reads a body does it through `readJsonObject(request)` or `parseBody(request, schema)` (`lib/api/body.ts`), and there is no bare `request.json()` left in `app/api`.** Both return the parsed value or the 400 to return, shaped like `requireUser()` so `if (x instanceof NextResponse) return x;` reads as the guard idiom already in use — and so a route that forgets the check gets a type error rather than a 500. The bug it exists for: `null` is valid JSON, so it survived `request.json()` and only threw on the first `body.field` read, which in **six** routes sat outside the try/catch. Each answered HTTP 500, measured against the running app: `PATCH /api/patterns/[id]` (`reading 'name'`), `.../graduate` (`'sizes'`), `/api/billing/purchase` (`destructure property 'type'`), `PATCH /api/account/profile`, `POST /api/account/password` (`'currentPassword'`), `POST /api/size-charts` (`'sourceId'`). Three routes had guarded it correctly — with the same explanatory comment copy-pasted into all three, which is the actual lesson: extract the guard at the second occurrence instead of duplicating the comment. `POST /api/size-charts` keeps its deliberate tolerance of an unusable body (it just means "no `sourceId`"), so there the guard result is folded into `sourceId` rather than returned.

**`parseBody<T>(request, schema, maxBytes?)` is `readJsonObject`'s schema-validated sibling** — same shape, same guard idiom, but it also proves the body against a zod schema (`lib/schemas/*`) before the route ever sees it, answering a bare `bad_body` on failure rather than a zod issue path or message (which is English prose that would leak the schema shape to the client). It does **not** replace a route's own downstream trust boundary: a schema field stays `z.unknown()` (or `.optional()`, since zod v4 treats a bare `z.unknown()` key as required-but-any-value, not required-key-optional-absence — an entirely absent key would otherwise 400 as the generic `bad_body` before reaching a route's own more specific domain code) wherever the route already clamps or narrows that field itself downstream (`validateName`, `changePassword`, `isPurchaseType`, `validateAttachmentInput`, …) — `parseBody` only proves the body is an object carrying the right keys, the same job `readJsonObject` always did. Adopted at `PATCH /api/account/profile` and `POST /api/size-charts` (#146), then at the money/AI routes — `POST /api/billing/purchase`, `POST /api/billing/webhook`, `POST /api/account/password`, `POST /api/patterns/[id]/generate` (keeping its own route-local, larger `maxBytes` ceiling for the base64 attachment payload — `parseBody`'s third argument, identical to `readJsonObject`'s), `.../graduate`, and `.../conflict/resolve` (whose `action` field is the one schema in this app validated with a real `z.enum(["fix", "ignore"])` rather than `z.unknown()`, since #54 made an unrecognised action a hard reject with no downstream fallback to defer to) (#152). `PATCH /api/size-charts/[id]` is a deliberate, permanent exception, still on `readJsonObject`: it forwards its raw body to `updateSizeChart`, whose `validateSizeChartPatch` owns the trust boundary with drop-or-clamp-never-throw merge semantics — a schema there would either duplicate that logic or regress it into reject-on-invalid, breaking the documented behaviour that an unusable field is ignored while the rest of the patch applies.

All pattern-mutating routes live under `/api/patterns/[id]/*`, scoped to one pattern and 404'ing via `patternNotFound()`:

- `POST /api/signup` — creates an account (name/email/password) and returns `{status:"ok"}` or a machine-readable `SignupErrorCode` the client resolves through the catalog. It is unauthenticated — deliberately at the top level, outside both the `[...nextauth]` catch-all and the uniformly `requireUser()`-gated `/api/account/*`. Validation lives in the pure, DI'd `lib/account/signup.ts`; `lib/db/users.ts`'s `createUser` returns `null` on the P2002 insert race so a lost race reads as `email_taken`.
- `POST /api/verify-email` (consumes the token, stamps `emailVerified`, mints no session) and `POST /api/verify-email/resend` (credential-gated reissue, 60 s cooldown).
- `POST /api/password-reset/request` (email in, always answers 200 regardless of whether the address exists — an "ok" body must not double as an account-existence oracle — issues a single-use token and mails it) and `POST /api/password-reset/confirm` (token + new password in, IP-keyed only like `verify`, since the 256-bit token is the real backstop). Both unauthenticated by necessity: the visitor has forgotten their password, not just their session. With `POST /api/signup`, `GET /api/health` (below), and NextAuth's own handlers, these are the only unauthenticated route handlers.
- `GET /api/health` — unauthenticated, backs the Docker/Compose healthcheck. Postgres (`SELECT 1`) is a hard dependency and its failure answers 503; Redis (`PING`) is reported (`redis: "ok" | "unreachable"`) but never fails the check, matching the rate limiter's own fail-open philosophy — a Redis blip degrades throttling, it doesn't mean the app can't serve requests.
- `GET /api/patterns` — the session user's pattern list; `POST /api/patterns` — create a blank one, returns its `id`. With a `{sloperId}` body it instead copies that base's frozen snapshot into an already-drafted pattern (`createPatternFromState`) and costs **0 credits** — local drafting, no Anthropic call, the same reason `conflict/resolve` is free.
- `GET /api/patterns/[id]` — the composed `EditorState`; `PATCH` renames (body `{name}`); `DELETE` deletes (the only way to "reset").
- `POST /api/patterns/[id]/generate` — the core AI flow (below). Debit-then-mutate; insufficient balance → HTTP 402 (no debit, no AI call).
- `POST /api/patterns/[id]/graduate` — same debit-then-mutate + 402 pattern. **Its precondition is `pieces.length === 0` → 400 `pattern_not_drafted`, not the size list.** The old `sizes.length === 0` guard could never fire for the case it looked like it covered, because a blank pattern is bootstrapped with a full `PP..GG` list — so grading a freshly created pattern answered 200, bumped version 0→1, left `pieces` at 0 and debited `COSTS.graduate`, the most expensive action in the app, for grading nothing (ledger row `debit / graduate / 6`, verified live). UI-unreachable today (the button lives in `PieceDetailsPanel`, which needs a selected piece), but `withPatternAndWallet` is the money path. The route tests had _encoded_ the bug by using a blank `seedPatternState` as a stand-in for a real pattern; they now draft one first.
- `POST /api/patterns/[id]/conflict/resolve` — free, no debit (see conflicts below).
- `GET /api/account/summary` — account-level, not pattern-scoped: `{credits, recentUsage}` (last 3 debit-type ledger rows via `lib/db/account.ts`'s `getRecentUsage`) backing the dashboard's summary cards.
- `GET /api/account/ledger`, `PATCH /api/account/profile`, `POST /api/account/password`, `DELETE /api/account` — back `/settings` (below).
- `/api/size-charts/*` — see Size charts.
- `/api/slopers/*` — see Atelier bases. <!-- dangling reference: no "Atelier bases" section exists in this archive; the fact this points at may live in docs/architecture/slopers.md instead. --> `GET /api/slopers` lists the account's bases (thumbnails drafted server-side, the `listPatternsForUser` precedent); `POST /api/slopers {patternId, name}` composes validate-name → `loadPattern` → drafted check → conflict check → `createSloper`, so it alone can tell 404 (`patternNotFound`) from 400 (`invalid_name`, `pattern_not_drafted` when `pieces.length === 0`, `pattern_has_conflict` when the pattern has a live seam conflict — founding a future garment on divergent seams is the same mistake as cutting fabric from them); `PATCH /api/slopers/[id]` renames (`invalid_name` gated by the same `MAX_PATTERN_NAME_LENGTH`) and `DELETE` removes one, both 404ing via `sloperNotFound()`.
