### SEO and crawlability (2026-09-03 audit)

- **The finding that started it: `metadataBase` was never set, so production served `og:image` and `twitter:image` pointing at `http://localhost:3000`.** Confirmed at source rather than inferred — `node_modules/next/dist/lib/metadata/resolvers/resolve-url.js`'s `getSocialImageMetadataBaseFallback` resolves `metadataBase || VERCEL_PROJECT_PRODUCTION_URL || createLocalMetadataBase()`, and `createLocalMetadataBase()` is literally `http://localhost:${PORT || 3000}`. This app is self-hosted Docker: no `VERCEL_PROJECT_PRODUCTION_URL`, no `VERCEL_URL`, so every page took the localhost branch in production exactly as it did in dev. The effect is that `app/opengraph-image.tsx` — a satori card written specifically so "a link to this site shared anywhere should preview as something branded rather than a bare URL" (its own B10 comment) — was **unreachable for every real share since it shipped**. This is the worst failure shape there is: the build passes, all the tags render, `next build` prints nothing, and the only symptom is a blank preview on a machine you do not own. Re-verified after the fix by running `next start` with `APP_URL=https://moldai.example.com` and reading the served `<head>`: all four dynamic public routes emitted the real origin.
- **`APP_URL` turned out to be a build input, not only a runtime one — and the split is visible in the output.** `metadataBase` is read at module scope in `app/layout.tsx`, which is server boot for a dynamic route (so `/`, `/planos`, `/privacy`, `/terms` get the runtime value from `env_file`) but **build time** for a statically prerendered one. Measured in the same verification run: with `APP_URL` overridden at start, `/login` still served `http://localhost:3000/opengraph-image` because it is `○` and had frozen the build's value, while every `ƒ` route served the override. Hence `ARG APP_URL` in the Dockerfile's `build` stage. It is passed to both `app` and `cron` in `docker-compose.prod.yml` with the identical expression — not because the cron loop renders anything (it does not), but because two services building the same `runner` target with different build args fork the layer cache into two near-identical images. Baking it is safe in a way the other env vars are not: it is the URL users type, not a secret, and the prod stack builds locally per deploy anyway.
- **`app/robots.ts` and `app/sitemap.ts` are `force-dynamic`, which is not the default.** Next's own docs for both file conventions say they are "cached by default unless it uses a Request-time API or dynamic config option." Left cached, each would bake the build-time origin into the `Sitemap:` line and every `<loc>` — the same class of bug as the `metadataBase` one, in the two files whose entire job is to state absolute URLs. The cost is two uncached string renders at a request rate measured in crawls per day.
- **Blocking a URL and de-indexing it are opposite tools, and reaching for both achieves neither.** The four public-but-unwanted routes (`/login`, `/signup`, `/verify`, `/password-reset`) get a `robots` meta tag and are deliberately **left out** of robots.txt's disallow list. A `Disallow` stops the crawler fetching the page, which stops it ever seeing the `noindex`; the URL can then still be indexed from an inbound link, just with no snippet — strictly worse than either tool used alone. This is the one non-obvious rule in the whole change, so it is pinned by a test (`lib/seo/site.test.ts`, "never disallows a route that relies on a noindex meta tag") that cross-products the two exported lists rather than restating either. `/verify` and `/password-reset` additionally get `nofollow`, because their URLs carry a single-use token from a mailed link.
- **The route lists live in `lib/seo/site.ts` and are hand-maintained, not derived from the filesystem.** "Renders without a session" and "belongs in the index" are different questions — deriving the second from the first would have enrolled the two auth pages and the two token screens into the sitemap automatically. `app/seo.test.ts` then derives its per-page assertions **from those lists** (mapping `"/planos"` to `planos/page.tsx`), so adding a route to a list without touching its page fails, which is the only thing that keeps a hand-maintained list honest.
- **The sitemap emits `url` alone.** `lastModified` has no truthful source here: `new Date()` claims all four pages changed on every crawl forever, and a hardcoded date rots silently. Google states it ignores a `lastmod` it does not trust, and ignores `changefreq`/`priority` outright — so all three would be invented numbers that nothing reads, in a repo whose standing rule is not to ship a value it cannot substantiate. The test asserts the property's absence by matching the property, not the bare word, since the doc comment explaining the omission necessarily contains it.
- **`Organization` carries no `logo` and no `sameAs`, and that is a decision rather than an oversight.** Google wants both. This repo has neither: `components/shared/Wordmark.tsx` is live text on the page, not an image asset, and `app/opengraph-image.tsx` is a 1200x630 social card that would render as a wide type banner in a knowledge panel expecting a square mark. There is no social profile at all. Pointing the logo at the OG card, or inventing a profile URL, is the same fabricated-record line the landing page's own "proof is product facts, never social proof — there are no customers, so there is no testimonial or logo strip" rule already draws. Guarded by a test asserting both properties are absent, so a future "improvement" has to argue with the rule rather than quietly add a fake. **Adding a real square logo asset is the one follow-up this audit deliberately left open.**
- **`/planos` emits an `Offer` for three tiers, not four.** Confecção has a real published price and renders a card like the others, but its CTA is permanently disabled behind an "em breve" badge, because there is no sales channel anywhere in this repo to route "Falar com vendas" to (issue #9's own audit). A JSON-LD `Offer` with `availability: InStock` is a machine-readable claim that something is for sale — emitting one would be precisely the overclaim `PLAN_FEATURES`' own comments refuse to make in prose ("A public pricing page must not sell what another screen admits does not exist"), restated in the format a crawler actually parses. Rather than encode that judgement twice, `SELF_SERVE_PLAN_IDS` moved into `lib/billing/plans.ts` and `PlanCta` now tests membership instead of `id === "factory"`, so the rendered page and its structured data read one constant.
- **`priceDecimalString` lives in `lib/billing/plans.ts`, next to `formatBRL`, for the reason `formatBRL` does.** schema.org's `Offer.price` wants `"59.00"` — major units, `.` separator, no symbol — where `formatBRL` produces `"R$ 59,00"`. That is still a decimal separator, and this module is documented as the only place one may appear; building the conversion at the call site would be a second copy of a number Stripe charges, the exact drift the deleted `Wallet.planLabel` column stands for. The `/planos` test asserts the emitted prices equal `SELF_SERVE_PLAN_IDS.map(id => priceDecimalString(PLAN_PRICE_CENTS[id]))` rather than the literals, so a price change cannot leave the schema stale.
- **What was checked and deliberately not changed.** `<html lang="pt-BR">`, the viewport meta, a single `<h1>` per public page with no skipped levels, alt text on all four landing illustrations, the hero preloaded while below-fold thumbs lazy-load, HSTS/`nosniff`/`X-Frame-Options`, and nav+footer internal linking were all already correct. One expected finding was disproved by checking rather than assumed: the `<img>` tags carry no `width`/`height` attributes, but all four SVGs declare intrinsic `width`/`height` alongside `viewBox` (`hero-editor.svg` is `540x347`), so the browser already has an aspect ratio and there is no CLS exposure to fix.
