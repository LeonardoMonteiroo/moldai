# Rate limiting

> This is the _why_. For the operative rule, see [`../architecture/rate-limiting.md`](../architecture/rate-limiting.md).
> For universal, cross-cutting rules, see the root [`CLAUDE.md`](../../CLAUDE.md).

### Rate limiting

Redis-backed fixed window: `consume()` (`lib/rate-limit/consume.ts`) runs one atomic `MULTI` — `INCR` + `EXPIRE … NX` + `TTL` — so the window starts on the first request and expires itself; no sweep job. The whole policy is the table in `lib/rate-limit/limits.ts`, reproduced here in full so a stale copy is a visible mismatch rather than a silent one:

```
signup 5/h · signup_email 3/h · login 20/15min · login_email 10/15min
verify 20/h · resend 10/h · resend_email 5/h · resend_attempt 10/15min
create 60/h · password_reset_request 10/h · password_reset_request_email 5/h
password_reset_confirm 20/h · purchase 10/h · purchase_user 10/h
```

Every sensitive endpoint gets an IP-keyed bucket **and** an email-keyed one — `x-forwarded-for` is spoofable when the app isn't behind a trusted proxy (`lib/rate-limit/ip.ts`'s `clientIp`), so the email-keyed bucket is the non-spoofable backstop. Deployment consequence: behind a reverse proxy, that proxy must overwrite `x-forwarded-for` for the IP limits to mean anything — Next only fills the header when the client didn't send one. Four buckets are deliberate exceptions to that IP+email pairing, each for its own reason: `verify` and `password_reset_confirm` (`app/api/password-reset/confirm/route.ts`) each guard a request that carries no email, only a single-use 256-bit token, so the token itself is the backstop and a counter would add nothing; `create` (#101) and `purchase_user` (#6) are keyed on the account id rather than the IP because the caller is already a known account — `create` — it covers `POST /api/patterns`, `/api/slopers` and `/api/size-charts`, none of which had any throttle before besides whatever credit cost the request happened to carry, while `purchase_user` pairs with an IP-keyed `purchase` on `POST /api/billing/purchase`, which had no bucket at all before — under the mock provider that meant unlimited free credits in a loop, and under asaas it means creating hosted checkouts that cost against a real third party per request. `resend_attempt` (#23) caps password-reset-style _attempts_ against a known address on `/api/verify-email/resend`, the same job `login_email` does on the login path, because the IP-keyed `resend` bucket alone is spoofable without a trusted proxy. In the resend route, the `resend_email` consume sits **after** the credential check and the cooldown check, so it counts mails actually attempted per address — a victim can't have their quota burned by someone without their password, and a legitimate user's impatient retries inside the cooldown (which send no mail) don't cost them anything. `password_reset_request`/`password_reset_request_email` (`app/api/password-reset/request/route.ts`, #24) follow the ordinary IP+email shape: consumed regardless of whether the address exists, so an attacker who knows a victim's email can't flood their inbox just because the account is unregistered.

The limiter reaches the pure `authorizeUser` (`lib/auth/authorize.ts`) through `AuthorizeDeps` (`consume`/`reset`), never an import, keeping that module DB-free, Redis-free, and testable with fakes. **It fails open:** if Redis is unreachable, `consume` (`lib/rate-limit/client.ts` holds the one lazy `ioredis` singleton) logs and allows — a system that locks everyone out when its cache dies is worse than one that briefly loses throttling. This backs rate limiting in both Docker stacks (`app` there is gated on `redis`'s healthcheck) — the host flow (`npm run dev` against `npm run db:up`) is **not** automatically covered: `db:up` brings up Redis alongside Postgres for exactly this reason, but skipping it (or running an older `db:up` that only started Postgres) means every `consume()` call on the host silently takes the fail-open branch instead.

**`REDIS_OPTIONS` (exported from `lib/rate-limit/client.ts`) is a correctness setting, not a preference.** `enableOfflineQueue` was `false`, to "fail fast rather than queue commands forever" — but ioredis connects lazily, so the first commands of a fresh process were issued before the socket was writeable and rejected outright (`Stream isn't writeable and enableOfflineQueue options is false`), which `consume` dutifully turned into fail-open. **Measured, against a healthy Redis: both `consume` calls in a new process's very first signup failed open** (`signup` at `route.ts:46` and `signup_email` at `:54`), so every deploy, restart and scale-out served its first sensitive request unthrottled. It is now `true`, which closes that window; "forever" is not the alternative, because `maxRetriesPerRequest` bounds the reconnect attempts a queued command waits through and `commandTimeout` (1 s) is a hard per-command ceiling. Both directions verified live: 0 fail-opens on a cold process's first request, and with Redis stopped the request still succeeds in ~1 s with `failing open` logged. `client.test.ts` asserts the three options as a regression guard, because the symptom only ever shows in a real process's first request.

**Accepted trade-off:** `login_email` is consumed before the password check, and only a _successful_ password clears it — so anyone who knows a victim's email can spend that bucket's 10 attempts and soft-lock the account for the rest of the 15-minute window; the victim's own correct password can't clear the counter, because the throttle returns first. Self-expiring and standard for per-account throttling, but a real property of the system, recorded here rather than left implicit.
