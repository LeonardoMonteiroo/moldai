# Screens

> For universal, cross-cutting rules, see the root [`CLAUDE.md`](../../CLAUDE.md).

### Screens

- **The editor opens on a blank pattern.** A new pattern starts with no pieces, empty chat, name "Novo molde", and `version: 0` — the user always generates from scratch. The first AI generation creates the garment's (variable) piece set — e.g. front/back/sleeve for a blouse, plus a skirt piece for a dress. `CanvasArea` shows a "Molde em branco" empty state and hides the floating toolbar while `pieces` is empty; `sendMessage` auto-selects the first piece once a generation produces one.
- **Canvas overlays are mutually exclusive:** `PieceDetailsPanel` and `ConflictInfoCard` share the top-right slot over the canvas in `CanvasArea.tsx`, and a conflict always takes the slot. Fold new overlays into that same exclusivity check rather than adding a third independent floating panel.
- **`/` is the dashboard for a signed-in, onboarded account — but it has four branches, not one.** `app/page.tsx` is a thin server component that: renders `<LandingPage />` for a signed-out visitor (#13 — before it, the only way in was a bare centered `/login` card with no product explanation); `redirect("/login")` when the session's account no longer exists (#62 — a JWT outlives account deletion by up to 30 days on any device that isn't the one that deleted it); `redirect("/onboarding")` when `onboardedAt === null` (#14); and otherwise `DashboardShell`, reading `?missing=pattern` as plain data — the `?section=` precedent in `/settings`, not a client `useSearchParams`. It is also **the one route whose `generateMetadata` depends on session state**, and the one that must spell out its own `— MoldAI` suffix: Next.js does not apply a layout's `title.template` to a `page.tsx` in that _same_ route segment, and root layout + `/` are the same segment (every other route sits a directory below and composes automatically) rendering `DashboardShell`, which renders through the shared `AppShell` passing neither `title` nor `backHref` — it **is** `/`, and its sidebar already marks the section, so a header title would print "Meus moldes" twice — and composes `Sidebar` ("Meus moldes" active; "Medidas e grades" navigates to `/size-charts`; "Bases do ateliê" navigates to `/slopers` — it was disabled with an "em breve" badge until that screen shipped, and `Sidebar` takes an `active` prop plus an `onNewPattern` callback rather than reading `useDashboardStore` itself, because `/slopers` renders the same component and a failed create there has to record its error on _that_ screen's store, the one whose `ActionErrorNotice` is rendered), `PatternGrid` (search + garment-type filter, reusing the `garmentType.*` catalog keys per the EN-enum-lookup convention), and `CreditsCard`/`RecentUsageCard` (backed by `GET /api/account/summary`). **#114: `PatternGrid` owns no scroll region of its own** — `DashboardShell` wraps it together with the summary-card row in one `ScrollArea` (deliberately without `fill`, see above), so the grid's own `Empty` state renders at its natural content height instead of stretching to fill the viewport and pinning the cards to the bottom edge; the truly-empty state (`patterns.length === 0`, as opposed to a search/filter with no matches) also gets a primary "Criar meu primeiro molde" `EmptyContent` action, reusing the same `onNewPattern`/`handleNewPattern` callback `Sidebar`'s own new-pattern button already calls. The dashed "Importar .dxf · Audaces" card is inert and badged "em breve". Pattern cards deliberately show **no state badge** (the design's rascunho/graduado/exportado): export never touches the server, so "exportado" can't be derived honestly, and a partial 2-state badge wasn't worth shipping — a deliberate simplification, not a bug. Rename (a `Dialog` + `Field`/`Input`, replacing the earlier deliberately-minimal `window.prompt`) and delete (shared `components/shared/ConfirmModal.tsx`, now an `AlertDialog` — it previously rendered `absolute inset-0` _inside the card_, so a 380px panel overflowed a ~220px tile) live **only** in the card "⋯" menu (`PatternCard.tsx`) via `useDashboardStore`; the editor has no delete affordance — its "← Voltar" button just navigates back to `/`. **`/pattern/[id]` redirects to `/?missing=pattern` for a pattern that is gone or not owned**, and the dashboard shows a dismissible notice — it used to be a bare `redirect("/")`, so you simply materialised on the dashboard with no idea why (a stale bookmark or a back button being the usual way in). Deliberately one flag rather than distinguishing "deleted" from "not yours": that would make the dashboard an existence oracle for other accounts' pattern ids, which is exactly what `lib/db/pattern.ts`'s uniform 404 avoids.
- **`/settings` is one unified page, not a modal**, reached from the shared header's avatar menu — its three items ("Créditos e uso", "Plano e cobrança", "Preferências", in `components/shared/PageHeader.tsx`) deep-link via a `?section=` query param (`profile` default, plus `password`/`danger`/`usage`/`plan`), and because that header is on every screen the editor can reach settings too. No dashboard-sidebar entry; the page has its own internal `SettingsSidebar` (5 items, same 186px-column idiom as the dashboard's `Sidebar.tsx`). The section list (`SettingsSection`, `SETTINGS_SECTIONS`) lives in plain `lib/settings/sections.ts`, **outside** the `"use client"` component — the Server Component page needs it as plain data to validate the query param, and importing a non-component value from a client module into server code becomes a broken client reference at runtime. `app/settings/page.tsx` is the usual thin server component: it loads the user (`getUserById`, `lib/db/users.ts`), `Wallet` (`loadWallet`), and the last 30 ledger entries (`getLedgerHistory`, `lib/db/account.ts` — like `getRecentUsage` but without the debit-only filter) — no API round-trip for first render — and renders `SettingsShell`, which shows exactly one of five sections:
  - `ProfileSection` — name editable; email deliberately **read-only** (it's the Auth.js Credentials login identifier; editing it is out of scope).
  - `PasswordSection` — current/new/confirm; client-side confirm-mismatch gating plus a server-verified current-password check.
  - `DangerZoneSection` — account deletion gated by both a client-side "type your email to confirm" match **and** a server-verified password (stronger than the single-pattern `ConfirmModal`, since one irreversible `prisma.user.delete` cascades away every pattern, the wallet, and the ledger via the existing `onDelete: Cascade` — no manual cleanup).
  - `UsageSection` — balance/renewal, a "Comprar créditos avulsos" top-up reusing `purchase("topup")` with an optimistic client-side ledger update, and the full transaction history (all ledger types, not just spend).
  - `PlanSection` — the 4 plans from design `5c` (issue #9: real plan switching, not static display cards). Every tier above the account's own renders an enabled `Button` (`t("subscribeButton", {plan})`, e.g. "Assinar Estúdio") that calls `purchase("subscribe", plan)` — `lib/billing/plans.ts`'s `isPlanUpgrade` decides which; a lower tier stays disabled + badged "em breve", with a `downgradeNote` line explaining that only upgrades are self-serve here (issue #9 decision 2: downgrades are refused server-side, not merely hidden). A failed switch resolves `PlanSection.errors.{code}` (`invalid_plan`, `plan_not_upgradable`, …) from the thrown `ApiError`'s wire code; a successful one updates the card grid locally and calls `router.refresh()` so the `AppShell` header's credits bar and `UsageSection` pick up the new plan without a manual reload. Links out to `/planos` for the fuller card content (feature bullets, the annual toggle, Confecção's "Falar com vendas") rather than duplicating it. Plus a cost-per-action footer from the `COSTS` constant.

  Backed by `PATCH /api/account/profile`, `POST /api/account/password`, `DELETE /api/account`, and `GET /api/account/ledger` (alongside the existing summary route), all `requireUser()`-gated. The profile/password/deletion validation logic lives in DB-free, dependency-injected `lib/account/settings.ts` (mirroring `lib/auth/authorize.ts`'s `AuthorizeDeps` shape) so it's unit-testable without a live DB. Password changes do **not** invalidate the current JWT session — a deliberate choice for this single-device personal-use MVP, not an oversight.

- **`/planos` is a public route** (`app/planos/page.tsx` + `components/pricing/PricingPage.tsx`, issue #15) — the pricing screen design `5c` specifies, reachable without a session (a pt-BR marketing path, the one deliberate exception to the English-screen-route convention — `docs/design/` has screens for it but no shipped English-route precedent to follow). Four cards from `PLAN_CREDITS`/`PLAN_PRICES`/`PLAN_FEATURES` (`lib/billing/plans.ts`), a Mensal/Anual −20% toggle that only changes the **displayed** price (annual billing isn't implemented, so its CTA is disabled + badged "em breve" instead of starting a checkout billed monthly under an annual label), and a cost-per-action footer rendered from `COSTS`/`TOPUP_CREDITS`/`TOPUP_PRICE` — never the design's own literal numbers, which don't match what the app actually charges. Four capabilities design 5c advertises are marked "em breve" rather than claimed as shipped: a second AI model ("Modelo v2 Pro" — every plan drafts with the same `claude-sonnet-5`), per-plan user seats (there is no multi-user concept anywhere), a priority queue/API product, and dedicated support (no support channel exists in this repo at all). "Plano de corte automático" and "Histórico ilimitado de versões" are deliberately **absent** from every plan's bullet list rather than shown as a paid differentiator — both ship free, unrestricted, on every plan (`CutPlanTab`; issue #16's version history has no retention cap or plan gate). "Falar com vendas" (Confecção) is always disabled + badged — there is no sales contact destination to link to. CTAs: signed-out → `/signup`; signed-in on a different plan → `/settings?section=plan` (`PlanSection` is where the real upgrade/downgrade enforcement lives — this page doesn't duplicate it); the current plan's card shows "Plano atual" instead of a control. The landing page's own nav (`LandingNav`, issue #13) links "Planos" here now instead of the disabled+badged placeholder it shipped with.

- **`/` doubles as the public landing for a signed-out visitor** (`components/landing/`, issue #13) — `LandingPage` (hero, step cards, formats section, `LandingNav`), not a redirect to `/login`, which before it was the only way in and offered no product explanation. It is the only consumer of the `text-hero`/`tracking-hero` tokens.

- **Screenshots were tried first for the four landing images and rejected.** The design gives the hero a 531×341 box and each of the three step thumbnails 321×148; a 1400px real capture of the app scaled down into either box lands the app's 12px UI text under 5px rendered — a grey smudge, not something a visitor could read even at a glance. **Enlarging the boxes instead is not the fix** — that breaks the rest of the layout, and it was tried and reverted before settling on cartooned SVGs drawn at the size they're actually seen, rather than photographed and shrunk.
- **A sleeve and a body panel were deliberately drawn with different silhouettes** — a domed cap on the sleeve versus flat shoulders and a neck scoop on the body panel. The first attempt drew them alike (both roughly rectangular blobs), and at thumbnail size they read as two copies of the same shape rather than as a garment — nothing in the image communicated "this is a sleeve, this is a body." Differentiating the silhouettes was the fix, not adding a label (a label would fight the "illustration, not diagram" tone the rest of the hero uses).

- **`/onboarding` is the 3-step post-signup wizard** (design `5b`, issue #14) — `app/onboarding/page.tsx` + `components/onboarding/OnboardingShell.tsx`. A centered card with no header, rendering its own `Wordmark` like `/login`/`/signup`/`/verify` rather than going through `AppShell` (which would need `credits`/`userEmail` this screen has no reason to fetch for chrome alone). Local `useState`, no store. **`User.onboardedAt`/`workStyle`** (migration `20260826150000_add_user_onboarding`, additive) back it: `app/page.tsx` gates on `onboardedAt === null` only, and existing rows were backfilled as already-onboarded, so the wizard only ever fires for accounts created after it shipped — the same grandfather-clause shape the email-verification backfill used. `workStyle` (`patternmaker`/`brand`/`personal`) is **honest, unused research data**, never read by any drafting or billing path; `POST /api/account/onboarding` still rejects an unrecognised value rather than storing it, the `isPurchaseType` trust-boundary shape. Step 2 activates the system female chart; step 3 creates a pattern and generates from the typed request, staying put with a notice on anything that isn't a real draft rather than navigating to a blank pattern. Both "Pular por agora" and a successful submit stamp `onboardedAt`, and the page redirects to `/` if it's already set, so a stale bookmark can't re-show the wizard. Its own two "em breve" rows (import a chart, fill measurements by hand) are disabled+badged, not hidden.

- **`/pattern/[id]/versions` is the version-history screen** (issue #16) — `components/versions/` (`VersionsShell`, `VersionList`, `VersionCompare`), local `useState`, no store. **`PatternVersion` (Prisma) stores the `GarmentSpec` plus the frozen size snapshot only — never the drafted pieces**, on exactly the `Sloper` reasoning: `draftGarment` is deterministic, so geometry would duplicate what `spec` + `sizeTable` already determine. `userId` is denormalized (also reachable via `pattern.userId`) so ownership is one indexed lookup, matching `Transaction.userId`. **A row is written by `recordVersion` inside the SAME transaction as every `bumpVersion`** — generate, graduate, `conflict/resolve`, and restore itself — so a snapshot can never exist without the state that produced it and a failed mutation leaves no orphan. `reason` is machine-readable (`generate`/`adjust`/`graduate`/`conflict_fix`/`restore`), resolved through the catalog, never pt-BR prose. `GET /api/patterns/[id]/versions` returns `null` (never an empty array) for a pattern that isn't the caller's, so it can't become an existence oracle. **Restore is free and append-only**: it uses `withPatternVersioned` (a Pattern-only transaction, never `withPatternAndWallet` — it must not be able to debit), carries the OLD version's frozen size snapshot forward rather than re-resolving against today's active chart, and restoring v3 while at v5 produces **v6 carrying v3's spec** — it never rewrites or deletes v3. There is no retention cap and no plan gate.

- **#273 (Style3D spike) found a gap in `VersionCompare`'s own overlay, filed as [#308](https://github.com/LeonardoMonteiroo/moldai/issues/308), not landed here.** GarmageNet's progressive-editing loop compares regenerated panels against their predecessors and marks each one retained or modified; `VersionCompare.tsx` already drafts both compared versions' full piece sets (`drafted.from.pieces`/`drafted.to.pieces`, matched by stable piece id) but overlays every piece at identical visual weight, with no per-piece signal for which ones actually changed — only three aggregate numbers (Cava, Comprimento, Consumo). Full evidence: [`style3d-spike/README.md`](../reference/style3d-spike/README.md).

- **`/import` is the DXF import flow** (design `5g`, scoped down; issue #11) — `app/import/page.tsx` + `components/import/` (`ImportShell`, `FileSummaryCard`, `LayerMappingPanel`, `VerificationPanel`), a two-step parse → analyse → verify screen with no sidebar. **Entirely client-side: it makes no server call at all**, costs nothing, and says so with its own badge rather than reading a balance for a number that is never spent. `lib/import/` is the framework-free half — `dxf.ts` hand-parses DXF's ASCII group-code/value stream in a single forward pass (which is what makes "never loops forever" structurally guaranteed: every branch either advances or does nothing), written to recognise this repo's own `toDxf`/`toDxfAama` output as a baseline via a round-trip test; `analyze.ts` detects layer roles (`cut`/`seam`/`notch`/`grain`/`ignore`) and emits machine-readable `ImportCheckCode`s (`unitCm`, `piecesClosed`, `missingGrain`, `fileTruncated`, …) the screen resolves as `t("checks." + code)` — the wire-carries-codes rule applied to a client-only module. **An uploaded file is untrusted input, the `validateSpec`/`validateSizeChartPatch` trust boundary**: `parseDxf` never throws and caps text length (`MAX_DXF_CHARS`, ~8 MB), entity count (`MAX_ENTITIES`) and vertices per entity, with `MAX_IMPORT_FILE_BYTES` (10 MB) rejecting an oversized upload before any parse work — the `MAX_ATTACHMENT_SOURCE_BYTES` precedent. **Creating a `Pattern` from the parsed geometry is explicitly "em breve"**, disabled+badged on `VerificationPanel`: this pass reads and verifies a file, it does not yet import one. `FileSummaryCard` resolves each of `pick()`'s three failure causes to its own message rather than using `ActionErrorNotice`, which couldn't tell "too large" from "not a readable DXF".

- **#213: the Molde.me import promise was dropped from `Import.formatNote`, not built.** #11 shipped DXF-only and left `Import.formatNote` naming both Audaces and Molde.me as "chegam em breve", but neither has code behind it — #212 and #213 split the two out to decide each on its own. Molde.me's own pattern format is proprietary with no published specification, and this repo holds no sample file to verify a parser against, the same blocker #212 states for Audaces. The two format promises are not actually symmetric, though: Audaces is the CAD seat this product's target users run day to day, so a real exported file could plausibly turn up and #212 stays open, legitimately "em breve". Molde.me carries no such path in sight, and leaving a proprietary format permanently "em breve" is the exact drift CLAUDE.md's honesty rule exists to catch — "em breve" is supposed to mean planned, not aspirational. So #213 answered its own scope question by dropping the label rather than shipping a guessed binary parser (the one outcome both issues explicitly forbid): `Import.formatNote` now names only DXF (shipped) and Audaces (still "em breve", #212). `lib/import/types.ts`'s own comment already treated Molde.me as out of scope for this pass, so no code elsewhere needed to change. This is scoped to the _import_ promise only — `ExportFormatList`'s `SOON_FORMATS` still lists `"moldeme"` as an unbuilt **export** target (`Pricing.feature.moldeme` too), which is a different, still-open gap: exporting a Molde.me-compatible file doesn't require reverse-engineering their reader the way importing one does, so #213's reasoning doesn't transfer to it.
