# Authentication

> This is the _why_. For the operative rule, see [`../architecture/auth.md`](../architecture/auth.md).
> For universal, cross-cutting rules, see the root [`CLAUDE.md`](../../CLAUDE.md).

### Credentials + email verification

- Verification tokens are backed by migration `20260820120000_add_email_verification`, additive, backfilling every existing user as verified — the grandfather-clause shape that lets the feature ship without locking out anyone who signed up before it existed.
- **Verified live** against the dev stack (real Postgres + Redis + Mailpit), not just unit-tested: the migration applied via `prisma migrate deploy`, and a pre-existing account logged in through the full credentials flow afterwards — which is what proves the backfill's grandfather clause. Sign-up → Mailpit → confirm → login works end to end; the mailed subject renders from the catalog (so `getTranslations` inside a route handler is exercised, which no unit test covers); a login before confirming returns `unverified_email` rather than a bad-password error; a consumed token is rejected on reuse; and with the `login_email` bucket exhausted the correct password is still throttled, while stopping Redis lets it through with `[rate-limit] … failing open` — the documented trade-off, observed.

### Authentication (Google OAuth, #235)

- **Verified live**, not just unit-tested: with a real Google Cloud OAuth client configured, a browser click through `/login`'s "Continuar com Google" button completed a real Google consent screen and landed back signed in, auto-linked (no password prompt) to an existing Credentials account sharing that Google account's verified email — confirmed at the database level (`Account.provider = "google"` pointing at that pre-existing `User` row).

- **`allowDangerousEmailAccountLinking: true` is the intended behavior here, not a misconfiguration left on by accident.** Auth.js's default — refuse a Google sign-in with `OAuthAccountNotLinked` whenever the email already names a `User` row with no linked `Account` — exists to protect providers that do NOT verify email ownership. Google does: its OAuth profile carries `email_verified`, and the `signIn` callback in `auth.ts` checks it explicitly (`profile.email_verified === true`) before ever reaching the adapter's auto-link path. The flag's own "dangerous" name describes the failure mode of trusting an unverified provider blindly; this repo never does that, because the callback runs first.
- **Linking also retroactively verifies an existing unverified Credentials account.** Before Google OAuth, an account that signed up but never clicked MoldAI's own mail link stayed locked out of Credentials login forever (or until it found that mail). Google's own proof of the same address is strictly stronger evidence than an unclicked link this repo sent itself, so `stampEmailVerifiedIfMissing` (`lib/db/users.ts`) fires on every Google sign-in and is a no-op for an already-verified row — a single `updateMany` with the null check in its own `WHERE` clause, not a read-then-write, so there is no race to close. This is a deliberate asymmetry: MoldAI's own verification flow (spec B, `2026-08-20-email-verification-design.md`) never retroactively grants access from a _different_ signal — Google is trusted here specifically because it is a second, independent verifier, not because the bar for "verified" was quietly lowered.
- **`Session` and `VerificationToken` exist and are permanently empty — a real, considered tradeoff, not an oversight.** `@auth/prisma-adapter` is typed against the full standard Auth.js schema; this app keeps JWT sessions (required anyway, since the Credentials provider cannot use database sessions) and already has its own `EmailVerificationToken`/`PasswordResetToken` for the flows Auth.js's own `VerificationToken` would otherwise back (its Email/magic-link provider, unused here). The alternative — a lightweight `googleId` column on `User` with no adapter at all — was considered and rejected: it would mean re-implementing account-linking logic (matching by email, creating the linking record, handling the at-least-once nature of an OAuth callback) that the adapter already gets right. Two empty tables were judged cheaper than that reimplementation.
- **No new rate-limit bucket for the Google/NextAuth routes.** Unlike Credentials, there is no password to brute-force behind `POST /api/auth/callback/google`, and neither `OAuthAccountNotLinked` nor `AccessDenied` reveals whether a given email has a MoldAI account — the enumeration concern the Credentials/password-reset buckets exist for doesn't apply here.
- **`User.passwordHash` became nullable rather than backfilled with a placeholder hash.** A Google-only account genuinely has no password; a fabricated unusable hash would be a value nothing could ever legitimately produce, indistinguishable at the type level from a real one, and every future `passwordHash` read site would need to know to treat it as fake. `null` makes "this account has no password" a fact the type system carries, which is what let `authorizeUser` (`no_password`), `changePassword`, and `verifyForDeletion` each get one explicit branch instead of a magic-string check. **One call site the initial design missed:** `POST /api/verify-email/resend` also compares against `user.passwordHash` directly (outside `lib/account/settings.ts`) — the typecheck surfaced it immediately once the type widened, since it would otherwise call `bcrypt.compare(password, null)` and throw. It needed the identical guard, spending the same dummy-hash cost as its unknown-address branch so a Google-only account (which can never legitimately reach this route — Google signups skip MoldAI's own verification mail entirely) doesn't answer measurably faster than a real credential check.
- **`LoginCard` needed a `<Suspense>` boundary it didn't have before.** Reading a failed Google redirect's `?error=` requires `useSearchParams()`, and Next.js requires that hook's Client Component subtree to sit inside a `Suspense` boundary or the whole page opts out of static prerendering (`missing-suspense-with-csr-bailout`) — caught by `next build` itself, not a review comment. `app/login/page.tsx` now wraps `<LoginCard />` in `<Suspense fallback={null}>`, keeping `/login` statically prerenderable.
- **Two more findings, both only surfaced by an actual live Google sign-in, not by any unit or component test:**
  1. **`Google(...)` needs `clientId`/`clientSecret` passed explicitly.** Auth.js v5's `setEnvDefaults` (`@auth/core`) only auto-populates a provider's credentials from env vars named `AUTH_<PROVIDER>_ID`/`_SECRET` — for the Google provider specifically, `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET`, never an arbitrary name. This repo's own `.env.example` (matching its existing `STRIPE_SECRET_KEY`-style naming, not Auth.js's magic convention) uses `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, so without an explicit `clientId: process.env.GOOGLE_CLIENT_ID` the client id silently stayed `undefined` — every unit test mocks `next-auth` entirely, so nothing caught this until a real browser click redirected to Google with `client_id=undefined` and a 401.
  2. **The button's own width.** The design mock has the Google button spanning the same width as the email/password fields and the "Entrar" submit button. Those all get that width for free by being flex children of the credentials `<form>` (`flex flex-col`, `align-items: stretch` by default). The Google button and its divider sit **outside** that form (deliberately — they are not part of the credentials submit), so as a plain sibling in a non-flex parent, the button (`inline-flex` per shadcn's own base classes) shrank to its content width instead of stretching. Fixed with an explicit `w-full` on the button itself, in both `LoginCard` and `SignupCard`. No test caught this either — RTL's jsdom environment doesn't compute real flex layout widths, so this needed a real rendered screenshot to see.
