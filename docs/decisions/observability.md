# Observability

> This is the _why_. For the operative rule, see [`../architecture/observability.md`](../architecture/observability.md).
> For universal, cross-cutting rules, see the root [`CLAUDE.md`](../../CLAUDE.md).

- **Before `reportError` existed, the AI generation flow's `catch` had no error binding at all.** An Anthropic 401/429 (a rotated key, a spend cap) was structurally unloggable, the credit was silently refunded, and the operator's stdout held nothing: not the cause, not even a line saying a generation was attempted. That silence — a real failure with zero trace of it anywhere — is the whole reason `reportError(scope, err, context?)` exists as a single seam rather than each catch block growing its own `console.error`.
- It's now called from that catch (with `patternId`/`userId` context), from `app/error.tsx`/`app/global-error.tsx`'s boundaries (replacing a bare `console.error(error)`), and from `scripts/cron-renew.ts`'s failure path — three call sites chosen because each one previously either had no logging or an inconsistent one-off. (The seam has since grown to 13 call sites as more catches adopted it — see `architecture/observability.md`.)
- **#275 spent that seam: `reportError` forwards to Sentry, still logging to stdout unchanged.** Four decisions worth recording:
  - **One `NEXT_PUBLIC_SENTRY_DSN` var, not a server-only `SENTRY_DSN` plus a public one.** A DSN ships inside the browser bundle regardless of what it's named — it identifies a project, not a secret that grants access — so a second var holding the identical value would be exactly the "second copy of a fact that already has an owner" CLAUDE.md's non-negotiables forbid. The cost is that this is the repo's first `NEXT_PUBLIC_*` var, so unlike every other one in `lib/schemas/env.ts` it also has to be read at Docker **build** time (the Dockerfile's `ARG NEXT_PUBLIC_SENTRY_DSN`), not just at runtime.
  - **Errors only: no tracing, no Session Replay.** Replay records the DOM to reconstruct a session — that would ship chat message bodies and generated pattern images to Sentry, directly against the issue's "chat message bodies and attached images are never attached to an event" criterion. It also keeps volume inside the free Developer tier (5k events/month) with no reason yet to pay for more.
  - **Source-map upload gated on `SENTRY_AUTH_TOKEN` being set.** `next.config.ts`'s `withSentryConfig` wrap only activates when the token is present. `npm run typecheck` **is** `next build` (`package.json`), and CI's `build` job (`.github/workflows/ci.yml`) sets no Sentry vars at all — an unconditional wrap would put source-map upload, and any plugin failure mode, on every PR's critical path for a feature CI can't exercise anyway.
  - **Redact in the seam, not at the `password-reset-request` call site.** `app/api/password-reset/request/route.ts` deliberately swallows its mail-send error and reports only `{ email }` — that address is the operator's only handle on a broken SMTP config, and stdout is local to the operator, so it stays. `lib/observability/sentry.ts`'s `redactContext` strips any key that looks sensitive (`email`, `token`, `password`, `message`, `image`, …) before the Sentry payload is built, so the third party never receives it while the console line is untouched.
- **`SECURITY_HEADERS` had to be pure data specifically because `next.config.ts` sits outside both vitest projects' include globs** (`lib/**`, `app/**`, `components/**`) — if the header list lived inline in `next.config.ts`, nothing in the test suite could ever assert against it, and a header silently dropped from the array would ship unnoticed.
- **A Content-Security-Policy is deliberately absent, not forgotten.** Next's inline bootstrap script needs a nonce and a naive policy would break the app outright, so it stays a tracked follow-up rather than a rushed, broken CSP; `X-Frame-Options` is the interim clickjacking mitigation for `/login`'s credentials form that CSP's `frame-ancestors` would otherwise supersede once it lands.
