## Conventions

- **Commits:** always English, [Conventional Commits](https://www.conventionalcommits.org/) — `type(scope): summary` (e.g. `feat(i18n): add pt-BR catalog`, `fix(export): clamp dxf tolerance`). Common types: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `ci`, `style`.
- **Language boundary:** code identifiers, wire keys, enum values, Prisma models/columns, and routes are **English**; UI display text is **pt-BR**; the AI's chat replies mirror the user's own language (see i18n below). Full-page screen routes are English — `/pattern/[id]`, `/settings`, `/size-charts` (the first two were renamed from `/molde/[id]`/`/configuracoes`, along with `Molde`→`Pattern` and `/api/moldes/*`→`/api/patterns/*`).
- **Translate domain terms from the pt-BR design doc, don't transliterate them:** "grades" → `SizeChart` (not `Grade`), "molde" → `Pattern` (not `Molde`). Both were shipped transliterated first and each cost a repo-wide rename sweep — files, functions, routes, Prisma models/columns, i18n keys, plus a migration apiece (`rename_molde_to_pattern`, `rename_grade_to_size_chart`). Get it right up front. (Separately, the earlier general PT→EN rename of the persisted `EditorState`'s keys/values changed the stored JSON shape and required `reset_moldes_english`, which wiped every persisted pattern blob — a wire-shape change, not just an identifier rename, is the expensive kind.)
- **UI labels come from catalog lookups keyed by the EN enum value** — e.g. `t("garmentType." + spec.type)` in `TechSheetTab`, the `PatternData` namespace's `neckline.*`/`skirtSilhouette.*`/`sleeveType.*` keys resolved inside the drafters — never hand-written `Record<Enum, string>` label maps.
- **Surface feature limitations on-screen, never silently.** A scope boundary, unsupported case, or mock standing in for the real thing must be explicit where the user meets it (inline note, disabled control with a reason, badge) rather than failing, no-op'ing, or pretending completeness. Mark planned/feasible-later capabilities **"em breve"** so they're distinguishable from hard limitations, and prefer showing an option disabled+badged over hiding it. Anchors: the `Prova 3D` tab's honest "ainda não disponível" empty state; the AAMA/ASTM DXF export tagged "beta" with its gaps noted inline.
- **Design tokens live in `app/globals.css`** as Tailwind v4 `@theme` variables (colors, radius, shadow scale) — this project has no `tailwind.config.ts`. Fonts (Bricolage Grotesque for display/titles, Archivo for UI/body) load via `next/font/google` in `app/layout.tsx`, exposed as CSS variables. Extend the `@theme` block; never hardcode hex values in components.
- **Reuse `components/shared/PageHeader.tsx` for any full-page screen's header** (logo, back-to-`/` button, title/subtitle, credits bar, "Comprar créditos", avatar, sign out). The editor's `Topbar` is a thin wrapper over it (title = pattern name, subtitle = formatted saved-version string); `SettingsShell` passes a title with no subtitle. Don't hand-roll new headers.
- **Don't add abstractions beyond what's needed** — e.g. `/settings` deliberately has no Zustand store: it has no cross-component shared state and section choice lives in the URL, so local `useState` per section is enough.

## What this is

MoldAI is an AI pattern-making product for clothing: chat with an AI to generate/adjust 2D sewing patterns, grade sizes, and export to Audaces/Molde.me/plotter/PDF. This repo is a Next.js app with a real backend — the "real backend" roadmap (Phase A auth → B persistence → C billing) is fully shipped:

- **Auth:** Auth.js v5 (Credentials + JWT), users in Postgres via Prisma (local Docker Compose). Login/logout only — self-signup is deferred, shown as "em breve".
- **Chat:** a real Anthropic API call (`claude-sonnet-5`) interprets the user's request and returns a `GarmentSpec` (garment type + measurement overrides + style); the server validates/clamps that spec and drafts the pattern pieces from it.
- **Patterns:** persisted per account, many per account (the dashboard's list).
- **Billing:** a real per-account `Wallet` + append-only `Transaction` ledger, shared across the account's patterns. The **only mock left is the payment gateway** — "purchase"/"subscribe" simulate instant success instead of charging a card.

Requires `ANTHROPIC_API_KEY`, `DATABASE_URL`, and `AUTH_SECRET` in `.env.local`.

### Scope

**MVP (small-scale/personal-use production) is five subsystems — four shipped, one roadmap:**

- **Pattern editor** (design `4a`) — `/pattern/[id]`. The single most complex screen of the design handoff. The paywall (`5d`) and the seam-conflict warning (`5e`) are implemented inline here.

**Out of scope:** landing (`5a`), onboarding (`5b`), public plans/pricing screen (`5c`), version history (`5f`), import (`5g`), export as a dedicated screen (`5h` — programmatic export itself is shipped).

## Architecture

### Data layer: pure logic + thin repositories

- `Pattern` (Prisma) has its own cuid `id` with `userId` as a plain indexed foreign key — many patterns per account. Each row holds a `PatternState` JSON blob (pattern, chat, active conflict — no credits).
- Editor-state logic is pure and DB-free in `lib/editor/state.ts` (`seedPatternState`, `addMessage`, `bumpVersion`, `setConflict`, `applyGarmentSpec`, `refitSleeve`, `applySizes`), unit-tested without a live DB.
- `lib/db/pattern.ts` is the only layer touching Prisma for patterns. Every function is scoped to `(patternId, userId)` and returns `null`/`false` — never throws, never leaks whether the row exists — when the pattern is missing or not owned; routes turn that into `patternNotFound()` (404).
- `withPattern(patternId, userId, fn)` runs load→mutate→save in an interactive transaction with a row lock (`SELECT … FOR UPDATE WHERE id = $1 AND userId = $2`), built from the exported primitives `lockPattern`/`savePattern` so `withPatternAndWallet` (below) reuses the same SQL. The transaction timeout is raised to 30s because the AI call runs inside it.
- CRUD: `loadPattern` (ownership-scoped read), `createPattern` (new blank pattern), `listPatternsForUser` (projects `{id, name, garmentType, updatedAt, thumbnailSvg}`; the thumbnail is server-built by `lib/editor/thumbnail.ts`'s `buildThumbnailSvg` from the already-drafted pieces — no redraft, no AI call), `renamePattern`, `deletePattern`. There is no pattern-reset endpoint — delete + create replaces it.
- Every `app/api/*` route is gated by `requireUser()` (`lib/auth/guard.ts`) — 401 without a session. Auth logic is likewise pure/DB-free (`lib/auth/authorize.ts`, `lib/auth/session.ts`); the NextAuth config is `auth.ts` (`trustHost: true` for self-hosted/prod).

### Billing (real; only the gateway is mocked)

- `Wallet` (1:1 with `User` — credits are an account-level resource, shared across all its patterns) + append-only `Transaction` ledger, same pure-logic + thin-repo split: `lib/billing/wallet.ts` + `lib/db/wallet.ts` (`lockWallet`/`saveWallet`, plus `saveLedger`). Wallets are lazily seeded on first access (`INSERT … ON CONFLICT DO NOTHING` inside `lockWallet`) — no backfill migration was written for the pre-Phase-C mock credits.
- `generate` and `graduate` debit atomically with the pattern mutation via `lib/db/pattern-wallet.ts`'s `withPatternAndWallet(patternId, userId, fn)`: both rows locked in one transaction, **always `Pattern` first, then `Wallet`** — it is the only function ever allowed to hold both locks, which makes cross-lock deadlock structurally impossible — and it returns `null` without ever locking the wallet when the pattern isn't found/owned.
- `lib/api/compose.ts` exports `buildCredits(wallet, now)` (account-level, pattern-independent) and `composeEditorState(patternState, wallet, now)` (built on top of it) — the wire `EditorState` the client sees. `Credits.renewsInDays` derives from the real `Wallet.renewsAt` timestamp.
- Auto-renewal: `scripts/cron-renew.ts` (run via `tsx`, same convention as `prisma/seed.ts`), scheduled by the `cron` Docker Compose service (hourly loop, no external scheduler), resets `balance` to `total` and rolls `renewsAt` forward 30 days from the _scheduled_ renewal time for every past-due wallet — "use it or lose it," no accumulation.
- `POST /api/billing/purchase` simulates instant success (no real gateway). With an optional `patternId` it returns that pattern's full composed `EditorState` (so the editor shows the just-purchased credits without a second fetch); without one, `{status: "ok", credits}` (the account-level context the dashboard has). It only adds credits — it has no 402 path.

### API routes

All pattern-mutating routes live under `/api/patterns/[id]/*`, scoped to one pattern and 404'ing via `patternNotFound()`:

- `GET /api/patterns` — the session user's pattern list; `POST /api/patterns` — create a blank one, returns its `id`.
- `GET /api/patterns/[id]` — the composed `EditorState`; `PATCH` renames (body `{name}`); `DELETE` deletes (the only way to "reset").
- `POST /api/patterns/[id]/generate` — the core AI flow (below). Debit-then-mutate; insufficient balance → HTTP 402 (no debit, no AI call).
- `POST /api/patterns/[id]/graduate` — same debit-then-mutate + 402 pattern.
- `POST /api/patterns/[id]/conflict/resolve` — free, no debit (see conflicts below).
- `GET /api/account/summary` — account-level, not pattern-scoped: `{credits, recentUsage}` (last 3 debit-type ledger rows via `lib/db/account.ts`'s `getRecentUsage`) backing the dashboard's summary cards.
- `GET /api/account/ledger`, `PATCH /api/account/profile`, `POST /api/account/password`, `DELETE /api/account` — back `/settings` (below).
- `/api/size-charts/*` — see Size charts.

### Generation flow (`POST /api/patterns/[id]/generate`)

- Debits `COSTS.adjust` immediately, then `proposeGarment` (`lib/ai.ts`) asks `claude-sonnet-5`, via forced tool-use, for `{ decision: "apply" | "decline" | "ask", spec, questions?, declineReason?, assistantMessage }`.
- **Trust boundary:** the returned `spec` is never trusted as-is — `validateSpec` (`lib/draft/garment.ts`) re-checks every enum and clamps every numeric field before use; `questions` go through `validateQuestions` the same way. The AI never emits SVG or pixel coordinates — only a `GarmentSpec`.
- `apply` → `applyGarmentSpec` → `draftGarment(spec, baseMeasurements, t)` recomputes `pieces`/`viewBox`/`baseMeasurements` from scratch and bumps the version.
- `decline`, and any API/parse error, refunds the credit.
- `ask` (underspecified request) → 1–4 single-choice `questions` attached to the AI chat message (`ChatMessage.questions`), credit refunded, response `status: "clarify"` — no draft, no version bump. The client renders `ClarifyCard`; answering calls `sendMessage(phrase, { answering: true })` with the picks as natural-language text, and the `answering` flag (threaded to `proposeGarment`, enforced by a server-side guard) prevents the AI from asking again.

### Seam-conflict detection (live, apply-with-warning)

- The AI-settable, `validateSpec`-clamped `style.armholeDeepenCm` (0–6 cm) deepens **only** the body's armhole, while the sleeve cap is sized from the **base** (un-adjusted) armhole (`draftAll` returns `armholeLenCm` for the body and `sleeveArmholeCm` for the sleeve) — so the two seams diverge by the adjustment.
- `applyGarmentSpec` runs `seamCheck` (`lib/draft/garment.ts`) on those two lengths; when the diff exceeds 1 cm, `detectConflict` attaches a real `ConflictInfo` (actual `diffCm`, dashed markers over the body/sleeve armhole). The generation still applies, bumps the version, and debits; the chat message gets `tone: "conflict"` and the route responds `status: "conflict"`.
- The client mirrors `state.conflict` into the existing `ConflictInfoCard`/markers; Export is blocked while a conflict is active.
- `POST /api/patterns/[id]/conflict/resolve`: "fix" calls `refitSleeve` for free — it sets the internal `style.sleeveRefit` and re-drafts so the cap uses the adjusted armhole (seams match, conflict clears); "ignore" just clears the warning, leaving the pieces divergent. `sleeveRefit` is deliberately **not** accepted by `validateSpec`, so the AI can never fake a refit.

### Drafting engine (`lib/draft/*`)

- **Pieces are drafted from measurements, not deltas.** `lib/measurements.ts` defines `Measurements` (bust, waist, shoulder, … — `shoulder` is the half-width from the body's center line to the shoulder tip, not the full shoulder seam) plus the legacy `SIZE_TABLE` (female)/`SIZE_TABLE_MALE` (male) tables, now used only as seed data for the two system size charts and the pre-generation bootstrap default.
- `resolveMeasurements(base, overrides)` applies chat-driven `measurementOverrides` onto an already-resolved base row (clamped to `MEASUREMENT_RANGES`); the base row comes from the pattern's frozen `sizeTable` snapshot (see Size charts). No size/gender table lookup happens here anymore.
- `GarmentType` = `"blouse" | "dress" | "skirt" | "tshirt"`. A `GarmentSpec` (`type` + `gender` (`"female" | "male"`) + `measurementOverrides` + `style`) plus a resolved `Measurements` row flow into `draftGarment(spec, baseMeasurements, t)` (`lib/draft/garment.ts`), which calls the per-block drafters (`body.ts`, `sleeve.ts`, `skirt.ts`, shared helpers in `core.ts`) to build each `Piece`'s outline/guide/grainline/dart in cm and lay them into one computed `viewBox` (`autoLayout`). The engine doesn't know `SizeLabel` — it's a plain per-chart `string` now, not the old fixed `"PP"|"P"|"M"|"G"|"GG"` union.
- `tshirt` is a knit archetype (round neck, no darts, short sleeves by default) drafted through the same `body`/`sleeve` drafters, with `knit: true` in `BlockOpts` and those style defaults pre-filled in `draftGarment`.
- Outlines: `outlinePath` (`core.ts`) takes a flat cm point list plus drafter-supplied `curvedSpans: [number, number][]` — only marked ranges (neckline, armhole, sleeve cap) get Catmull-Rom-derived Bézier curves with tangents locked at span edges; every other edge is a straight `L`. No global smoothing pass, no `curvedIds` — curvature is per-edge-range, opt-in per drafter.
- Each drafter attaches its own `piece.detailRows` (label/value pairs) — the old fixed `PieceDetails` shape is gone.

### Size charts (`/size-charts`)

Real, per-account, and they drive generation/grading.

- `SizeChart` (Prisma, JSON-blob-per-row like `Pattern`/`Wallet`) holds `SizeChartData`: `name`, `gender`, `bodyType` (descriptive metadata only — never affects drafted geometry, an honest documented limitation), `isSystem`, ordered `sizes: string[]`, `baseSizeIndex`, `baseMeasurements`, a `progressionRule` (cm delta per size step from the base), and per-cell `overrides` that win over the rule. Resolution lives in `lib/sizeCharts/compute.ts` (`resolveSizeChartSize`, `buildSizeTable`).
- Every account lazily gets two seeded `isSystem` charts on first access (`lib/db/sizeChart.ts`'s `ensureSystemSizeCharts`, same lazy-seed precedent as `Wallet`): "Feminino adulto · ABNT" and "Masculino adulto", derived losslessly from the legacy tables by `lib/sizeCharts/seed.ts`'s `buildSystemSizeChartData` (the rule+override reconstruction reproduces the original tables exactly). System charts can be duplicated but not edited or deleted (enforced in the repository layer).
- `User.activeSizeChartId` is the account-level "chart in use."
- **A pattern snapshots its size chart once, at its first-ever generation:** the generate route calls `getSizeChartForGeneration(userId, spec.gender)` (`lib/db/sizeChart.ts` — the active chart if its gender matches the spec being drafted, else the system default for that gender), then `seedPatternSizeSnapshot` (`lib/editor/state.ts`) freezes `sizes`/`baseSize`/a fully resolved `sizeTable: Record<string, Measurements>` onto the pattern. Every later regeneration reuses the frozen snapshot — editing or reassigning the account's active chart never retroactively changes an in-progress pattern (same precedent as the i18n locale snapshot below). A brand-new blank pattern bootstraps from the system female-adult chart via the same `buildSystemSizeChartData`/`buildSizeTable` pair, so `Pattern.sizeTable`/`sizes` are always populated, never optional.
- Screen: `components/size-charts/SizeChartsShell.tsx` + `SizeChartLibrary.tsx` + `SizeChartTable.tsx`, with their own `useSizeChartsStore`. Browse the library; edit a custom chart's base row/progression rule/per-cell overrides/size list; duplicate any chart (system or custom); mark one active (`POST /api/size-charts/[id]/activate`). The Audaces spreadsheet-import block is an inert dashed placeholder on this screen.

### Client state (Zustand)

- **Editor:** one store — `lib/store.ts`'s `useEditorStore` — scoped to a single pattern via `init(patternId)`, threading that id through every server call (`generate`/`graduate`/`resolveConflict`/`purchase`). It mirrors the server's `EditorState` after every mutating call and owns UI-only state (active tab, selected piece, details-panel open, active tool, measure-tool measurements — auto-cleared when the pattern version changes — generation status/step, and paywall open/required/retry). All server calls go through `lib/api-client.ts`; components never call `fetch` directly. `sendMessage` optimistically appends the user's chat message before the request resolves; `cancelGeneration` rolls that optimistic message back and refunds the cost client-side (there's no server-side cancel).
- **The paywall is action-agnostic:** any store action that can fail on insufficient credits (`sendMessage`, `graduateSizes`) stashes its own retry closure in `paywall.retry`; `purchase()` applies the mock purchase, closes the modal, and invokes whatever `retry` was stashed — "buy credits then automatically finish what I was doing" works for any future paid action that follows the same set-paywall-state-with-a-retry-thunk pattern.
- **Dashboard:** its own separate store (`lib/dashboardStore.ts`'s `useDashboardStore`) — same fetch-through-`api-client`-into-Zustand shape, but owning a pattern _list_ (plus account credits/recent-usage and client-side search/type-filter) instead of one pattern's state. The two stores never share instances, matching the two screens' different lifetimes.

### Screens

- **The editor opens on a blank pattern.** A new pattern starts with no pieces, empty chat, name "Novo molde", and `version: 0` — the user always generates from scratch. The first AI generation creates the garment's (variable) piece set — e.g. front/back/sleeve for a blouse, plus a skirt piece for a dress. `CanvasArea` shows a "Molde em branco" empty state and hides the floating toolbar while `pieces` is empty; `sendMessage` auto-selects the first piece once a generation produces one.
- **Canvas overlays are mutually exclusive:** `PieceDetailsPanel` and `ConflictInfoCard` share the top-right slot over the canvas in `CanvasArea.tsx`, and a conflict always takes the slot. Fold new overlays into that same exclusivity check rather than adding a third independent floating panel.
- **Dashboard is the app's home (`/`).** `app/page.tsx` is a thin server component (session check only) rendering `DashboardShell`, which composes `DashboardTopbar` (account-menu credit pill), `Sidebar` ("Meus moldes" active; "Medidas e grades" navigates to `/size-charts`; "Bases do ateliê" disabled with an "em breve" badge), `PatternGrid` (search + garment-type filter, reusing the `garmentType.*` catalog keys per the EN-enum-lookup convention), and `CreditsCard`/`RecentUsageCard` (backed by `GET /api/account/summary`). The dashed "Importar .dxf · Audaces" card is inert and badged "em breve". Pattern cards deliberately show **no state badge** (the design's rascunho/graduado/exportado): export never touches the server, so "exportado" can't be derived honestly, and a partial 2-state badge wasn't worth shipping — a deliberate simplification, not a bug. Rename (`window.prompt`, deliberately minimal) and delete (shared `components/shared/ConfirmModal.tsx`) live **only** in the card "⋯" menu (`PatternCard.tsx`) via `useDashboardStore`; the editor has no delete affordance — its "← Voltar" button just navigates back to `/`.
- **`/settings` is one unified page, not a modal**, reached only from the dashboard's account-menu — its three items ("Créditos e uso", "Plano e cobrança", "Preferências", in `DashboardTopbar.tsx`) deep-link via a `?section=` query param (`profile` default, plus `password`/`danger`/`usage`/`plan`). No dashboard-sidebar entry; the page has its own internal `SettingsSidebar` (5 items, same 186px-column idiom as the dashboard's `Sidebar.tsx`). The section list (`SettingsSection`, `SETTINGS_SECTIONS`) lives in plain `lib/settings/sections.ts`, **outside** the `"use client"` component — the Server Component page needs it as plain data to validate the query param, and importing a non-component value from a client module into server code becomes a broken client reference at runtime. `app/settings/page.tsx` is the usual thin server component: it loads the user (`getUserById`, `lib/db/users.ts`), `Wallet` (`loadWallet`), and the last 30 ledger entries (`getLedgerHistory`, `lib/db/account.ts` — like `getRecentUsage` but without the debit-only filter) — no API round-trip for first render — and renders `SettingsShell`, which shows exactly one of five sections:
  - `ProfileSection` — name editable; email deliberately **read-only** (it's the Auth.js Credentials login identifier; editing it is out of scope).
  - `PasswordSection` — current/new/confirm; client-side confirm-mismatch gating plus a server-verified current-password check.
  - `DangerZoneSection` — account deletion gated by both a client-side "type your email to confirm" match **and** a server-verified password (stronger than the single-pattern `ConfirmModal`, since one irreversible `prisma.user.delete` cascades away every pattern, the wallet, and the ledger via the existing `onDelete: Cascade` — no manual cleanup).
  - `UsageSection` — balance/renewal, a "Comprar créditos avulsos" top-up reusing `purchase("topup")` with an optimistic client-side ledger update, and the full transaction history (all ledger types, not just spend).
  - `PlanSection` — the 4 plans from design `5c` as static display cards; only Ateliê is marked "Plano atual" (`lib/billing/wallet.ts`'s `applyPurchase` only ever issues that plan); the other 3 are badged "em breve" rather than faking a plan switch; plus a cost-per-action footer from the `COSTS` constant.

  Backed by `PATCH /api/account/profile`, `POST /api/account/password`, `DELETE /api/account`, and `GET /api/account/ledger` (alongside the existing summary route), all `requireUser()`-gated. The profile/password/deletion validation logic lives in DB-free, dependency-injected `lib/account/settings.ts` (mirroring `lib/auth/authorize.ts`'s `AuthorizeDeps` shape) so it's unit-testable without a live DB. Password changes do **not** invalidate the current JWT session — a deliberate choice for this single-device personal-use MVP, not an oversight.

### i18n (`next-intl`, single-locale pt-BR, no routing)

- One locale, no `[locale]` segment or middleware: `app/layout.tsx` calls `getMessages()` and wraps the tree in `NextIntlClientProvider` with the single catalog `messages/pt-BR.json`, keyed **per component namespace** (`Footer`, `Topbar`, `ChatPanel`, `TechSheetTab`, `Login`, …). Every component reads its own namespace via `useTranslations("ComponentName")` — all static UI chrome (headers, labels, empty states, "em breve" notes) comes from the catalog, never hardcoded pt-BR JSX. (All display-text screens are client components today; a server component would use `await getTranslations(...)`, but none needs it yet.) This is deliberately **not** a translation system — it's the seam that lets one land later without another sweep through every component.
- `lib/` stays framework-free (no `next-intl` import), so functions that produce display text take an injected resolver (shipped as "i18n Fase 2"): `Translate` (`lib/i18n/translate.ts`, `(key, values?) => string`) — next-intl's `t` (from `getTranslations` in route handlers, `useTranslations` in components) is structurally assignable to it and passed through `draftGarment`/`draftPiecesCm`/`buildExportModel`/`planCutLayout`/`applyGarmentSpec`/`refitSleeve`. Drafter strings (`piece.detailRows`/`name`) and `detectConflict`'s title/description/suggestion live in the `PatternData` namespace (plus `GeneratingOverlay.steps` and `TechSheetTab.garmentType`/`gender`). Drafters emit the **resolved string**, not the key, so the persisted blob shape is unchanged — no reset migration was needed.
- **Known limitation:** a persisted `Pattern` holds a draft-time-locale snapshot — a future locale switch won't retranslate an already-drafted pattern's piece labels/conflict text until it's re-drafted (next generation, "Corrigir manga", or graduation).
- The AI's `assistantMessage`/chat text is model-produced, outside the catalogs entirely: `lib/ai.ts`'s system prompt (written in English) instructs the model to mirror the language of the user's own message in `assistantMessage` and clarifying-question labels/options — so an AI chat reply may not be pt-BR even though the rest of the UI is.
- **Known asymmetry, not yet reconciled:** canned strings that don't go through the model stay fixed pt-BR — the empty-`assistantMessage` fallbacks and credit-cost chip label in the generate route, the sleeve-refit chat message + chip label in the conflict/resolve route, and `exportPattern`'s failure message.

### Export (client-side transform, no server call)

- `lib/export/` turns the drafted pattern into a downloadable file with no API route, credit cost, or state mutation. `buildExportModel(pattern, t)` (`lib/export/model.ts`) re-drafts the pieces in exact cm via `draftPiecesCm(spec, baseMeasurements, t)` (exposed from `lib/draft/garment.ts`) — it never reverses the store's px back to cm, so it doesn't inherit `PX()` rounding. The `ExportModel` is format-agnostic: per-piece outlines as typed cm segments (`line`/`cubic`, Béziers preserved) plus grainline/dart/name/qty and a `seamAllowanceCm` annotation. The exported geometry is the **net sewing line** — seam allowance is not offset into it.
- `exportPattern(pattern, format, t, onError?)` (`lib/export/index.ts`) builds the model, serializes, and triggers a browser download via `downloadFile` (`lib/export/download.ts`, the only DOM touchpoint), dispatching all five formats (`svg`/`dxf`/`dxf-aama`/`pdf-a4`/`pdf-single`) via an exhaustive `switch`/`never`. The `Footer`'s "Exportar" menu is disabled when a conflict is active, the pattern is blank, or there is no `spec`.
- `toSvg` (`svg.ts`) — 1:1 SVG in mm (`MM = 10`, so a 10 cm edge is 100 units; `width`/`height` in `mm`).
- `toDxf` (`dxf.ts`) — the **generic geometry-only DXF**: net line, `$INSUNITS=4` mm, 1:1, Y flipped to DXF's up-axis; hand-written ASCII `LWPOLYLINE`/`LINE`/`TEXT` on named layers `CONTORNO`/`INTERNO`/`GRAINLINE`/`TEXTO`; cubics flattened by adaptive De Casteljau (`flattenCubic`, 0.2 mm tolerance).
- `toDxfAama` (`dxf-aama.ts`) — a **"compatível AAMA/ASTM D6673" subset**: numbered layers with fixed semantics (`1` piece boundary + piece system text, `7` grainline, `8` internal/dart lines), each piece wrapped in a `BLOCK`/`INSERT`, header R13 (`AC1012`), classic `POLYLINE`/`VERTEX`/`SEQEND` (not R14's `LWPOLYLINE`) for wider Audaces/Gerber compatibility; reuses `flattenOutlineCm`/`TOL_CM` from `toDxf`. It is an **honest subset**: notches (layer 4), drill holes (13), and a separate sew line (14) are not emitted (MoldAI doesn't model them yet) and the net line lands on layer 1 — the menu item is tagged "beta" with those gaps noted inline. The strict-complete AAMA/ASTM (structured system text, block records, derived notches/sew line) remains a later "Fase 2.5".
- `toPdf` (`pdf.ts`) — a 1:1 PDF in two modes: `pdf-a4` (tiled A4 with glue overlap, page numbering, and a 10 cm calibration ruler on the first sheet) and `pdf-single` (one page the exact size of the pattern sheet, for plotter/large-format). It reuses `flattenOutlineCm` and loads `pdf-lib` (the feature's only added runtime dependency) via a dynamic `import()` inside `toPdf`, code-splitting it out of the main bundle — `toPdf` is `async` and the facade's pdf cases are fire-and-forget.
- The cm-accurate model is also reused **on-screen**: `buildPathD` (`lib/export/model.ts`) is the shared outline→SVG-`d` builder for both `toSvg` and the React previews, and `planCutLayout` (`lib/export/cutplan.ts`) reuses `buildExportModel` to compute a real (first-fit, not optimal) cut-plan nesting — expanding each piece by its cut quantity and shelf-packing the copies into a selectable fabric-width strip (grain locked, no rotation), returning positioned copies + consumed length + efficiency. This backs the data-driven `CutPlanTab` (fabric-width presets `FABRIC_WIDTHS_CM`, consumption/efficiency metrics, an SVG nesting preview; manual/optimized nesting "em breve") and `TechSheetTab` (per-piece dimensions from the same model plus a garment summary header).
