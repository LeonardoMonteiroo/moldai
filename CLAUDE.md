## Conventions

> Every rule below is operative. The evidence behind each — the renames they cost, the bugs that produced them, the shadcn items considered and skipped: [`docs/decisions.md`](docs/decisions.md).

- **Commits:** always English, [Conventional Commits](https://www.conventionalcommits.org/) — `type(scope): summary` (e.g. `feat(i18n): add pt-BR catalog`). Types: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `ci`, `style`.
- **Language boundary:** code identifiers, wire keys, enum values, Prisma models/columns, and routes are **English**; UI display text is **pt-BR**; the AI's chat replies mirror the user's own language. Full-page screen routes are English, with `/planos` the one deliberate marketing exception.
- **Translate domain terms from the pt-BR design doc, don't transliterate them:** "grades" → `SizeChart` (not `Grade`), "molde" → `Pattern` (not `Molde`). Both shipped transliterated first and each cost a repo-wide rename sweep plus a migration. **Get it right up front** — and note the expensive kind of change is a _wire-shape_ change, not an identifier rename: the earlier PT→EN rename of the persisted `EditorState`'s keys/values wiped every persisted pattern blob.
- **UI labels come from catalog lookups keyed by the EN enum value** — e.g. `t("garmentType." + spec.type)` — never a hand-written `Record<Enum, string>` label map.
- **The core flow has to be audible, not just visible.** `ChatPanel`'s thread is `role="log"` + `aria-live="polite"` (`log`, not a bare `aria-live`, so only the new turn is read rather than the whole history). **`GeneratingOverlay` is `role="status"` and the _single_ live region for progress** — `ChatPanel` renders the same step text and is deliberately left silent, or every step would be announced twice. Each screen's loading state is `role="status"` and its load error `role="alert"`.
- **Surface feature limitations on-screen, never silently.** A scope boundary, unsupported case, or mock standing in for the real thing must be explicit where the user meets it (inline note, disabled control with a reason, badge) rather than failing, no-op'ing, or pretending completeness. Mark planned capabilities **"em breve"** so they're distinguishable from hard limitations, and **prefer showing an option disabled+badged over hiding it**. Anchors: `Proof3DTab.notSupportedForTrousers`; `Footer.formatPdfLayeredNote`; the AAMA/ASTM DXF export tagged "beta" with its remaining gap noted inline.
- **Design tokens live in `app/globals.css`** as Tailwind v4 `@theme` variables — this project has **no `tailwind.config.ts`**. Fonts (Bricolage Grotesque for display, Archivo for UI/body) load via `next/font/google` in `app/layout.tsx`. Extend the `@theme` block; never hardcode hex values in components. One token deliberately diverges from the handoff: **`--color-muted` was darkened to `#6e6b60`** because the original failed WCAG AA on every ground it is used against.
- **shadcn/ui is installed, but the MoldAI tokens stay the source of truth.**
  - **Never run `shadcn init`, `shadcn apply <preset>`, or `init --preset`** — each overwrites the `@theme` block and components, wiping the alias layer. `components.json` is hand-written.
  - shadcn's semantic names exist only as a **second `@theme inline` block aliasing the MoldAI tokens** — never give one a literal value. **`--color-border` and `--color-muted` are deliberately not aliased**: shadcn means a _surface_ by "muted" where this repo means _text_, so a ported component's `bg-muted` becomes `bg-surface-alt` while `text-muted-foreground` maps through as-is.
  - The app is **light-only**: `@custom-variant dark (&:is(.dark *))` keeps shadcn's `dark:` classes inert. Without it Tailwind v4 fires them on `prefers-color-scheme` and a dark-OS visitor gets half-dark controls on a light page.
  - **Every screen consumes these primitives — raw `<button>` is down to 9 deliberate exceptions, every one a clickable _region_ or an ARIA-role-bearing option rather than a control** (the pattern thumbnail, the two paywall plan cards, the multi-line size-chart rows, `ImportSizeChartDialog`'s dashed trigger card, and `OnboardingShell`'s four). A new plain `<button>` needs to clear that bar or it should be a `Button`.
  - **Tune a primitive in `components/ui/`, never with per-call-site `className` overrides.** That is where the extra `Button` sizes/variants (`chrome`, `accent`, `soft`, `destructiveOutline`) and `Badge`'s `size="chip"`/`soon` live.
  - **The chat stream is `bubble` + `marker`,** whose variants are the design's own: `default` (olive, the user), `paper` (the AI), `notice` (amber — a seam conflict, failed generation, or size-chart substitution; deliberately **not** `destructive`, the red alert token), `surface` (white, for a bubble holding controls). `ChatMessage.tone` keeps `"notice"` and `"conflict"` distinct in the data model because an informational caveat is not a seam conflict.
  - **`ScrollArea` carries two local additions, both forced by Radix:** `viewportRef` (the scrolling element is the viewport, not the Root) and `fill` (Radix's inline `display:table` box has no definite height and collapses a `flex-1` child). `PatternGrid` deliberately does **not** use `fill`. Its thumb is `bg-muted` rather than shadcn's `bg-border` — a draggable thumb owes WCAG 1.4.11's 3:1, and `--color-border` reads 1.26:1 on paper.
  - **After any `shadcn add`:** review the `app/globals.css` diff (`cssVariables: true` lets the CLI inject into it) and run `npm run format`. `components.json` carries **no `registries` map on purpose** — `@shadcn` is built-in and hand-writing its URL would shadow it with a broken one; pass `registries: ["@shadcn"]` to the MCP tools instead.
- **Type comes from the named scale, never `text-[Npx]`.** `app/globals.css` defines 8 steps as `--text-*` tokens — `text-tick` (10.5px) · `text-meta` (11.5) · `text-ui` (12.5, the default UI size) · `text-control` (13.5, buttons/inputs/tabs) · `text-body` (16) · `text-title` (21) · `text-display` (26) · `text-hero` (44, `LandingHero` its only user). Uppercase labels take `tracking-eyebrow`; the wordmark's tightening is `tracking-wordmark` and the landing hero's is `tracking-hero`, each named after its only user. Body text is `font-normal` — `font-semibold` had spread to 85 call sites and stopped meaning emphasis. **The sweep is finished and staying at zero is the rule:** `app/` and `components/` hold no `text-[Npx]` and no bracketed tracking, and **the shadcn primitives carry no stock Tailwind size either** (`text-sm`/`xs`/`base`/`lg` → `text-control`/`text-ui`/`text-meta`/`text-body`), because a 14px shadcn default is out of scale against a 12.5px UI. **A glyph used as an icon is sized as an icon** (lucide + `size-*`, or `EmptyMedia`), never priced on the type scale.
- **Every full-page screen renders through `components/shared/AppShell.tsx`**, with one exception: `/login`, `/signup`, `/verify` and `/onboarding` are centered-card screens with no header, rendering their own `Wordmark`. `AppShell` owns the page frame and builds `PageHeader` itself from plain data props, so a screen cannot hand-roll a header. Three `PageHeader` props are optional, all three because of the dashboard: `backHref` (it **is** `/`), `title` (the sidebar already marks the section), and `credits` (nullable because the balance arrives after first paint — the bar is simply absent until it lands rather than flickering in; if the summary fetch fails it stays null for good, and the content region's error message is what keeps that from being silent). **There is no global nav sidebar** — `sidebar` is whatever column the screen owns, and `AppShell` renders it bare, so **a new sidebar-bearing screen must set the 186px width itself**. The editor is the one screen keeping a full-screen loading early-return, because the header's title _is_ the pattern name.
- **A display name that reaches a layout needs a cap _and_ a truncation.** `MAX_PATTERN_NAME_LENGTH` (`lib/types.ts`) is enforced by the API and reused as the rename dialog's `maxLength`, so the field stops you before the round trip does. Both `PageHeader`'s title and `PatternCard`'s name `truncate` with **`min-w-0` on the flex column** — without it there is nothing for `truncate` to shrink against and the overflow just shoves its siblings.
- **A control must not rewrite what you typed.** `MeasurementCell` holds in-progress text locally and commits only on blur/Enter, only when it parses and is in range; out-of-range gets `aria-invalid` plus a message naming the accepted range (lifted to the table — a 56px column has no room), and Escape restores. Displaying clamped output while writing every keystroke back corrupted the input outright. The progression-rule input is deliberately untouched: it isn't clamped on display, so it has no feedback loop, and `0` is a meaningful rule value.
- **Don't add abstractions beyond what's needed** — `/settings` and `/pattern/[id]/versions` deliberately have no Zustand store: no cross-component shared state, and section choice lives in the URL.
- **`.claude/hooks/check-conventions.mjs` is not a complete audit — a manual pass still matters.** Its hardcoded-pt-BR (CHECK 1) and hex-color (CHECK 2) checks scan `.tsx` **and `.ts`** (each with a `lib/` exemption list for modules baking text/color into an exported _file_ rather than the UI), CHECK 3 catches direct `fetch(`, and its i18n key-existence check (CHECK 4) **matches only a literal `t("…")` first argument** — it cannot evaluate a template-built key. The wire-error-codes sweep is the standing lesson: three successive audit passes each found something the previous one missed, because no single grep shape sees a backtick template, a label opening on a digit, or a string with no accented character in it.
- **Component tests are the `dom` vitest project** — jsdom + RTL, configured in `vitest.workspace.ts` as a **second project** so the pure-logic `node` suite never loads the DOM setup file. `vitest.setup.ts` installs the jest-dom matchers, RTL auto-cleanup, and the browser APIs jsdom lacks that Radix calls (`ResizeObserver`, pointer capture, `scrollIntoView`, `matchMedia`) — **a Radix component that will not open in a test is almost always a missing one of those, not a broken assertion.**
  - Render through `renderWithIntl` (`components/test-utils.tsx`), which wraps the tree in the **real** `messages/pt-BR.json`. **But next-intl does not throw on a missing key** — it renders the literal key path, logs `IntlError: MISSING_MESSAGE`, and **the test still passes** (verified empirically). An assertion matching a substring, a regex, or the key name is therefore **vacuous**. Catalog-text assertions must compare against the exact resolved `ptBR` value.
  - **Assert against the exported `ptBR` catalog object, never a pasted pt-BR literal** — the no-hardcoded-display-text rule applies to tests, and it makes a copy change a one-place edit. That governs _catalog text_, not _test data_: arbitrary strings passed in as fixture props are fine as plain literals.
- **A `vi.mock(...)` call must use the exact specifier the subject module itself imports** — never assume `@/...` and a relative path to the same file are interchangeable. If the subject imports `./prisma` and the test mocks `"@/lib/db/prisma"`, both must independently resolve to the same absolute path, and **if that resolution is ever wrong the mismatch is silent**: the mock never intercepts, the real dependency runs, and the test's own assertions report zero calls instead of an error. `lib/db/*.test.ts` all mock `"./prisma"`, matching their subjects exactly; `lib/db/aliasResolution.test.ts` is a standing regression guard pinning the alias-vs-relative collapse.

## Commands

```bash
npm run dev      # start dev server (Turbopack) at http://localhost:3000
npm run build    # production build (also runs the TypeScript check)
npm run lint     # eslint
npm test         # vitest run — two projects (see vitest.workspace.ts)
                 #   node: lib/**/*.test.{ts,tsx} + app/**/*.test.{ts,tsx}  (pure logic, no DOM)
                 #   dom:  components/**/*.test.{ts,tsx}                    (jsdom + React Testing Library)
                 # scope one: npx vitest run --project dom
npm run db:up          # local Postgres + Redis (host ports 5433 / 6380)
npm run db:migrate     # apply Prisma migrations
npm run docker:up     # app + Postgres in Docker (dev, hot reload) at http://localhost:3000
npm run docker:prod   # the production image (next start) + Postgres
npm run smoke:prod    # brings up the prod stack and does a REAL login (catches regressions like UntrustedHost)
npm run smoke         # just the HTTP login checker, against a server already running (SMOKE_URL)
```

Also in `package.json`: `test:watch`, `typecheck`, `format`/`format:check`, `cron:renew`. **There is no seed script** — a dev account is created the same way a production one is, through `/signup`, then confirmed via the link in Mailpit's inbox at `:8025` (dev stack only). `smoke`/`smoke:prod` therefore need `SMOKE_EMAIL`/`SMOKE_PASSWORD` pointed at an account created that way.

**Docker vs host:** inside the container the app reaches Postgres at `db:5432` and Redis at `redis:6379`; on the host (dev stack only) they are `localhost:5433` and `localhost:6380`. Secrets come in via `env_file` at runtime — **never baked into the image** — and the npm docker scripts also pass `.env.local` as `--env-file`, since Compose's own `${VAR}` interpolation reads a project-level env file, not each service's `env_file:`. `.env.example` documents every variable.

**Compose services.** `cron` runs the hourly wallet-renewal loop in both stacks; **`docker-compose.prod.yml` overrides it to build the `runner` target**, because the base `dev` target carries no application code (it's bind-mounted at runtime), so on an image-only deploy host the loop found nothing to run. It also gets `restart: unless-stopped` there and its own entrypoint that skips `prisma migrate deploy`, so it no longer races the app container's migration on every stack start. `app` carries a `healthcheck` (`GET /api/health`) — `restart:` alone only reacts to the process exiting, not to one that's up but wedged. `redis` backs rate limiting in both stacks. `docker-compose.override.yml` adds a dev-only **Mailpit** (SMTP 1025, inbox at :8025); Compose auto-merges it for a bare `docker compose up` and ignores it for the explicit two-file prod stack, **so production never gets Mailpit.**

**`db`/`redis` publish to the host only in the dev stack.** `POSTGRES_PASSWORD`/`REDIS_PASSWORD` have no default (`${VAR:?...}`), so `docker compose up` fails loudly rather than letting the committed dev defaults reach a real deploy. `docker-compose.prod.yml` additionally resets both services' `ports:` to nothing: **Docker's published ports bind `0.0.0.0` and its iptables `DOCKER` chain bypasses `ufw`, so a host-published db/redis on a VPS is reachable from the internet regardless of any firewall rule** — an unauthenticated Redis in particular is both a `FLUSHALL`-away rate-limiter kill switch (`consume()` fails open) and, via `CONFIG SET dir/dbfilename`, a known RCE primitive. Production reaches both exclusively over the compose network.

**Two dev-stack traps, both bind-mount-related and neither an app bug:**

1. Turbopack's watcher misses edits through the Windows bind mount and the HMR socket never handshakes — `docker restart moldai-app` after editing, or run `npm run dev` on the host instead.
2. **`POST /api/patterns/[id]/conflict/resolve` answers 404 in the Docker dev stack**, so the seam-conflict buttons appear broken there. Measured: its depth-1 siblings and a depth-2 route with no dynamic segment all answer 401, so the guard is reached; only the route two static segments below a dynamic one — whose intermediate `conflict/` directory holds no `route.ts` — 404s. The same request answers 401 against `next dev` on the host, and `npm run build` lists the route. **Verify anything touching it on the host, not in the container.** (Cause unconfirmed; presumably Turbopack's route discovery over the mount.)

Also: the container's `node_modules` and `.next` are anonymous volumes, so `--renew-anon-volumes` against a stale image resets dependencies to whatever that image baked — **rebuild the image first** (`docker compose up -d --build app`), then renew, or the app boots unable to resolve packages added since.

## What this is

MoldAI is an AI pattern-making product for clothing: chat with an AI to generate/adjust 2D sewing patterns, grade sizes, and export to Audaces/Molde.me/plotter/PDF. This repo is a Next.js app with a real backend — the "real backend" roadmap (Phase A auth → B persistence → C billing) is fully shipped:

- **Auth:** Auth.js v5 (Credentials + JWT), users in Postgres via Prisma. Self-service sign-up at `/signup` creates the account and mails a verification link; it does **not** sign the visitor in. `authorizeUser` returns `AuthorizeResult` — `{ok:true,user}` or `{ok:false,reason:"invalid"|"unverified"|"rate_limited"}` — and `auth.ts` maps `invalid` to Auth.js's generic `null` and the other two to `CredentialsSignin` subclasses carrying `code: "unverified_email"` / `"rate_limited"`, so `/login` distinguishes them. Verification tokens are sha-256 digests of 32 random bytes, 24 h, single use, newest-only (`lib/auth/verification.ts` pure + `lib/db/verification.ts` repo; migration `20260820120000_add_email_verification`, additive, backfills every existing user as verified). Mail goes through `lib/mail/` (`nodemailer`); with `SMTP_HOST` unset it logs the link outside production and throws (`mail_unavailable`) in production — never a silent drop. **Verified live** against the dev stack (real Postgres + Redis + Mailpit), not just unit-tested: the migration applied via `prisma migrate deploy`, and a pre-existing account logged in through the full credentials flow afterwards — which is what proves the backfill's grandfather clause. Sign-up → Mailpit → confirm → login works end to end; the mailed subject renders from the catalog (so `getTranslations` inside a route handler is exercised, which no unit test covers); a login before confirming returns `unverified_email` rather than a bad-password error; a consumed token is rejected on reuse; and with the `login_email` bucket exhausted the correct password is still throttled, while stopping Redis lets it through with `[rate-limit] … failing open` — the documented trade-off, observed.
- **Chat:** a real Anthropic API call (`claude-sonnet-5`) interprets the user's request and returns a `GarmentSpec` (garment type + measurement overrides + style); the server validates/clamps that spec and drafts the pattern pieces from it.
- **Patterns:** persisted per account, many per account (the dashboard's list).
- **Billing:** a real per-account `Wallet` + append-only `Transaction` ledger, shared across the account's patterns. The gateway is **Stripe** (#206), behind `PAYMENT_PROVIDER=stripe`; the default is still a **mock** that simulates instant success instead of charging a card, and no live Stripe account has ever been exercised from this repo.

Requires `ANTHROPIC_API_KEY`, `DATABASE_URL`, and `AUTH_SECRET` in `.env.local`.

## Architecture

### Data layer: pure logic + thin repositories

- `Pattern` (Prisma) has its own cuid `id` with `userId` as a plain indexed foreign key — many patterns per account. Each row holds a `PatternState` JSON blob (pattern, chat, active conflict — no credits).
- Editor-state logic is pure and DB-free in `lib/editor/state.ts` (`seedPatternState`, `addMessage`, `bumpVersion`, `setConflict`, `applyGarmentSpec`, `refitSleeve`, `applySizes`), unit-tested without a live DB.
- `lib/db/pattern.ts` is the only layer touching Prisma for patterns. Every function is scoped to `(patternId, userId)` and returns `null`/`false` — never throws, never leaks whether the row exists — when the pattern is missing or not owned; routes turn that into `patternNotFound()` (404).
- `withPattern(patternId, userId, fn)` runs load→mutate→save in an interactive transaction with a row lock (`SELECT … FOR UPDATE WHERE id = $1 AND userId = $2`), built from the exported primitives `lockPattern`/`savePattern` so `withPatternAndWallet` (below) reuses the same SQL. The transaction timeout is raised to 30s because the AI call runs inside it.
- CRUD: `loadPattern` (ownership-scoped read), `createPattern` (new blank pattern), `listPatternsForUser` (projects `{id, name, garmentType, updatedAt, thumbnailSvg}`; the thumbnail is server-built by `lib/editor/thumbnail.ts`'s `buildThumbnailSvg` from the already-drafted pieces — no redraft, no AI call), `renamePattern`, `deletePattern`. There is no pattern-reset endpoint — delete + create replaces it.
- Every `app/api/*` route is gated by `requireUser()` (`lib/auth/guard.ts`) — 401 without a session, with the small set of deliberate exceptions listed below (signup, email verification, password reset, `GET /api/health`, and the Stripe webhook — none of which can carry a session). Auth logic is likewise pure/DB-free (`lib/auth/authorize.ts`, `lib/auth/session.ts`); the NextAuth config is `auth.ts` (`trustHost: true` for self-hosted/prod).
- `Pattern` has **no `savedAgo`**. It was persisted pt-BR display text that nothing recomputed — the editor header claimed "salvo agora" indefinitely, including after a reload, a live bug independent of this sweep's scope. The wire carries `updatedAt` instead and the editor renders `relativeTime(t, updatedAt)`. The final shape is not `Pattern` plus a field: `Pattern` (`lib/types.ts`) stayed blob-only, and a new **`PatternRecord extends Pattern { updatedAt: string }`** is the wire shape used by `EditorState.pattern` and the editor store — the existing `SizeChartRecord extends SizeChartData` precedent. That makes an absent `updatedAt` unrepresentable rather than merely unreachable: leave it out and `relativeTime` falls through to render the literal string "Invalid Date" instead of compiling to a value that's simply never missing. `loadPattern` widened to return `{state, updatedAt}`; `lockPattern` deliberately did **not**, because `savePattern` sets `updatedAt = now()` inside the same transaction, so a mutating route's own `now` already _is_ the row's timestamp. No reset migration was needed — old blobs keep an inert `savedAgo` key that nothing reads, the cheap direction of a blob change, unlike `reset_moldes_english` above.

### Rate limiting

> Full rationale — the `REDIS_OPTIONS` cold-start measurement and the per-bucket ordering reasoning: [`docs/decisions.md`](docs/decisions.md).

Redis-backed fixed window: `consume()` (`lib/rate-limit/consume.ts`) runs one atomic `MULTI` — `INCR` + `EXPIRE … NX` + `TTL` — so the window starts on the first request and expires itself; no sweep job. **The whole policy is the table in `lib/rate-limit/limits.ts`, reproduced here in full so a stale copy is a visible mismatch rather than a silent one:**

```
signup 5/h · signup_email 3/h · login 20/15min · login_email 10/15min
verify 20/h · resend 10/h · resend_email 5/h · resend_attempt 10/15min
create 60/h · password_reset_request 10/h · password_reset_request_email 5/h
password_reset_confirm 20/h · purchase 10/h · purchase_user 10/h
```

- **Every sensitive endpoint gets an IP-keyed bucket AND a second non-spoofable one**, because `x-forwarded-for` is spoofable when the app isn't behind a trusted proxy. **Deployment consequence: behind a reverse proxy, that proxy must overwrite `x-forwarded-for` for the IP limits to mean anything** — Next only fills the header when the client didn't send one.
- **Four buckets are deliberate exceptions to the IP+email pairing:** `verify` and `password_reset_confirm` guard a request carrying no email, only a single-use 256-bit token, so the token _is_ the backstop and a counter would add nothing; `create` and `purchase_user` are keyed on the **account id** rather than the IP, since the caller is already a known account (`create` covers the three authenticated-write creates that had no throttle at all before; `purchase_user` pairs with an IP-keyed `purchase` on a route that had no bucket at all — under the mock provider that meant unlimited free credits in a loop, and under stripe it means creating hosted checkouts that cost against a real third party per request).
- **Bucket ordering within a route is deliberate.** `resend_email` is consumed **after** the credential and cooldown checks, so it counts mails actually attempted per address — a victim can't have their quota burned by someone without their password, and impatient retries inside the cooldown (which send no mail) cost nothing. `password_reset_request*` is consumed **regardless of whether the address exists**, so an attacker can't flood a victim's inbox just because the account is unregistered.
- **The limiter reaches the pure `authorizeUser` through `AuthorizeDeps` (`consume`/`reset`), never an import** — keeping that module DB-free, Redis-free, and testable with fakes.
- **It fails open:** if Redis is unreachable, `consume` logs and allows. A system that locks everyone out when its cache dies is worse than one that briefly loses throttling. Both Docker stacks gate `app` on `redis`'s healthcheck; **the host flow is not automatically covered** — `npm run db:up` brings up Redis for exactly this reason, and skipping it means every `consume()` silently takes the fail-open branch.
- **`REDIS_OPTIONS` (`lib/rate-limit/client.ts`) is a correctness setting, not a preference.** `enableOfflineQueue: false` looked like "fail fast rather than queue forever", but ioredis connects lazily, so a fresh process's first commands were issued before the socket was writeable and rejected outright — which `consume` dutifully turned into fail-open. **Measured against a healthy Redis: both `consume` calls in a new process's very first signup failed open**, so every deploy, restart and scale-out served its first sensitive request unthrottled. It is `true` now; "forever" isn't the alternative, because `maxRetriesPerRequest` bounds the wait and `commandTimeout` (1 s) is a hard per-command ceiling. **`client.test.ts` asserts the three options as a regression guard, because the symptom only ever shows in a real process's first request.**
- **Accepted trade-off:** `login_email` is consumed before the password check and only a _successful_ password clears it — so anyone who knows a victim's email can spend those 10 attempts and soft-lock the account for the rest of the window, and the victim's own correct password can't clear the counter because the throttle returns first. Self-expiring and standard for per-account throttling, but a real property of the system.

### Observability

**`lib/observability/report.ts`'s `reportError(scope, err, context?)` is the one seam between "logged to stdout" and a real error-reporting service** — it wraps `console.error` today, so wiring in a real reporter later is an edit to this one file, not a sweep across every catch block that calls it. Before it existed, the AI generation flow's `catch` at `app/api/patterns/[id]/generate/route.ts` had no error binding at all — an Anthropic 401/429 (a rotated key, a spend cap) was structurally unloggable, the credit was silently refunded, and the operator's stdout held nothing: not the cause, not even a line saying a generation was attempted. It's now called from that catch (with `patternId`/`userId` context), from `app/error.tsx`/`app/global-error.tsx`'s boundaries (replacing a bare `console.error(error)`), and from `scripts/cron-renew.ts`'s failure path. `GET /api/health` (unauthenticated, see API routes below) gives the Docker/Compose healthcheck something to probe — Postgres (`SELECT 1`) is a hard dependency and its failure answers 503; Redis (`PING`) is reported in the body (`redis: "ok" | "unreachable"`) but never fails the check, since the rate limiter already fails open by design rather than treating a Redis blip as the app being down.

**`lib/security/headers.ts`'s `SECURITY_HEADERS` is pure data for one reason: `next.config.ts` is covered by neither vitest project's include globs** (`lib/**`, `app/**`, `components/**`), so the header list has to live somewhere the `node` suite can actually assert against — `next.config.ts` just spreads it over `source: "/(.*)"`. Four ship today (#27): `Strict-Transport-Security` (2 years, `includeSubDomains`), `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff`, alongside `poweredByHeader: false`. **A Content-Security-Policy is deliberately absent, not forgotten** — Next's inline bootstrap script needs a nonce and a naive policy would break the app, so it stays a tracked follow-up on #27; `X-Frame-Options` is the interim clickjacking mitigation for `/login`'s credentials form that CSP's `frame-ancestors` would otherwise supersede.

### Billing (real; only the gateway is mocked)

> Full rationale — the #179 → #193 → #196 → #198 defect chain in detail, each reversal's exact semantics, and the migration backfill reasoning: [`docs/decisions.md`](docs/decisions.md).

- **`Wallet` (1:1 with `User` — credits are account-level, shared across all its patterns) + an append-only `Transaction` ledger**, same pure-logic + thin-repo split: `lib/billing/wallet.ts` + `lib/db/wallet.ts`. Wallets are lazily seeded on first access (`INSERT … ON CONFLICT DO NOTHING` inside `lockWallet`) at the **Free tier** — open sign-up must not grant a paid balance.
- **`lib/billing/plans.ts` is the one exported source for every paid tier's terms** (the `lib/export/formats.ts` leaf-module precedent): `PLAN_CREDITS`/`PLAN_PRICE_CENTS`, `TOPUP_CREDITS`/`TOPUP_PRICE_CENTS`, `CURRENCY`, `formatBRL`, `PaidPlanId`, the trust-boundary narrower `isPaidPlanId`, `isPlanUpgrade(from, to)` (derived from `PLAN_CREDITS`, **no second rank table**), and `PLAN_FEATURES`. Never hardcode a price, credit count or rank anywhere else.
- **Prices are stored in centavos and formatted in exactly one place.** Stripe's `unit_amount` is always the currency's minor unit, so `PLAN_PRICE_CENTS.atelier` is `5900`; the rename from `PLAN_PRICES`/`TOPUP_PRICE` was deliberate rather than a silent rescale, so every call site became a compile error — the safe direction for a money constant changing units by 100×. **`formatBRL(cents)` is the only place a currency symbol or decimal separator appears**, and the catalog carries **no price literal at all** any more (it held `"R$ 0"`/`"R$ 59"`/`"R$ 149"`/`"R$ 399"`, plus `PaywallModal`'s and `UsageSection`'s own copies — each one a number that could disagree with what Stripe charges). Note `Intl` emits a **non-breaking space** between symbol and amount, which is why `components/test-utils.tsx` exports `priceText` for `getByText` matchers (an accessible-name matcher needs the raw string instead — see its comment).
- **Settlement is BRL-only and the app says so on screen.** A Brazil-based Stripe account is in a foreign-exchange-control country, so Adaptive Pricing converts the amount for _presentation_ at checkout while the charge still settles in reais; that account also accepts **only Visa and Mastercard** (no Elo/Amex/Hipercard/Diners), and Pix is invite-only. These are permanent properties, not gaps, so `PlanSection.paymentNote` and `Pricing.paymentNote` state them plainly rather than marking them "em breve".
- **`applyPurchase(wallet, purchase, now)` is the one function every mutation path routes through — mock and gateway alike — so guards belong in it, not in a route.** It takes a discriminated union (`{type:"topup"}` or `{type:"subscribe", plan}`) and can move a wallet to any paid tier. An upgrade's balance becomes `PLAN_CREDITS[plan] + wallet.purchased`, never destroying a prior top-up.
- **Four invariants govern every wallet mutation. Each was a shipped defect, all of the same shape — a reversal or reapplication that did not mirror what it undid or repeated:**
  1. **A renewal never touches `purchased`** — it is a carry-over pool, separate from the plan allowance (`total`). `total` stays the plan allowance only, or it misreports the plan. Because `balance` can legitimately exceed `total`, **every credits-meter bar clamps its fill at 100%**.
  2. **A confirmation never walks the plan down.** `applyPurchase`'s subscribe branch carries a monotonicity guard reusing `isPlanUpgrade` (so a same-tier reapply is refused by the identical check), because a gateway delivers at-least-once and out-of-order. **Only a rank-based guard is achievable, not a chronological one** — the payload carries no ordering signal this app trusts. **A refused plan change never swallows the payment:** the money has settled, so the tier's full credit value folds into `purchased` and the ledger entry keeps `type: "subscribe"`.
  3. **A refund reverses exactly what its entry contributed, decided against the _locked_ wallet.** `reverseRefundedEntry(wallet, entry, refundedExternalId)` is the one pure dispatch for every shape a gateway refund can name: `"topup"` and a _folded_ subscribe share one reversal (`reversePurchasedCredits` — they perform the identical wallet movement, so they must not drift); a subscribe resolves `"reset"` only when it **is** `wallet.planSourceExternalId`, `"folded"` when `entry.planChanged` was false, and `"superseded"` when it moved the plan but a later upgrade has since overwritten it (nothing left to claw back — a zero-amount ledger row records the refund's own idempotency). Two additive columns make those cases distinguishable: **`Wallet.planSourceExternalId`, written once and centrally by `withWalletIdempotent`** (not per-handler, so every future caller gets it free), and **`Transaction.planChanged`**, recording whether `applyPurchase` actually moved the plan.
  4. **`lib/billing/invariants.test.ts` is the standing guard**, not one case per issue. It drives the real pure functions through 200 seeded 60-step walks of credits/debits/refunds/plan changes/renewals in arbitrary order, checking after **every** step: the ledger reproduces the balance; `total === PLAN_CREDITS[plan]`; `purchased` equals the sum of unreversed grants and is never negative; `planSourceExternalId` names an entry that really moved the plan; a confirmation never walks the plan down. **The `purchased` check is computed from what each entry contributed at credit time, never from the outcome the dispatch reports for its reversal** — that is what makes a _misclassified_ reversal fail rather than redefine the check. Verified by reverting each fix in turn and watching the right invariant go red.
- **`withPatternAndWallet(patternId, userId, fn)` (`lib/db/pattern-wallet.ts`) is the only function ever allowed to hold both locks, and it always takes `Pattern` first, then `Wallet`** — which makes cross-lock deadlock structurally impossible. It returns `null` without ever locking the wallet when the pattern isn't found/owned. `generate` and `graduate` debit atomically through it.
- `lib/api/compose.ts` exports `buildCredits(wallet, now)` and `composeEditorState(patternState, wallet, now)` — the wire `EditorState`. `Credits.renewsInDays` derives from the real `Wallet.renewsAt`.
- **Auto-renewal** is `scripts/cron-renew.ts`, scheduled by the `cron` Compose service (hourly, no external scheduler): resets `balance` to `total + purchased` and rolls `renewsAt` forward 30 days from the _scheduled_ time. "Use it or lose it" governs only the plan allowance. **Its past-due query excludes any wallet with a non-null `stripeSubscriptionId`** (#161) — a subscribed wallet is renewed by its own `invoice.paid` webhook, and without the exclusion both would fire, silently doubling credits with no ledger row flagging it. **That column is therefore written inside the same transaction as the first payment's credit** (`withWalletIdempotent`'s optional 4th argument), not best-effort afterwards: a credit that committed without it would leave the wallet in _both_ renewal paths at once, which is the very state the exclusion exists to prevent.
- **A subscription renewal calls `renewWallet`, never `applyPurchase`. This is invariant 1, not a style choice.** A recurring payment leaves the plan unchanged, so routing it through `applyPurchase` means `isPlanUpgrade` is false and the #193 monotonicity guard folds the whole plan allowance into `purchased` — the carry-over pool a renewal must never touch — and `renewWallet`'s own `total + purchased` then compounds it every month, forever. The pre-#206 Asaas webhook did exactly that for every confirmed payment; it was never exercised against a real account, and the split is now structural: `invoice.paid` + `billing_reason: "subscription_create"` → `applyPurchase` (a real plan change), `subscription_cycle` → `renewWallet`.
- **`POST /api/billing/purchase` has two providers.** Mock (the default) simulates instant success and returns the pattern's composed `EditorState` when given a `patternId`, else `{status:"ok", credits}`. Under `PAYMENT_PROVIDER=stripe` it answers `{status:"redirect", url}` (a hosted Checkout Session) and **never touches the wallet** — the webhook does, once payment confirms. Both branches run the same `resolvePurchase` trust check before any provider call, and both now **refuse a downgrade inside the wallet lock** (`plan_not_upgradable`) via `withStripeCustomerId`'s `guard` — the Asaas branch checked only `isPaidPlanId`, so a downgrade created a real charge that the monotonicity guard then folded into `purchased`. **Which plan a subscribe checkout was for round-trips through Stripe `metadata`**, stamped on **both** the session and the subscription (a renewal arrives as an invoice, which carries the _subscription's_ metadata, not the session's), and `parsePurchaseMetadata` **re-validates the embedded plan with `isPaidPlanId`**, so a forged value still cannot name an arbitrary tier. The line item is priced with **inline `price_data` from `lib/billing/plans.ts`, never a Dashboard `Price` object** — a Dashboard amount is a second copy of the price this repo cannot see. **Adaptive Pricing is requested explicitly** rather than inherited from an account setting. _Verified against the mock provider, the SDK's own type declarations and unit tests only — no live Stripe account is reachable from this environment._
- **Every credit is keyed on the Stripe payment-intent id, because that is the only id a refund and its original credit can both name.** In this API version a `Charge` carries nothing but `payment_intent` to identify what it paid for (there is no `charge.invoice`, and a `PaymentIntent` has no `invoice`), so an invoice-keyed credit could never be matched by the `charge.refunded` that reverses it. An invoice does not expose its payment intent inline, hence `resolveInvoicePaymentIntent`'s one `expand: ["payments"]` retrieve. An invoice that yields no payment intent is reported unprocessable rather than credited under a guessed key. **A PARTIAL refund is never applied**: `reverseRefundedEntry` reverses an entry's whole contribution, so it is logged for reconciliation instead of clawing back more than was given back.
- **The webhook's status codes were re-decided for Stripe, not copied from Asaas.** Asaas paused an account's entire webhook queue after 15 consecutive non-2xx responses, so that route answered 200 to everything; Stripe retries with backoff for ~3 days instead, which makes a blanket 200 a way to silently discard a recoverable credit. Now: **400** for a missing/invalid signature (not a Stripe event at all — nothing to retry), **200** for a genuine but permanently unprocessable event (an unhandled type, unreadable ids/metadata), and **500** for a transient failure on our side, so Stripe retries.
- **`type` is validated, and `applyPurchase` is exhaustive.** `isPurchaseType` narrows it (unknown/absent → 400, wallet untouched) and `applyPurchase` `switch`es with a `never` binding, so a new `PurchaseType` member is a compile error rather than a silent subscribe. **The pattern is also resolved before the wallet is touched** — charging first meant a bad `patternId` credited the account and then answered 404.
- **`Wallet` has no `planLabel`.** It stored pt-BR fully derivable from `plan`, which let the label drift from the plan it named. `PageHeader` resolves ``tPlan(`plans.${credits.plan}.name`)`` from the existing catalog instead, which works for all four `PlanId` members rather than just the two `applyPurchase` ever issues.

### API routes

> Full rationale — the six routes that 500'd on a `null` body, and the per-route `parseBody` adoption notes: [`docs/decisions.md`](docs/decisions.md).

**Every route that reads a body does it through `readJsonObject(request)` or `parseBody(request, schema)` (`lib/api/body.ts`) — with exactly one exception, `POST /api/billing/webhook`, which must hash the RAW bytes.** Stripe's authenticity check is an HMAC over the exact body it sent, so parsing and re-serializing (which changes key order and whitespace) would make every real event fail verification; that route reads `request.text()` and hands those bytes to the SDK's `constructEvent`, which parses only _after_ verifying. The parsed payload's own trust boundary is `parseGatewayEvent` (`lib/billing/stripe.ts`), which is why there is no webhook zod schema at all. Otherwise: Both return the parsed value **or the 400 to return**, shaped like `requireUser()` so `if (x instanceof NextResponse) return x;` reads as the guard idiom already in use — and so **a route that forgets the check gets a type error rather than a 500**. The bug they exist for: `null` is valid JSON, so it survived `request.json()` and only threw on the first field read, which in six routes sat outside the try/catch. Three routes had guarded it correctly, with the same explanatory comment copy-pasted into all three — **the actual lesson being to extract the guard at the second occurrence instead of duplicating the comment.**

**`parseBody<T>` also proves the body against a zod schema (`lib/schemas/*`) before the route sees it, answering a bare `bad_body`** rather than a zod issue path (English prose that would leak the schema shape). It does **not** replace a route's own downstream trust boundary: a field stays `z.unknown()` (or `.optional()` — zod v4 treats a bare `z.unknown()` key as required-but-any-value) wherever the route already clamps or narrows it itself. `parseBody` only proves the body is an object carrying the right keys. **`PATCH /api/size-charts/[id]` is a deliberate, permanent exception, still on `readJsonObject`:** it forwards its raw body to `validateSizeChartPatch`, whose drop-or-clamp-never-throw merge semantics a schema would either duplicate or regress into reject-on-invalid.

All pattern-mutating routes live under `/api/patterns/[id]/*`, scoped to one pattern and 404'ing via `patternNotFound()`.

- **`requireUser()` (`lib/auth/guard.ts`) gates every route — 401 without a session — with exactly six deliberate exceptions, none of which can carry one:** `POST /api/signup`, the email-verification and password-reset routes, `GET /api/health`, `POST /api/billing/webhook` (authenticated instead by Stripe's HMAC signature over the raw body), and NextAuth's own handlers.
- `POST /api/signup` — returns `{status:"ok"}` or a machine-readable `SignupErrorCode`. Deliberately at the top level, outside both the `[...nextauth]` catch-all and the uniformly-gated `/api/account/*`. `createUser` returns `null` on the P2002 insert race so a lost race reads as `email_taken`.
- `POST /api/verify-email` (consumes the token, stamps `emailVerified`, **mints no session**) and `POST /api/verify-email/resend` (credential-gated, 60 s cooldown).
- `POST /api/password-reset/request` — **always answers 200 regardless of whether the address exists**; an "ok" body must not double as an account-existence oracle. `POST /api/password-reset/confirm` is IP-keyed only, like `verify`, since the 256-bit token is the real backstop.
- `GET /api/health` — unauthenticated, backs the Compose healthcheck. Postgres (`SELECT 1`) is a hard dependency and its failure answers 503; **Redis (`PING`) is reported but never fails the check**, matching the rate limiter's own fail-open philosophy.
- `GET`/`POST /api/patterns` — list, and create a blank one. With a `{sloperId}` body it copies that base's frozen snapshot into an already-drafted pattern and **costs 0 credits** (local drafting, no Anthropic call — the same reason `conflict/resolve` is free).
- `GET`/`PATCH`/`DELETE /api/patterns/[id]` — the composed `EditorState`, rename, delete. **Delete + create is the only "reset"** — there is no reset endpoint.
- `POST /api/patterns/[id]/generate` — the core AI flow. Debit-then-mutate; insufficient balance → **402, no debit, no AI call**.
- `POST /api/patterns/[id]/graduate` — same shape. **Its precondition is `pieces.length === 0` → `pattern_not_drafted`, not the size list.** The old `sizes.length === 0` guard could never fire, because a blank pattern bootstraps with a full size list — so grading a fresh pattern answered 200, bumped the version, drafted nothing, and **debited the most expensive action in the app** (verified live). UI-unreachable today, but this is the money path. **The route tests had encoded the bug** by using a blank `seedPatternState` as a stand-in for a real pattern; they draft one first now.
- `POST /api/patterns/[id]/conflict/resolve` — free, no debit.
- `GET /api/patterns/[id]/versions` and `.../[versionId]/restore` — see the versions screen under Screens.
- `GET /api/account/summary` — account-level: `{credits, recentUsage}` backing the dashboard cards. Also `/api/account/ledger`, `PATCH /api/account/profile`, `POST /api/account/password`, `DELETE /api/account`, `POST /api/account/onboarding`, `GET`/`PUT /api/account/export-preset`.
- `/api/size-charts/*` (including `[id]/activate` and `[id]/duplicate`) and `/api/slopers/*` — see their own sections. `POST /api/slopers` alone can tell 404 from 400 (`invalid_name`, `pattern_not_drafted`, `pattern_has_conflict` — founding a future garment on divergent seams is the same mistake as cutting fabric from them).

### Generation flow (`POST /api/patterns/[id]/generate`)

> Full rationale — why `explain` replaced the planned glossary screen, and the attachment-preparation details: [`docs/decisions.md`](docs/decisions.md).

- Debits `COSTS.adjust` immediately, then `proposeGarment` (`lib/ai/`) asks `claude-sonnet-5`, via **forced tool-use**, for `{ decision: "apply" | "decline" | "ask" | "explain", spec, questions?, declineReason?, assistantMessage, assemblyOrder? }`.
- **`lib/ai/` is split by responsibility, all derived from one source of truth:** `prompt.ts` (sectioned system prompt), `schema.ts` (the `propose_garment` tool), `history.ts` (pure `buildHistory`), `decision.ts` (pure `resolveDecision`), `index.ts` (**the only file importing the SDK**). **The prompt's and schema's every enum and numeric bound render from `lib/draft/garment.ts`'s exported `TYPES`/`GENDERS`/`NECKLINES`/`SLEEVES`/`SKIRTS`/`COLLARS`/`CUFFS`/`WAISTBANDS`/`STYLE_LIMITS` plus `MEASUREMENT_RANGES`** — the same constants `validateSpec` clamps with, so the model is never told a range the validator doesn't enforce. **Add a style field in one place and all three follow.** **Never hardcode a bound in the prompt or schema.** The rule covers prices and formats too: `# Product facts` renders costs from `COSTS` and formats from `EXPORT_FORMATS`.
- **Trust boundary: the returned `spec` is never trusted as-is.** `validateSpec` re-checks every enum and clamps every numeric field before use; `questions` go through `validateQuestions`. **The same rule covers the _user's_ size-chart patch** (`lib/sizeCharts/validate.ts`) — it was written for the AI's input and initially forgotten on the human's, which reaches the identical drafter.
- **The AI never emits SVG or pixel coordinates — only a `GarmentSpec`.** A `decision: "apply"` carrying no usable `spec` object **throws** rather than letting `validateSpec` fabricate a default blouse; the route's catch refunds the credit.
- **Per decision:** `apply` → `applyGarmentSpec` → `draftGarment` recomputes everything from scratch and bumps the version. `decline`, and any API/parse error, **refunds**. `ask` (underspecified) attaches 1–4 single-choice `questions`, **refunds**, and responds `status: "clarify"` with no draft and no version bump — answering calls `sendMessage(phrase, { answering: true })`, and that flag (server-side enforced) prevents the AI asking again.
- **`explain` is the one non-drafting decision that is NOT refunded.** The user asked a question and got a real answer from a real Anthropic call, where `ask`/`decline` refund precisely because they delivered nothing. `resolveDecision` throws on an `explain` carrying a blank `assistantMessage` — the message _is_ the payload — so the catch refunds rather than charging for an empty bubble. This replaced the planned glossary screen: a hand-written term list would be a second, thinner source of knowledge the model already has, and it could not answer "por que minha manga não fecha?". Out-of-scope questions still `decline`.
- **A chat message can carry one photo/sketch attachment, sent as an image block in the same call — and never persisted (#18).** `lib/editor/attachment.ts`'s `prepareImage` downscales to `MAX_ATTACHMENT_LONG_EDGE_PX` and re-encodes as JPEG client-side, **rejecting an unsupported type or oversized source before any decode work**. The attachment travels only with the request, never into the persisted `PatternState` — only `ChatMessage.hasImage` records that one was used, rendered as a small chip rather than a thumbnail that would vanish on reload.
- **The browser's preparation is a UX affordance, not the trust boundary.** The route re-validates `body.image` with `validateAttachmentInput` **before any debit or Anthropic call**, answering `invalid_attachment` otherwise, and reads its body through a route-local larger `maxBytes` ceiling (an attachment's base64 would blow past the 64 KB limit sized for plain form fields).
- **Prompt injection via an attached image's own text is not a new attack surface.** The prompt tells the model to treat text inside an image as content to describe, never an instruction — but **the actual defence is structural**: `applyGarmentSpec` drafts through `resolveMeasurements`, which clamps every measurement to `MEASUREMENT_RANGES` regardless of what the model claims prompted the value. (`resolveDecision` itself passes `measurementOverrides` through unclamped; the range is applied downstream, at draft time.)
- Costs exactly `COSTS.adjust`, identical to a text-only message — one `propose_garment` call either way.

### Seam-conflict detection (live, apply-with-warning) — the seam graph (#134)

> Full rationale — the dress waist-join gap, why #177's first pass was itself wrong (#185), and the per-pair risk analysis: [`docs/decisions.md`](docs/decisions.md).

- **`draftAll` builds a real seam graph, not a single hardcoded comparison.** Each drafter declares its own edge-index ranges on `DraftedPiece.seamEdges`, and `draftAll` — the one place that knows the whole garment's topology — pairs matching edges across pieces into `SeamPairDecl` entries (`lib/draft/seams.ts`). `walkSeamPairs` is the pure function that measures every declared pair's **real arc length off the already-drafted pieces** (`curveArcLengthCm`, never a bespoke per-drafter number) and returns the full graph — every pair, divergent or not. This is the structure the assembly order walks.
- **`seamCheck` is a consumer of that graph, not the comparison itself** — it narrows to the pairs whose actual gap misses their own intended ease by more than `SEAM_TOLERANCE_CM` (1 cm). `applyGarmentSpec` calls it on the `seamGraph` and `detectConflict` attaches a real `ConflictInfo`. **The generation still applies, bumps the version, and debits**; the chat message gets `tone: "conflict"` and the route responds `status: "conflict"`.
- **Most pairs are equal by construction and are declared anyway, as regression guards** — shoulder, side seam, the sleeve's own underarm, the three sub-piece pairs (`collar-neckline`, `cuff-hem`, `waistband-waist`) and the five trousers pairs. **The armhole/cap pair is the one divergence reachable today**: `style.armholeDeepenCm` deepens only the body's armhole while the cap is sized from the base one, unless refit.
- **The dress waist-join was a real, previously-undetected gap the graph surfaced.** Its fix is a rule worth keeping: **a fitted bodice ends at the natural waist, so its hem is sized off the waist, never the hip** — `dressWaistHalfCm(waistCm)` takes **no silhouette parameter at all**, because the bodice describes the body and which skirt happens to be attached cannot change its own hem width. A standalone skirt's waist ease is deliberately not reused there (that ease is for a separately-worn waistband, not an already-eased bodice seam). **The topology must also match the seam's physical shape:** `skirtPiece.qty === 1` signals one undivided panel whose single waist arc is the _full_ waist, so each bodice half pairs against its own half of that arc — comparing both halves against the whole arc made "zero divergence" require a bodice twice the width of the body, and the graph reported it as correct because the check was asking the wrong question. Every dress's geometry changed as a result; a pattern persisted earlier re-drafts with the new hem the next time it's regenerated, since nothing about the frozen snapshot changed.
- **Multiple simultaneous divergences render as a list, not multiple panels.** `ConflictInfo.entries?: ConflictEntry[]` (additive — absent on a conflict persisted earlier, which still renders through the singular fields) holds one entry per divergence with a pre-resolved `label`, `diffCm`, `fixable`, and its own canvas `markers`. The canvas's single top-right slot still holds exactly one card, now rendering one group per entry.
- **The two divergent lengths behind each entry are NOT persisted** — `ConflictEntry` carries only `diffCm`. `measureSeamGraph(spec, baseMeasurements, t)` is called once in `CanvasArea` and matched back to each entry by `key`, the same derive-at-render-time rule as `fitPieceLabel`/`measureSeams` — which is also what gives the comparison to conflicts persisted before this existed. A pile of per-seam numbers in the blob would have broken that rule.
- **`conflict/resolve` is free, no debit.** "fix" calls `refitSleeve` — setting the internal `style.sleeveRefit` and re-drafting so the cap uses the adjusted armhole — closing **only** the armhole/cap divergence; any other entry is untouched and the conflict stays open with whatever remains. "ignore" clears the whole warning regardless of how many entries it holds. **`sleeveRefit` is deliberately not accepted by `validateSpec`, so the AI can never fake a refit.** `ConflictActions`'s "Corrigir manga" button renders **only while at least one entry is `fixable`** — a conflict made entirely of unfixable divergences shows the lengths with no button, rather than one that would silently do nothing.

### Assembly / sewing order (#138)

> Full rationale — the phase table's reasoning and the hem-consumption rules: [`docs/decisions.md`](docs/decisions.md).

- **The sewing order is derived data, walked from the seam graph — not a hand-written sequence per garment archetype.** `lib/draft/assembly.ts`'s `buildAssemblyOrder(pattern, t)` is pure and DB-free, redrafting from the pattern's own frozen `sizeTable` (so it works on a pattern drafted before it existed) and **never persisted**. It produces one ordered `steps` list: a `"dart"` step per piece that has any, one `"seam"` step per `SeamMeasurement` the graph actually walked — **never more, never fewer**, the invariant `assembly.test.ts`'s matrix suite pins — and a `"hem"` step for any piece whose own `seamEdges.hem` isn't already claimed by another declared pair (`HEM_CONSUMED_BY`).
- **Ordering among seam steps is a lookup by the pair's own stable `key`, not a branch on `spec.type`.** `PHASE_BY_KEY` maps every key to one of six phases — `primary`, `sleeve`, `side`, `attach`, `waistJoin`, `band` — and **darts are unconditionally sewn before every seam/hem step** (a stricter ordering than interleaving per-piece, not a looser one). A future key with no entry falls to `"other"` (sewn last, never dropped) rather than crashing, but every key the drafting matrix produces today is exhaustively asserted.
- **Each seam step cites the two real drafted lengths and the pair's own intended `easeCm`** — `SeamMeasurement` carries `easeCm` precisely so "how much ease to distribute" is a real number a step can cite rather than a guess. `diverges` comes from `seamCheck`, **not a second threshold**; `AssemblyOrder.hasConflict` is true when any step does. The order is still returned — knowing the sequence is still useful — but **a consumer must say so rather than presenting a plausible-looking, fully-closing seam.**
- **Piece names come from the pattern's own already-persisted, already-locale-resolved `pieces` list** (`pieceDisplayName`, matched by id), never a fresh redraft — the draft-time-locale-snapshot rule, and what keeps a step's name byte-identical to what the canvas already shows. A seam step's `key` is deliberately **not** resolved through a catalog label: it's handed to the model as a stable English identifier for it to phrase itself.
- **A piece set with nothing to derive gets an honestly empty order (`steps: []`), not a fabricated one.** No spec the matrix produces reaches it today (#188 gave skirt panels and trouser legs their own `seamEdges.hem`, so a waistband-less skirt now derives one real hem step), but the prompt still instructs the model to say plainly that no order could be derived rather than inventing one.
- **Reachable from chat, not a new screen.** A sewing-order question answers through the existing `decision: "explain"` path (same debit, same credit chip). `RawToolInput`/`AiDecision` carry an `assemblyOrder?: boolean` the model sets **only** alongside `explain`; `resolveDecision` strips it for every other decision even if the model set it. The route tags the persisted `ChatMessage` with `assembly: true`, and `ChatBubble` renders the **catalog-sourced** disclaimer — the chrome and disclaimer come from the catalog, the step prose does not — so "labelled as AI-generated guidance" is a structural signal, not the route sniffing the model's words.
- **The model may never invent a step for a seam absent from the structure** — enforced by instruction, not by re-validating the model's prose against the JSON (the same trust level every other `explain` answer has). `buildSystem` embeds the JSON and its own prompt section instructs: walk the steps in order, name pieces by `aPieceName`/`bPieceName`, cite lengths and (only when meaningfully above 0) the ease, and state when a step `diverges` that the seam needs the conflict resolved first.

### Drafting engine (`lib/draft/*`)

> Full rationale — the `backWidth` fit bug, the bbox-vs-boundary decoration bug, mated-notch derivation, and every sub-piece/archetype decision: [`docs/decisions.md`](docs/decisions.md).

- **Pieces are drafted from measurements, not deltas.** `lib/measurements.ts` defines `Measurements` (`shoulder` is the half-width from the centre line to the shoulder tip, not the full seam) plus the legacy `SIZE_TABLE`/`SIZE_TABLE_MALE`, now only seed data for the two system size charts and the pre-generation bootstrap.
- **`Measurements` has two tiers (#132).** `CORE_MEASUREMENT_KEYS` — the 9 proportional keys (`bust`, `waist`, `hip`, `hipHeight`, `backLength`, `shoulder`, `skirtLength`, `shortSleeveLength`, `longSleeveLength`) — stay **required**, enforced by `assertResolvedMeasurements` on every base row. `EXTENDED_MEASUREMENT_KEYS` are 6 **optional** overrides, each read by exactly one drafter and each falling back to the proportion it replaces:

  ```
  neckGirth     → body.ts     neckHalf = neckGirth/6 + offset      ← bust/14 + offset
  highBust      → body.ts     armholeDepthBase = highBust/8 + off  ← bust/8 + offset
  shoulderSlope → body.ts     shoulderSlope                        ← 4.0 female / 4.5 male
  backWidth     → body.ts     BACK PANEL ONLY: armCtrlX at midArmY ← (shoulderHalf + halfChest)/2 - 1
  bicep         → sleeve.ts   bicep = bicep + wearingEase          ← bust*BICEP_PROPORTION_OF_BUST + ease
  rise          → trousers.ts riseCm (crotch depth)                ← hip/4 + 4
  ```

  **`halfChest` (the underarm-level width where front, back and sleeve all meet) stays bust-derived for both panels, always — never wire `backWidth` into it.** `backWidth` is an upper-chest/shoulder-blade measurement feeding the armhole curve's control point; routing it through `halfChest` makes a user who measures honestly get a back ~5 cm too narrow per side. Seeding is a deliberate no-op for four keys (`neckGirth`/`highBust`/`shoulderSlope`/`bicep` seed to the exact value reproducing the fallback) but **intentionally not** for `backWidth` (`bust*0.4`, a real proportion) or `rise` (per-size graded) — both genuinely change what a new chart drafts. **No migration:** a pattern snapshots its chart once, so an existing pattern keeps taking every fallback forever. That is correct, not a gap to backfill.

- `resolveMeasurements(base, overrides)` applies chat-driven `measurementOverrides` onto an already-resolved base row, clamped to `MEASUREMENT_RANGES`. No size/gender table lookup happens here — the base row comes from the pattern's frozen `sizeTable`.
- `GarmentType` = `"blouse" | "dress" | "skirt" | "tshirt" | "trousers"`. A `GarmentSpec` (`type` + `gender` + `measurementOverrides` + `style`) plus a resolved `Measurements` flow into `draftGarment(spec, baseMeasurements, t)` (`garment.ts`), which calls the per-block drafters (`body.ts`, `sleeve.ts`, `skirt.ts`, `trousers.ts`, shared helpers in `core.ts`) and lays the pieces into one computed `viewBox` (`autoLayout`). The engine doesn't know `SizeLabel` — it's a per-chart `string`.
- `tshirt` is a knit archetype (round neck, no darts, short sleeves) through the same drafters, with `knit: true` in `BlockOpts`.
- **Curvature is per-edge-range and opt-in.** `outlinePath` (`core.ts`) takes cm points plus `curvedSpans: [number, number][]`; only marked ranges (neckline, armhole, sleeve cap) get Catmull-Rom-derived Béziers with tangents locked at span edges. Every other edge is a straight `L`. No global smoothing pass.
- Each drafter attaches its own `piece.detailRows` (label/value pairs).
- **A decoration is placed from the piece's own boundary, never from its bounding box.** The bbox is a superset of the piece, so a constant offset from it lands outside the outline wherever the piece is scooped or tapered — the body grainline shipped inside the neck opening on every front bodice for exactly this reason, and it reaches all five export formats, so that was a data defect, not a screen one. It starts at `neckDrop + 3` now. Placement that depends on _rendered text width_ can't live in the drafter: `lib/canvas/pieceLabel.ts`'s `fitPieceLabel` recomputes the canvas label at render time from `piece.vertices`, which also repairs already-drafted patterns. `estimateTextWidth`'s 0.7em advance is deliberately an over-estimate, so a mis-estimate shrinks the label instead of overflowing the piece. **The invariant is guarded generically:** `garment.test.ts`'s containment suite asserts every grainline and dart point lies inside its own outline across the whole `DECORATION_CASES` matrix.
- **Notches are typed, drafter-derived, and never persisted or user-movable (#124).** `DraftedPiece.notches` (`core.ts`'s `NotchCm`: `type` + `outerCm` + `innerCm`) follows the derive-don't-store precedent. `single`/`double`/`triple` are told apart purely by depth (`NOTCH_DEPTH_CM` 0.3/0.6/0.9 cm), which is simultaneously the printable size — not a second number to keep in sync. `notchAt(point, tangent, insideRef, type)` orients the inward normal by biasing toward a caller-known interior point, so it works regardless of which winding direction that outline walks (drafters mix both).
- **Mated notches share one computed distance, not two independent guesses.** `bodice()` computes `pitchNotchCm`/`basePitchNotchCm`; `draftAll` picks whichever matches the armhole the cap was **actually** drafted against and passes that single number into `draftSleeve`. Both pieces then walk that identical value from their own underarm vertex, so the positions match by construction. Single marks the front, double the back; the cap's apex notch is excluded from the cross-check (it has no single body-side counterpart).
- **`Piece`/`DraftedPiece` carry a typed `internals` channel (#127)** — `InternalCm` (`dart`/`foldLine`/`drillHole` ship; `pleat`/`styleLine`/`placementMark` reserved). A dart's **fold line** is its own press line, a different concept from the piece's cut-on-fold axis (`foldEdge`). `dartInternals` derives all three marks together; each free apex gets a drill hole `DRILL_HOLE_SETBACK_CM` (1.25 cm) short of the point. **Migration:** the legacy `Piece.darts` field is never written again but stays readable via `lib/types.ts`'s `resolvePieceInternals` at render time — the `savedAgo` precedent, no reset migration.
- **Three sub-piece drafters live in `lib/draft/subpieces.ts`, each sized from a MEASURED edge on an already-drafted piece, never a proportion of the bust/waist (#129/#130/#131).** `GarmentStyle` gained `collar?: "none" | "convertible"`, `cuff?: "none" | "straight"`, `waistband?: "none" | "straight"`, clamped by `validateSpec` and rendered into the prompt/schema from the exported `COLLARS`/`CUFFS`/`WAISTBANDS`. **There is deliberately no third enum value for an unsupported shape** (mandarin collar, contoured waistband), so the AI's only path for one is `decline`/`ask` — never a silent substitution. Collar: sized to the summed real neckline arc across all four `necklineLeft`/`necklineRight` edges. Cuff: the measured sleeve hem plus `WRIST_EASE_CM` (a flat table — the hem is bicep-derived and far wider than a wrist), long sleeves only. Waistband: the skirt/trouser waist summed across the panel's own `qty` plus `WAISTBAND_OVERLAP_CM`, and **defaults ON** (unlike collar/cuff) because a skirt with no waistband is the defect #131 exists to fix. Its button/zip placement mark is still missing and the detail row says so.
- **A fifth archetype, `trousers` — a straight-leg block only (#128).** Front and back are each a genuinely asymmetric single-leg shape, so **neither declares a `foldEdge`**; both are `qty: 2` (mirrored by flipping fabric, not folding). They share rise depth, total length and hip quarter-width; only the crotch extension differs, which is what keeps inseam and outseam identical front-vs-back by construction. `style.trouserLengthCm` defaults to a flat per-gender constant — there is no per-size leg-length measurement to grade against yet. **Prova 3D does not cover trousers:** `buildProofMesh` recognizes only body/sleeve/skirt ids, so `Proof3DTab` renders a named `notSupportedForTrousers` gap rather than a silently empty preview.
- **The drafted-ease report (`lib/draft/easeReport.ts`'s `buildEaseReport`) states how much ease the FINISHED garment has**, deliberately distinct from `wearingEaseCm` (the ease the drafter was _asked_ for) — a style adjustment, dart or silhouette can make the two diverge. Pure and DB-free, redrafting from the pattern's own frozen `sizeTable`, so it works on patterns drafted before it existed. Per girth it scans the piece's real width at a height derived from **public data only** (a `seamEdges` vertex or a raw `Measurements` field — never an internal per-drafter formula), then subtracts what any dart removes at that same height, which handles every drafter's dart shape generically. **A girth it cannot measure honestly is reported `unavailable` with a reason, never a wrong number** — a circle/gore/half-circle panel is drafted from polar coordinates where a horizontal scanline is meaningless (`unsupportedSilhouette`), and a bust-less garment has `noPanel`. Trousers read hip WITHOUT dart subtraction (a waist dart doesn't remove hip fabric, and the block drafts both at the same height). Fit class comes from `classifyGirthFit`, whose band boundaries are the **midpoints between consecutive `FIT_EASE_CM` figures** — never a second, competing scale.

### Size charts (`/size-charts`)

> Full rationale — the `validateSizeChartPatch` bug in detail, the ABNT provenance removal, and the seed reconstruction: [`docs/decisions.md`](docs/decisions.md).

Real, per-account, and they drive generation/grading.

- **`SizeChart` (Prisma, JSON-blob-per-row like `Pattern`/`Wallet`)** holds `SizeChartData`: `name`, `gender`, `bodyType`, `isSystem`, ordered `sizes`, `baseSizeIndex`, `baseMeasurements`, a `progressionRule` (cm delta per size step), and per-cell `overrides` that win over the rule. Resolution lives in `lib/sizeCharts/compute.ts`. **`bodyType` is descriptive metadata only — it never affects drafted geometry**, an honest limitation the screen states via a caption tied to the control by `aria-describedby`, not just here.
- **Every account lazily gets two seeded `isSystem` charts on first access** (the `Wallet` lazy-seed precedent), derived losslessly from the legacy tables — the rule+override reconstruction reproduces the original tables exactly. **System charts can be duplicated but not edited or deleted, enforced in the repository layer.** Both names resolve from the catalog rather than a hardcoded literal, threaded through as a required `t: Translate`. **A rename affects nothing already seeded** — existing rows keep the name they were created with, the `PatternData.newPatternName` precedent. The female chart's name used to read "· ABNT", **a standards-body provenance the app cannot substantiate** (the numbers come from this repo's own legacy table); the library now says on every system card that it is a proportional house standard, not a certified one.
- **`User.activeSizeChartId` is not a promise the chart will be used, and the app says so.** `pickSizeChartForGeneration` returns a `SizeChartChoice` (`{chart, rejectedActive}`) rather than a bare record — it used to discard the fact that it had fallen back, so nothing could report it. Observed: with a male chart active, a female garment drafted from the system female chart while the screen still showed the male one as active and the AI said "usando as medidas padrão". **Surfaced in three places, per the three places the question comes up:** a `tone: "notice"` chat bubble at generation time (the only moment a substitution can happen), a "Grade usada" chip in `TechSheetTab`, and the active badge now reading its _scope_ ("usada só em peças femininas") because "ativa" alone implied it applied to everything. The frozen `Pattern.sizeChartName` backs the chip — additive, frozen for the same reason `sizeTable` is, **absent on older patterns and therefore omitted rather than guessed.**
- **A `PATCH` body is validated before it can reach the drafter** — `validateSizeChartPatch` (`lib/sizeCharts/validate.ts`) is the size-chart half of the `validateSpec` trust boundary, and `updateSizeChart`'s `patch` parameter is deliberately `unknown` (the old `Partial<SizeChartData>` was an assertion about data straight off the wire). **It drops or clamps, never throws**, so an unusable field is ignored while the rest of the patch applies. The bug it exists for, verified live: a bogus `gender`, a NaN-ish `progressionRule` and arbitrary unknown keys all persisted verbatim, and **`baseMeasurements:{}` replaced the whole row** — generation then answered `status:"ok"` while persisting a null `viewBox` and detail rows reading "NaN cm". **`MEASUREMENT_RANGES` was no defence: `Math.min`/`max` propagate NaN.** So `baseMeasurements` **merges** onto the current row — a patch can change a value but can never drop a key — and **`isSystem` appears in no branch**, so a request can never claim it. `MEASUREMENT_KEYS` and `BODY_TYPES` are exported for it, and `SizeChartTable` reads those instead of its own copies.
- **A pattern snapshots its size chart once, at its first-ever generation.** The route calls `getSizeChartForGeneration(userId, spec.gender)` (the active chart if its gender matches the spec, else the system default for that gender), then `seedPatternSizeSnapshot` freezes `sizes`/`baseSize`/a fully resolved `sizeTable`. **Every later regeneration reuses the frozen snapshot** — editing or reassigning the active chart never retroactively changes an in-progress pattern. A blank pattern bootstraps from the system female chart via the **name-free** `buildSystemSizeChart` (not `buildSystemSizeChartData` — this bootstrap only holds a `PatternData`-scoped translator, and that function's name would resolve the wrong namespace), so `sizeTable`/`sizes` are always populated, never optional.
- **Screen:** `SizeChartsShell` + `SizeChartLibrary` + `SizeChartTable`, with their own `useSizeChartsStore`. Browse; edit a custom chart's base row/progression rule/per-cell overrides/size list; duplicate any chart; mark one active.
- **Spreadsheet import is real (#12), not the inert dashed placeholder it shipped as.** `ImportSizeChartDialog` parses a file entirely client-side via `lib/sizeCharts/import.ts`'s `parseSizeChartFile` (framework-free like every other `lib/sizeCharts` module — the DOM half stays in the dialog), previews exactly what will be created **including every rejected cell and its reason**, and only then persists through `createSizeChartFromImport`. **The preview is a review step, not the trust boundary** — the server re-runs everything through `validateSizeChartPatch` exactly as a hand-typed `PATCH` would. Deliberately **`.csv`/`.tsv` only, no `.xlsx`**: a binary format needs a real parsing dependency an MVP import doesn't justify, and the limitation is stated on screen before a file is even picked, with an `.xlsx` upload answering `unsupported_file_type` rather than being silently misread as text.

### Atelier bases (`/slopers`)

A `Sloper` (Prisma, JSON-blob-per-row like `Pattern`/`SizeChart`) holds `SloperData`: `name`, `spec`, and the frozen `sizes`/`baseSize`/`sizeTable`/`sizeChartName?` snapshot — **never the pieces**, because `draftGarment` is deterministic and persisting them would duplicate what the spec already determines (the `savedAgo`/`planLabel` lesson, applied before the fact). `lib/slopers/convert.ts` holds the pure pair `sloperFromPattern`/`patternFromSloper`, and the round-trip test asserting identical pieces is what licenses not storing geometry; the list thumbnail is drafted server-side for the same reason. `POST /api/slopers {patternId, name}` copies the snapshot off a pattern the server itself read under the ownership scope — the client never sends a spec, so there is no second `validateSpec`-shaped trust boundary. Creating a pattern from a base (`POST /api/patterns {sloperId}`) costs **0 credits**: it is local drafting with no Anthropic call, the same reason `conflict/resolve` is free. The UI term is pt-BR "base"; `Sloper` is its translation, not a transliteration — `Block` was unavailable because `lib/draft/body.ts` already exports `BlockOpts` for the per-block (body/sleeve/skirt) drafters. Screen: `components/slopers/SlopersShell.tsx` + `SloperGrid.tsx` + `SloperCard.tsx`, with their own `useSlopersStore` (`lib/slopersStore.ts`) — the same shell/grid/card-plus-own-store shape as the size-charts screen, and, like `/slopers`'s own create flow, deliberately not folded into `useDashboardStore` even though both screens list cards: a failed create on `/slopers` has to record its error on this screen's store, not the dashboard's.

### Client state (Zustand)

> Full rationale — the permanent-loading-screen bug, and the paywall-retry decision: [`docs/decisions.md`](docs/decisions.md).

- **Editor:** `lib/store.ts`'s `useEditorStore`, scoped to a single pattern via `init(patternId)` and threading that id through every server call. It mirrors the server's `EditorState` after every mutating call and owns UI-only state (active tab, selected piece, active tool, measure-tool measurements — **auto-cleared when the pattern version changes** — generation status/step, paywall state). **All server calls go through `lib/api-client.ts`; components never call `fetch` directly.** `sendMessage` optimistically appends the user's message before the request resolves; `cancelGeneration` rolls that back and refunds client-side (there is no server-side cancel).
- **Failures are data, not silence — and `res.ok` is actually checked.** `getJson`/`postJson` never looked at the status, so an error body came back typed as the success shape (a 401 became an "`EditorState`" with no pattern). `lib/api-client.ts` exports **`ApiError`** (status + wire code), thrown for any non-2xx a call did not opt into; **`handled` lists the statuses whose body _is_ the contract** — `PAYWALL` (402) and `DOMAIN_ERRORS` — enumerated per call site so each endpoint's failure contract stays visible. Every former bare `fetch` (rename, delete, activate, duplicate, create) goes through it too; those used to ignore the response entirely, so a failed rename looked like a success.
- **Every store has an error path.** The editor store had _no_ `try`/`catch` at all: `init` threw so `ready` never became true and the screen showed "Carregando molde…" **forever**; `sendMessage` skipped `clearTimeout` so the overlay spun indefinitely; and `applyState` wrote `pattern: undefined` from an error body, which is how an expired JWT dropped a mid-session user onto a permanent loading screen. Now `error` + `clearError`, with `EditorShell` rendering a load-error screen with a retry — plus **a distinct `sessionExpired` message for 401**, different advice for a different cause.
- **A failed _load_ and a failed _mutation_ are different states.** The dashboard, size-charts and slopers stores keep `actionError`/`clearActionError` separate from their `error` boolean: a failed load has nothing to show and replaces the content region, while a failed mutation leaves a usable screen that needs a notice. All four screens render `components/shared/ActionErrorNotice` (amber `notice`, **not** the red alert token); `/settings` renders the same component off plain local `useState`. **Mutations update local state only after the server confirms**, and `dashboardStore.create()` resolves to `null` instead of rejecting, because its caller navigates to the returned id.
- **The paywall is action-agnostic:** any store action that can fail on insufficient credits stashes its own retry closure in `paywall.retry`. Under the mock provider, `purchase()` applies the credits, closes the modal, and invokes whatever `retry` was stashed — so "buy credits then automatically finish what I was doing" works for any future paid action following the same pattern.
- **All three purchase call sites also handle `PurchaseResult`'s third shape, `{status:"redirect", url}`** — what a real gateway answers, since the wallet isn't touched until the webhook confirms. None applies any state on that shape (there is nothing yet to apply) before navigating via `window.location.href`. **The store closes the paywall _without_ invoking `retry`** — a settled decision: retrying before the webhook has landed would spend a second credit hoping the purchase already went through. The user re-sends once they're back; the composer still holds their text.
- **Five stores in total, one per screen family, none sharing an instance:** `lib/store.ts` (editor), `lib/dashboardStore.ts`, `lib/sizeChartsStore.ts`, `lib/slopersStore.ts` and `lib/importStore.ts` — **each screen's own lifetime and its own load-vs-action error split, never reaching into another screen's store** even when both list similarly-shaped cards. **`useImportStore` is the one store with no split at all**: `/import` has no server load, so it carries `actionError` alone. Two screens deliberately have **no** store — `/settings` and `/pattern/[id]/versions` read off plain local `useState`.

### Screens

> Full rationale — the `/planos` "em breve" audit, the settings-section split, and the pattern-card badge decision: [`docs/decisions.md`](docs/decisions.md).

- **The editor (`/pattern/[id]`) opens on a blank pattern.** No pieces, empty chat, name "Novo molde", `version: 0` — the user always generates from scratch, and the first generation creates the garment's (variable) piece set. `CanvasArea` shows an empty state and hides the floating toolbar while `pieces` is empty; `sendMessage` auto-selects the first piece once a generation produces one.
- **Canvas overlays are mutually exclusive:** `PieceDetailsPanel` and `ConflictInfoCard` share the top-right slot in `CanvasArea`, and **a conflict always takes the slot**. Fold new overlays into that same exclusivity check rather than adding a third independent floating panel.
- **`/` is the dashboard for a signed-in, onboarded account — but it has four branches, not one.** `app/page.tsx` renders `<LandingPage />` for a signed-out visitor (#13 — before it, the only way in was a bare centered `/login` card with no product explanation); `redirect("/login")` when the session's account no longer exists (#62 — a JWT outlives account deletion by up to 30 days on any device that isn't the one that deleted it); `redirect("/onboarding")` when `onboardedAt === null` (#14); otherwise `DashboardShell`, reading `?missing=pattern` as plain data — the `?section=` precedent, not a client `useSearchParams`. It is **the one route whose `generateMetadata` depends on session state**, and the one that must spell out its own `— MoldAI` suffix: Next.js does not apply a layout's `title.template` to a `page.tsx` in that _same_ route segment, and root layout + `/` are the same segment.
- **Dashboard** — `DashboardShell` renders through `AppShell` passing **neither `title` nor `backHref`** (it _is_ `/`, and its sidebar already marks the section) and composes `Sidebar`, `PatternGrid` (search + garment-type filter reusing the `garmentType.*` catalog keys), and `CreditsCard`/`RecentUsageCard`. **`Sidebar` takes `active` and `onNewPattern` as props rather than reading `useDashboardStore` itself**, because `/slopers` renders the same component and a failed create there has to record its error on _that_ screen's store. **`PatternGrid` owns no scroll region** — `DashboardShell` wraps it with the summary cards in one non-`fill` `ScrollArea`, so an empty grid takes its natural height instead of pinning the cards to the floor. Rename and delete live **only** in the card "⋯" menu; the editor has no delete affordance. **Pattern cards deliberately show no state badge** — export never touches the server, so "exportado" can't be derived honestly, and a partial 2-state badge wasn't worth shipping. **`/pattern/[id]` redirects to `/?missing=pattern` for a pattern that is gone or not owned**, deliberately one flag rather than distinguishing "deleted" from "not yours" — that would make the dashboard an existence oracle for other accounts' pattern ids.
- **`/` doubles as the public landing for a signed-out visitor** (`components/landing/`, #13) — `LandingPage` (hero, step cards, formats section, `LandingNav`). The only consumer of the `text-hero`/`tracking-hero` tokens.
- **`/onboarding` is the 3-step post-signup wizard** (design `5b`, #14) — a centered card rendering its own `Wordmark`, local `useState`, no store. **`User.onboardedAt`/`workStyle`** (migration `20260826150000_add_user_onboarding`, additive) back it: `app/page.tsx` gates on `onboardedAt === null` only, and existing rows were backfilled as already-onboarded, so the wizard only fires for accounts created after it shipped — the email-verification grandfather-clause shape. **`workStyle` is honest, unused research data**, never read by any drafting or billing path; the route still **rejects an unrecognised value rather than storing it** (the `isPurchaseType` trust boundary). Step 2 activates the system female chart; step 3 creates a pattern and generates, **staying put with a notice on anything that isn't a real draft** rather than navigating to a blank pattern. Both "Pular por agora" and a successful submit stamp `onboardedAt`, and the page redirects to `/` if it's already set, so a stale bookmark can't re-show the wizard. Its two "em breve" rows are disabled+badged, not hidden.
- **`/pattern/[id]/versions` is the version-history screen** (#16) — `components/versions/`, local `useState`, no store. **`PatternVersion` stores the `GarmentSpec` plus the frozen size snapshot only — never the drafted pieces**, on the `Sloper` reasoning: `draftGarment` is deterministic, so geometry would duplicate what `spec` + `sizeTable` already determine. `userId` is denormalized so ownership is one indexed lookup. **A row is written by `recordVersion` inside the SAME transaction as every `bumpVersion`** — generate, graduate, `conflict/resolve`, restore — so a snapshot can never exist without the state that produced it and a failed mutation leaves no orphan. `reason` is machine-readable, never pt-BR prose. `GET .../versions` returns `null` (never an empty array) for a pattern that isn't the caller's, so it can't become an existence oracle. **Restore is free and append-only:** it uses `withPatternVersioned` (a Pattern-only transaction, never `withPatternAndWallet` — it must not be able to debit), carries the OLD version's frozen snapshot forward rather than re-resolving against today's active chart, and **restoring v3 while at v5 produces v6 carrying v3's spec** — it never rewrites or deletes v3. No retention cap, no plan gate.
- **`/import` is the DXF import flow** (design `5g`, scoped down; #11) — `ImportShell`/`FileSummaryCard`/`LayerMappingPanel`/`VerificationPanel`, a two-step parse → analyse → verify screen with no sidebar. **Entirely client-side: it makes no server call at all**, costs nothing, and says so with its own badge rather than reading a balance for a number never spent. `lib/import/` is the framework-free half — `dxf.ts` hand-parses DXF's group-code/value stream in **a single forward pass**, which is what makes "never loops forever" structurally guaranteed, and is written to recognise this repo's own `toDxf`/`toDxfAama` output as a round-trip baseline; `analyze.ts` detects layer roles and emits machine-readable `ImportCheckCode`s the screen resolves as `t("checks." + code)`. **An uploaded file is untrusted input, the `validateSpec` trust boundary:** `parseDxf` never throws and caps text length, entity count and vertices per entity, with `MAX_IMPORT_FILE_BYTES` rejecting an oversized upload before any parse work. **Creating a `Pattern` from the parsed geometry is explicitly "em breve"**, disabled+badged — this pass reads and verifies a file, it does not yet import one. `FileSummaryCard` resolves each of `pick()`'s three failure causes to its own message rather than a fixed banner that couldn't tell "too large" from "not a readable DXF".
- **`/settings` is one unified page, not a modal**, reached from the shared header's avatar menu, deep-linked via `?section=` (`profile` default, plus `password`/`danger`/`usage`/`plan`). Because that header is on every screen, the editor can reach settings too. It has its own `SettingsSidebar`, no dashboard-sidebar entry. **`SettingsSection`/`SETTINGS_SECTIONS` live in plain `lib/settings/sections.ts`, outside the `"use client"` component** — the Server Component page needs them as plain data, and importing a non-component value from a client module into server code becomes a broken client reference at runtime. The page loads user, wallet and the last 30 ledger entries server-side, so first render needs no API round-trip. Five sections:
  - `ProfileSection` — name editable; **email deliberately read-only** (it's the Credentials login identifier).
  - `PasswordSection` — client-side confirm-mismatch gating plus a server-verified current-password check. **Password changes do not invalidate the current JWT** — a deliberate choice for this single-device MVP, not an oversight.
  - `DangerZoneSection` — deletion gated by both a typed-email match **and** a server-verified password (stronger than the single-pattern confirm, since one `prisma.user.delete` cascades away every pattern, the wallet and the ledger).
  - `UsageSection` — balance/renewal, a top-up reusing `purchase("topup")` with an optimistic ledger update, and the full transaction history (all types, not just spend).
  - `PlanSection` — real plan switching. Every tier above the account's own renders an enabled subscribe button; **a lower tier stays disabled + badged with a note explaining that only upgrades are self-serve** (downgrades are refused server-side, not merely hidden). A failed switch resolves `PlanSection.errors.{code}` from the thrown `ApiError`; a successful one calls `router.refresh()` so the header's credits bar picks up the new plan. Links out to `/planos` rather than duplicating its card content.
- **`/planos` is a public route** (#15) — the pricing screen design `5c` specifies, reachable without a session. Four cards from `lib/billing/plans.ts`, and a cost-per-action footer rendered from `COSTS`/`TOPUP_*` — **never the design's own literal numbers, which don't match what the app actually charges.** The Mensal/Anual −20% toggle changes only the **displayed** price; annual billing isn't implemented, so its CTA is disabled + badged rather than starting a checkout billed monthly under an annual label. **Four capabilities design 5c advertises are marked "em breve" rather than claimed as shipped** (a second AI model, per-plan seats, a priority queue/API, dedicated support — none exist), and **"Plano de corte automático" and "Histórico ilimitado de versões" are deliberately absent from every bullet list rather than shown as a paid differentiator**, because both ship free on every plan. "Falar com vendas" is always disabled — there is no destination to link to. CTAs: signed-out → `/signup`; signed-in on another plan → `/settings?section=plan` (where the real enforcement lives); the current plan shows "Plano atual".
- **`/pattern/[id]/export`** — see the Export section.

### i18n (`next-intl`, single-locale pt-BR, no routing)

- One locale, no `[locale]` segment or middleware: `app/layout.tsx` calls `getMessages()` and wraps the tree in `NextIntlClientProvider` with the single catalog `messages/pt-BR.json`, keyed **per component namespace** (`Footer`, `Topbar`, `ChatPanel`, `TechSheetTab`, `Login`, …). Every component reads its own namespace via `useTranslations("ComponentName")` — all static UI chrome (headers, labels, empty states, "em breve" notes) comes from the catalog, never hardcoded pt-BR JSX. (Every display-text screen was a client component until `app/verify/page.tsx` — see below — the project's first server component with display text, using `await getTranslations(...)` directly; its interactive part, `components/auth/VerifyCard.tsx`, is still a client component reading the same `Verify` namespace via `useTranslations`. `/login` and `/signup` followed the same split under #109, so `generateMetadata` could set each route's tab title: `app/login/page.tsx`/`app/signup/page.tsx` are now the server-component shells rendering the static heading, and `components/auth/LoginCard.tsx`/`SignupCard.tsx` hold the interactive form, still reading the `Login`/`Signup` namespaces via `useTranslations`.) This is deliberately **not** a translation system — it's the seam that lets one land later without another sweep through every component.
- `lib/` stays framework-free (no `next-intl` import), so functions that produce display text take an injected resolver (shipped as "i18n Fase 2"): `Translate` (`lib/i18n/translate.ts`, `(key, values?) => string`) — next-intl's `t` (from `getTranslations` in route handlers, `useTranslations` in components) is structurally assignable to it and passed through `draftGarment`/`draftPiecesCm`/`buildExportModel`/`planCutLayout`/`applyGarmentSpec`/`refitSleeve`. Drafter strings (`piece.detailRows`/`name`) and `detectConflict`'s title/description/suggestion live in the `PatternData` namespace (plus `GeneratingOverlay.steps` and `TechSheetTab.garmentType`/`gender`). Drafters emit the **resolved string**, not the key, so the persisted blob shape is unchanged — no reset migration was needed.
- A persisted `Pattern` holds a draft-time-locale snapshot: its piece labels/conflict text reflect the locale in effect when it was drafted, not retranslated except by the next generation, "Corrigir manga", or graduation.
- The verification email's copy lives in the `VerificationEmail` namespace and reaches `lib/mail/templates.ts`'s `verificationEmail(t, link, name)` through the same injected `Translate` seam, scoped to that namespace by the caller (`getTranslations("VerificationEmail")` in the verify/resend routes) before it's passed in.
- The AI's `assistantMessage`/chat text is model-produced, outside the catalogs entirely: `lib/ai/prompt.ts`'s system prompt (written in English) instructs the model to mirror the language of the user's own message in `assistantMessage` and clarifying-question labels/options — so an AI chat reply may not be pt-BR even though the rest of the UI is.
- **The wire and the database carry codes, never pt-BR prose.** Every `app/api/*` error payload is `{status, error: <code>}` where the code is machine-readable and the client resolves it through the catalog (`t("errors." + code)`), the `SignupErrorCode` precedent. Shared route-level codes and the `apiError` helper live in `lib/api/errors.ts`; **domain codes stay beside their own pure logic** (`ChangePasswordResult` in `lib/account/settings.ts`, `SignupErrorCode` in `lib/account/signup.ts`) because those unions type a pure function's return — each route unions the two and maps its own HTTP statuses in a local `Record`, the way `app/api/signup/route.ts` already did. `apiError` takes a bare `string` for exactly that reason: a fixed union would drag every domain union into `lib/api/errors.ts` and invert the dependency. Its internal `STATUS_WORD` map reproduces each response's pre-existing wire `status` discriminator, **warts included**: `/api/account/*` answers its 404 with `status: "error"`, not `"not_found"`.

### Export (client-side transform, no server call)

> Full rationale — the offset/mitre math, the `foldEdge`-is-a-chord finding, the sheet-packing overlap bug, and every per-format decision: [`docs/decisions.md`](docs/decisions.md).

- **`lib/export/` turns the drafted pattern into a downloadable file with no API route, credit cost, or state mutation.** `buildExportModel(pattern, t)` (`model.ts`) re-drafts in exact cm via `draftPiecesCm` — **it never reverses the store's px back to cm**, so it doesn't inherit `PX()` rounding. The `ExportModel` is format-agnostic: per-piece outlines as typed cm segments (`line`/`cubic`, Béziers preserved) plus grainline/dart/notches/name/qty.
- **Every piece carries two outlines (#123): `outline` (the net sewing line) and `cutOutline` (the real cut boundary, `outline` offset outward by `seamAllowanceCm`).** Before this, `seamAllowanceCm` was an annotation nothing exported turned into geometry.
- **`offsetOutlineCm` (`offset.ts`) computes `cutOutline` with one rule that _is_ both required corner treatments at once**: flatten curved spans to a dense polyline (via the shared `bezier.ts`'s `flattenCubic`), translate each fine segment outward, and rebuild each vertex as the intersection of its two adjacent offset lines — a convex corner's lines diverge past the original vertex (mitre), a concave one's cross before it (trim). No per-corner branching. **Outward direction is self-calibrated, never assumed from a fixed winding** (drafters walk some pieces clockwise, others not): it builds both candidate polygons and keeps the larger-area one. `removeSelfCrossingLoops` repairs the one real limitation — a sharp reflex feature (a max-depth V-neck apex) can leave a self-crossing loop. Verified against the real `DECORATION_CASES` matrix, not hand-built shapes.
- **`foldEdge` is a chord, not a boundary edge.** It names two diametrically-opposite vertices on an already-whole, mirrored outline, because every current drafter joins both halves before attaching it — there is no literal edge to zero out, and the adjacent-edge check in `offsetOutlineCm` is inert for every piece any drafter produces today. It doesn't need to fire: at a true axis-of-symmetry vertex the tangent is forced perpendicular by the mirror symmetry, so a uniform offset already keeps the point on the fold line. The check stays wired for a future drafter that genuinely emits a half-piece.
- **A mitred convex corner can grow past a plain edge offset, and any packer must reserve for that or two pieces' cut lines touch.** Mitre growth is `d / sin(θ/2)` — unbounded as the corner sharpens; measured up to ~4.9 cm per side at the maximum allowance, so two neighbours' combined growth can exceed a fixed 8 cm gap outright. `buildExportModel` computes each piece's `growLeft`/`growTop`/`growRight`/`growBottom` and packs by the effective footprint, offsetting `originCm` so the **cut line's** bbox lands on the shelf cursor. `planCutLayout` fixes the same exposure differently — re-zeroing each `CutInstance` to the cut line's own bbox up front, since a fresh instance shares no frame with a net outline.
- `exportPattern(pattern, format, t, onError?, size?, opts?)` builds the model, serializes, and downloads via `downloadFile` (`download.ts`, the only DOM touchpoint), dispatching all seven formats (`svg`/`dxf`/`dxf-aama`/`pdf-a4`/`pdf-single`/`pdf-layered`/`plt`) through an exhaustive `switch`/`never`. `opts: ExportRenderOptions` (`{pageSize?, rollWidthCm?}`) is optional and additive. The `Footer`'s menu is disabled when a conflict is active, the pattern is blank, or there is no `spec`.
- **Per format:**
  - `toSvg` — 1:1 in mm (`MM = 10`). Cut line solid and primary; net line a secondary dashed gray, its dash distinct from the grainline's and the fold's. Notches are short solid `#000` ticks (a notch is a cut mark, not a construction line).
  - `toDxf` — generic geometry-only, `$INSUNITS=4` mm, Y flipped, named layers `CONTORNO` (cut) / `COSTURA` (net) / `INTERNO` / `GRAINLINE` / `TEXTO` / `DOBRA` / `PIQUE`. Cubics flattened by adaptive De Casteljau at 0.2 mm.
  - `toDxfAama` — a **"compatível AAMA/ASTM D6673" subset**: numbered layers with fixed semantics (`1` cut boundary, `4` notches, `6` fold, `7` grainline, `8` internal/dart, `13` drill holes, `14` sew line), each piece in a `BLOCK`/`INSERT`, header R13 with classic `POLYLINE`/`VERTEX`/`SEQEND` for wider Audaces/Gerber compatibility. **Still tagged "beta" — not for a modelling gap any more, but because none of it has ever been opened in a real CAD importer**, only parsed back apart in this repo.
  - `toPdf` — 1:1 in four modes. `"a4"` tiles with page numbering and a 10 cm calibration ruler on sheet 1; `"single"` is one page the exact size of the sheet; `"roll"` (#135/#136) is a single row of numbered strips up to `rollWidthCm` wide, overlapping by `STRIP_OVERLAP_CM`, its math in the shared `strips.ts` so PLT reports the same strip count. `PdfPageSize` (`"a4" | "a0" | "letter"`) parameterizes `"a4"` only — `"single"` is sized to the pattern, not a named format. Loads `pdf-lib` via a dynamic `import()` inside `toPdf`, code-splitting it out of the main bundle.
  - `toPdfLayered` (#136) — one real **Optional Content Group per size** on a single sheet, plus a legend and the calibration ruler, redrafting one `ExportModel` per size in `baseSize` ∪ `sizesApplied`. Each size gets its own `LAYER_PALETTE` color. **The net sewing line and fold are deliberately not drawn at all** — overlaying N monochrome sets would be illegible, and `Footer.formatPdfLayeredNote` states that gap on the export menu itself. Note a byte search for `/OCProperties` finds nothing (pdf-lib defaults to `useObjectStreams: true`); inflate the object streams to verify.
  - `toPlt` (#135) — standard HPGL/2, `1016/2.54` units per cm. Distinguishable pens mirror the DXF layer split one-for-one; drill holes use HPGL/2's native `CI`. Verified two ways, neither a real device: **structurally** by `plt.test.ts`, and **differentially** by `plt.differential.test.ts`, which parses the output back with `plt-test-reader.ts` — an HPGL reader written from the format's semantics that **imports nothing from `plt.ts`** — and compares the drawn geometry against the `ExportModel`, across the `DECORATION_CASES` matrix. That second pass exists because a serializer and its own string assertions can share a misconception; it is **test-only** and deliberately not the seed of a PLT importer (`/import`, #11, is where one would live). **Still badged "beta", the larger of the two uncertainties: never plotted on a physical device** — an independent parser agreeing is not a device agreeing — and `LB` text renders in whatever font the plotter has loaded. Both caveats are stated on-screen.
- **The cm-accurate model is reused on-screen too.** `buildPathD` is the shared outline→`d` builder for `toSvg` and the React previews. `planCutLayout` (`cutplan.ts`) computes a real nesting — expanding each piece by cut quantity and packing copies into a selectable fabric-width strip, grain locked, no rotation — and **nests the cut line, not the net line**, so a larger seam allowance legitimately consumes more length. Backs `CutPlanTab` and `TechSheetTab`.
- **`planCutLayout` exposes two `NESTING_MODES`, both nesting each copy's _bounding box_, not its outline (#8)** — true no-fit-polygon nesting is out of scope and `CutPlanTab.layoutNoteAuto` says so. `"auto"` is the best of two pure packers (shelf and bottom-left skyline), never worse than shelf by construction and measured up to ~31% shorter. `"manual"` starts from the auto placement and overwrites named origins, clamped inside the fabric width; `overlappingInstanceIds` **flags but never auto-corrects** an overlap, per "a control must not rewrite what you typed." No rotation is offered at all — not even 180°, since MoldAI doesn't model directional/napped fabric. Placements live in `useEditorStore`, cleared on the same version-change reset that clears `measurements` (a regeneration changes the copy set), and **do not survive a reload** — `CutPlanTab.layoutNoteManual` says so.
- **`/pattern/[id]/export` is a dedicated screen (design `5h`, #17), distinct from the editor footer's menu** — `ExportShell` through `AppShell`. Lists every real `EXPORT_FORMATS` entry plus the unbuilt ones disabled and badged; an options panel whose unbacked controls are **honestly disabled with a stated reason** while page-size/roll-width are real and format-conditional; and a checklist (conflicts, closed-piece count, fabric consumption) that **blocks** the download while a conflict is active.
- **`User.exportPreset Json?` is one preset per account** — not per pattern, not multiple named presets, matching design 5h's single affordance. `GET`/`PUT /api/account/export-preset` round-trip it, and `lib/db/exportPreset.ts` **re-validates on every read and write** through `validateExportPreset` (drop-unknown/clamp-out-of-range/never-throw, the `validateSizeChartPatch` contract), so a hostile or stale body can never persist verbatim. `PUT` deliberately stays on `readJsonObject`, not `parseBody` — the validator already owns the whole trust boundary. `ExportShell` fetches on mount but first paint is always `DEFAULT_EXPORT_PRESET`, matching the server render, so there is no hydration mismatch. **`localStorage` was dropped, not kept as a fallback:** a per-browser cache of an account-level fact is the same duplicated-fact mistake as `Wallet.planLabel`.
