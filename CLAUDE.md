## Project stage

## Conventions

- **Commits:** always English, [Conventional Commits](https://www.conventionalcommits.org/) — `type(scope): summary` (e.g. `feat(i18n): add pt-BR catalog`, `fix(export): clamp dxf tolerance`). Common types: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `ci`, `style`.
- **Language boundary:** code identifiers, wire keys, enum values, Prisma models/columns, and routes are **English**; UI display text is **pt-BR**; the AI's chat replies mirror the user's own language (see i18n below). Full-page screen routes are English — `/pattern/[id]`, `/settings`, `/size-charts` (the first two were renamed from `/molde/[id]`/`/configuracoes`, along with `Molde`→`Pattern` and `/api/moldes/*`→`/api/patterns/*`).
- **Translate domain terms from the pt-BR design doc, don't transliterate them:** "grades" → `SizeChart` (not `Grade`), "molde" → `Pattern` (not `Molde`). Both were shipped transliterated first and each cost a repo-wide rename sweep — files, functions, routes, Prisma models/columns, i18n keys, plus a migration apiece (`rename_molde_to_pattern`, `rename_grade_to_size_chart`). Get it right up front. (Separately, the earlier general PT→EN rename of the persisted `EditorState`'s keys/values changed the stored JSON shape and required `reset_moldes_english`, which wiped every persisted pattern blob — a wire-shape change, not just an identifier rename, is the expensive kind.)
- **UI labels come from catalog lookups keyed by the EN enum value** — e.g. `t("garmentType." + spec.type)` in `TechSheetTab`, the `PatternData` namespace's `neckline.*`/`skirtSilhouette.*`/`sleeveType.*` keys resolved inside the drafters — never hand-written `Record<Enum, string>` label maps.
- **The core flow has to be audible, not just visible.** The app shipped with five live regions, none on the path a user walks: you sent a chat request and the AI's reply appeared announcing nothing, and the multi-step generation progress changed announcing nothing. `ChatPanel`'s thread is `role="log"` + `aria-live="polite"` (`log`, not a bare `aria-live`, so only the new turn is read rather than the whole history); `GeneratingOverlay` is `role="status"` and is the **single** live region for progress — `ChatPanel` renders the same step text in its composer and is deliberately left silent, or every step would be announced twice; each screen's loading state is `role="status"` and its load error `role="alert"`.
- **Surface feature limitations on-screen, never silently.** A scope boundary, unsupported case, or mock standing in for the real thing must be explicit where the user meets it (inline note, disabled control with a reason, badge) rather than failing, no-op'ing, or pretending completeness. Mark planned/feasible-later capabilities **"em breve"** so they're distinguishable from hard limitations, and prefer showing an option disabled+badged over hiding it. Anchors: the `Prova 3D` tab's honest "ainda não disponível" empty state; the AAMA/ASTM DXF export tagged "beta" with its gaps noted inline.
- **Design tokens live in `app/globals.css`** as Tailwind v4 `@theme` variables (colors, radius, shadow scale) — this project has no `tailwind.config.ts`. Fonts (Bricolage Grotesque for display/titles, Archivo for UI/body) load via `next/font/google` in `app/layout.tsx`, exposed as CSS variables. Extend the `@theme` block; never hardcode hex values in components. One token deliberately diverges from the handoff: `--color-muted` was darkened from `#8b8779` to `#6e6b60` because the original sat at 3.2–3.6:1 and failed WCAG AA on every ground it is used against; `#6e6b60` clears 4.5:1 on white, surface-alt, paper, olive-tint and amber-bg, and stays lighter than `--color-muted-2` so the two-level text hierarchy survives.
- **shadcn/ui is installed, but the MoldAI tokens stay the source of truth.** `components.json` (hand-written — never run `shadcn init`: it overwrites the `@theme` block with its own oklch palette), `components/ui/`, `lib/utils.ts`'s `cn()`, and the version-pinned `shadcn` MCP server in `.mcp.json`. shadcn's semantic names (`--color-primary`, `--color-background`, `--radius-md`, …) exist only as a **second `@theme inline` block aliasing the MoldAI tokens above** — never give one a literal value. `--color-border` and `--color-muted` are deliberately **not** aliased: they are MoldAI tokens with ~90/~105 existing call sites, and shadcn means a _surface_ by "muted" where this repo means _text_ — so a ported component's `bg-muted` becomes `bg-surface-alt`, while `text-muted-foreground` maps through and works as-is. The app is light-only: `@custom-variant dark (&:is(.dark *))` keeps the `dark:` classes shadcn ships inert (without it, Tailwind v4 fires them on `prefers-color-scheme` and a dark-OS visitor gets half-dark controls on a light page). Every screen consumes these primitives now; raw `<button>` is down to 4 deliberate exceptions (the pattern thumbnail surface, the two paywall plan cards, the multi-line size-chart rows — clickable _regions_, not controls). Tune a primitive in `components/ui/`, never with per-call-site `className` overrides: that is where the extra `Button` sizes/variants (`chrome`, `accent`, `soft`, `destructiveOutline`), `Badge`'s `size="chip"` and `soon`, and the `text-sm`→`text-ui`/`text-control` retuning live. **The chat stream is `bubble` + `marker`,** whose variants are the design's own: `default` (olive, the user's turn), `paper` (the AI's), `notice` (amber — a seam conflict, a failed generation, or a size-chart substitution; deliberately not `destructive`, which is the red alert token), `surface` (white, for a bubble holding controls rather than prose — the clarifying-question card). `ChatMessage.tone` carries `"notice"` alongside `"conflict"`: both render the amber bubble, but they stay distinct in the data model because an informational caveat is not a seam conflict. `components/ui/textarea.tsx` was added via `shadcn add` for the chat composer and retuned like the rest — its stock `text-base`/`md:text-sm` replaced by `input.tsx`'s `text-body`/`md:text-control` pair. The 3px corner in `BubbleContent` is the bubble's tail, not a `--radius-*` step. Three sibling registry items were considered and skipped: `message` (pure align/avatar/header scaffolding this chat has no use for), `attachment` (a full upload-lifecycle card, where MoldAI has three permanently-disabled "em breve" pills), and `message-scroller` (a new `@shadcn/react` runtime dependency that injects CSS into `app/globals.css`, overwrites `button.tsx`, and virtualizes a list holding a handful of messages — its one real benefit, not yanking a reader who scrolled up, is ~10 lines in `ChatPanel` instead). **`ScrollArea` carries two local additions, both forced by Radix:** `viewportRef` (the scrolling element is the viewport, not the Root — `ChatPanel`'s scroll-to-bottom has to target it) and `fill` (Radix wraps content in an inline-styled `display:table` box, which has no definite height and so collapses a `flex-1` child; `fill` swaps in a block box at the viewport's height and the call site adds `min-h-full` — needed by `PatternGrid`'s `Empty` states, `CutPlanTab`'s empty state and `SizeChartsShell`'s two full-height columns). Its scrollbar defaults to `type="auto"`, visible exactly while the content overflows like the native bar it replaces, and its thumb is `bg-muted` rather than shadcn's `bg-border`: #ded9cc reads 1.26:1 on paper, so a hand-drawn thumb in it would be invisible where the native one was not, and a draggable thumb owes WCAG 1.4.11's 3:1. After any `shadcn add`: review the `app/globals.css` diff (`cssVariables: true` lets the CLI inject into it) and run `npm run format`, since the CLI's output doesn't match this repo's prettier config. `components.json` carries no `registries` map on purpose: `@shadcn` is built-in and its real URL holds an internal `{style}` placeholder, so hand-writing it would shadow the built-in with a broken one — pass `registries: ["@shadcn"]` explicitly to the MCP's search/list tools instead. The `shadcn` skill is installed at `.claude/skills/shadcn/` (pinned in `skills-lock.json`); it will suggest `shadcn apply <preset>` / `init --preset`, which **overwrite CSS variables and components** — never run either here, they would wipe the alias layer.
- **Type comes from the named scale, never `text-[Npx]`.** `app/globals.css` defines 7 steps as `--text-*` tokens — `text-tick` (10.5px) · `text-meta` (11.5) · `text-ui` (12.5, the default UI size) · `text-control` (13.5, buttons/inputs/tabs) · `text-body` (16) · `text-title` (21) · `text-display` (26) — each set to the dominant member of a measured cluster, collapsing the 259 ad-hoc `text-[Npx]` values that had drifted across 19 near-duplicate sizes (11/11.5, 12/12.5, 13/13.5). Uppercase labels take `tracking-eyebrow` (`0.08em`, so the tracking follows the step it is set at instead of pinning one absolute value across three sizes) — one named value for the 3 ad-hoc positive trackings that had drifted apart (`.8px`, `.6px`, `.5px`); the wordmark's display tightening is `tracking-wordmark` (`-0.4px`), named after its only user. Body text is `font-normal` — `font-semibold` had spread to 85 call sites and stopped meaning emphasis. **The sweep is finished, and staying at zero is the rule, not an aspiration:** `app/` and `components/` hold no `text-[Npx]` and no bracketed tracking, and the shadcn primitives carry no stock Tailwind size either (`text-sm`/`xs`/`base`/`lg` → `text-control` for controls, `text-ui` for secondary copy, `text-meta` for small print, `text-body` for headings), because a 14px shadcn default is out of scale against a 12.5px UI. A glyph used as an icon is sized as an icon (lucide + `size-*`, or `EmptyMedia`), never priced on the type scale — the `◍` at 28px in the `Prova 3D` empty state was the last of those.
- **Every full-page screen renders through `components/shared/AppShell.tsx`**, with one deliberate exception: `/login`, `/signup` and `/verify` are centered-card screens with no header, so they render their own `Wordmark` directly instead of going through `AppShell`. For every other screen, `AppShell` owns the page frame (header row, optional sidebar slot, content region as a flex column, optional footer slot) and builds `components/shared/PageHeader.tsx` itself from plain data props, so a screen cannot hand-roll a header. `PageHeader` is the one header: wordmark (`components/shared/Wordmark.tsx`, also used by the three centered-card auth screens above), optional `← Voltar`, title/subtitle, credits bar, "Comprar créditos", and an avatar dropdown carrying the `/settings` deep links plus sign out. Three props are deliberately optional, all three because of the dashboard: `backHref` (it **is** `/`, so a back button would point at the screen you are on); `title` (its sidebar already marks "Meus moldes" active, so a header title printed the same words twice — and with neither `backHref` nor `title` the wordmark's trailing `Separator` is suppressed too, or it would dangle against the empty spacer); and `credits`, which is nullable because the dashboard's balance arrives after first paint — the bar and "Comprar créditos" are simply absent until it lands, instead of the header flickering in. That last one is honestly named "transient" only on the happy path: if `GET /api/account/summary` fails, `credits` stays null for good and the content region's error message is what keeps the missing bar from being silent. There is **no global nav sidebar**; `sidebar` is whatever column the screen owns (`dashboard/Sidebar`, `SettingsSidebar`), and the editor and `/size-charts` pass none. `AppShell` itself renders `{sidebar}` bare — the 186px width (`w-[186px] border-r bg-surface p-[14px]`) is each sidebar component's own chrome, not a slot `AppShell` sizes, so a new sidebar-bearing screen must set that width itself. A screen whose body is a row (the editor: chat + canvas) passes one child that is itself a row. The editor is also the one screen that keeps a full-screen loading early-return rather than putting it in the content region, because the header's title _is_ the pattern name.
- **A display name that reaches a layout needs a cap _and_ a truncation.** `MAX_PATTERN_NAME_LENGTH` (`lib/types.ts`, beside `COSTS`) is enforced by `PATCH /api/patterns/[id]` and reused as the rename dialog's `maxLength`, so the field stops you before the round trip does. The API had accepted a 5000-character name, and neither `PageHeader`'s title nor `PatternCard`'s name truncated — the tell was that `lib/account/settings.ts` already capped the _user's_ name at 80 while a pattern's was unbounded. Both now `truncate` with `min-w-0` on the flex column; without `min-w-0` there is nothing for `truncate` to shrink against and the overflow just shoves its siblings (the credits bar and avatar off the header, the "⋯" menu off the tile).
- **A control must not rewrite what you typed.** `SizeChartTable`'s cells displayed `resolveSizeChartSize`'s _clamped_ output and wrote every keystroke straight back with `Number(e.target.value)` — the round trip corrupted the input outright: clearing the bust cell and typing "96" stored **1406**, each digit appended to the clamped value the previous digit produced. (`Number("")` being `0` was the smaller face of it: clearing a cell rewrote 92 to the range minimum.) `MeasurementCell` holds the in-progress text locally and commits only on blur/Enter, only when it parses and is in range; out-of-range or emptied gets `aria-invalid` plus a message naming the accepted range (lifted to the table — a 56px column has no room), and Escape restores. The progression-rule input is deliberately untouched: it is not clamped on display, so it has no feedback loop, and `0` is a meaningful rule value.
- **Don't add abstractions beyond what's needed** — e.g. `/settings` deliberately has no Zustand store: it has no cross-component shared state and section choice lives in the URL, so local `useState` per section is enough.
- **`.claude/hooks/check-conventions.mjs`'s hardcoded-pt-BR check (CHECK 1) and hex-color check (CHECK 2) scan `.tsx` files; its i18n key-existence check (CHECK 4) matches only a literal `t("…")` first argument** (it does not evaluate a template-built key like ``t(`plans.${plan}.name`)``, the `PageHeader` plan lookup above). The wire-error-codes sweep is the standing lesson on why a manual pass still matters: no single grep shape is a complete audit for display text — `lib/export/pdf.ts`'s tiled-page label was a backtick template and its calibration-ruler label opened on a digit, and `lib/sizeCharts/seed.ts:42`'s two system-chart names contain no accented character at all, so an accent-class pattern couldn't see them either. Three successive audit passes each found something the previous one missed.
- **Component tests are the `dom` vitest project** — jsdom + React Testing Library, configured in `vitest.workspace.ts` as a **second project** so the pure-logic `node` suite never loads the DOM setup file. `vitest.setup.ts` installs the jest-dom matchers, RTL auto-cleanup, and the browser APIs jsdom lacks that the Radix primitives call (`ResizeObserver`, pointer capture, `scrollIntoView`, `matchMedia`) — a Radix component that will not open in a test is almost always a missing one of those, not a broken assertion. Render through `renderWithIntl` (`components/test-utils.tsx`), which wraps the tree in the **real** `messages/pt-BR.json` rather than a stub translator — but next-intl does not throw on a missing key: it renders the literal key path (e.g. `"ProfileSection.errors.unauthorized"`), logs `IntlError: MISSING_MESSAGE` to the console, and **the test still passes**, verified empirically, not assumed. An assertion matching a substring, a regex, or the key name itself is therefore vacuous — it passes whether or not the catalog actually has the string — so catalog-text assertions must compare against the exact resolved `ptBR` value, never a pattern that a missing-key fallback could also satisfy. This is not hypothetical: an `unauthorized` catalog gap shipped mid-branch unnoticed and had to be fixed once a real assertion caught it. (The repo also has no next-intl typed-messages augmentation, so `t()` keys are checked statically in neither direction — not against the catalog, not against call sites.) For catalog-sourced display text — button labels, menu items, empty states, anything a component reads from `messages/pt-BR.json` — assert against the exported `ptBR` catalog object, never against a pasted pt-BR literal: the no-hardcoded-display-text rule applies to tests, and it makes a copy change a one-place edit. That rule governs assertions on catalog text, not test data: arbitrary strings passed in as fixture props (a pattern name, a garment label, a formatted subtitle like `AppShell.test.tsx`'s `"Configurações"` or `PageHeader.test.tsx`'s `"Meus moldes"`/`"Blusa"`/`"há 2 min · v3"`) are fine as plain literals, since they're test-supplied data rather than app-owned copy. (`.claude/hooks/check-conventions.mjs` already exempts `*.test.tsx` from the mechanical hardcoded-pt-BR check, so this written rule is the only thing governing the distinction.)

Also in `package.json`: `test:watch`, `typecheck`, `format`/`format:check`, `cron:renew` (one wallet-renewal sweep — see Billing). There is no seed script anymore — a dev account is created the same way a production one is, through `/signup`, then confirmed via the verification link in Mailpit's inbox at `:8025` (dev stack only). `smoke`/`smoke:prod` therefore need `SMOKE_EMAIL`/`SMOKE_PASSWORD` pointed at an account created that way.

**Docker vs host:** Inside the container, the app talks to Postgres at `db:5432` (Docker Compose DNS); on the host, at `localhost:5433`. Secrets (`.env.local`) come in via `env_file` at runtime — never baked into the image. A third compose service, `cron`, runs the hourly wallet-renewal loop (defined in `docker-compose.yml`, so it runs in both the dev and prod stacks). A fourth base-compose service, `redis` (host **6380**, `redis:6379` inside the network — same split as Postgres' 5433/5432), backs rate limiting in both the dev and prod stacks. `docker-compose.override.yml` adds a dev-only **Mailpit** (SMTP **1025**, web inbox at **:8025**) and points the app's `SMTP_*` at it; Compose auto-merges an override file for a bare `docker compose up` (`npm run docker:up`) and ignores it for the explicit two-file prod stack (`npm run docker:prod`), so production never gets Mailpit. `.env.example` documents every variable.

**Two dev-stack traps, both bind-mount-related and neither an app bug.** Turbopack's watcher misses edits through the Windows bind mount and the HMR socket never handshakes, so `docker restart moldai-app` after editing (or run `npm run dev` on the host instead). Worse, one route silently isn't served: **`POST /api/patterns/[id]/conflict/resolve` answers 404 in the Docker dev stack**, so the seam-conflict buttons ("Corrigir manga" / "Ignorar") appear broken there. Measured, on a freshly rebuilt container with renewed volumes: its depth-1 siblings (`[id]/generate`, `size-charts/[id]/activate`) and a depth-2 route with no dynamic segment (`verify-email/resend`) all answer 401, so the guard is reached; only the route two static segments below a dynamic one — whose intermediate `conflict/` directory holds no `route.ts` — 404s. The same request answers 401 against `next dev` on the host, and `npm run build` lists the route, so verify anything touching it on the host, not in the container. (Cause unconfirmed: presumably Turbopack's route discovery over the mount.) Also: the container's `node_modules` and `.next` are anonymous volumes, so `--renew-anon-volumes` against a stale image resets dependencies to whatever that image baked — rebuild the image first (`docker compose up -d --build app`), then renew, or the app boots unable to resolve packages added since.

## What this is

MoldAI is an AI pattern-making product for clothing: chat with an AI to generate/adjust 2D sewing patterns, grade sizes, and export to Audaces/Molde.me/plotter/PDF. This repo is a Next.js app with a real backend — the "real backend" roadmap (Phase A auth → B persistence → C billing) is fully shipped:

- **Auth:** Auth.js v5 (Credentials + JWT), users in Postgres via Prisma. Self-service sign-up at `/signup` creates the account and mails a verification link; it does **not** sign the visitor in. `authorizeUser` returns `AuthorizeResult` — `{ok:true,user}` or `{ok:false,reason:"invalid"|"unverified"|"rate_limited"}` — and `auth.ts` maps `invalid` to Auth.js's generic `null` and the other two to `CredentialsSignin` subclasses carrying `code: "unverified_email"` / `"rate_limited"`, so `/login` distinguishes them. Verification tokens are sha-256 digests of 32 random bytes, 24 h, single use, newest-only (`lib/auth/verification.ts` pure + `lib/db/verification.ts` repo; migration `20260820120000_add_email_verification`, additive, backfills every existing user as verified). Mail goes through `lib/mail/` (`nodemailer`); with `SMTP_HOST` unset it logs the link outside production and throws (`mail_unavailable`) in production — never a silent drop. **Verified live** against the dev stack (real Postgres + Redis + Mailpit), not just unit-tested: the migration applied via `prisma migrate deploy`, and a pre-existing account logged in through the full credentials flow afterwards — which is what proves the backfill's grandfather clause. Sign-up → Mailpit → confirm → login works end to end; the mailed subject renders from the catalog (so `getTranslations` inside a route handler is exercised, which no unit test covers); a login before confirming returns `unverified_email` rather than a bad-password error; a consumed token is rejected on reuse; and with the `login_email` bucket exhausted the correct password is still throttled, while stopping Redis lets it through with `[rate-limit] … failing open` — the documented trade-off, observed.
- **Chat:** a real Anthropic API call (`claude-sonnet-5`) interprets the user's request and returns a `GarmentSpec` (garment type + measurement overrides + style); the server validates/clamps that spec and drafts the pattern pieces from it.
- **Patterns:** persisted per account, many per account (the dashboard's list).
- **Billing:** a real per-account `Wallet` + append-only `Transaction` ledger, shared across the account's patterns. The **only mock left is the payment gateway** — "purchase"/"subscribe" simulate instant success instead of charging a card.

Requires `ANTHROPIC_API_KEY`, `DATABASE_URL`, and `AUTH_SECRET` in `.env.local`.

## Architecture

### Data layer: pure logic + thin repositories

- `Pattern` (Prisma) has its own cuid `id` with `userId` as a plain indexed foreign key — many patterns per account. Each row holds a `PatternState` JSON blob (pattern, chat, active conflict — no credits).
- Editor-state logic is pure and DB-free in `lib/editor/state.ts` (`seedPatternState`, `addMessage`, `bumpVersion`, `setConflict`, `applyGarmentSpec`, `refitSleeve`, `applySizes`), unit-tested without a live DB.
- `lib/db/pattern.ts` is the only layer touching Prisma for patterns. Every function is scoped to `(patternId, userId)` and returns `null`/`false` — never throws, never leaks whether the row exists — when the pattern is missing or not owned; routes turn that into `patternNotFound()` (404).
- `withPattern(patternId, userId, fn)` runs load→mutate→save in an interactive transaction with a row lock (`SELECT … FOR UPDATE WHERE id = $1 AND userId = $2`), built from the exported primitives `lockPattern`/`savePattern` so `withPatternAndWallet` (below) reuses the same SQL. The transaction timeout is raised to 30s because the AI call runs inside it.
- CRUD: `loadPattern` (ownership-scoped read), `createPattern` (new blank pattern), `listPatternsForUser` (projects `{id, name, garmentType, updatedAt, thumbnailSvg}`; the thumbnail is server-built by `lib/editor/thumbnail.ts`'s `buildThumbnailSvg` from the already-drafted pieces — no redraft, no AI call), `renamePattern`, `deletePattern`. There is no pattern-reset endpoint — delete + create replaces it.
- Every `app/api/*` route is gated by `requireUser()` (`lib/auth/guard.ts`) — 401 without a session. Auth logic is likewise pure/DB-free (`lib/auth/authorize.ts`, `lib/auth/session.ts`); the NextAuth config is `auth.ts` (`trustHost: true` for self-hosted/prod).
- `Pattern` has **no `savedAgo`**. It was persisted pt-BR display text that nothing recomputed — the editor header claimed "salvo agora" indefinitely, including after a reload, a live bug independent of this sweep's scope. The wire carries `updatedAt` instead and the editor renders `relativeTime(t, updatedAt)`. The final shape is not `Pattern` plus a field: `Pattern` (`lib/types.ts`) stayed blob-only, and a new **`PatternRecord extends Pattern { updatedAt: string }`** is the wire shape used by `EditorState.pattern` and the editor store — the existing `SizeChartRecord extends SizeChartData` precedent. That makes an absent `updatedAt` unrepresentable rather than merely unreachable: leave it out and `relativeTime` falls through to render the literal string "Invalid Date" instead of compiling to a value that's simply never missing. `loadPattern` widened to return `{state, updatedAt}`; `lockPattern` deliberately did **not**, because `savePattern` sets `updatedAt = now()` inside the same transaction, so a mutating route's own `now` already _is_ the row's timestamp. No reset migration was needed — old blobs keep an inert `savedAgo` key that nothing reads, the cheap direction of a blob change, unlike `reset_moldes_english` above.

### Rate limiting

Redis-backed fixed window: `consume()` (`lib/rate-limit/consume.ts`) runs one atomic `MULTI` — `INCR` + `EXPIRE … NX` + `TTL` — so the window starts on the first request and expires itself; no sweep job. The whole policy is the table in `lib/rate-limit/limits.ts`, seven buckets:

```
signup 5/h · signup_email 3/h · login 20/15min · login_email 10/15min
verify 20/h · resend 10/h · resend_email 5/h
```

Every sensitive endpoint gets an IP-keyed bucket **and** an email-keyed one — `x-forwarded-for` is spoofable when the app isn't behind a trusted proxy (`lib/rate-limit/ip.ts`'s `clientIp`), so the email-keyed bucket is the non-spoofable backstop. Deployment consequence: behind a reverse proxy, that proxy must overwrite `x-forwarded-for` for the IP limits to mean anything — Next only fills the header when the client didn't send one. `verify` is the deliberate exception with no email-keyed pair: there's no email in that request, and its real backstop is the 256-bit token, not a counter. In the resend route, the `resend_email` consume sits **after** the credential check and the cooldown check, so it counts mails actually attempted per address — a victim can't have their quota burned by someone without their password, and a legitimate user's impatient retries inside the cooldown (which send no mail) don't cost them anything.

The limiter reaches the pure `authorizeUser` (`lib/auth/authorize.ts`) through `AuthorizeDeps` (`consume`/`reset`), never an import, keeping that module DB-free, Redis-free, and testable with fakes. **It fails open:** if Redis is unreachable, `consume` (`lib/rate-limit/client.ts` holds the one lazy `ioredis` singleton) logs and allows — a system that locks everyone out when its cache dies is worse than one that briefly loses throttling.

**`REDIS_OPTIONS` (exported from `lib/rate-limit/client.ts`) is a correctness setting, not a preference.** `enableOfflineQueue` was `false`, to "fail fast rather than queue commands forever" — but ioredis connects lazily, so the first commands of a fresh process were issued before the socket was writeable and rejected outright (`Stream isn't writeable and enableOfflineQueue options is false`), which `consume` dutifully turned into fail-open. **Measured, against a healthy Redis: both `consume` calls in a new process's very first signup failed open** (`signup` at `route.ts:46` and `signup_email` at `:54`), so every deploy, restart and scale-out served its first sensitive request unthrottled. It is now `true`, which closes that window; "forever" is not the alternative, because `maxRetriesPerRequest` bounds the reconnect attempts a queued command waits through and `commandTimeout` (1 s) is a hard per-command ceiling. Both directions verified live: 0 fail-opens on a cold process's first request, and with Redis stopped the request still succeeds in ~1 s with `failing open` logged. `client.test.ts` asserts the three options as a regression guard, because the symptom only ever shows in a real process's first request.

**Accepted trade-off:** `login_email` is consumed before the password check, and only a _successful_ password clears it — so anyone who knows a victim's email can spend that bucket's 10 attempts and soft-lock the account for the rest of the 15-minute window; the victim's own correct password can't clear the counter, because the throttle returns first. Self-expiring and standard for per-account throttling, but a real property of the system, recorded here rather than left implicit.

### Billing (real; only the gateway is mocked)

- `Wallet` (1:1 with `User` — credits are an account-level resource, shared across all its patterns) + append-only `Transaction` ledger, same pure-logic + thin-repo split: `lib/billing/wallet.ts` + `lib/db/wallet.ts` (`lockWallet`/`saveWallet`, plus `saveLedger`). Wallets are lazily seeded on first access (`INSERT … ON CONFLICT DO NOTHING` inside `lockWallet`) — no backfill migration was written for the pre-Phase-C mock credits. New wallets seed at the design's **Free tier** (`free`/"Grátis", 30/30, 30-day renewal) rather than the pre-billing mock's Ateliê 320/500 — open sign-up must not grant a paid balance. `applyPurchase("subscribe")` is the upgrade path to Ateliê, and `PlanSection` already renders "Plano atual" off `credits.plan`, so nothing downstream needed changing.
- `generate` and `graduate` debit atomically with the pattern mutation via `lib/db/pattern-wallet.ts`'s `withPatternAndWallet(patternId, userId, fn)`: both rows locked in one transaction, **always `Pattern` first, then `Wallet`** — it is the only function ever allowed to hold both locks, which makes cross-lock deadlock structurally impossible — and it returns `null` without ever locking the wallet when the pattern isn't found/owned.
- `lib/api/compose.ts` exports `buildCredits(wallet, now)` (account-level, pattern-independent) and `composeEditorState(patternState, wallet, now)` (built on top of it) — the wire `EditorState` the client sees. `Credits.renewsInDays` derives from the real `Wallet.renewsAt` timestamp.
- Auto-renewal: `scripts/cron-renew.ts` (run via `tsx`), scheduled by the `cron` Docker Compose service (hourly loop, no external scheduler), resets `balance` to `total` and rolls `renewsAt` forward 30 days from the _scheduled_ renewal time for every past-due wallet — "use it or lose it," no accumulation.
- `POST /api/billing/purchase` simulates instant success (no real gateway). With an optional `patternId` it returns that pattern's full composed `EditorState` (so the editor shows the just-purchased credits without a second fetch); without one, `{status: "ok", credits}` (the account-level context the dashboard has). It only adds credits — it has no 402 path.
- **`type` is validated, and `applyPurchase` is exhaustive.** It used to be read through an `as` cast (an assertion, not a validation) and `applyPurchase` treated anything that wasn't literally `"topup"` as `"subscribe"` via an implicit else — so `POST /api/billing/purchase {}` answered 200 and moved the wallet from free/30 to **atelier/500**, for any authenticated user, verified against the running app. Now `isPurchaseType` narrows it (unknown/absent → 400 `invalid_purchase_type`, wallet untouched) and `applyPurchase` `switch`es with a `never` binding, so a new `PurchaseType` member is a compile error rather than a silent subscribe — the same shape `exportPattern` uses for its five formats. **The pattern is also resolved before the wallet is touched:** charging first meant `{type:"topup", patternId:"does-not-exist"}` credited +100 and then answered 404, so the credits landed and the client never saw them.
- `Wallet` has **no `planLabel`** (migration `20260821120000_drop_wallet_plan_label`). It stored pt-BR (`"Grátis"`/`"Ateliê"`) fully derivable from `plan`, which let the label drift from the plan it named. `PageHeader` now resolves ``tPlan(`plans.${credits.plan}.name`)`` from the **existing** `PlanSection.plans.*.name` catalog entries, per the catalog-lookup-keyed-by-EN-enum rule — which is what makes it work for all four `PlanId` members (`free`/`atelier`/`studio`/`factory`), not just the two `applyPurchase` ever issues.

### API routes

**Every route that reads a body does it through `readJsonObject(request)` (`lib/api/body.ts`), and there is no bare `request.json()` left in `app/api`.** It returns the object or the 400 to return, shaped like `requireUser()` so `if (x instanceof NextResponse) return x;` reads as the guard idiom already in use — and so a route that forgets the check gets a type error rather than a 500. The bug it exists for: `null` is valid JSON, so it survived `request.json()` and only threw on the first `body.field` read, which in **six** routes sat outside the try/catch. Each answered HTTP 500, measured against the running app: `PATCH /api/patterns/[id]` (`reading 'name'`), `.../graduate` (`'sizes'`), `/api/billing/purchase` (`destructure property 'type'`), `PATCH /api/account/profile`, `POST /api/account/password` (`'currentPassword'`), `POST /api/size-charts` (`'sourceId'`). Three routes had guarded it correctly — with the same explanatory comment copy-pasted into all three, which is the actual lesson: extract the guard at the second occurrence instead of duplicating the comment. `POST /api/size-charts` keeps its deliberate tolerance of an unusable body (it just means "no `sourceId`"), so there the guard result is folded into `sourceId` rather than returned.

All pattern-mutating routes live under `/api/patterns/[id]/*`, scoped to one pattern and 404'ing via `patternNotFound()`:

- `POST /api/signup` — creates an account (name/email/password) and returns `{status:"ok"}` or a machine-readable `SignupErrorCode` the client resolves through the catalog. It is unauthenticated — deliberately at the top level, outside both the `[...nextauth]` catch-all and the uniformly `requireUser()`-gated `/api/account/*`. Validation lives in the pure, DI'd `lib/account/signup.ts`; `lib/db/users.ts`'s `createUser` returns `null` on the P2002 insert race so a lost race reads as `email_taken`.
- `POST /api/verify-email` (consumes the token, stamps `emailVerified`, mints no session) and `POST /api/verify-email/resend` (credential-gated reissue, 60 s cooldown). With `POST /api/signup` and NextAuth's own handlers, these are the only unauthenticated route handlers.
- `GET /api/patterns` — the session user's pattern list; `POST /api/patterns` — create a blank one, returns its `id`.
- `GET /api/patterns/[id]` — the composed `EditorState`; `PATCH` renames (body `{name}`); `DELETE` deletes (the only way to "reset").
- `POST /api/patterns/[id]/generate` — the core AI flow (below). Debit-then-mutate; insufficient balance → HTTP 402 (no debit, no AI call).
- `POST /api/patterns/[id]/graduate` — same debit-then-mutate + 402 pattern. **Its precondition is `pieces.length === 0` → 400 `pattern_not_drafted`, not the size list.** The old `sizes.length === 0` guard could never fire for the case it looked like it covered, because a blank pattern is bootstrapped with a full `PP..GG` list — so grading a freshly created pattern answered 200, bumped version 0→1, left `pieces` at 0 and debited `COSTS.graduate`, the most expensive action in the app, for grading nothing (ledger row `debit / graduate / 6`, verified live). UI-unreachable today (the button lives in `PieceDetailsPanel`, which needs a selected piece), but `withPatternAndWallet` is the money path. The route tests had _encoded_ the bug by using a blank `seedPatternState` as a stand-in for a real pattern; they now draft one first.
- `POST /api/patterns/[id]/conflict/resolve` — free, no debit (see conflicts below).
- `GET /api/account/summary` — account-level, not pattern-scoped: `{credits, recentUsage}` (last 3 debit-type ledger rows via `lib/db/account.ts`'s `getRecentUsage`) backing the dashboard's summary cards.
- `GET /api/account/ledger`, `PATCH /api/account/profile`, `POST /api/account/password`, `DELETE /api/account` — back `/settings` (below).
- `/api/size-charts/*` — see Size charts.

### Generation flow (`POST /api/patterns/[id]/generate`)

- Debits `COSTS.adjust` immediately, then `proposeGarment` (`lib/ai/`) asks `claude-sonnet-5`, via forced tool-use, for `{ decision: "apply" | "decline" | "ask" | "explain", spec, questions?, declineReason?, assistantMessage }`.
- **`lib/ai/` is split by responsibility, all derived from one source of truth:** `prompt.ts` (sectioned system prompt), `schema.ts` (the `propose_garment` tool), `history.ts` (pure `buildHistory` — normalizes the persisted chat into Messages-API turns: serializes an ai turn's `questions` into its text, merges consecutive same-role turns, drops leading assistant turns), `decision.ts` (pure `resolveDecision` — ask/apply normalization + validation), `index.ts` (the API call; the only file importing the SDK). **The prompt's and schema's every enum and numeric bound render from `lib/draft/garment.ts`'s exported `TYPES`/`GENDERS`/`NECKLINES`/`SLEEVES`/`SKIRTS`/`STYLE_LIMITS` plus `MEASUREMENT_RANGES`** — the same constants `validateSpec` clamps with, so the model is never told a range the validator doesn't enforce. Add a style field in one place and all three follow; never hardcode a bound in the prompt or schema. The rule now covers prices and formats too: the prompt's `# Product facts` section renders its credit costs from `COSTS` and its format list from `EXPORT_FORMATS` (`lib/export/formats.ts` — a leaf module holding the array plus the `ExportFormat` type derived from it, so `prompt.ts` can name the formats without importing the export facade's serializers and `download.ts`'s DOM access; `lib/export/index.ts` re-exports both, so existing `@/lib/export` importers are unchanged).
- A `decision: "apply"` carrying no usable `spec` object (missing, null, or an array) **throws** rather than letting `validateSpec` fabricate a default blouse — the route's existing catch refunds the credit.
- **Trust boundary:** the returned `spec` is never trusted as-is — `validateSpec` (`lib/draft/garment.ts`) re-checks every enum and clamps every numeric field before use; `questions` go through `validateQuestions` the same way. The AI never emits SVG or pixel coordinates — only a `GarmentSpec`. **The same rule now covers the _user's_ size-chart patch** (`lib/sizeCharts/validate.ts`, see Size charts) — it was written for the AI's input and initially forgotten on the human's, which reaches the identical drafter.
- `apply` → `applyGarmentSpec` → `draftGarment(spec, baseMeasurements, t)` recomputes `pieces`/`viewBox`/`baseMeasurements` from scratch and bumps the version.
- `decline`, and any API/parse error, refunds the credit.
- `ask` (underspecified request) → 1–4 single-choice `questions` attached to the AI chat message (`ChatMessage.questions`), credit refunded, response `status: "clarify"` — no draft, no version bump. The client renders `ClarifyCard`; answering calls `sendMessage(phrase, { answering: true })` with the picks as natural-language text, and the `answering` flag (threaded to `proposeGarment`, enforced by a server-side guard) prevents the AI from asking again.
- **`explain` is the one non-drafting decision that is _not_ refunded.** The user asked a question — about pattern-making, or about MoldAI itself — instead of ordering a garment: the route posts the answer with the credit chip, keeps the `COSTS.adjust` debit, and responds `status: "answered"` with no draft, no version bump and no size-chart snapshot. It is charged because the Anthropic call is as real as a draft's and the user got what they asked for, where `ask`/`decline` refund precisely because they delivered nothing. `resolveDecision` throws on an `explain` carrying a blank `assistantMessage` — the message _is_ the payload there — so the route's catch refunds instead of charging for an empty bubble. This replaced the planned glossary screen (issue #20): a hand-written term list would have been a second, thinner source of knowledge the chat's model already has, and it could not answer "por que minha manga não fecha?". The prompt's `# Modeling knowledge` and `# Product facts` sections are what the decision reads from, and out-of-scope questions still `decline`.

### Seam-conflict detection (live, apply-with-warning)

- The AI-settable, `validateSpec`-clamped `style.armholeDeepenCm` (0–6 cm) deepens **only** the body's armhole, while the sleeve cap is sized from the **base** (un-adjusted) armhole (`draftAll` returns `armholeLenCm` for the body and `sleeveArmholeCm` for the sleeve) — so the two seams diverge by the adjustment.
- `applyGarmentSpec` runs `seamCheck` (`lib/draft/garment.ts`) on those two lengths; when the diff exceeds 1 cm, `detectConflict` attaches a real `ConflictInfo` (actual `diffCm`, dashed markers over the body/sleeve armhole). The generation still applies, bumps the version, and debits; the chat message gets `tone: "conflict"` and the route responds `status: "conflict"`.
- The client mirrors `state.conflict` into the existing `ConflictInfoCard`/markers; Export is blocked while a conflict is active.
- **The two divergent lengths are shown by default, and are derived rather than persisted.** `ConflictInfo` carries only their `diffCm`, so the card and the markers get the lengths from `measureSeams(spec, baseMeasurements, t)` (`lib/draft/garment.ts` — `draftAll` without the pieces or the layout, symmetric with `draftPiecesCm`), called once in `CanvasArea` and passed to both. Storing them on the blob would duplicate what `spec` already determines — the `savedAgo`/`planLabel` mistake a third time — and deriving them also gives the comparison to conflicts persisted before it existed, the `fitPieceLabel` precedent. `ConflictInfoCard` renders two labelled rows on a shared scale (the shorter seam's shortfall is the bar's `alert` remainder) plus the gap line; `PatternCanvas` labels each dashed marker with its own value, keyed off `[pieceAId, pieceBId]` and only when `markers.length === 2`, so a legacy blob whose piece had no `vertices` gets bare circles rather than a number against the wrong seam. All three displayed numbers round to 0.1 cm independently, so the two lengths need not subtract to exactly the gap; the gap stays `diffCm` because the alternative makes the card disagree with the chat message about the same divergence. This is what issue #19's "Ver diferença" became: the button was `disabled` + "em breve" and had never had a handler, and the resolution was to delete the gate — a conflict is precisely the moment those numbers matter — not to build a toggle.
- `POST /api/patterns/[id]/conflict/resolve`: "fix" calls `refitSleeve` for free — it sets the internal `style.sleeveRefit` and re-drafts so the cap uses the adjusted armhole (seams match, conflict clears); "ignore" just clears the warning, leaving the pieces divergent. `sleeveRefit` is deliberately **not** accepted by `validateSpec`, so the AI can never fake a refit.

### Drafting engine (`lib/draft/*`)

- **Pieces are drafted from measurements, not deltas.** `lib/measurements.ts` defines `Measurements` (bust, waist, shoulder, … — `shoulder` is the half-width from the body's center line to the shoulder tip, not the full shoulder seam) plus the legacy `SIZE_TABLE` (female)/`SIZE_TABLE_MALE` (male) tables, now used only as seed data for the two system size charts and the pre-generation bootstrap default.
- `resolveMeasurements(base, overrides)` applies chat-driven `measurementOverrides` onto an already-resolved base row (clamped to `MEASUREMENT_RANGES`); the base row comes from the pattern's frozen `sizeTable` snapshot (see Size charts). No size/gender table lookup happens here anymore.
- `GarmentType` = `"blouse" | "dress" | "skirt" | "tshirt"`. A `GarmentSpec` (`type` + `gender` (`"female" | "male"`) + `measurementOverrides` + `style`) plus a resolved `Measurements` row flow into `draftGarment(spec, baseMeasurements, t)` (`lib/draft/garment.ts`), which calls the per-block drafters (`body.ts`, `sleeve.ts`, `skirt.ts`, shared helpers in `core.ts`) to build each `Piece`'s outline/guide/grainline/dart in cm and lay them into one computed `viewBox` (`autoLayout`). The engine doesn't know `SizeLabel` — it's a plain per-chart `string` now, not the old fixed `"PP"|"P"|"M"|"G"|"GG"` union.
- `tshirt` is a knit archetype (round neck, no darts, short sleeves by default) drafted through the same `body`/`sleeve` drafters, with `knit: true` in `BlockOpts` and those style defaults pre-filled in `draftGarment`.
- Outlines: `outlinePath` (`core.ts`) takes a flat cm point list plus drafter-supplied `curvedSpans: [number, number][]` — only marked ranges (neckline, armhole, sleeve cap) get Catmull-Rom-derived Bézier curves with tangents locked at span edges; every other edge is a straight `L`. No global smoothing pass, no `curvedIds` — curvature is per-edge-range, opt-in per drafter.
- Each drafter attaches its own `piece.detailRows` (label/value pairs) — the old fixed `PieceDetails` shape is gone.
- **A decoration is placed from the piece's own boundary, never from its bounding box.** The bbox is a superset of the piece, so a constant offset measured from it lands _outside_ the outline wherever the piece is scooped (a neckline) or tapered (a sleeve hem) — and both shipped that way. The body grainline started at `y = 3` cm from the bbox top, which put it inside the neck opening for **every** front bodice (measured: 4.6 cm outside a round neck, 6.9 cm on a male t-shirt, 17.6 cm on a max-depth V); since the grainline reaches all five export formats, that was a data defect, not a screen one. It now starts at `neckDrop + 3` — 3 cm below the piece's own neckline. The canvas label was the other half: `place()` anchors it at `bbox-left + 6` and `PatternCanvas` drew it `text-anchor: start` at a fixed 11 px, but "MANGA · 2×" is wider than a size-M sleeve's bicep (68–75 px of text against 64 px of piece), so it spilled past the outline. Placement that depends on the _rendered text's_ width can't live in the drafter, so `lib/canvas/pieceLabel.ts`'s `fitPieceLabel` recomputes it at render time from `piece.vertices` — a scanline for the piece's real horizontal span at the label's baseline, then the largest size up to `MAX_LABEL_FONT_SIZE` that fits — which also repairs patterns drafted before the fix. A piece with no `vertices` (blobs predating the measure tool's snap) keeps the stored anchor, so `piece.label` survives as the legacy fallback only; it is also why nobody noticed that it ignores `bbox.minX`/`minY` and is correct purely because every drafter happens to normalize its outline to 0,0. `estimateTextWidth`'s 0.7em advance is deliberately wider than Archivo's real uppercase average, so a mis-estimate shrinks the label instead of overflowing the piece — `getComputedTextLength()` would be exact but needs a render pass, and jsdom doesn't implement it, which would put the rule beyond a test's reach. The invariant is guarded generically, not per-case: `garment.test.ts`'s containment suite asserts every grainline and dart point of every piece lies inside its own outline across seven garment/style combinations. (Note the design prototype puts each label _below_ its piece rather than inside it; contained-inside is what the bug report asked for and what shipped.)

### Size charts (`/size-charts`)

Real, per-account, and they drive generation/grading.

- `SizeChart` (Prisma, JSON-blob-per-row like `Pattern`/`Wallet`) holds `SizeChartData`: `name`, `gender`, `bodyType` (descriptive metadata only — never affects drafted geometry, an honest documented limitation), `isSystem`, ordered `sizes: string[]`, `baseSizeIndex`, `baseMeasurements`, a `progressionRule` (cm delta per size step from the base), and per-cell `overrides` that win over the rule. Resolution lives in `lib/sizeCharts/compute.ts` (`resolveSizeChartSize`, `buildSizeTable`).
- Every account lazily gets two seeded `isSystem` charts on first access (`lib/db/sizeChart.ts`'s `ensureSystemSizeCharts`, same lazy-seed precedent as `Wallet`): "Feminino adulto · ABNT" and "Masculino adulto", derived losslessly from the legacy tables by `lib/sizeCharts/seed.ts`'s `buildSystemSizeChartData` (the rule+override reconstruction reproduces the original tables exactly). System charts can be duplicated but not edited or deleted (enforced in the repository layer). Those two names are hardcoded pt-BR literals (`lib/sizeCharts/seed.ts:42`), persisted into `SizeChart.data.name` by the lazy seed and rendered by `SizeChartLibrary` — unlike the `" (cópia)"` duplicate suffix two modules away, which is threaded through an injected `Translate`. A rename would affect nothing already seeded: existing rows keep the name they were created with, exactly like `PatternData.newPatternName`.
- `User.activeSizeChartId` is the account-level "chart in use." **It is not a promise the chart will be used, and the app now says so.** `pickSizeChartForGeneration` returns a `SizeChartChoice` (`{chart, rejectedActive}`) rather than a bare record, and `getSizeChartForGeneration` returns `{chart, rejectedActiveName}` — it used to discard the fact that it had fallen back, so nothing could report it. Observed: with a male chart active, "blusa feminina manga curta" drafted from the system female chart (bust 92) while `/size-charts` still showed the male chart as active and the AI said "usando as medidas padrão". Surfaced in **three** places, per the three places the question comes up: a `tone: "notice"` chat bubble at generation time (the only moment a substitution can happen, since the snapshot is taken once), a **"Grade usada"** chip in `TechSheetTab`, and the active chart's badge in `SizeChartLibrary` now reading its scope ("usada só em peças femininas") because "ativa" alone implied it applied to everything. The frozen `Pattern.sizeChartName` is what the chip reads — additive blob key, frozen for the same reason `sizeTable` is (renaming a chart must not rewrite an existing pattern's history), absent on older patterns and therefore omitted rather than guessed.
- **A `PATCH` body is validated before it can reach the drafter** — `validateSizeChartPatch` (`lib/sizeCharts/validate.ts`), the size-chart half of the `validateSpec` trust boundary, called from `updateSizeChart` (whose `patch` parameter is deliberately `unknown`: the old `Partial<SizeChartData>` was an assertion about data straight off the wire). It drops or clamps, never throws, so an unusable field is ignored while the rest of the patch applies. The bug it exists for, verified against the running app: `gender:"banana"`, `progressionRule:{bust:"NaN-ish"}` and arbitrary unknown keys all persisted verbatim, and **`baseMeasurements:{}` replaced the whole row** — `resolveSizeChartSize` then iterated the surviving keys only and generation answered `status:"ok"` while persisting `viewBox:{w:null,h:null}`, `sizeTable` `{"bust":null,"waist":55}` and detailRows reading **"NaN cm"**. `MEASUREMENT_RANGES` was no defence: `Math.min`/`max` propagate NaN. So `baseMeasurements` **merges** onto the current row — a patch can change a value but can never drop a key — and `isSystem` appears in no branch, so a request can never claim it. (Not reachable from the UI, where `type="number"` cannot emit NaN; this is hardening on the money-and-draft path.) `MEASUREMENT_KEYS` (`lib/measurements.ts`) and `BODY_TYPES` (`lib/types.ts`) are exported for it, and `SizeChartTable` now reads those instead of its own copies — the one-exported-source rule the drafting/AI enums already follow.
- **A pattern snapshots its size chart once, at its first-ever generation:** the generate route calls `getSizeChartForGeneration(userId, spec.gender)` (`lib/db/sizeChart.ts` — the active chart if its gender matches the spec being drafted, else the system default for that gender), then `seedPatternSizeSnapshot` (`lib/editor/state.ts`) freezes `sizes`/`baseSize`/a fully resolved `sizeTable: Record<string, Measurements>` onto the pattern. Every later regeneration reuses the frozen snapshot — editing or reassigning the account's active chart never retroactively changes an in-progress pattern (same precedent as the i18n locale snapshot below). A brand-new blank pattern bootstraps from the system female-adult chart via the same `buildSystemSizeChartData`/`buildSizeTable` pair, so `Pattern.sizeTable`/`sizes` are always populated, never optional.
- Screen: `components/size-charts/SizeChartsShell.tsx` + `SizeChartLibrary.tsx` + `SizeChartTable.tsx`, with their own `useSizeChartsStore`. Browse the library; edit a custom chart's base row/progression rule/per-cell overrides/size list; duplicate any chart (system or custom); mark one active (`POST /api/size-charts/[id]/activate`). The Audaces spreadsheet-import block is an inert dashed placeholder on this screen.

### Client state (Zustand)

- **Editor:** one store — `lib/store.ts`'s `useEditorStore` — scoped to a single pattern via `init(patternId)`, threading that id through every server call (`generate`/`graduate`/`resolveConflict`/`purchase`). It mirrors the server's `EditorState` after every mutating call and owns UI-only state (active tab, selected piece, details-panel open, active tool, measure-tool measurements — auto-cleared when the pattern version changes — generation status/step, and paywall open/required/retry). All server calls go through `lib/api-client.ts`; components never call `fetch` directly. `sendMessage` optimistically appends the user's chat message before the request resolves; `cancelGeneration` rolls that optimistic message back and refunds the cost client-side (there's no server-side cancel).
- **Failures are data, not silence — and `res.ok` is actually checked now.** `getJson`/`postJson` never looked at the status, so an error body came back typed as the success shape (a 401 became an "`EditorState`" with no pattern). `lib/api-client.ts` exports **`ApiError`** (status + wire code), thrown for any non-2xx a call did not opt into; `handled` lists the statuses whose body _is_ the contract — `PAYWALL` (402, the paywall's required/balance) and `DOMAIN_ERRORS` (the codes the auth/settings screens resolve through the catalog) — enumerated per call site so each endpoint's failure contract stays visible. Every bare `fetch` (rename, delete, activate, duplicate, create) goes through it too; those used to ignore the response entirely, so a failed rename looked like a success.
- **Every store has an error path.** The editor store had _no_ `try`/`catch` at all: `init` threw on `state.pattern.pieces[0]` so `ready` never became true and the screen showed "Carregando molde…" **forever**; `sendMessage` skipped `clearTimeout(stepTimer)` so the overlay spun indefinitely; and `applyState` wrote `pattern: undefined` from an error body, which is how an expired JWT dropped a mid-session user onto a permanent loading screen. Now `error` (wire code) + `clearError`, and `EditorShell` renders a load-error screen with a retry — plus a distinct `sessionExpired` message for 401, different advice for a different cause. The dashboard and size-charts stores gain **`actionError`/`clearActionError`, kept separate from their existing `error` boolean**: a failed _load_ has nothing to show and replaces the content region, while a failed _mutation_ leaves a usable screen that needs a notice. All three render `components/shared/ActionErrorNotice` (amber `notice`, not the red alert token). Mutations update local state only after the server confirms, and `dashboardStore.create()` resolves to `null` instead of rejecting, because its caller navigates to the returned id.
- **The paywall is action-agnostic:** any store action that can fail on insufficient credits (`sendMessage`, `graduateSizes`) stashes its own retry closure in `paywall.retry`; `purchase()` applies the mock purchase, closes the modal, and invokes whatever `retry` was stashed — "buy credits then automatically finish what I was doing" works for any future paid action that follows the same set-paywall-state-with-a-retry-thunk pattern.
- **Dashboard:** its own separate store (`lib/dashboardStore.ts`'s `useDashboardStore`) — same fetch-through-`api-client`-into-Zustand shape, but owning a pattern _list_ (plus account credits/recent-usage and client-side search/type-filter) instead of one pattern's state. The two stores never share instances, matching the two screens' different lifetimes.

### Screens

- **The editor opens on a blank pattern.** A new pattern starts with no pieces, empty chat, name "Novo molde", and `version: 0` — the user always generates from scratch. The first AI generation creates the garment's (variable) piece set — e.g. front/back/sleeve for a blouse, plus a skirt piece for a dress. `CanvasArea` shows a "Molde em branco" empty state and hides the floating toolbar while `pieces` is empty; `sendMessage` auto-selects the first piece once a generation produces one.
- **Canvas overlays are mutually exclusive:** `PieceDetailsPanel` and `ConflictInfoCard` share the top-right slot over the canvas in `CanvasArea.tsx`, and a conflict always takes the slot. Fold new overlays into that same exclusivity check rather than adding a third independent floating panel.
- **Dashboard is the app's home (`/`).** `app/page.tsx` is a thin server component (session check, plus reading `?missing=pattern` as plain data — the `?section=` precedent in `/settings`, not a client `useSearchParams`) rendering `DashboardShell`, which renders through the shared `AppShell` passing neither `title` nor `backHref` — it **is** `/`, and its sidebar already marks the section, so a header title would print "Meus moldes" twice — and composes `Sidebar` ("Meus moldes" active; "Medidas e grades" navigates to `/size-charts`; "Bases do ateliê" disabled with an "em breve" badge), `PatternGrid` (search + garment-type filter, reusing the `garmentType.*` catalog keys per the EN-enum-lookup convention), and `CreditsCard`/`RecentUsageCard` (backed by `GET /api/account/summary`). The dashed "Importar .dxf · Audaces" card is inert and badged "em breve". Pattern cards deliberately show **no state badge** (the design's rascunho/graduado/exportado): export never touches the server, so "exportado" can't be derived honestly, and a partial 2-state badge wasn't worth shipping — a deliberate simplification, not a bug. Rename (a `Dialog` + `Field`/`Input`, replacing the earlier deliberately-minimal `window.prompt`) and delete (shared `components/shared/ConfirmModal.tsx`, now an `AlertDialog` — it previously rendered `absolute inset-0` _inside the card_, so a 380px panel overflowed a ~220px tile) live **only** in the card "⋯" menu (`PatternCard.tsx`) via `useDashboardStore`; the editor has no delete affordance — its "← Voltar" button just navigates back to `/`. **`/pattern/[id]` redirects to `/?missing=pattern` for a pattern that is gone or not owned**, and the dashboard shows a dismissible notice — it used to be a bare `redirect("/")`, so you simply materialised on the dashboard with no idea why (a stale bookmark or a back button being the usual way in). Deliberately one flag rather than distinguishing "deleted" from "not yours": that would make the dashboard an existence oracle for other accounts' pattern ids, which is exactly what `lib/db/pattern.ts`'s uniform 404 avoids.
- **`/settings` is one unified page, not a modal**, reached from the shared header's avatar menu — its three items ("Créditos e uso", "Plano e cobrança", "Preferências", in `components/shared/PageHeader.tsx`) deep-link via a `?section=` query param (`profile` default, plus `password`/`danger`/`usage`/`plan`), and because that header is on every screen the editor can reach settings too. No dashboard-sidebar entry; the page has its own internal `SettingsSidebar` (5 items, same 186px-column idiom as the dashboard's `Sidebar.tsx`). The section list (`SettingsSection`, `SETTINGS_SECTIONS`) lives in plain `lib/settings/sections.ts`, **outside** the `"use client"` component — the Server Component page needs it as plain data to validate the query param, and importing a non-component value from a client module into server code becomes a broken client reference at runtime. `app/settings/page.tsx` is the usual thin server component: it loads the user (`getUserById`, `lib/db/users.ts`), `Wallet` (`loadWallet`), and the last 30 ledger entries (`getLedgerHistory`, `lib/db/account.ts` — like `getRecentUsage` but without the debit-only filter) — no API round-trip for first render — and renders `SettingsShell`, which shows exactly one of five sections:
  - `ProfileSection` — name editable; email deliberately **read-only** (it's the Auth.js Credentials login identifier; editing it is out of scope).
  - `PasswordSection` — current/new/confirm; client-side confirm-mismatch gating plus a server-verified current-password check.
  - `DangerZoneSection` — account deletion gated by both a client-side "type your email to confirm" match **and** a server-verified password (stronger than the single-pattern `ConfirmModal`, since one irreversible `prisma.user.delete` cascades away every pattern, the wallet, and the ledger via the existing `onDelete: Cascade` — no manual cleanup).
  - `UsageSection` — balance/renewal, a "Comprar créditos avulsos" top-up reusing `purchase("topup")` with an optimistic client-side ledger update, and the full transaction history (all ledger types, not just spend).
  - `PlanSection` — the 4 plans from design `5c` as static display cards; only Ateliê is marked "Plano atual" (`lib/billing/wallet.ts`'s `applyPurchase` only ever issues that plan); the other 3 are badged "em breve" rather than faking a plan switch; plus a cost-per-action footer from the `COSTS` constant.

  Backed by `PATCH /api/account/profile`, `POST /api/account/password`, `DELETE /api/account`, and `GET /api/account/ledger` (alongside the existing summary route), all `requireUser()`-gated. The profile/password/deletion validation logic lives in DB-free, dependency-injected `lib/account/settings.ts` (mirroring `lib/auth/authorize.ts`'s `AuthorizeDeps` shape) so it's unit-testable without a live DB. Password changes do **not** invalidate the current JWT session — a deliberate choice for this single-device personal-use MVP, not an oversight.

### i18n (`next-intl`, single-locale pt-BR, no routing)

- One locale, no `[locale]` segment or middleware: `app/layout.tsx` calls `getMessages()` and wraps the tree in `NextIntlClientProvider` with the single catalog `messages/pt-BR.json`, keyed **per component namespace** (`Footer`, `Topbar`, `ChatPanel`, `TechSheetTab`, `Login`, …). Every component reads its own namespace via `useTranslations("ComponentName")` — all static UI chrome (headers, labels, empty states, "em breve" notes) comes from the catalog, never hardcoded pt-BR JSX. (Every display-text screen was a client component until `app/verify/page.tsx` — see below — the project's first server component with display text, using `await getTranslations(...)` directly; its interactive part, `components/auth/VerifyCard.tsx`, is still a client component reading the same `Verify` namespace via `useTranslations`.) This is deliberately **not** a translation system — it's the seam that lets one land later without another sweep through every component.
- `lib/` stays framework-free (no `next-intl` import), so functions that produce display text take an injected resolver (shipped as "i18n Fase 2"): `Translate` (`lib/i18n/translate.ts`, `(key, values?) => string`) — next-intl's `t` (from `getTranslations` in route handlers, `useTranslations` in components) is structurally assignable to it and passed through `draftGarment`/`draftPiecesCm`/`buildExportModel`/`planCutLayout`/`applyGarmentSpec`/`refitSleeve`. Drafter strings (`piece.detailRows`/`name`) and `detectConflict`'s title/description/suggestion live in the `PatternData` namespace (plus `GeneratingOverlay.steps` and `TechSheetTab.garmentType`/`gender`). Drafters emit the **resolved string**, not the key, so the persisted blob shape is unchanged — no reset migration was needed.
- A persisted `Pattern` holds a draft-time-locale snapshot: its piece labels/conflict text reflect the locale in effect when it was drafted, not retranslated except by the next generation, "Corrigir manga", or graduation.
- The verification email's copy lives in the `VerificationEmail` namespace and reaches `lib/mail/templates.ts`'s `verificationEmail(t, link, name)` through the same injected `Translate` seam, scoped to that namespace by the caller (`getTranslations("VerificationEmail")` in the verify/resend routes) before it's passed in.
- The AI's `assistantMessage`/chat text is model-produced, outside the catalogs entirely: `lib/ai/prompt.ts`'s system prompt (written in English) instructs the model to mirror the language of the user's own message in `assistantMessage` and clarifying-question labels/options — so an AI chat reply may not be pt-BR even though the rest of the UI is.
- **The wire and the database carry codes, never pt-BR prose.** Every `app/api/*` error payload is `{status, error: <code>}` where the code is machine-readable and the client resolves it through the catalog (`t("errors." + code)`), the `SignupErrorCode` precedent. Shared route-level codes and the `apiError` helper live in `lib/api/errors.ts`; **domain codes stay beside their own pure logic** (`ChangePasswordResult` in `lib/account/settings.ts`, `SignupErrorCode` in `lib/account/signup.ts`) because those unions type a pure function's return — each route unions the two and maps its own HTTP statuses in a local `Record`, the way `app/api/signup/route.ts` already did. `apiError` takes a bare `string` for exactly that reason: a fixed union would drag every domain union into `lib/api/errors.ts` and invert the dependency. Its internal `STATUS_WORD` map reproduces each response's pre-existing wire `status` discriminator, **warts included**: `/api/account/*` answers its 404 with `status: "error"`, not `"not_found"`.

### Export (client-side transform, no server call)

- `lib/export/` turns the drafted pattern into a downloadable file with no API route, credit cost, or state mutation. `buildExportModel(pattern, t)` (`lib/export/model.ts`) re-drafts the pieces in exact cm via `draftPiecesCm(spec, baseMeasurements, t)` (exposed from `lib/draft/garment.ts`) — it never reverses the store's px back to cm, so it doesn't inherit `PX()` rounding. The `ExportModel` is format-agnostic: per-piece outlines as typed cm segments (`line`/`cubic`, Béziers preserved) plus grainline/dart/name/qty and a `seamAllowanceCm` annotation. The exported geometry is the **net sewing line** — seam allowance is not offset into it.
- `exportPattern(pattern, format, t, onError?)` (`lib/export/index.ts`) builds the model, serializes, and triggers a browser download via `downloadFile` (`lib/export/download.ts`, the only DOM touchpoint), dispatching all five formats (`svg`/`dxf`/`dxf-aama`/`pdf-a4`/`pdf-single`) via an exhaustive `switch`/`never`. The `Footer`'s "Exportar" menu is disabled when a conflict is active, the pattern is blank, or there is no `spec`.
- `toSvg` (`svg.ts`) — 1:1 SVG in mm (`MM = 10`, so a 10 cm edge is 100 units; `width`/`height` in `mm`).
- `toDxf` (`dxf.ts`) — the **generic geometry-only DXF**: net line, `$INSUNITS=4` mm, 1:1, Y flipped to DXF's up-axis; hand-written ASCII `LWPOLYLINE`/`LINE`/`TEXT` on named layers `CONTORNO`/`INTERNO`/`GRAINLINE`/`TEXTO`; cubics flattened by adaptive De Casteljau (`flattenCubic`, 0.2 mm tolerance).
- `toDxfAama` (`dxf-aama.ts`) — a **"compatível AAMA/ASTM D6673" subset**: numbered layers with fixed semantics (`1` piece boundary + piece system text, `7` grainline, `8` internal/dart lines), each piece wrapped in a `BLOCK`/`INSERT`, header R13 (`AC1012`), classic `POLYLINE`/`VERTEX`/`SEQEND` (not R14's `LWPOLYLINE`) for wider Audaces/Gerber compatibility; reuses `flattenOutlineCm`/`TOL_CM` from `toDxf`. It is an **honest subset**: notches (layer 4), drill holes (13), and a separate sew line (14) are not emitted (MoldAI doesn't model them yet) and the net line lands on layer 1 — the menu item is tagged "beta" with those gaps noted inline.
- `toPdf` (`pdf.ts`) — a 1:1 PDF in two modes: `pdf-a4` (tiled A4 with glue overlap, page numbering, and a 10 cm calibration ruler on the first sheet) and `pdf-single` (one page the exact size of the pattern sheet, for plotter/large-format). It reuses `flattenOutlineCm` and loads `pdf-lib` (the feature's only added runtime dependency) via a dynamic `import()` inside `toPdf`, code-splitting it out of the main bundle — `toPdf` is `async` and the facade's pdf cases are fire-and-forget.
- The cm-accurate model is also reused **on-screen**: `buildPathD` (`lib/export/model.ts`) is the shared outline→SVG-`d` builder for both `toSvg` and the React previews, and `planCutLayout` (`lib/export/cutplan.ts`) reuses `buildExportModel` to compute a real (first-fit, not optimal) cut-plan nesting — expanding each piece by its cut quantity and shelf-packing the copies into a selectable fabric-width strip (grain locked, no rotation), returning positioned copies + consumed length + efficiency. This backs the data-driven `CutPlanTab` (fabric-width presets `FABRIC_WIDTHS_CM`, consumption/efficiency metrics, an SVG nesting preview) and `TechSheetTab` (per-piece dimensions from the same model plus a garment summary header).
