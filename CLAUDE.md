## What this is

MoldAI is an AI pattern-making product for clothing (chat with an AI to generate/adjust 2D sewing patterns, grade sizes, export to Audaces/Molde.me/plotter/PDF). This repo currently implements **only the pattern editor screen** — the single most complex screen of a larger design handoff — as a Next.js app with a real backend for auth and per-user molde persistence (Postgres/Prisma); only billing/credits remain mocked. The chat is backed by a **real Anthropic API call** (`claude-sonnet-5`) that interprets requests and returns a `GarmentSpec` (garment type + measurement overrides + style); the server validates/clamps that spec and **drafts** the pattern pieces from it. Authentication is now **real** (Fase A do "backend real", roadmap A→B→C): login/logout via **Auth.js v5** (Credentials + JWT), with users persisted in **Postgres via Prisma** (local Docker Compose). Only login exists — self-signup is deferred (shown as "em breve"). Cada conta tem o seu próprio molde persistido (Postgres/Prisma); billing/créditos seguem mock (top-up local) até a Fase C. Requires `ANTHROPIC_API_KEY`, `DATABASE_URL`, and `AUTH_SECRET` in `.env.local`.

Dashboard, landing, onboarding, plans, import, export, version history, and measurement-grid screens are explicitly out of scope for the current state of this codebase.

**Design source of truth: `docs/design/`.** The official design handoff for the _whole_ MoldAI platform lives there — `README.md` (design tokens, per-screen specs, interaction/state model) and `MoldAI Wireframes.dc.html` (a single navigable HTML prototype; each screen is a `div.dv-opt[id]`). High-fidelity screens to implement as-is: `4a` (the pattern editor — the only one this repo currently builds), `4b` dashboard, `5a`–`5i` (landing, onboarding, plans, paywall, seam conflict, version history, import, export, measurement grids). Low-fi wireframes (structure/flow only, not final UI): `1a`–`1f`, `2a`, `3a`–`3g`. It is **reference to recreate in this codebase's patterns, not code to copy**. When building any screen or reconciling tokens/behavior, consult it — where an out-of-scope screen is later brought in scope, this is its spec.

## Architecture

**The molde state and users are both real (Postgres/Prisma).** Each user has their own `EditorState` (pattern, pieces, chat, credits, active conflict) persisted as a JSON blob in the `Molde` table (one row per user, keyed by `userId`; `prisma/schema.prisma`). The editor-state logic lives in pure, DB-free functions in `lib/editor/state.ts` (each takes and mutates an `EditorState` — `seedState`, `addMessage`, `debitCredits`, `refundCredits`, `bumpVersion`, `setConflict`, `applyGarmentSpec`, `refitSleeve`, `applySizes`, `applyPurchase`), unit-tested without a live DB. The repository `lib/db/molde.ts` is the only layer that touches Prisma: `withMolde(userId, fn)` runs load→mutate→save inside an interactive transaction with a row lock (`SELECT … FOR UPDATE`, materializing the seed via `INSERT … ON CONFLICT DO NOTHING` first) so the credit flow is atomic; its transaction timeout is raised (30s) because the AI call runs inside it. `loadMolde(userId)` is a read-only get-or-seed for the `GET`, and `resetMolde(userId)` reseeds. Every `app/api/*` route is gated by `requireUser()` (`lib/auth/guard.ts`) — 401 without a session — and keys all state off the session user's id. Auth logic is likewise split into pure, DB-free modules (`lib/auth/authorize.ts`, `lib/auth/session.ts`); the NextAuth config is `auth.ts` (`trustHost: true` for self-hosted/prod). The molde now survives server restarts and is independent per account (Fase B do "backend real"; billing/credits remain a mock top-up until Fase C).

**The editor opens on a blank molde.** `seedPattern` starts with **no pieces**, empty chat, name "Novo molde", and `version: 0` — so the user always generates from scratch. The garment's pieces (a variable set — e.g. frente/costas/manga for a blouse, plus a skirt piece for a dress) are created by the **first** AI generation, which drafts a full `GarmentSpec` and hands it to `draftGarment`. `CanvasArea` shows a "Molde em branco" empty state and hides the floating toolbar while `pieces` is empty; `store.sendMessage` auto-selects the first piece once a generation produces one.

**API routes simulate real backend behavior**, not just return static data:

- `POST /api/pattern/generate` — debits `COSTS.adjust` immediately, then calls `proposeGarment` (`lib/ai.ts`) which asks `claude-sonnet-5`, via forced tool-use, for a `{ decision: "apply" | "decline" | "ask", spec, questions?, declineReason?, assistantMessage }`. The returned `spec` is never trusted as-is: `validateSpec` (`lib/draft/garment.ts`) re-checks every enum and clamps every numeric field before use. `apply` runs `applyGarmentSpec`, which calls `draftGarment(spec, size)` to recompute `pieces`/`viewBox`/`baseMeasurements` from scratch and bumps the version; `decline` and any API/parse error refund the credit. `proposeGarment` can also return `decision: "ask"`: when the request is underspecified, it returns `questions` (1–4 single-choice questions, validated/clamped by `validateQuestions` in `lib/draft/garment.ts` — same trust boundary as `validateSpec`) instead of drafting; the route attaches those questions to the AI chat message (`ChatMessage.questions`), refunds the credit (like `decline`), and responds `status: "clarify"` — no `applyGarmentSpec`, no `bumpVersion`. The client renders `ClarifyCard`; answering calls `sendMessage(frase, { answering: true })`, sending the picks as natural-language text, and the `answering` flag (threaded to `proposeGarment` and enforced by a server-side guard) prevents the AI from asking again. Conflict detection is now **live** (apply-with-warning): the AI-settable, `validateSpec`-clamped `style.armholeDeepenCm` (0–6 cm) deepens **only** the body's armhole, while `draftSleeve`'s cap is sized from the **base** (un-adjusted) armhole (`draftAll` returns both `armholeLenCm` for the body and `mangaArmholeCm` for the sleeve), so the two seams diverge by the adjustment. `applyGarmentSpec` runs `seamCheck` (`lib/draft/garment.ts`) on those two lengths and, when the diff exceeds 1 cm, attaches a real `ConflictInfo` (actual `diffCm`, dashed markers over the body/sleeve armhole) via `detectConflict` — the generation still applies, bumps the version and debits (credit flow untouched); the AI chat message gets `tone: "conflict"` and the route responds `status: "conflict"` (already in `GenerateResult`). The client mirrors `state.conflict` and renders the existing `ConflictInfoCard`/markers, and Export is blocked while active. `POST /api/pattern/conflict/resolve` "fix" calls `refitSleeve` (sets the internal, non-AI `style.sleeveRefit` and re-drafts so the cap uses the adjusted armhole → seams match → conflict clears) for free; "ignore" just clears the warning, leaving the pieces divergent. `sleeveRefit` is deliberately **not** accepted by `validateSpec`, so the AI can never fake a refit. Insufficient balance returns HTTP 402 (no debit, no AI call).
- `POST /api/pattern/graduate`, `POST /api/pattern/conflict/resolve`, `POST /api/billing/purchase` follow the same debit-then-mutate pattern; grading and purchase both 402 the same way generate does.

**Client state lives in one Zustand store** (`lib/store.ts`, `useEditorStore`): it mirrors the server's `EditorState` after every mutating call and additionally owns UI-only state (active tab, selected piece, details-panel open, active tool, generation status/step, and the paywall's open/required/retry state). All server calls go through `lib/api-client.ts`; components never call `fetch` directly. `sendMessage` optimistically appends the user's chat message before the request resolves, and `cancelGeneration` rolls that optimistic message back and refunds the cost client-side (there's no server-side cancel).

**The paywall is action-agnostic.** Any store action that can fail on insufficient credits (`sendMessage`, `graduateSizes`) stores its own retry closure in `paywall.retry`. `purchase()` applies the mock purchase, closes the modal, and invokes whatever `retry` was stashed — so "buy credits then automatically finish what I was doing" works for any future paid action without new plumbing, as long as it follows the same "set paywall state with a retry thunk" pattern.

**Design tokens live in `app/globals.css`** as Tailwind v4 `@theme` variables (colors, radius, shadow scale) rather than a `tailwind.config.ts` — this project has no JS Tailwind config file. Fonts (Bricolage Grotesque for display/titles, Archivo for UI/body) are loaded via `next/font/google` in `app/layout.tsx` and exposed as the same kind of CSS variables. When adding new colors/spacing, extend the `@theme` block, don't hardcode hex values in components.

**Two floating panels compete for the same canvas slot**: `PieceDetailsPanel` and `ConflictInfoCard` both render top-right over the pattern canvas in `CanvasArea.tsx`. They are mutually exclusive by design — a conflict always takes over that slot — so new canvas overlays need to be folded into that same exclusivity check rather than added as a third independent floating panel.

**Surface feature limitations on-screen, never silently.** When a feature ships with a limitation — something it doesn't support, a scope boundary, or a mock/stub standing in for the real thing — make that explicit in the UI where the user meets it (an inline note, a disabled control with a reason, a badge), rather than failing, no-op'ing, or pretending completeness. When the missing capability is planned or feasible later, mark it with an **"em breve"** label/badge so the user knows it's coming (and can tell it apart from a hard limitation that won't change). Prefer showing the planned option marked "em breve" over hiding it. Example anchor: the `Prova 3D` tab already renders an honest "ainda não disponível" empty state instead of fabricated content — new limitations should follow that spirit, and export targets that ship only partially (e.g. the AAMA/ASTM DXF subset, tagged "beta" with its gaps noted inline) or not yet at all belong in the menu labeled honestly rather than omitted.

**Pieces are drafted from measurements, not deltas.** `lib/measurements.ts` defines `Measurements` (bust, waist, shoulder, etc.) — `shoulder` is the meia-largura from the body's center line to the shoulder tip, not the full shoulder seam — and two base tables per `SizeLabel` (PP–GG): `SIZE_TABLE` (female) and `SIZE_TABLE_MALE` (male). `resolveMeasurements(size, overrides, gender)` picks the table for `gender` (default `"female"`), then applies chat-driven `measurementOverrides`, clamped to `MEASUREMENT_RANGES`. `GarmentType` is `"blouse" | "dress" | "skirt" | "tshirt"`; a `GarmentSpec` (`type` + `gender` (`"female" | "male"`, selects which size table `resolveMeasurements`/`draftGarment` use) + `measurementOverrides` + `style`) plus a size flow into `draftGarment` (`lib/draft/garment.ts`), which calls the per-block drafters in `lib/draft/*` (`body.ts`, `sleeve.ts`, `skirt.ts`, shared helpers in `core.ts`) to build each `Piece`'s outline/guide/grainline/dart in cm and lay them out into a single computed `viewBox` (`autoLayout`). `tshirt` is a knit archetype (round neck, no darts, short sleeves by default) drafted through the same `body`/`sleeve` drafters as `blouse`/`dress`, just with `knit: true` in `BlockOpts` and those style defaults pre-filled in `draftGarment`. Each piece's outline is built by `outlinePath` (`lib/draft/core.ts`) from a flat cm point list plus a drafter-supplied `curvedSpans: [number, number][]` — only the point ranges a drafter marks (neckline, armhole, sleeve cap) get Catmull-Rom-derived Bézier curves with tangents locked at the span's edges; every other edge is a straight `L`. There is no more global smoothing pass and no `curvedIds` — curvature is per-edge-range and opt-in per drafter. The AI never emits SVG or pixel coordinates — it only returns a `GarmentSpec`, which the server always re-validates and clamps via `validateSpec` before drafting, regardless of what the model returned. The old fixed `PieceDetails` (seamAllowance/bustDart/armhole/grain/consumption) is gone; each drafter instead attaches whatever `piece.detailRows` (label/value pairs) make sense for that piece.

**Code identifiers, wire keys, and enum values (`GarmentType`, `Gender`, `Measurements` fields, `GarmentStyle` fields, piece ids, drafter file/function names) are all English; UI display text and the AI's chat responses stay pt-BR.** That boundary is enforced by small display-label maps that translate the EN enum values back to PT for the screen — e.g. `GARMENT_TYPE_LABELS_PT` in `FichaTecnicaTab`, and the neckline/skirt-silhouette PT-label maps in `lib/draft/body.ts` (`NECKLINE_LABELS_PT`) and `lib/draft/skirt.ts` (`SKIRT_SILHOUETTE_LABELS_PT`) — plus the piece `name` fields ("Frente"/"Costas"/"Manga"/"Saia") set directly by the drafters. A migration (`reset_moldes_english`) reset every persisted `Molde` blob when this rename shipped, since the stored JSON shape changed from PT to EN keys/values.

**Export is a client-side transform, not a server call.** `lib/export/` turns the drafted pattern into a downloadable file with no API route, credit cost, or state mutation. `buildExportModel(pattern)` (`lib/export/model.ts`) re-drafts the pieces in exact cm via `draftPiecesCm(spec, size)` (exposed from `lib/draft/garment.ts` alongside the unchanged `draftGarment`) — it never reverses the store's px back to cm, so it doesn't inherit `PX()` rounding. The `ExportModel` is format-agnostic (per-piece outlines as typed cm segments — `line`/`cubic`, Béziers preserved — plus grainline/dart/name/qty and a `seamAllowanceCm` annotation; the exported geometry is the **net sewing line**, seam allowance is not offset into it). Pure serializers consume it: `toSvg` (`lib/export/svg.ts`) emits a 1:1 SVG in mm (`MM = 10`, so a 10 cm edge is 100 units and `width`/`height` are in `mm`). `exportPattern(pattern, format)` (`lib/export/index.ts`) builds the model, serializes, and triggers a browser download via `downloadFile` (`lib/export/download.ts`, the only DOM touchpoint). The `Footer`'s "Exportar" button opens a format menu and is disabled when a conflict is active, the molde is blank, or there is no `spec`. `toDxf` (`lib/export/dxf.ts`) serializes a **geometry-only DXF** (net line, `$INSUNITS=4` mm, 1:1, Y flipped to DXF's up-axis) — hand-written ASCII, `LWPOLYLINE`/`LINE`/`TEXT` on named layers `CONTORNO`/`INTERNO`/`GRAINLINE`/`TEXTO`, cubics flattened by adaptive De Casteljau (`flattenCubic`, 0.2 mm tolerance). It is the **generic** DXF; the AAMA/ASTM variant is separate. `toDxfAama` (`lib/export/dxf-aama.ts`) serializes a **"compatível AAMA/ASTM D6673" subset**: the industry convention of **numbered layers** with fixed semantics (`1` piece boundary + piece system text, `7` grainline, `8` internal/dart lines) with each piece wrapped in a `BLOCK`/`INSERT`, header R13 (`AC1012`) and classic `POLYLINE`/`VERTEX`/`SEQEND` (not `LWPOLYLINE`, which is R14) for wider Audaces/Gerber compatibility. It reuses `flattenOutlineCm`/`TOL_CM` from `toDxf` (DRY). It is an **honest subset** — the `ExportModel` only carries boundary/grainline/dart/name, so notches (layer 4), drill holes (13) and a separate sew line (14) are **not** emitted (MoldAI doesn't model them yet), and the net line lands on layer 1; the Footer menu item is tagged **"beta"** with those gaps noted inline. The **strict-complete** AAMA/ASTM (structured system text, block records, derived notches/sew line) remains a later "Fase 2.5". `toPdf` (`lib/export/pdf.ts`) serializes a **1:1 PDF** in two modes — `pdf-a4` (tiled A4 with glue overlap, page numbering, and a 10 cm calibration ruler on the first sheet) and `pdf-single` (one page the exact size of the molde sheet, for plotter/large-format). It reuses `flattenOutlineCm` (extracted from `toDxf`, shared DXF/PDF outline flattening) and loads `pdf-lib` — the feature's only new runtime dependency — via a dynamic `import()` inside `toPdf` so it is code-split out of the main bundle; `toPdf` is therefore `async` and its facade cases are fire-and-forget. `exportPattern` dispatches all five formats (`svg`/`dxf`/`dxf-aama`/`pdf-a4`/`pdf-single`) via an exhaustive `switch`/`never`. The whole export module (SVG, generic + AAMA/ASTM-subset DXF, PDF) is now shipped; the strict-complete AAMA/ASTM DXF remains a later "Fase 2.5". The cm-accurate model is also reused **on-screen** (not just for downloads): `buildPathD` (`lib/export/model.ts`) is the shared outline→SVG-`d` builder for both `toSvg` and the React previews, and `planCutLayout` (`lib/export/cutplan.ts`) reuses `buildExportModel` to compute a real (but first-fit, not optimal) cut-plan nesting — it expands each piece by its cut quantity and shelf-packs the copies into a selectable fabric-width strip (grain locked, no rotation), returning positioned copies + consumed length + efficiency. This backs the now data-driven `PlanoCorteTab` (fabric-width presets `FABRIC_WIDTHS_CM`, consumption/efficiency metrics, and an SVG nesting preview, honestly labeled first-fit/grain-locked/"em breve" for manual+optimized nesting) and `FichaTecnicaTab` (per-piece dimensions from the same model plus a garment summary header) — both previously best-effort extrapolations.
