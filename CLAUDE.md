## What this is

MoldAI is an AI pattern-making product for clothing (chat with an AI to generate/adjust 2D sewing patterns, grade sizes, export to Audaces/Molde.me/plotter/PDF). This repo currently implements **the pattern editor and the dashboard** — the editor is the single most complex screen of a larger design handoff — as a Next.js app with a real backend for auth and per-user molde persistence (Postgres/Prisma); only billing/credits remain mocked. The chat is backed by a **real Anthropic API call** (`claude-sonnet-5`) that interprets requests and returns a `GarmentSpec` (garment type + measurement overrides + style); the server validates/clamps that spec and **drafts** the pattern pieces from it. Authentication is now **real** (Phase A of "real backend", roadmap A→B→C): login/logout via **Auth.js v5** (Credentials + JWT), with users persisted in **Postgres via Prisma** (local Docker Compose). Only login exists — self-signup is deferred (shown as "em breve"). Each account has its own persisted molde (Postgres/Prisma) and its own real Wallet/Transaction ledger (Phase C of "real backend"); the only thing still mocked is the payment gateway itself — "purchase"/"subscribe" simulate instant success rather than charging a real card. Requires `ANTHROPIC_API_KEY`, `DATABASE_URL`, and `AUTH_SECRET` in `.env.local`.

Landing, onboarding, plans, import, export (as a dedicated screen — programmatic export itself is in scope), version history, and measurement-grid screens are explicitly out of scope for the current state of this codebase.

**Design source of truth: `docs/design/`.** The official design handoff for the _whole_ MoldAI platform lives there — `README.md` (design tokens, per-screen specs, interaction/state model) and `MoldAI Wireframes.dc.html` (a single navigable HTML prototype; each screen is a `div.dv-opt[id]`). High-fidelity screens to implement as-is: `4a` (the pattern editor) and `4b` (the dashboard) — the two screens this repo currently builds — plus `5a`–`5i` (landing, onboarding, plans, paywall, seam conflict, version history, import, export, measurement grids), still out of scope. Low-fi wireframes (structure/flow only, not final UI): `1a`–`1f`, `2a`, `3a`–`3g`. It is **reference to recreate in this codebase's patterns, not code to copy**. When building any screen or reconciling tokens/behavior, consult it — where an out-of-scope screen is later brought in scope, this is its spec.

## Architecture

**The molde state and users are both real (Postgres/Prisma), and an account can hold many moldes.** `Molde` has its own `id` (cuid), with `userId` as a plain indexed foreign key (`prisma/schema.prisma`) — not the 1-per-user, `userId`-as-primary-key shape this table had before the dashboard shipped. Each molde holds its own `MoldeState` (pattern, chat, active conflict — no credits) as a JSON blob. The editor-state logic lives in pure, DB-free functions in `lib/editor/state.ts` (each takes and mutates a `MoldeState` — `seedMoldeState`, `addMessage`, `bumpVersion`, `setConflict`, `applyGarmentSpec`, `refitSleeve`, `applySizes`), unit-tested without a live DB. The repository `lib/db/molde.ts` is the only layer that touches Prisma for it: every function is scoped to `(moldeId, userId)` and returns `null`/`false` — never throws, never leaks whether the row exists — when the molde doesn't exist or isn't owned by that user; a route turns that into `moldeNotFound()` (404). `withMolde(moldeId, userId, fn)` runs load→mutate→save inside an interactive transaction with a row lock (`SELECT … FOR UPDATE WHERE id = $1 AND userId = $2`), built from two exported primitives (`lockMolde`/`saveMolde`) so the combined transaction below can reuse the exact same SQL; its transaction timeout is raised (30s) because the AI call runs inside it. `loadMolde(moldeId, userId)` is the ownership-scoped read for `GET`; `createMolde(userId)` makes a new blank molde and returns its id; `listMoldesForUser(userId)` projects `{id, name, garmentType, updatedAt, thumbnailSvg}` for the dashboard grid (thumbnail server-built by `lib/editor/thumbnail.ts`'s `buildThumbnailSvg` from the molde's already-drafted pieces — no redraft, no AI call); `renameMolde`/`deleteMolde` round out CRUD. There is no more molde-reset endpoint — deleting a molde (and creating a fresh one) replaces what `resetMolde` used to do. Every `app/api/*` route is gated by `requireUser()` (`lib/auth/guard.ts`) — 401 without a session — and molde-scoped routes additionally check ownership via the `(moldeId, userId)` pattern above. Auth logic is likewise split into pure, DB-free modules (`lib/auth/authorize.ts`, `lib/auth/session.ts`); the NextAuth config is `auth.ts` (`trustHost: true` for self-hosted/prod). Billing is likewise real as of Phase C: credits/plan/renewal live in their own `Wallet` (1:1 with `User`, `prisma/schema.prisma`, shared across all of an account's moldes — credits are an account-level resource, not a per-molde one) plus an append-only `Transaction` ledger, both DB-free-pure-logic + thin-repository like the molde (`lib/billing/wallet.ts` + `lib/db/wallet.ts`, same `lockWallet`/`saveWallet` split, plus `saveLedger`). The two endpoints that debit credit atomically with a molde mutation (`generate`, `graduate`) use `lib/db/molde-wallet.ts`'s `withMoldeAndWallet(moldeId, userId, fn)`, which locks both rows in one transaction — always `Molde` first, then `Wallet`, a fixed order that makes cross-lock deadlock structurally impossible (it's the only function ever allowed to hold both locks) — and returns `null` without ever locking the wallet when the molde isn't found/owned. `lib/api/compose.ts` exports `buildCredits(wallet, now)` (account-level, molde-independent) and `composeEditorState(moldeState, wallet, now)` (built on top of it) — the wire `EditorState` the client has always seen; `Credits.renewsInDays` is computed from a real `Wallet.renewsAt` timestamp, but the client/store/components are unchanged. A subscription renews automatically: a standalone `scripts/cron-renew.ts` (run via `tsx`, same convention as `prisma/seed.ts`), scheduled by a dedicated `cron` Docker Compose service (hourly loop, no external scheduler), resets `balance` to `total` and rolls `renewsAt` forward 30 days for every wallet past due — "use it or lose it," no accumulation. There's still no real payment gateway: `POST /api/billing/purchase` simulates instant success — it takes an optional `moldeId`, returning the full composed `EditorState` for that molde when the editor triggered it (so the just-purchased credits show up without a second fetch) or bare `{credits}` when called with none (the account-level context the dashboard has, with no molde open) — and no backfill migration was written for the pre-Phase-C mock credits that used to live inside the `Molde` JSON blob — existing dev-seeded wallets are lazily reseeded to the default on first access, same precedent as the earlier `reset_moldes_english` migration.

**The editor opens on a blank molde.** `seedPattern` starts with **no pieces**, empty chat, name "Novo molde", and `version: 0` — so the user always generates from scratch. The garment's pieces (a variable set — e.g. front/back/sleeve for a blouse, plus a skirt piece for a dress) are created by the **first** AI generation, which drafts a full `GarmentSpec` and hands it to `draftGarment`. `CanvasArea` shows a "Molde em branco" empty state and hides the floating toolbar while `pieces` is empty; `store.sendMessage` auto-selects the first piece once a generation produces one.

**API routes simulate real backend behavior**, not just return static data. Every pattern-mutating route now lives under `/api/moldes/[id]/*`, scoped to one molde and 404'ing via `moldeNotFound()` when that molde isn't found or isn't the session user's:

- `GET /api/moldes` — lists the session user's moldes (`listMoldesForUser`); `POST /api/moldes` creates a new blank one and returns its `id`.
- `GET /api/moldes/[id]` — the composed `EditorState` for that molde (replaces the old single-molde `GET /api/pattern`). `PATCH /api/moldes/[id]` renames it (body `{name}`); `DELETE /api/moldes/[id]` deletes it — this is the only way to reset a molde now; there's no dedicated reset endpoint.
- `POST /api/moldes/[id]/generate` — debits `COSTS.adjust` immediately, then calls `proposeGarment` (`lib/ai.ts`) which asks `claude-sonnet-5`, via forced tool-use, for a `{ decision: "apply" | "decline" | "ask", spec, questions?, declineReason?, assistantMessage }`. The returned `spec` is never trusted as-is: `validateSpec` (`lib/draft/garment.ts`) re-checks every enum and clamps every numeric field before use. `apply` runs `applyGarmentSpec`, which calls `draftGarment(spec, size)` to recompute `pieces`/`viewBox`/`baseMeasurements` from scratch and bumps the version; `decline` and any API/parse error refund the credit. `proposeGarment` can also return `decision: "ask"`: when the request is underspecified, it returns `questions` (1–4 single-choice questions, validated/clamped by `validateQuestions` in `lib/draft/garment.ts` — same trust boundary as `validateSpec`) instead of drafting; the route attaches those questions to the AI chat message (`ChatMessage.questions`), refunds the credit (like `decline`), and responds `status: "clarify"` — no `applyGarmentSpec`, no `bumpVersion`. The client renders `ClarifyCard`; answering calls `sendMessage(phrase, { answering: true })`, sending the picks as natural-language text, and the `answering` flag (threaded to `proposeGarment` and enforced by a server-side guard) prevents the AI from asking again. Conflict detection is now **live** (apply-with-warning): the AI-settable, `validateSpec`-clamped `style.armholeDeepenCm` (0–6 cm) deepens **only** the body's armhole, while `draftSleeve`'s cap is sized from the **base** (un-adjusted) armhole (`draftAll` returns both `armholeLenCm` for the body and `mangaArmholeCm` for the sleeve), so the two seams diverge by the adjustment. `applyGarmentSpec` runs `seamCheck` (`lib/draft/garment.ts`) on those two lengths and, when the diff exceeds 1 cm, attaches a real `ConflictInfo` (actual `diffCm`, dashed markers over the body/sleeve armhole) via `detectConflict` — the generation still applies, bumps the version and debits (credit flow untouched); the AI chat message gets `tone: "conflict"` and the route responds `status: "conflict"` (already in `GenerateResult`). The client mirrors `state.conflict` and renders the existing `ConflictInfoCard`/markers, and Export is blocked while active. `POST /api/moldes/[id]/conflict/resolve` "fix" calls `refitSleeve` (sets the internal, non-AI `style.sleeveRefit` and re-drafts so the cap uses the adjusted armhole → seams match → conflict clears) for free; "ignore" just clears the warning, leaving the pieces divergent. `sleeveRefit` is deliberately **not** accepted by `validateSpec`, so the AI can never fake a refit. Insufficient balance returns HTTP 402 (no debit, no AI call).
- `POST /api/moldes/[id]/graduate`, `POST /api/moldes/[id]/conflict/resolve`, `POST /api/billing/purchase` follow the same debit-then-mutate pattern; grading and purchase both 402 the same way generate does.
- `GET /api/account/summary` — account-level, not molde-scoped: `{credits, recentUsage}` (last 3 debit-type `Transaction` rows via `lib/db/account.ts`'s `getRecentUsage`) backing the dashboard's "Créditos do mês"/"Uso recente" cards.

**The editor's client state lives in one Zustand store** (`lib/store.ts`, `useEditorStore`), now scoped to a single molde via a `moldeId` set by `init(moldeId)` and threaded through every server call the store makes (`generate`/`graduate`/`resolveConflict`/`purchase`/`deleteCurrentMolde`); it mirrors the server's `EditorState` after every mutating call and additionally owns UI-only state (active tab, selected piece, details-panel open, active tool, generation status/step, and the paywall's open/required/retry state). All server calls go through `lib/api-client.ts`; components never call `fetch` directly. `sendMessage` optimistically appends the user's chat message before the request resolves, and `cancelGeneration` rolls that optimistic message back and refunds the cost client-side (there's no server-side cancel). The dashboard has its own, separate store — `lib/dashboardStore.ts`'s `useDashboardStore` — following the same fetch-through-`api-client`-into-Zustand shape but owning a molde _list_ (plus account credits/recent-usage and client-side search/type-filter) instead of one molde's state; the two stores never share instances, matching the two screens' different lifetimes.

**The paywall is action-agnostic.** Any store action that can fail on insufficient credits (`sendMessage`, `graduateSizes`) stores its own retry closure in `paywall.retry`. `purchase()` applies the mock purchase, closes the modal, and invokes whatever `retry` was stashed — so "buy credits then automatically finish what I was doing" works for any future paid action without new plumbing, as long as it follows the same "set paywall state with a retry thunk" pattern.

**The dashboard (`4b`) is the app's home (`/`); the editor moved to `/molde/[id]`.** `app/page.tsx` is now a thin server component (session check only) rendering `components/dashboard/DashboardShell.tsx`, which composes `DashboardTopbar` (account-menu credit pill), `Sidebar` ("Meus moldes" active; "Medidas e grades"/"Bases do ateliê" disabled with an **"em breve"** badge — those screens are still out of scope), `MoldeGrid` (search + garment-type filter, reusing `TechSheetTab`'s `garmentType.*` catalog keys rather than a new label map, per the EN-enum-keyed-lookup convention above), and `CreditsCard`/`RecentUsageCard` (both backed by `GET /api/account/summary`). The dashed "Importar .dxf · Audaces" card in the grid is inert and badged "em breve" — import is still out of scope. **Molde cards intentionally show no state badge** (the design's rascunho/graduado/exportado): export never touches the server (it's a client-side transform — see below), so "exportado" can't be derived honestly without adding a tracking endpoint, and rather than ship a partial 2-state badge, the badge was dropped entirely — a known, deliberate simplification, not a bug. Rename (via `window.prompt`, deliberately minimal — no dedicated rename UI) and delete (via the shared `components/shared/ConfirmModal.tsx`, also now what the editor's "✕ Excluir" button uses in place of the old "↺ Resetar") are the only molde-management actions in the card's "⋯" menu; both go through `useDashboardStore`.

**Design tokens live in `app/globals.css`** as Tailwind v4 `@theme` variables (colors, radius, shadow scale) rather than a `tailwind.config.ts` — this project has no JS Tailwind config file. Fonts (Bricolage Grotesque for display/titles, Archivo for UI/body) are loaded via `next/font/google` in `app/layout.tsx` and exposed as the same kind of CSS variables. When adding new colors/spacing, extend the `@theme` block, don't hardcode hex values in components.

**Two floating panels compete for the same canvas slot**: `PieceDetailsPanel` and `ConflictInfoCard` both render top-right over the pattern canvas in `CanvasArea.tsx`. They are mutually exclusive by design — a conflict always takes over that slot — so new canvas overlays need to be folded into that same exclusivity check rather than added as a third independent floating panel.

**Surface feature limitations on-screen, never silently.** When a feature ships with a limitation — something it doesn't support, a scope boundary, or a mock/stub standing in for the real thing — make that explicit in the UI where the user meets it (an inline note, a disabled control with a reason, a badge), rather than failing, no-op'ing, or pretending completeness. When the missing capability is planned or feasible later, mark it with an **"em breve"** label/badge so the user knows it's coming (and can tell it apart from a hard limitation that won't change). Prefer showing the planned option marked "em breve" over hiding it. Example anchor: the `Prova 3D` tab already renders an honest "ainda não disponível" empty state instead of fabricated content — new limitations should follow that spirit, and export targets that ship only partially (e.g. the AAMA/ASTM DXF subset, tagged "beta" with its gaps noted inline) or not yet at all belong in the menu labeled honestly rather than omitted.

**Pieces are drafted from measurements, not deltas.** `lib/measurements.ts` defines `Measurements` (bust, waist, shoulder, etc.) — `shoulder` is the half-width from the body's center line to the shoulder tip, not the full shoulder seam — and two base tables per `SizeLabel` (PP–GG): `SIZE_TABLE` (female) and `SIZE_TABLE_MALE` (male). `resolveMeasurements(size, overrides, gender)` picks the table for `gender` (default `"female"`), then applies chat-driven `measurementOverrides`, clamped to `MEASUREMENT_RANGES`. `GarmentType` is `"blouse" | "dress" | "skirt" | "tshirt"`; a `GarmentSpec` (`type` + `gender` (`"female" | "male"`, selects which size table `resolveMeasurements`/`draftGarment` use) + `measurementOverrides` + `style`) plus a size flow into `draftGarment` (`lib/draft/garment.ts`), which calls the per-block drafters in `lib/draft/*` (`body.ts`, `sleeve.ts`, `skirt.ts`, shared helpers in `core.ts`) to build each `Piece`'s outline/guide/grainline/dart in cm and lay them out into a single computed `viewBox` (`autoLayout`). `tshirt` is a knit archetype (round neck, no darts, short sleeves by default) drafted through the same `body`/`sleeve` drafters as `blouse`/`dress`, just with `knit: true` in `BlockOpts` and those style defaults pre-filled in `draftGarment`. Each piece's outline is built by `outlinePath` (`lib/draft/core.ts`) from a flat cm point list plus a drafter-supplied `curvedSpans: [number, number][]` — only the point ranges a drafter marks (neckline, armhole, sleeve cap) get Catmull-Rom-derived Bézier curves with tangents locked at the span's edges; every other edge is a straight `L`. There is no more global smoothing pass and no `curvedIds` — curvature is per-edge-range and opt-in per drafter. The AI never emits SVG or pixel coordinates — it only returns a `GarmentSpec`, which the server always re-validates and clamps via `validateSpec` before drafting, regardless of what the model returned. The old fixed `PieceDetails` (seamAllowance/bustDart/armhole/grain/consumption) is gone; each drafter instead attaches whatever `piece.detailRows` (label/value pairs) make sense for that piece.

**Code identifiers, wire keys, and enum values (`GarmentType`, `Gender`, `Measurements` fields, `GarmentStyle` fields, piece ids, drafter file/function names) are all English; UI display text stays pt-BR while the AI's chat responses mirror the user's language (see the i18n paragraph below).** That boundary is enforced by catalog-driven lookups keyed off the EN enum value (e.g. `TechSheetTab`'s `t("garmentType." + pattern.spec.type)`/`t("gender." + pattern.spec.gender)`, and the `PatternData` namespace's `neckline.*`/`skirtSilhouette.*`/`sleeveType.*` keys resolved inside the drafters) rather than hand-written `Record<Enum, string>` label maps — see the i18n paragraph below for how those lookups get their translator. A migration (`reset_moldes_english`) reset every persisted `Molde` blob when the EN rename shipped, since the stored JSON shape changed from PT to EN keys/values.

**i18n is `next-intl`, single-locale pt-BR, set up without routing.** There is one locale and no `[locale]` segment or middleware — `app/layout.tsx` calls `getMessages()` and wraps the tree in `NextIntlClientProvider`, feeding it the single catalog `messages/pt-BR.json`. That catalog is keyed **per component namespace** (e.g. `Footer`, `Topbar`, `ChatPanel`, `TechSheetTab`, `Login`), and every component reads its own namespace via `useTranslations("ComponentName")` (all screens with display text are client components today; a server component would use `await getTranslations(...)`, but none currently needs it — `app/page.tsx` and `app/molde/[id]/page.tsx` only do a session check and mount `DashboardShell`/`EditorShell` respectively) — all static UI chrome (headers, labels, empty states, "em breve" notes) is sourced from there, never hardcoded pt-BR JSX text. This is deliberately **not** a translation system yet — it's the seam that lets one land later without another sweep through every component. **i18n Fase 2** moved the pt-BR strings that used to be hardcoded in `lib/` — drafter `piece.detailRows`/`name` (`lib/draft/body.ts`/`sleeve.ts`/`skirt.ts`) and `lib/editor/state.ts`'s `detectConflict` title/description/suggestion — into a new `PatternData` catalog namespace (plus `GeneratingOverlay.steps` for the generating-overlay step text and `TechSheetTab.garmentType`/`gender`). Since `lib/` must stay framework-free (no `next-intl` import), those functions take an injected resolver instead: `Translate` (`lib/i18n/translate.ts`, `(key, values?) => string`) — next-intl's `t`, from either `getTranslations` (route handlers, e.g. `POST /api/moldes/[id]/generate`) or `useTranslations` (components, e.g. `Footer`/`TechSheetTab`/`CutPlanTab` each hold their own `PatternData` translator alongside their own namespace's), is structurally assignable to it and passed straight through `draftGarment`/`draftPiecesCm`/`buildExportModel`/`planCutLayout`/`applyGarmentSpec`/`refitSleeve`. Drafters still emit the resolved string (not the key), so the persisted `Molde` blob shape is unchanged — no reset migration for this phase. **Known limitation:** a persisted `Molde` therefore holds a draft-time-locale snapshot; a future locale switch won't retranslate an already-drafted pattern's piece labels/conflict text until it's re-drafted (next AI generation, "Corrigir manga", or graduation). The AI's own `assistantMessage`/chat text is produced by the model, not static screen chrome, so it stays outside the `PatternData`/`messages` catalogs entirely: `lib/ai.ts`'s system prompt is written in English and instructs the model to mirror the language of the user's own message in `assistantMessage` and any clarifying-question labels/options, rather than defaulting to a fixed language — so an AI chat reply may not be pt-BR even though the rest of the UI is. Hardcoded fallback/canned chat strings that don't go through the model (the empty-`assistantMessage` fallbacks and the credit-cost chip label in `app/api/moldes/[id]/generate/route.ts`, and the "sleeve refit" chat message + chip label in `app/api/moldes/[id]/conflict/resolve/route.ts`) are unaffected by this and remain fixed pt-BR, same as the rest of the UI catalog — a known asymmetry, not yet reconciled.

**Export is a client-side transform, not a server call.** `lib/export/` turns the drafted pattern into a downloadable file with no API route, credit cost, or state mutation. `buildExportModel(pattern)` (`lib/export/model.ts`) re-drafts the pieces in exact cm via `draftPiecesCm(spec, size)` (exposed from `lib/draft/garment.ts` alongside the unchanged `draftGarment`) — it never reverses the store's px back to cm, so it doesn't inherit `PX()` rounding. The `ExportModel` is format-agnostic (per-piece outlines as typed cm segments — `line`/`cubic`, Béziers preserved — plus grainline/dart/name/qty and a `seamAllowanceCm` annotation; the exported geometry is the **net sewing line**, seam allowance is not offset into it). Pure serializers consume it: `toSvg` (`lib/export/svg.ts`) emits a 1:1 SVG in mm (`MM = 10`, so a 10 cm edge is 100 units and `width`/`height` are in `mm`). `exportPattern(pattern, format)` (`lib/export/index.ts`) builds the model, serializes, and triggers a browser download via `downloadFile` (`lib/export/download.ts`, the only DOM touchpoint). The `Footer`'s "Exportar" button opens a format menu and is disabled when a conflict is active, the molde is blank, or there is no `spec`. `toDxf` (`lib/export/dxf.ts`) serializes a **geometry-only DXF** (net line, `$INSUNITS=4` mm, 1:1, Y flipped to DXF's up-axis) — hand-written ASCII, `LWPOLYLINE`/`LINE`/`TEXT` on named layers `CONTORNO`/`INTERNO`/`GRAINLINE`/`TEXTO`, cubics flattened by adaptive De Casteljau (`flattenCubic`, 0.2 mm tolerance). It is the **generic** DXF; the AAMA/ASTM variant is separate. `toDxfAama` (`lib/export/dxf-aama.ts`) serializes a **"compatível AAMA/ASTM D6673" subset**: the industry convention of **numbered layers** with fixed semantics (`1` piece boundary + piece system text, `7` grainline, `8` internal/dart lines) with each piece wrapped in a `BLOCK`/`INSERT`, header R13 (`AC1012`) and classic `POLYLINE`/`VERTEX`/`SEQEND` (not `LWPOLYLINE`, which is R14) for wider Audaces/Gerber compatibility. It reuses `flattenOutlineCm`/`TOL_CM` from `toDxf` (DRY). It is an **honest subset** — the `ExportModel` only carries boundary/grainline/dart/name, so notches (layer 4), drill holes (13) and a separate sew line (14) are **not** emitted (MoldAI doesn't model them yet), and the net line lands on layer 1; the Footer menu item is tagged **"beta"** with those gaps noted inline. The **strict-complete** AAMA/ASTM (structured system text, block records, derived notches/sew line) remains a later "Fase 2.5". `toPdf` (`lib/export/pdf.ts`) serializes a **1:1 PDF** in two modes — `pdf-a4` (tiled A4 with glue overlap, page numbering, and a 10 cm calibration ruler on the first sheet) and `pdf-single` (one page the exact size of the molde sheet, for plotter/large-format). It reuses `flattenOutlineCm` (extracted from `toDxf`, shared DXF/PDF outline flattening) and loads `pdf-lib` — the feature's only new runtime dependency — via a dynamic `import()` inside `toPdf` so it is code-split out of the main bundle; `toPdf` is therefore `async` and its facade cases are fire-and-forget. `exportPattern` dispatches all five formats (`svg`/`dxf`/`dxf-aama`/`pdf-a4`/`pdf-single`) via an exhaustive `switch`/`never`. The whole export module (SVG, generic + AAMA/ASTM-subset DXF, PDF) is now shipped; the strict-complete AAMA/ASTM DXF remains a later "Fase 2.5". The cm-accurate model is also reused **on-screen** (not just for downloads): `buildPathD` (`lib/export/model.ts`) is the shared outline→SVG-`d` builder for both `toSvg` and the React previews, and `planCutLayout` (`lib/export/cutplan.ts`) reuses `buildExportModel` to compute a real (but first-fit, not optimal) cut-plan nesting — it expands each piece by its cut quantity and shelf-packs the copies into a selectable fabric-width strip (grain locked, no rotation), returning positioned copies + consumed length + efficiency. This backs the now data-driven `CutPlanTab` (fabric-width presets `FABRIC_WIDTHS_CM`, consumption/efficiency metrics, and an SVG nesting preview, honestly labeled first-fit/grain-locked/"em breve" for manual+optimized nesting) and `TechSheetTab` (per-piece dimensions from the same model plus a garment summary header) — both previously best-effort extrapolations.
