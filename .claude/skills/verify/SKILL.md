# Verify

## Overview

Evidence before assertions. Three commands, in this order, from the repo root. **Work is not complete until all three pass and you have reported their actual output.**

```bash
npx vitest run                    # 1. tests
npx eslint app lib components     # 2. lint — scoped, never bare
npm run build                     # 3. typecheck
```

## The sequence, and why each is written this way

### 1. `npx vitest run`

The suite is 49 spec files (`lib/**/*.test.ts` + `app/**/*.test.ts`, per the `include` in `vitest.config.ts`) — pure logic in `lib/` plus `app/api/**/route.test.ts` handlers. It is DB-free by design (repositories are mocked), so it runs without Postgres.

If far fewer files run than expected, you filtered by accident — re-run unfiltered before believing a green result.

### 2. `npx eslint app lib components` — MUST be scoped

`eslint.config.mjs` only globally ignores `.next/`, `out/`, `build/`, `next-env.d.ts`. It does **not** ignore `.claude/worktrees/`. So the repo-root `npm run lint` (bare `eslint`) walks any nested git worktree and lints a *second copy* of `app/`, `lib/`, `components/` — producing errors in files you never touched, in paths that look real. Scoping to the three source directories is the fix; `.husky/pre-push` and `.github/workflows/ci.yml` both use the scoped form for the same reason.

### 3. `npm run build` — this is the typecheck

`npm run typecheck` is literally `next build`. **`tsc --noEmit` is not a valid substitute** — and its failure mode is worse than a plain error, because it is *intermittent*:

`next-env.d.ts` does `import "./.next/types/routes.d.ts"` and `"./.next/types/root-params.d.ts"`, and `tsconfig.json` pulls in `.next/types/**/*.ts`. Those files are generated by `next build`/`next dev`. So bare `tsc` passes only when a previous build happens to have left `.next/types/` on disk, and fails on generated types it cannot see after a clean checkout, a `rm -rf .next`, or in CI. A green bare-`tsc` therefore proves nothing about whether the build is actually sound.

Run `npm run build`. It is the only self-contained typecheck.

The build imports routes that instantiate `PrismaClient` and NextAuth at module load, so `DATABASE_URL`, `AUTH_SECRET`, and `ANTHROPIC_API_KEY` must be present (Next loads `.env.local` automatically) — but the build does **not** connect to the database. CI passes dummy values for exactly this reason.

## Step 3 is the one that gets skipped — guard it

`.husky/pre-push` runs steps **1 and 2 only**:

```
npm run test
npx eslint app lib components
```

Nothing local runs the build before a push. CI does (`format:check` → scoped eslint → `vitest run` → `npm run build`). A push that sails through the hooks can still fail CI on a type error. Run the build yourself.

CI also runs `npm run format:check`; `.husky/pre-commit` (`npx lint-staged`) normally keeps formatting clean, but if you wrote files outside a commit, `npm run format` before pushing.

## When a step fails

Fix the cause. In this order of preference: fix the code, fix the test if the test encoded the wrong expectation, and only then discuss changing the rule with the user.

Never: skip the step, narrow the command until it passes, re-run hoping for a different result, or report "mostly passing."

## Anything touching Prisma needs the DB up

Schema changes, migrations, or `lib/db/*` work:

```bash
npm run db:up        # docker compose up -d db
npm run db:migrate   # dotenv -e .env.local -- prisma migrate dev
```

Postgres is on **host port 5433** (`localhost:5433`); **inside** the Docker network it is `db:5432`. Using the wrong one is the usual "connection refused." See the `new-migration` skill before writing a migration.

## Red flags — you are about to claim completion falsely

- "The tests pass, so it's done" — the build has not run.
- "`npm run lint` is reporting errors in files I didn't touch" — wrong command; scope it to `app lib components`.
- "`tsc --noEmit` is faster" — it is invalid here; the `LayoutProps` error is spurious.
- "The pre-push hook passed" — the hook does not build.
- Writing "all checks pass" without three actual command outputs behind it.

## Rationalizations

| Excuse | Reality |
|--------|---------|
| "It's a one-line change" | One line changes types. The build is the typecheck. |
| "Only docs/comments changed" | Then all three finish fast. Run them. |
| "CI will catch it" | CI catching it means you shipped a broken claim first. |
| "The build takes too long" | Shorter than the round trip of a false completion claim. |
| "I'll run the build after committing" | The claim of completeness comes before the commit. Order matters. |
| "The failure is unrelated to my change" | Prove it with output, then say so explicitly — don't skip. |

## Report the output, don't assert success

Say what actually ran and what it printed — pass/fail per step, real counts, real error text. "Verified" with no output behind it is not verification.
